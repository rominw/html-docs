先能判断代码行为，再理解容器实现。

基础必会 1. 基本类型、包装类型与值传递：到底复制了什么？

先看问题：同样写着 Integer a=200、Integer b=200，为什么 a==b 不应拿来判断数值相等？方法里换一个对象，又为什么没改掉调用方变量？

原理怎样推出来

基本类型的变量保存值，引用类型的变量保存引用。对引用用 == 比较的是是否指向同一对象，equals 按类型定义内容相等。自动装箱可能复用某些包装对象，所以小数值比较“碰巧相等”不能推广到所有数值；包装值拆箱时若为 null，会抛 NullPointerException。

Java 总是值传递：调用方法会复制参数值，引用参数复制的也是引用值。两个引用副本可以改同一个对象的内容，但给参数重新赋值只改变方法内的那个副本。

把它放进一个例子

void change(List<String> xs) {
    xs.add("A");                  // 改共享对象
    xs = new ArrayList<>();        // 只改局部引用
    xs.add("B");
}
// 原列表新增 A，未因重新赋值而变成只含 B 的列表

边界与反例：业务金额不要用浮点近似表示需要精确计算的十进制金额；选最小货币单位整数或明确精度与舍入规则的 BigDecimal。包装类型相等还要考虑类型和 null。

停一下，自己推：把方法参数改成 final，就能禁止 xs.add 吗？

展开自测解析

不能。final 禁止对参数引用重新赋值，不禁止修改引用指向的可变对象。

理解后，再这样简述：区分值、引用与对象；参数值被复制，改对象和改参数指向不是同一种操作。

核对原文：JLS：方法调用参数。

基础必会 2. 接口、继承与多态：为什么业务依赖接口？

先看问题：同一个通知服务，测试时发到内存，生产时发邮件。调用者希望使用同一契约，而不是到处判断实现类型。

原理怎样推出来

接口规定协作契约，具体类提供实现；通过父类型或接口引用调用被重写的实例方法，运行时会分派到实际对象的实现。重载则是同名不同参数的选择，主要由编译期参数类型决定，不能与重写混为一谈。

继承应体现可替代关系：子类接受原有输入、维持原有语义，而不随意让父类允许的操作失效。组合让对象委托协作者完成部分工作，通常更适合仅想复用一段能力的场景；不必为了每个只有一个实现的类都增加接口。

把它放进一个例子

Notifier n = new EmailNotifier();
n.send(message); // 调用 EmailNotifier 的实例方法实现

Spring 可以把不同实现注入同一个业务类，测试也可注入替身。若实现抛异常、改变顺序或重复发送，仍须遵守契约，接口本身不会替你保证。

边界与反例：static 方法、字段访问与普通重写方法的分派规则不同；private 方法不作为同样的可重写入口。不要把所有同名调用都解释成运行时多态。

停一下，自己推：把一个服务抽成接口，就自动解耦数据库事务与 HTTP 副作用了吗？

展开自测解析

没有。接口只分离调用契约与实现，跨资源原子性与错误语义仍要在业务设计中解决。

理解后，再这样简述：接口表达契约，重写实现多态；复用选择继承或组合要看职责与可替代关系。

核对原文：JLS：方法调用与重写。

基础必会 3. equals 与 hashCode：为什么必须配套？

先看问题：两份设备对象 id 一样，你认为是同一设备，HashSet 却装了两份；或者 Map 放进去以后取不出来。先检查你的“相等”规则。

原理怎样推出来

哈希集合先用 hash 缩小候选范围，再用 equals 区分是否同一键。契约要求 equals 相等的对象拥有相同 hashCode；不同对象可以 hash 相同，那叫碰撞，不叫相等。只重写 equals 却留下不一致的 hashCode，两个相等对象可能被送到不同桶，集合就没有机会按你预期比较。

把参与判等的字段当作键身份，插入哈希集合后应保持稳定。改变字段后计算出新 hash，而条目还在原来的桶，就可能找不到它。equals 也需要对称、传递等性质，继承层次中随意扩展判等字段容易破坏这些规则。

把它放进一个例子

若设备以不可变 deviceId 判等，两份相同 id 的对象就应返回相同 hash。若设备改名不影响身份，name 就不应同时被纳入键判等。使用 record 可以生成组件判等方法，但组件若含可变对象，仍要考虑稳定性。

边界与反例：HashSet 并不按业务 id 自动去重；字符串、record 或自定义对象各有契约。重写方法要围绕稳定身份，不是把所有字段机械加进去。

停一下，自己推：两个对象 hashCode 一样但 equals 不同，集合必须只保留一个吗？

展开自测解析

不需要。它们可同桶共存，集合仍用 equals 区分；碰撞会增加查找工作。

理解后，再这样简述：相等必同 hash，同 hash 未必相等；哈希键身份必须稳定。

核对原文：Java：Object 相等与哈希契约。

基础必会 4. List、Set、Map 与集合选型：你要保存什么关系？

先看问题：列表页按序展示、设备编号去重、按编号取详情，是三种数据关系；不能因为熟悉 ArrayList 就全部用它遍历查找。

原理怎样推出来

List 保存有顺序的元素并允许重复；Set 表达元素唯一性；Map 表达键到值的映射。ArrayList 用数组支持下标访问与尾部追加，容量不足时扩容搬迁，中间插入删除要移动后续元素。LinkedList 用节点连接，已找到节点后的局部操作方便，但按下标定位通常要遍历，也付出节点和指针的内存成本。

HashSet/HashMap 按哈希定位，不承诺排序；TreeSet/TreeMap 按比较规则维持有序，适合范围与排序需求；LinkedHashMap 可保留指定的迭代顺序。选择依据是主要读写模式、顺序和并发要求，不是“链表插入必然更快”。

把它放进一个例子

任务列表选 List；去重设备 id 选 Set；大量按 id 查设备选 Map。队列/栈式两端操作常先看 ArrayDeque。需要多个线程更新时，再选择并发容器或统一同步协议，不直接共享普通集合写入。

边界与反例：遍历时直接对集合增删可能触发 fail-fast；它是发现错误的尽力检查，不是并发安全保证。需要删除时按迭代器协议或合适的批量操作处理。

停一下，自己推：每次插入前都先 get(i) 找位置，LinkedList 的插入真的只是 O(1) 吗？

展开自测解析

不是。已知节点后的链接修改可很小，但你还付了定位成本。端到端复杂度必须包含找位置这一步。

理解后，再这样简述：先选数据关系，再选主要操作与顺序；把定位、移动、内存与并发成本一起算。

核对原文：Java：ArrayList；Java：集合框架。

基础必会 5. 异常与资源关闭：为什么只打印日志还不够？

先看问题：数据库写入失败，你 catch 后返回“成功”；文件读取异常，你忘了关闭流。异常处理已经改变业务结果和资源生命周期。

原理怎样推出来

异常表示操作没按约定完成，调用者需要知道该重试、报错还是补偿。受检异常一般需要捕获或声明，RuntimeException 不要求同样的编译期处理；Error 通常不是普通业务分支。包装异常时保留 cause，日志要保留栈与关联信息，不用一个空 catch 隐藏故障。

资源关闭必须覆盖成功与失败路径。try-with-resources 管理 AutoCloseable 资源，按逆序关闭；若业务与关闭都抛异常，关闭异常可成为 suppressed 异常，不应无意覆盖原故障。

把它放进一个例子

try (InputStream in = Files.newInputStream(path)) {
    return in.readAllBytes();
} // 成功、失败都会尝试 close

事务方法吞掉数据库异常还可能让事务拦截器看见正常返回。决定恢复时要确认系统已经回到可继续状态，不能仅改一条日志就宣布成功。

边界与反例：不要用 finally 中的 return 覆盖原返回或异常。错误响应避免暴露 SQL、凭证或内部路径；日志也要对敏感字段做限制。

停一下，自己推：catch 到连接异常后返回空列表，与查询成功没有数据，是同一种结果吗？

展开自测解析

不是。前者是操作失败，后者是合法业务结果。混为一谈会掩盖故障，还可能误触发“没有任务”的后续动作。

理解后，再这样简述：异常处理要保留失败语义、原因和资源释放，恢复与忽略要有明确依据。

核对原文：Java：try-with-resources。

基础必会 6. String 不可变：为什么 final 数组还不够？

先看问题：多个模块共享一个字符串作为路径或 Map 的键，如果其中一个悄悄改掉内容，其他模块会在毫不知情时改变行为。

原理怎样推出来

不可变意味着构造完成后，通过正常 API 不能修改同一个字符串的字符内容。final 类避免子类改写行为；内部存储不向外暴露可修改入口，构造时按需要复制输入，操作方法返回结果而不改原内容。这是一整套封装，单靠 final 引用不够。

final 数组引用不能改指向，但数组元素仍能赋值。因此不可变对象还要控制对内部可变存储的访问。稳定内容让字符串可以共享字面量、缓存 hash，并降低作为键或参数时被其他代码修改的风险。

把它放进一个例子

String a = "dock";
String b = a.concat("-7");
// a 仍是 "dock"；b 是 "dock-7"
final char[] chars = {'a'};
chars[0] = 'b';  // final 引用并未阻止元素修改

反复拼接大字符串会创建中间结果，单线程构建常用 StringBuilder。StringBuffer 的方法同步不等于你的一组多步操作自动构成事务。

边界与反例：JDK 8 的典型存储为 char[]，JDK 9 引入紧凑字符串，常用 byte[] 加编码标记；不能把数组类型当作不可变性的本质。字符串对象不可变，也不让保存它的可变容器自动安全。

停一下，自己推：把 String 放进 HashMap 做键后，执行 key = key + "x" 会修改 Map 里的旧键吗？

展开自测解析

不会。赋值让局部变量指向另一个字符串，原字符串不变，Map 仍持有旧键。要改变映射键应显式删除旧映射并添加新映射。

理解后，再这样简述：不可变靠封装与 API 契约，带来安全共享与稳定键；final 引用只是其中一环。

核对原文：Java SE 21：String 契约；JDK 21 的 String 存储实现。

基础必会 7. HashMap：桶、碰撞和扩容如何连在一起？

先看问题：把任意键放进有限的数组，不同键可能落到同一格。HashMap 要同时解决“落在哪”“同格怎么找”“装不下怎么搬”。

原理怎样推出来

JDK 8 的 HashMap 把 hashCode 做高低位扰动，再用 (n-1) & hash 找桶；容量取 2 的幂，让这个位运算等价于对容量取余。同桶中还要用 equals 判断是不是同一个键，hash 相同不代表键相等。

碰撞条目以链表组织，达到树化触发条件且容量足够时转成树；容量较小时更倾向先扩容。树化阈值 8、最小容量 64 是实现里的常见数字，不应把插入触发与所有退化场景都说成一个严格统一的长度规则。

容量翻倍时掩码多了一位，旧桶条目只会留在原位置或移到原位置加 oldCap：判断 hash & oldCap 是 0 还是非 0 即可。不是判断结果是否“等于 1”，因为 oldCap 可能是 16、32 等。

把它放进一个例子

旧容量 16：只看 hash 的低 4 位
新容量 32：再多看第 5 位
hash = 3  → 旧桶 3，新桶 3
hash = 19 → 旧桶 3，新桶 19 (= 3 + 16)

若键插入后改变了参与 hashCode/equals 的字段，之后按新 hash 查找可能走到别的桶，原条目仍在旧位置，于是“明明放进去却取不出来”。

边界与反例：JDK 7 并发扩容的历史问题不是使用 HashMap 并发写的唯一风险；JDK 8 也未提供线程安全契约。负载因子是空间与碰撞概率的取舍，不是固定业务最优值。

停一下，自己推：两个不同对象 hashCode 相等，HashMap 一定把后者覆盖前者吗？

展开自测解析

不一定。还要 equals 判等；hash 只定位候选桶。hash 相同而 equals 不同的键可以共存，但增加桶内查找工作。

理解后，再这样简述：hash 定位桶、equals 区分键，碰撞靠桶内结构处理；翻倍扩容只按新增的一位分流。

核对原文：OpenJDK 8u：HashMap 实现。

项目常用 8. 泛型与反射：类型检查为什么有边界？

先看问题：List<Integer> 给你编译期类型检查，但有人通过原始类型塞入字符串，取出来才报错；框架还能在运行时找到方法与注解。

原理怎样推出来

泛型把许多类型错误提前到编译期。Java 泛型通常通过擦除等方式实现，运行时同一原始类不因类型参数就成为独立类；部分声明签名仍保留泛型信息，可供反射读取，不能简化成“运行时没有任何泛型信息”。

List<Dog> 不能直接赋给 List<Animal>，否则后者可放入 Cat 破坏原列表约束。读取一组子类型常用 extends 通配符，向能接收某类型的容器写入常用 super 通配符；反射则在运行时检查类、方法、字段和注解，框架用它装配对象或调用方法。

把它放进一个例子

框架根据实体字段与注解做序列化，是反射的典型用途；调用 getter 的结果仍可能抛异常。泛型 API 让业务少做强转，而原始类型、反射和不安全操作可能绕过一部分检查。

边界与反例：反射访问受可见性与模块规则约束；不要接受任意用户输入的类名或方法名后直接调用。泛型也不意味着可变容器自动线程安全。

停一下，自己推：List<String> 与 List<Integer> 的 getClass() 通常是否相同？

展开自测解析

若它们使用同一种列表实现，通常相同；类型参数不是创建两种运行时列表类。声明的泛型签名与对象实际类型要区分。

理解后，再这样简述：泛型主要提前检查契约，反射支持运行时检查与调用；两者都有边界，框架也不能取代业务校验。

核对原文：Java：泛型擦除；Java：反射 API。

3. 并发：先守住状态，再组织异步工作

从线程协作与原子性出发，走到锁、线程池、上下文和异步结果。

箭头表示该步未成功接纳才继续；每个“是”分支接纳任务后结束判断。实现还有入队后的并发状态复查。

基础必会 9. 线程状态与中断：怎么让任务正确停止？

先看问题：任务在等待队列或执行循环，你希望取消它。强行终止线程可能留下半更新状态，中断需要任务配合。

原理怎样推出来

NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED 是 Java 的线程状态。RUNNABLE 不保证此刻真的占用 CPU；BLOCKED 特指等待进入监视器锁，其他等待机制不必都显示为 BLOCKED。

interrupt 是协作式信号。部分阻塞方法会抛 InterruptedException，常同时清除中断状态；运行中的计算需主动检查标志。Thread.interrupted() 读取并清除当前线程标志，isInterrupted() 查询标志不做同样的清除。

把它放进一个例子

try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return; // 当前层不继续处理，交还取消语义
}

也可以向调用方抛出异常。关键是让取消语义继续传播，并用 finally 等释放已经取得的资源。

边界与反例：中断不等于强制停机；所有 I/O 和库调用也并非都同样响应中断。吞掉 InterruptedException 后继续无限循环会妨碍关闭。

停一下，自己推：Future.cancel(true) 返回成功，就代表业务副作用从未发生吗？

展开自测解析

不代表。任务可能已执行了一部分，取消也依赖响应中断；外部动作要查询状态或补偿，不能从取消结果推断没有执行。

理解后，再这样简述：状态描述等待与执行位置，中断是协作取消；保留信号、退出路径与资源释放。

核对原文：Java：Thread 状态与中断。

基础必会 10. volatile 与 synchronized：看得见就能改得对吗？

先看问题：两个线程给计数器加一，最终却少了一次。每个线程看到了最新值，也可能在同一旧值上各自加一后互相覆盖。

原理怎样推出来

count++ 可以拆成读取、计算、写入。volatile 保证对该字段的读写具有相应可见性与顺序约束，但不会把这三步变成一个不可插入的操作。synchronized 让使用同一监视器的线程互斥进入，并通过解锁与后续加锁建立 happens-before（先行发生）关系。

happens-before 是 Java 内存模型给程序员的可见性与顺序保证，不是要求按某种固定硬件缓存流程执行。volatile 写先行发生于后续对同一字段的读，因此常用于停止标志或正确发布状态；需要一起维护多个变量的不变式时，通常需要锁或其他原子协议。

把它放进一个例子

初始 count = 0
A 读到 0 → 计算 1
B 读到 0 → 计算 1
A 写入 1
B 写入 1    // 两次加一，结果仍为 1

用同一锁保护整个加一，或使用 AtomicInteger.incrementAndGet()，才针对这个丢失更新问题。若只是通知循环停止，volatile boolean stop 常能满足需求。

边界与反例：锁只保护遵守同一加锁协议的访问；其他线程不加锁仍可能破坏状态。偏向锁等优化随 JDK 版本变化，别把历史锁升级口诀当作语言保证。

停一下，自己推：把一个对象引用声明为 volatile，该对象里面的普通 count++ 就自动原子了吗？

展开自测解析

没有。volatile 修饰的是引用字段的访问，不会递归地给对象内部字段加锁，也不让复合操作原子化。

理解后，再这样简述：volatile 解决相关读写的可见性和顺序；synchronized 还提供互斥，复合修改要维护完整不变式。

核对原文：Java 内存模型：happens-before。

基础必会 11. CAS 与原子类：不加锁怎样避免覆盖？

先看问题：两个线程都读到余额版本 1，只有一个应成功修改。先检查值没变再写，若检查和写不是同一个动作仍会被插入。

原理怎样推出来

CAS 原子比较当前位置是否为预期值，只有匹配才替换。失败表示观察已经过时，常需重新读取并尝试。AtomicInteger 的增量操作提供相应原子更新，不像普通或 volatile 的 i++ 拆成可交错的读改写。

CAS 常用于单变量或不可变状态的原子替换。值从 A 变成 B 又回 A，单看值仍匹配，可能遗漏中间变化，这叫 ABA；若业务关心变化历史，可用版本/标记配套。竞争激烈时反复重试也有 CPU 成本。

把它放进一个例子

AtomicInteger count = new AtomicInteger();
count.incrementAndGet(); // 不会像两个普通 i++ 那样覆盖

库存与订单记录要一起维护时，单个 AtomicInteger 无法替代跨资源事务。LongAdder 适合高竞争统计，读取并发更新中的 sum 不是完整事务快照。

边界与反例：“无锁”不等于无等待、无冲突或所有业务都原子。多字段一致性要有共同状态或同步协议。

停一下，自己推：把两个账户分别用 AtomicInteger 表示，先减 A 再加 B，转账就原子了吗？

展开自测解析

没有。单次余额操作原子，但两步之间可被观察或失败；还需要保护整个转账约束。

理解后，再这样简述：CAS 把比较与替换合成一个原子动作，原子类保护其操作范围，不保护任意组合业务。

核对原文：Java：原子类。

项目常用 12. ReentrantLock 与 Condition：比 synchronized 多什么能力？

先看问题：线程等不到锁时希望超时返回，或等待库存补足后再被通知。除了互斥，还需要可控的等待协议。

原理怎样推出来

ReentrantLock 支持同一线程重入、tryLock、可中断等待与公平性选项；成功获取几次，须对应释放几次。synchronized 由语言结构管理退出释放，显式 Lock 则要求自己把 unlock 放在正确的 finally 中。

Condition 把等待者按条件组织。await 会释放关联锁并等待，返回前重新取得锁；signal 发出通知，不等于立刻把锁交给等待线程。唤醒后条件可能已改变，也可能存在伪唤醒，因此应在持锁时用 while 重新判断。

把它放进一个例子

lock.lock();
try {
    while (!ready) condition.await();
    consume();
} finally {
    lock.unlock();
}

示意方法须处理或声明 InterruptedException。设置公平锁要权衡排队和吞吐，不是总能让系统更快。

边界与反例：未获取成功不能 unlock；await、signal 必须遵守关联锁协议。当前 JVM 进程的 ReentrantLock 不会协调另一台机器。

停一下，自己推：被 signal 的线程为什么还不能马上 consume？

展开自测解析

它要重新竞争关联锁，并确认条件仍成立；通知只表示有机会重新检查，并不保证资源已经属于它。

理解后，再这样简述：显式锁提供可控获取与条件等待，代价是显式释放和完整的等待条件协议。

核对原文：Java：ReentrantLock。

基础必会 13. 死锁：为什么两个线程都没做错一步，却谁也走不了？

先看问题：A 拿住设备锁等机库锁，B 拿住机库锁等设备锁。它们各自的互斥步骤合法，整体却形成了环形等待。

原理怎样推出来

死锁通常与互斥、持有资源继续等待、不能强行抢走资源、循环等待共同有关。实际修复应打断形成等待环的协议：统一加锁顺序，避免持锁做长时间外部调用，或用超时获取后释放已持有资源并进行有界重试。

线程 dump 展示各线程等待哪把锁、谁持有它，才能把“接口卡住”对应到具体等待环。高 CPU 的活锁或自旋，与互相阻塞的死锁也要区分。

把它放进一个例子

A：拿设备锁 → 等机库锁
B：拿机库锁 → 等设备锁
改为双方都按同一规则：先机库锁，再设备锁

如果一次涉及多个设备，可按稳定 id 排序后取锁。所有相关路径都要遵守顺序，只修一个调用方不足以保证。

边界与反例：数据库锁、JVM 锁、Redis 锁属于不同层，可能形成跨层等待；超时退出还需要释放已取得资源并避免半完成业务。

停一下，自己推：超时后立即无限重试，为什么仍可能把系统打满？

展开自测解析

冲突条件没改变，重试反而放大竞争。应有界重试、适当退避、观测与失败处理，并先修等待协议。

理解后，再这样简述：死锁分析看等待关系和共同加锁顺序；超时与重试须配合资源清理和业务恢复。

核对原文：Java：线程管理与死锁检测。

基础必会 14. 线程池：任务来了，为什么先排队再扩线程？

先看问题：图片识别请求突增，你既不想每次 new Thread，也不想无限接任务吃光内存。线程池管理的是执行能力、缓冲能力和超载行为。

原理怎样推出来

ThreadPoolExecutor 的核心参数描述三件事：corePoolSize 与 maximumPoolSize 决定工作线程数量；workQueue 决定如何存等待任务；keepAliveTime、unit、threadFactory 和 handler 决定空闲回收、线程创建与拒绝处理。核心线程默认也不是启动时一次全部创建，而是按需创建。

通常运行流程是：线程数小于 core，创建线程处理任务；否则尝试入队；入队失败后再尝试扩到 max；仍不能接纳就拒绝。入队后实现还会复查运行状态并确保有工作线程，因此流程图是运行态主线，不是完整并发实现。

把它放进一个例子

设置 core=2、max=4、队列容量=2，连续提交 7 个一直阻塞的任务，且池未关闭：第 1、2 个创建线程；第 3、4 个排队；第 5、6 个因队列满而创建额外线程；第 7 个触发拒绝。若队列无界，任务通常一直入队，max=4 很可能根本用不到。

AbortPolicy 抛异常，让调用者处理超载；CallerRunsPolicy 让提交线程执行，能减缓继续提交，但也可能卡住 HTTP 请求线程或事件循环，池关闭时还会丢弃。两种 Discard 策略丢任务，只适合明确允许丢弃的工作。

若稳定到达率约 100 次/秒，平均执行耗时 0.2 秒，平均执行中的任务约 20 个，这是容量估算的起点。再检查 CPU、数据库连接数、外部服务限额、尾延迟与压测结果；“IO 型=2N”不能取代这些约束。

边界与反例：有界队列防止无上限积压，却不保证已接纳任务不丢；重要异步业务还需持久任务记录和补偿。图和示例假设运行态、线程创建正常且任务不提前完成。

停一下，自己推：队列从 100 扩到 100,000，max 不变，吞吐一定上升吗？

展开自测解析

通常不会。执行能力没变，只能容纳更多等待，可能让延迟和内存占用上升，并推迟扩线程或暴露拒绝。先判断瓶颈与允许排队时长。

理解后，再这样简述：线程池用线程、队列与拒绝策略控制负载；先核心、再入队、再扩容，参数必须结合任务耗时和下游容量。

核对原文：Java SE 21：ThreadPoolExecutor。

基础必会 15. ThreadLocal：线程池复用为什么会串用户？

先看问题：请求 A 把用户 id 放进 ThreadLocal，结束后没清理。池里的同一线程处理请求 B，B 可能看到 A 留下的值。

原理怎样推出来

ThreadLocal 把每线程绑定的值隔离开，不是为同一共享变量加锁。其绑定随线程而存活，线程池的工作线程比请求长寿，所以“请求结束”不会自动清除它。值仍可能引用用户对象、连接等，使资源和上下文长期保留。

使用时明确设置、读取与 remove 的范围，通常在 finally 清理。新线程和异步线程并不会自动得到普通 ThreadLocal 的值；InheritableThreadLocal 的创建时继承也不等于线程池的每次任务传播。

把它放进一个例子

try {
    currentUser.set(userId);
    handleRequest();
} finally {
    currentUser.remove();
}

异步链路需要显式传参或框架上下文传播，并考虑嵌套调用的恢复。Spring JDBC 事务资源的线程绑定也解释了为何切到新线程不自动继承事务。

边界与反例：同一可变对象若被多个线程各自绑定，对象本身仍被共享。ThreadLocalMap 的弱 key 不保证 value 及时释放，不能替代 remove。

停一下，自己推：只有设置了值的请求调用 remove，其他请求不清理就够了吗？

展开自测解析

首先应保证每次建立绑定都有对称清理，并检查所有异常和提前返回路径。遇到历史泄漏或上下文嵌套，还须定义入口初始化与恢复策略。

理解后，再这样简述：ThreadLocal 管线程范围的绑定，线程复用让请求范围需要显式清理；传播与共享对象安全另行处理。

核对原文：Java：ThreadLocal 契约。

基础必会 16. ConcurrentHashMap：容器安全，业务就安全吗？

先看问题：共享 Map 不会因并发 put 损坏，仍可能让“第一次收到回调才处理”被执行两次。容器操作原子与业务步骤原子不是同一件事。

原理怎样推出来

JDK 8 的经典实现把数据分散到桶：空桶安装节点可用 CAS（比较并交换），非空桶的部分更新用 synchronized 等机制协调，扩容可由多个线程协作。不同桶的更新不必全挤在一把全表锁上，读取一般也不用同样的全局锁。

API 保证要比实现口诀优先：putIfAbsent、compute 等能把针对一个键的判断与更新合并。containsKey 后再 put 是两个操作，其他线程能插入其间。遍历具有弱一致性，并发变化中的 size 不能当严格控制依据。

把它放进一个例子

// 不要用 containsKey + put 竞争“第一次”
if (seen.putIfAbsent(messageId, Boolean.TRUE) == null) {
    // 本进程内，这个键的首次登记者进入这里
}

这只是登记竞争的示意：业务失败后如何重试、记录何时清理、服务重启与跨进程怎么办，都还未解决。Map 里的可变对象也需要自己的线程安全策略。

边界与反例：compute 回调应短小，阻塞 I/O 可能拖住相关更新。ConcurrentHashMap 不支持 null 键和值；其原子能力也不覆盖两个键或外部数据库组成的事务。

停一下，自己推：map.get(key) 得到 ArrayList 后，两个线程直接 add，会因 Map 安全而安全吗？

展开自测解析

不会。Map 保证的是映射管理；取出的 ArrayList 是另一个共享可变对象，它的操作需要同步、并发集合或不可变替换等协议。

项目常用 17. CompletableFuture：异步不等于任务已经成功

基础必会 20. IOC 与 AOP：容器和代理各解决哪种重复？

先看问题：每个服务自己 new 数据库访问对象会紧耦合；每个业务方法自己写审计、计时和事务又会重复。IOC 与 AOP 分别处理这些问题。

原理怎样推出来

IOC 把对象装配控制权交给容器，DI（依赖注入）把依赖传入对象。业务类依赖接口或明确协作者，测试或配置可以换实现，不必到处修改 new 的位置。IOC 本身不意味着所有类都必须有接口。

AOP 把跨多个入口重复出现的行为放到统一拦截逻辑中。切点选择哪些方法，通知定义进入、返回、异常或环绕时做什么，代理把调用连接起来。环绕通知要理解 proceed：不执行它就可能阻止业务，执行两次就可能重复业务。

把它放进一个例子

调用方 → 代理：记录开始时间
       → 目标方法：执行业务
       → 代理：记录耗时与结果/异常

JDK 代理通过接口转发，类代理通过生成子类拦截可覆盖的方法。具体选择受 Spring 与 Boot 配置影响；审计应避免记录密码、完整凭证等字段，也不要让日志异常无意改变正常业务的异常语义。

边界与反例：代理只拦截经它发起的可拦截调用，自调用是共同边界。普通业务分支并非都适合塞进切面，否则读代码时很难看出流程。

停一下，自己推：一个环绕通知 catch 到业务异常后只记日志并返回 null，会影响什么？

展开自测解析

调用方不再收到原异常，依赖异常判断的事务回滚或重试也可能改变。切面要明确是否传播异常，并保留业务契约。

理解后，再这样简述：IOC 管装配与生命周期，AOP 管横切调用行为；理解代理路径和异常传播才能用对切面。

核对原文：Spring：代理机制与自调用。

基础必会 21. Spring MVC：一次 HTTP 请求怎样进入你的方法？

基础必会 23. 事务“失效”：没开启、没回滚，还是没覆盖到？

先看问题：同样写着 @Transactional，有时根本没进入事务，有时事务正常提交了，有时只有主线程的数据库操作受保护。先把这三种问题分开。

原理怎样推出来

默认代理模式下，调用先经过事务拦截器，再进入目标方法。拦截器决定开启或加入事务，方法完成后按规则提交或回滚。自己 new 的对象、绕过代理的自调用等情况，没有触发被标注方法的事务拦截。

异常被吞掉，拦截器看到正常返回，通常会提交；默认受检异常通常也不触发回滚，除非改变回滚规则。线程绑定的 JDBC 事务不会自动传给新线程；Redis 操作、HTTP 请求也不会自动加入数据库本地事务。

把它放进一个例子

class OrderService {
    public void place() {
        this.save();   // 直接进入目标对象，未经过 save 的代理入口
    }
    @Transactional
    public void save() { /* 写数据库 */ }
}

若 place 没有外层事务，save 的注解不会因此开启事务；若 place 已通过代理进入了事务，save 仍可处在现有事务里，但自身注解的 REQUIRES_NEW 等语义不会被这次自调用应用。常见修复是调整职责，把事务边界放到真正经代理调用的服务方法上。

边界与反例：“非 public 都失效”不是通则：Spring 6 的类代理默认可支持 protected 和包可见方法；接口代理要求 public 接口方法。private 方法与类代理的 final 方法等仍有代理限制，先核对版本和代理方式。

停一下，自己推：事务方法里先写 DB，再发 HTTP 指令，随后抛异常。DB 回滚能撤回设备收到的指令吗？

展开自测解析

不能。本地事务只约束参与其中的数据库操作。跨系统副作用需要 outbox、补偿或业务状态协议，并考虑命令已经执行但回执丢失的情况。

理解后，再这样简述：事务排查按代理入口、事务管理器与传播、回滚规则、线程和资源范围逐层检查。

核对原文：Spring：@Transactional 的代理与可见性规则。

基础必会 24. 事务传播：内层失败，外层还能提交吗？

先看问题：下单调用扣库存，扣库存失败被外层 catch 住。外层以为继续即可，提交时却抛 UnexpectedRollbackException。

原理怎样推出来

REQUIRED 表示有事务就加入、没有就创建；内外逻辑范围可能共享同一物理事务。内层把共享事务标记 rollback-only 后，外层 catch 不会自动撤销该标记，最终仍不能正常提交。

REQUIRES_NEW 使用独立物理事务，常挂起外层事务，因此内层提交可不随外层回滚撤销；它也可能需要另一条连接。NESTED 在支持的事务管理器与资源上使用保存点，可局部回滚，但外层整体回滚仍撤销它，不是独立提交。

把它放进一个例子

若库存与订单必须一起成功，用同一事务维护约束；若失败审计必须独立保存，可评估经另一个代理入口调用 REQUIRES_NEW。不要把多个 HTTP 或 Redis 副作用也想当然纳入其中。

外层线程已持连接，再获取内层连接，而连接池被其他外层事务占满，可能产生等待。这是传播选择带来的容量问题。

边界与反例：传播规则要实际经过事务代理才生效；自调用不应用内层注解。NESTED 支持、异常回滚规则和事务管理器类型需要按项目核对。

停一下，自己推：内层 REQUIRES_NEW 已提交，外层随后回滚，内层写入会自动撤销吗？

展开自测解析

不会。独立事务的成功提交不受外层回滚自动撤销；这正是它与共享事务或保存点方案的差异。

理解后，再这样简述：传播决定加入、独立或保存点关系；要同时看回滚标记、代理入口和连接需求。

核对原文：Spring：事务传播。

基础必会 25. MyBatis：参数绑定为什么防注入，字符串替换为什么危险？

先看问题：用户输入一个名称，你希望它是数据；但拼接 SQL 后，数据库可能把输入里的引号和 OR 当成语法。

原理怎样推出来

#{name} 通常生成 PreparedStatement 的参数占位，值通过参数接口传入，SQL 结构与参数数据分离。${name} 则先替换成文本，数据库收到的是已经改变的 SQL，不能区分哪段来自用户。

表名、列名与排序关键字通常不能用值参数占位；需要先把用户选项映射到固定白名单标识符，再形成结构。参数绑定保护的是值位置，不能承诺一段含动态结构的任意查询都安全。

把它放进一个例子

WHERE name = #{name}    -- 输入作为值
WHERE name = '${name}' -- 输入可能改变 SQL 结构
ORDER BY ${sortField}  -- 只允许服务端白名单映射结果

一级缓存主要在 SqlSession 范围，生命周期和配置影响共享；二级缓存按 namespace 等规则组织，修改会触发相应失效。跨 namespace 更新、多表查询和多实例环境要检查失效链路，不应把它当自动一致的全局缓存。

边界与反例：把危险字符删掉不是可靠的标识符白名单；也不要把 ${} 用于可绑定的普通值。改为 Redis 仍需设计一致性与失效，换存储并不会消除问题。

停一下，自己推：前端传 sortField="price DESC; ..."，后端直接用 ${sortField}，即使其他值都用 #{}，安全吗？

展开自测解析

不安全，危险来自排序结构。后端应接收有限选项，映射到固定列名和 ASC/DESC，拒绝其他输入。

理解后，再这样简述：值用参数绑定，结构用服务端白名单；缓存按实际会话和失效范围分析。

核对原文：MyBatis：参数、字符串替换与缓存。

它是有生命周期的外部资源，可能持有线程、任务与旧类加载器；应明确谁创建、谁关闭以及关闭时怎样处理未完成任务。

理解后，再这样简述：Bean 从实例化到注入、初始化和代理包装才适合对外使用；资源的创建与销毁都要有归属。

核对原文：Spring：初始化与销毁回调。

进阶追问 27. 循环依赖：三级缓存为什么保存“工厂”？

先看问题：A 需要 B，B 又需要 A，容器创建 A 时还没完成，却被 B 要求交出来。核心难题是怎样处理未完成的对象与最终代理的一致性。

原理怎样推出来

在允许循环引用的某些单例属性注入场景中，A 可以先实例化，再注册生成早期引用的工厂。创建 B 时，B 需要 A，容器就使用工厂取得 A 的早期引用；B 完成后，再继续给 A 注入 B。

这里的三级缓存是成品单例 singletonObjects、已生成的早期引用 earlySingletonObjects、早期引用工厂 singletonFactories。保存工厂可以延迟到真的被依赖时才获取早期引用，并给支持该流程的后处理器机会提供代理，避免其他 Bean 持有错误的原始对象。

把它放进一个例子

实例化 A → 注册 A 的早期引用工厂
填充 A 需要 B → 创建 B
填充 B 需要 A → 工厂提供 A 的早期引用
B 完成 → 注入 A → A 完成

构造器环则不同：要 new A 得先有 B，要 new B 又得先有 A，连可提前暴露的 A 实例都没有。拆分职责、抽取共同服务，通常比硬启用循环引用更容易维护。

边界与反例：不是所有循环都能解决：构造器、prototype 和某些代理组合要单独判断。Spring Boot 2.6 起默认禁止循环引用，不要把内部能力当成项目一定开启的功能。

停一下，自己推：把一边改成 @Lazy 可以启动，就说明依赖设计合理了吗？

展开自测解析

不说明。它可能通过延迟解析打破启动环，但运行时仍有双向耦合；应检查职责是否可拆开、调用是否形成递归，以及初始化时是否提前触发懒代理。

理解后，再这样简述：三级缓存帮助特定单例场景协调早期引用与代理；能启动只是底线，先分析为什么有双向依赖。

核对原文：Spring：构造器循环依赖与依赖注入；Boot 2.6 的循环引用默认行为。

基础必会 28. SQL 与 JOIN：结果为什么比订单数还多？

先看问题：订单关联明细后，一笔订单有三个明细，结果出现三行；再关联其他一对多表，结果还可能继续放大。

原理怎样推出来

JOIN 先按关联条件组合匹配行，一对多关系不会自动压成一行。INNER JOIN 保留匹配结果，LEFT JOIN 还保留左表没匹配的行，并将右侧补 NULL。若对右侧条件放进 WHERE，未匹配行常因条件不成立被过滤，可能改变你想要的左连接语义。

WHERE 过滤明细行，GROUP BY 组织分组，HAVING 判断聚合后的组。NULL 表示缺失/未知，普通 = NULL 不是正确测试，要用 IS NULL；COUNT(*) 计行，COUNT(column) 不计该列为 NULL 的行。

把它放进一个例子

SELECT o.id, COUNT(i.id) AS item_count
FROM orders o LEFT JOIN item i ON i.order_id = o.id
GROUP BY o.id;

这样才按订单聚合明细数。分页前若先把订单展开，LIMIT 取到的是连接结果行，不一定是期望数量的订单；可先分页主实体，再取关联内容。

边界与反例：SELECT 未分组字段的合法性受 SQL 模式与依赖关系等规则约束。拼接用户输入会改变结构，值要参数绑定，动态标识符要白名单。

停一下，自己推：LEFT JOIN 后 WHERE i.status='NEW'，没有明细的订单通常还能保留吗？

展开自测解析

通常不能，因为补出的 NULL 不满足等值条件。是否放到 ON 中、是否额外保留 NULL，要按你想得到的结果定义。

理解后，再这样简述：先理解关系和结果基数，再写过滤、聚合与分页；索引不能修正本来就错的 SQL 语义。

核对原文：MySQL：JOIN。

基础必会 29. 为什么索引常用 B+ 树？

先看问题：一千万行订单里找一行，数据库最怕的不是多做几次整数比较，而是为了找它读取大量数据页。索引要先减少需要访问的页。

原理怎样推出来

树上的一个节点可以对应一个页。二叉树每次只把候选范围分成两份，层数容易变多；B+ 树一个内部页保存很多分隔键和子页指针，一次把范围分成很多份，所以树更矮。若页不在 Buffer Pool 中，访问它才需要实际磁盘 I/O：树高表示查找路径上的页数，不等于每次都发生那么多物理 I/O。

B+ 树把数据项集中在叶子页，内部页专门做导航。与内部节点也保存数据项的 B 树相比，在相同页容量和键大小下，导航页通常能容纳更多分支。叶子页按键有序并相连，找到范围起点后就能向后扫描，不必每取一条都从根重新找。

把它放进一个例子

查 id BETWEEN 100 AND 200：先沿导航页找到 100 所在的叶子页，再顺着叶子页读到 200。哈希擅长按完整键找一个值，但没有自然的有序邻接关系，不能靠同一结构高效完成这种范围扫描。

InnoDB 的主键树叶子保存整行，二级索引叶子保存索引列和主键。两者都是 B+ 树，却不能统称为“叶子都存整行”。

边界与反例：“三层容纳两千万行”只是特定页大小、键长度、行宽和填充率下的估算。键越宽，分支越少；索引还会增加写入、分裂和存储成本。

停一下，自己推：把 bigint 主键换成很长的字符串，为什么其他二级索引也可能变大？

展开自测解析

二级索引叶子也携带主键。主键变宽会使每个二级索引条目变宽，同一页能装的条目变少；主键本身的导航键也变宽，可能降低扇出。

理解后，再这样简述：B+ 树通过多分支减少页访问，并利用有序叶子支持范围扫描；InnoDB 主键索引存行，二级索引存键与主键。

核对原文：MySQL：聚簇与二级索引。

基础必会 30. 联合索引为什么有最左匹配？

先看问题：你给任务表建了 (dock_id, status, created_at)，为什么按机库查很顺，单独按状态查却可能扫描很多条目？

原理怎样推出来

联合索引按整个元组排序：先比机库，机库相同再比状态，前两项相同才比时间。它不是三棵各自独立排序的树。确定前导列相当于先找到一本词典里的某个分区，后面的排序才能用于继续缩小连续范围。

前导列做等值匹配后，后续列通常还能确定查找范围；前导列用了 > 之类的范围条件后，后面的列在跨分组的结果中通常不再连续有序，不能同样缩小整段扫描。但它仍可能用于索引条件下推（ICP）过滤，或作为返回列实现覆盖。

把它放进一个例子

(A, DONE, 10:00)
(A, NEW,  09:00)
(A, NEW,  11:00)
(B, DONE, 08:00)
(B, NEW,  07:00)

dock_id='A' AND status='NEW' 对应中间连续两条；只查 status='NEW'，匹配条目却分散在 A、B 各组里。SQL 里把 status 写在 dock_id 前面不会改变索引的物理排序。

边界与反例：“使用索引”有两种不同含义：借有序关系快速定位，或把索引条目从头扫到尾再筛选。缺少最左列通常丢掉直接定位能力，却仍可能扫描整个索引。EXPLAIN 的 key 是所选索引名，非空只说明选择了它，不说明扫得少。

进阶补充：缺少最左列时，skip scan 为什么可能少扫？

对索引 (机库,时间)，查时间≥10:00，如果机库有 A、B 两组，优化器在满足条件时可先定位 A 组里≥10:00 的范围，再跳到 B 组重复。它相当于枚举前导列后分别查范围，不是把时间突然变成全局有序。

常见限制包括单表、查询列均来自索引、相应范围条件等；枚举很多机库也有成本。全索引扫描则是从头读所有条目再筛选。是否采用 skip scan 要看实际计划，Extra 可出现 Using index for skip scan。先理解排序和扫描，再学这个优化例外。

停一下，自己推：WHERE dock_id='A' ORDER BY created_at 能直接利用这个索引的顺序吗？

展开自测解析

通常不能：同一机库内部先按 status 分组，各状态组里的时间才有序。若再固定 status，created_at 才在选定分组内有序。最终看执行计划和排序方向等条件。

理解后，再这样简述：最左匹配来自元组的字典序；区分用于定位、用于过滤和用于覆盖这三种索引用途。

核对原文：MySQL：范围优化与 skip scan。

基础必会 31. 回表和覆盖索引到底多做了什么？

先看问题：同样按设备编号找任务，为什么只取 id 很快，改成取完整任务详情就可能更慢？

原理怎样推出来

在二级索引里找到条目，只拿到了该索引携带的列和主键；如果还要别的列，就拿主键去聚簇索引再找一次。这次额外访问叫回表。匹配很多行时，可能发生很多次这样的查找。

若查询所需的筛选与返回信息在这个索引里就能取得，就可以用覆盖索引避免为取缺失列而回表。“建了联合索引”与“这个查询被覆盖”是两回事，后者取决于查询实际使用的列。

把它放进一个例子

-- 假设主键为 id，二级索引为 (dock_id, status, created_at)
SELECT id, status, created_at FROM task WHERE dock_id = 7;
SELECT id, status, payload    FROM task WHERE dock_id = 7;

第一条所需字段都在索引条目里；第二条的 payload 不在，要回表。EXPLAIN 中 Using index 是覆盖查询的常见信号，Using index condition 则指索引条件下推，含义不同。

边界与反例：别为覆盖把所有字段都塞进索引：宽索引占空间、降低缓存命中并增加写入成本。MVCC 可见性等内部检查也可能带来聚簇索引访问，“覆盖”描述的是取列的访问路径。

停一下，自己推：查询只返回 id，但 WHERE 还判断一个不在索引里的 payload，仍是覆盖查询吗？

展开自测解析

不是。返回列够用不代表判断条件够用；数据库仍需取得 payload 才能判断，通常还要访问整行。

理解后，再这样简述：回表是从二级索引拿主键后再访问聚簇索引；覆盖要求查询所需信息可由索引提供。

核对原文：MySQL：二级索引记录。

基础必会 32. 索引“失效”：规则、成本还是查询语义出了问题？

先看问题：给时间列建了索引，却用 DATE(created_at)=某天查询；或者索引正常，优化器仍选择全扫。两种原因要分开分析。

原理怎样推出来

普通有序索引按原始列值排列。函数、运算、某些隐式转换或以通配符开头的匹配，可能让优化器不能直接把条件转换成这个索引的窄范围。可把日期筛选写成起止时间范围，并让参数类型与列类型匹配。

另一类是可以使用，但预计不划算：条件返回大部分行，需要大量回表时，全表扫描可能更便宜。优化器参考统计信息与成本，实际数据倾斜或统计陈旧可能使估计偏离。判断应看访问方式与扫描/返回量，不只看 key。

把它放进一个例子

WHERE created_at >= '2026-10-14 00:00:00'
  AND created_at <  '2026-10-15 00:00:00'

若按业务时区筛选，先正确换算边界。LIKE 'abc%' 与 LIKE '%abc' 的定位能力不同，前者有可用前缀，后者通常没有。

边界与反例：函数索引、生成列索引与特定优化会改变结论，所以“用了函数永远不能用索引”过于绝对。FORCE INDEX 也可能强迫更差路径，先拿证据。

停一下，自己推：状态列 99% 都是 NEW，建单列状态索引就一定能显著加速查所有 NEW 吗？

展开自测解析

不一定。筛选性低，扫描与回表很多；可结合其他等值维度、时间、覆盖或业务分页需求重新设计，并对照实际计划。

理解后，再这样简述：先辨认能否形成有效范围，再看使用索引的总成本；改写必须保持时间、类型和匹配语义。

核对原文：MySQL：范围优化。

基础必会 33. 慢 SQL：怎样找到真正花时间的步骤？

先看问题：接口用了 2 秒，可能是 SQL 扫描太多，也可能是等待行锁、连接池排队或传回太多数据。先确认时间花在哪，才谈索引。

原理怎样推出来

先从链路耗时、慢查询记录和具体参数找出问题查询，再看计划：走哪个索引、估计扫多少行、怎样连接与排序。EXPLAIN 的 rows 通常是估计，不是现场实际扫描计数；能在测试环境使用 EXPLAIN ANALYZE 时，再对照实际行数、循环次数与耗时。

假设要取某机库最新 20 个待执行任务，(dock_id,status,created_at,id) 可以先固定前两列，再按时间和 id 找结果。收益来自少扫描、少排序、少回表，而不是“Extra 看起来漂亮”。每多一个索引，都让写入多维护一份结构。

把它放进一个例子

SELECT id, created_at FROM task
WHERE dock_id = 7 AND status = 'NEW'
ORDER BY created_at DESC, id DESC LIMIT 20;

深分页 OFFSET 100000 即使返回 20 条，也通常要跳过大量条目。连续翻页可用上一页最后的 (created_at,id) 做游标；带 id 是为解决同时间记录的稳定排序。业务要求随机跳页时，要承认游标分页不直接满足它。

边界与反例：小表全扫、少量结果排序可能很便宜，ALL 或 filesort 不是一律错误。EXPLAIN ANALYZE 会实际执行语句，只在受控环境分析合适的查询。

停一下，自己推：“加索引后从 2 秒降到 100ms”能单独证明索引有效吗？

展开自测解析

还不够。要尽量控制数据、查询参数、缓存冷热和负载，再对比扫描行数、计划和多次耗时；锁等待消失或缓存变热也能使同一查询变快。

理解后，再这样简述：按定位、执行计划、实际工作量、改动和验证这条线排查；性能收益要能解释为少做了什么。

基础必会 34. ACID：事务究竟承诺什么？

先看问题：转账要让 A 减 100 与 B 加 100 一起成功；并发转账还要不破坏余额约束，系统重启后已提交结果也应按配置保留。

原理怎样推出来

原子性（A）让事务范围内的操作整体完成或撤销；一致性（C）要求操作保持定义好的数据约束，不是“所有缓存瞬时相同”；隔离性（I）规定并发事务可以怎样观察和影响彼此；持久性（D）描述提交结果的保存。

数据库提供事务与约束机制，业务仍须建立正确的不变式。即使 A、B 两次修改放进事务，如果代码计算错金额或没有余额条件，也不能让结果自动正确。隔离强度、存储引擎和日志刷盘设置会影响具体保证。

把它放进一个例子

BEGIN;
UPDATE account SET balance=balance-100
WHERE id=1 AND balance >= 100; -- 必须检查影响行数
UPDATE account SET balance=balance+100 WHERE id=2;
COMMIT; -- 前提：两步及目标账户校验成功，否则回滚

示意只包含本地数据库账户，不包含外部支付网关；异常时要有明确回滚路径。

边界与反例：不是所有表引擎都支持同样事务行为，DDL 也可能隐式提交。Redis、文件和 HTTP 副作用不会因为处在同一个 Java 方法里就自动参与 DB 事务。

停一下，自己推：事务里先读余额，再无条件减余额，两个事务都判断余额够，能保证不超扣吗？

展开自测解析

不一定。要用合适的锁定读或原子条件更新等协议，事务包装本身不消除“检查后再执行”的竞态。

理解后，再这样简述：ACID 描述事务保证，业务一致性还依赖约束和正确并发协议；明确资源与配置边界。

核对原文：MySQL：InnoDB 与 ACID。

基础必会 35. 事务隔离与 MVCC：读的是哪一版？

先看问题：A 正在统计库存，B 同时把库存从 10 改成 8。A 第二次查询该看到 10 还是 8？隔离级别是在规定这种并发观察。

原理怎样推出来

脏读是看见别人尚未提交的数据；不可重复读是同一事务重复读到不同已提交版本；幻读关注同一条件下匹配记录集合的变化。读未提交、读已提交（RC）、可重复读（RR）、串行化逐步加强隔离，但实现与代价需要结合数据库看。

InnoDB 的普通一致性 SELECT 使用 MVCC（多版本并发控制）：记录带有最近修改事务信息，undo 链保留可重建的旧版本，ReadView 判断哪些版本对本次快照可见。它不是把整张表复制一份，而是读到不可见的新版本时向历史版本回溯。

RC 每次一致性读建立新快照；RR 通常复用第一次一致性读建立的快照。自己的修改仍可见。ReadView 判断还要考虑创建者自身、事务编号边界和创建时的活跃事务集合，不能简化为“事务号小就都可见”。

把它放进一个例子

顺序ABA 的观察
1BEGIN；普通 SELECT stock尚未修改读到 10，RR 此时建立快照
2事务继续UPDATE stock=8；COMMITB 的新版本已提交
3再次普通 SELECT已结束RC 读到 8；RR 仍读到 10

SELECT ... FOR UPDATE 等锁定读不走上述旧快照观察，而是读取并锁定当前记录。需要更新库存时，别把普通查询的旧值当成并发决策依据。

边界与反例：RR 对一致性读靠快照保持观察，对范围锁定读靠 next-key 等锁抑制并发插入。混用快照读、当前读和自身修改时，不能承诺“事务里的所有查询永远相同”。

停一下，自己推：A 先 BEGIN，B 提交库存 8，A 才第一次普通 SELECT。在通常 RR 事务里，A 读到什么？

展开自测解析

通常读到 8。仅 BEGIN 不必然建立一致性读快照；第一次一致性读时才建立。显式 WITH CONSISTENT SNAPSHOT 等用法要单独分析。

理解后，再这样简述：MVCC 让读写可以并发，关键是版本可见性与快照创建时机；快照读和锁定读要分开分析。

核对原文：MySQL：一致性非锁定读。

基础必会 36. undo、redo、binlog：为什么有三种日志？

先看问题：事务写到内存数据页后断电，要恢复；写了一半发现业务失败，要撤销；另一台库还要复制改动。三种用途需要不同记录。

原理怎样推出来

undo 保存支持回滚和旧版本重建的信息，是 MVCC 的重要基础；redo 为 InnoDB 崩溃恢复记录页相关修改，使提交时不必把所有脏数据页同步刷完再算成功；binlog 属于服务器层，记录用于复制与恢复的数据库变更事件，具体格式可不同。

InnoDB 与 binlog 的提交通过内部协调让恢复判断尽量一致，常以内部两阶段提交说明 prepare/commit 关系；它不是任意跨系统业务的分布式事务。日志写到缓冲、操作系统与持久介质也不是同一时刻，刷盘配置决定不同故障下的丢失窗口。

把它放进一个例子

需要撤销这次更新 → 依赖 undo
崩溃后恢复 InnoDB 修改 → 依赖 redo
复制到从库/配合备份恢复 → 使用 binlog

一个事务写了几页数据，但提交可以先确保必要日志持久，数据页之后再按检查点等机制刷盘，这使随机数据页写入不必全部卡在提交路径。

边界与反例：不能说“有 redo 就永不丢数据”：还取决于刷盘、硬件与故障范围。binlog 恢复通常配合基础备份和保留范围，不是无起点重放即可还原全部历史。

停一下，自己推：错误 DELETE 已经提交，undo 一定能让你随时回滚到昨天吗？

展开自测解析

不能。事务已提交不再提供任意历史回滚承诺，undo 也可能清理；误删恢复应依赖备份与适当的日志恢复方案。

理解后，再这样简述：undo 管撤销与旧版本，redo 管引擎崩溃恢复，binlog 管变更复制与恢复；持久性按配置与故障定义。

核对原文：MySQL：redo；MySQL：undo；MySQL：binlog。

基础必会 37. 为什么锁住已有行，还需要间隙锁？

先看问题：你锁住价格 10 和 20 的商品，但别人仍能插入价格 15 的商品。已有记录被锁，并没有阻止“还不存在的记录”。

原理怎样推出来

Record Lock 锁的是索引记录；Gap Lock 限制向两条索引记录之间的间隙插入；Next-Key Lock 把记录和它前面的间隙一起锁住，通常用左开右闭区间表示。锁范围是在索引扫描过程中确定的，所以索引路径影响并发度。

RR 的范围锁定读通常需要保护扫描范围，防止同条件下冒出新记录。唯一索引等值命中已存在记录时，常只需记录锁，因为不存在第二个相同唯一键。无合适索引导致扫描大量记录时，锁范围可能很大；这不是自动升级成一把表锁。

把它放进一个例子

-- 在 RR、显式事务中，price 有非唯一索引，已有 10、20
SELECT * FROM product WHERE price > 10 AND price <= 20 FOR UPDATE;

理解时先画出 (10,20]：20 的记录与前面的间隙都在保护范围内，其他事务插入 15 就可能等待。真实扫描还可能锁到边界外的记录或间隙，需要结合实际索引和执行路径检查，不能只把 WHERE 区间照抄为完整锁范围。

边界与反例：RC 通常不为普通搜索保留间隙锁，但外键检查与重复键检查仍可能用到它；唯一键未命中与命中也不同。锁分析先交代隔离级别、索引、是否命中及事务边界。

停一下，自己推：两个事务都先锁 A 再锁 B，与一个锁 A→B、另一个锁 B→A，哪个更容易死锁？

展开自测解析

后者容易形成互相等待。统一加锁顺序和缩短事务可以降低风险，仍需处理数据库检测到死锁后的事务回滚与重试。

理解后，再这样简述：记录锁保护已有行，间隙锁限制新插入；索引决定扫描范围，也影响锁范围和死锁风险。

核对原文：MySQL：记录、间隙与 next-key 锁。

项目常用 38. 并发更新与数据库死锁：怎样守住业务状态？

先看问题：两个调度事务都读到机库 IDLE，随后各自创建任务；即使每个方法都有事务，也可能出现两个占用任务。

原理怎样推出来

把判断与状态转换放在同一个数据库原子条件中，并检查影响行数，可避免分离的“先查再改”窗口。更复杂的多行规则可用合适索引的锁定读与一致的加锁顺序；唯一约束能为不允许重复的业务键提供独立兜底。

死锁出现时 InnoDB 可检测等待环并回滚一个事务，应用要重新执行完整受影响事务，而不是只重试最后一句。重试要有限次与可观测，涉及外部副作用时先证明可重放。

把它放进一个例子

UPDATE task SET status='RUNNING', version=version+1
WHERE id=? AND status='NEW' AND version=?;
-- 1 行：获得本次转换；0 行：状态/版本已变或记录不存在

两个账户更新可按统一账户 id 顺序获取锁，降低相反顺序造成的死锁机会；不要持有 DB 锁等待长时间设备响应。

边界与反例：条件更新保护指定不变式，不自动保护全部业务过程；影响 0 行也不总表示“已完成”。锁等待超时与死锁对事务的处理可能不同，需要框架回滚策略明确。

停一下，自己推：“受影响 0 行”就把回调当成功丢弃，可能遗漏哪类情况？

展开自测解析

记录不存在、条件填错、当前状态非法等都可能返回 0。要按业务查询/错误语义区分，不能把所有未修改都当重复成功。

理解后，再这样简述：原子状态转换、约束和加锁顺序共同保护并发；失败重试以完整事务和幂等边界为单位。

核对原文：MySQL：处理死锁。

6. Redis：结构、缓存与运行边界

先会选类型与处理失效，再理解一致性、持久化和高可用。

基础必会 39. Redis 数据类型：缓存之外怎么选结构？

先看问题：设备详情、用户标签、待处理列表和排行榜，访问方式不同。把它们都存成巨大 JSON，再全量读改写，会丢掉结构本身的能力。

原理怎样推出来

String 保存单值、计数或编码后的对象；Hash 按字段读改一组属性；List 表达有序序列与两端操作；Set 表达无序唯一成员；Sorted Set 把成员与分数关联，支持排序和范围。这是命令语义，不是底层编码固定不变。

选择还要考虑原子操作、元素数量、单键体积和访问粒度。小对象序列化成 String 便于整体缓存；只改部分属性可考虑 Hash。Bitmap 与 HyperLogLog 适用于特定布尔统计/近似基数需求，不能直接代替精确业务账本。

把它放进一个例子

业务关系候选结构理由
设备详情快照String / Hash整体读或字段读改
标签去重Set成员唯一与集合操作
排行榜Sorted Set按分数排名和范围
简单待办序列List两端入出；可靠消费要另设计

边界与反例：这些结构不会自动组成跨键事务；列表取出就崩溃可能丢待办，不应把简单 List 直接当完整可靠 MQ。大 key 仍会影响内存和命令耗时。

停一下，自己推：排行榜同分时，业务要求按完成时间排序，单独保存相同分数就自然满足吗？

展开自测解析

不自然满足。要定义稳定的次级排序与编码规则，避免误把结构默认的成员排序当成业务时间顺序。

理解后，再这样简述：按数据关系、访问粒度与原子操作选类型，底层编码与可靠业务协议另外分析。

核对原文：Redis：数据类型。

基础必会 40. 过期与淘汰：没到 TTL 为什么也读不到？

先看问题：一个 key 明明设置了一小时 TTL，十分钟后却 miss。除了到期，还可能是主动删除、淘汰或故障恢复导致。

原理怎样推出来

过期依据键的生存时间，Redis 会在访问时以及后台主动检查等路径处理过期键；TTL 到点并不意味着必须在同一瞬间物理释放全部内存。淘汰则在达到 maxmemory 等条件时按策略移除键，可能发生在 TTL 未到之前。

noeviction 不按淘汰策略删键，但达到限制时会拒绝相应写入；allkeys 类策略可从全部键选择，volatile 类只从设了过期时间的候选键选择。LRU 关注最近使用，LFU 关注频次，具体实现通常是近似策略而非维护完美全排序。

把它放进一个例子

缓存节点选择允许淘汰的策略，应用必须能处理 miss 并保护回源。若同实例还保存不能随意失去的幂等键或锁，allkeys 淘汰可能破坏这类状态，需考虑隔离用途与容量约束。

边界与反例：TTL 是逻辑寿命，不是“保证至少存在这么久”。内存策略还要考虑复制、持久化开销与大 key；策略不能代替容量监控。

停一下，自己推：把 key 改成永不过期，在 allkeys-lru 下就不会丢吗？

展开自测解析

不会有这种保证。allkeys 范围包含没有 TTL 的键，仍可淘汰；持久性与副本恢复也有自己的边界。

理解后，再这样简述：过期管时间，淘汰管内存压力；按用途选策略，应用对缓存 miss 要有完整处理。

核对原文：Redis：淘汰策略；Redis：过期。

基础必会 41. 穿透、击穿、雪崩：数据库为什么被打满？

先看问题：这些名词描述的是缓存没有挡住请求时，数据库承受了哪种回源压力。先画请求去向，名称自然就能分清。

原理怎样推出来

不存在的设备 id 每次都 miss，查库又没有结果：如果只缓存真实结果，这种请求永远直接打库，这是穿透。一个很热的真实设备恰好过期，很多线程同时发现 miss 并查库，这是击穿。大量键一起过期，或者缓存服务整体不可用，让许多业务同时回源，这是雪崩。

对策要对应原因：空值缓存阻断重复的无结果查询，布隆过滤器快速排除肯定不存在的键；互斥重建把热点回源合并为一份；随机 TTL 打散共同过期时间。缓存宕机时随机 TTL 无效，需要限流、降级、故障转移等保护数据库。

把它放进一个例子

一个 key 每秒被读 5,000 次，DB 查一次需要 100ms。它过期后的 100ms 内可能积累约 500 个回源请求。重建锁让一个请求去加载，其他请求短暂等待或按规则读旧值，这才是保护数据库的机制。

缓存空值只给较短 TTL：否则设备刚创建，客户端却持续读到之前缓存的“不存在”。布隆过滤器可能误判存在，且需要同步新增数据。

边界与反例：逻辑过期可以返回旧值，但业务必须允许短暂过时；库存、权限等不能无条件套用。等待重建也要有超时与失败处理，不能无限排队。

停一下，自己推：给所有 key 的 TTL 加随机值，能解决每次请求都查一个新的无效 id 吗？

展开自测解析

不能。随机 TTL 针对共同过期；新的无效 id 是穿透，应考虑参数校验、访问控制、限流和不存在数据的过滤策略。

理解后，再这样简述：先区分无结果反复回源、单热点并发回源和整体回源，再选择空值缓存、重建合并或服务降级。

项目常用 42. 为什么先提交数据库，再删缓存仍有竞态？

先看问题：数据库和 Redis 是两个系统，通常没有一个共同的本地事务。你能安排操作顺序，却不能让所有读写都像一个瞬时动作。

原理怎样推出来

Cache Aside 的读是“缓存 miss → 查 DB → 写缓存”，写是“提交 DB → 删除缓存”。若反过来先删缓存，另一请求可在数据库更新前读到旧值并回填，然后 DB 提交后这个旧缓存还在。

先提交再删除减少了这类窗口，但旧读请求仍可能晚到：读请求在提交前已经拿到了旧数据，写请求提交并删掉缓存，旧读请求随后把旧值写回。因此该顺序提供的是常见最终一致方案，不是强一致证明。

把它放进一个例子

顺序读请求 R写请求 W缓存
1miss，查 DB 得到 v1，暂未回填—空
2暂停提交 DB v2，删除缓存空
3把之前得到的 v1 写入缓存已完成旧 v1

TTL 为旧值提供过期边界，删除失败要有可恢复的重试记录；版本控制、串行化同一业务键或订阅数据库变更可以加强方案，但仍需明确各自的失败窗口。

边界与反例：延迟双删依赖等待时间覆盖慢读窗口，不能证明所有请求都及时完成。若读库是有延迟的副本，删后回源也可能读到旧值。先问允许旧多久，再选一致性方案。

停一下，自己推：DB 已提交，进程在发送“删缓存消息”前崩溃，普通异步重试任务能补上吗？

展开自测解析

没有持久重试记录就可能永远不知道该补什么。可以将缓存失效事件与业务改动写进同一 DB 事务的 outbox，再异步投递；这解决事件丢失窗口，仍要分析回填竞态。

理解后，再这样简述：先提交 DB 再删缓存是常见起点；要分析删除失败、旧读回填和副本延迟，并按业务容忍度兜底。

基础必会 43. RDB 和 AOF：恢复时靠什么把内存找回来？

先看问题：Redis 的数据主要在内存。进程重启后，想恢复就必须提前留下可读取的持久记录，并决定可以接受丢多少最近的数据。

原理怎样推出来

RDB 在某个时刻把数据状态保存为快照：恢复时装载结果，不必重放全部写命令。但快照之后的修改如果没进入其他持久记录，就可能丢失。后台保存通常 fork 子进程，写时复制帮助父进程继续服务，仍会有 fork 和额外内存成本。

AOF 记录写操作，恢复时重放。写入 AOF 缓冲或操作系统缓存不等于已落稳定存储，fsync 策略决定持久性与性能取舍。everysec 常以约一秒的丢失窗口作工程预期，异常存储和调度环境不能拿它作绝对时限承诺。

把它放进一个例子

上午做 RDB，下午更新了 1,000 条数据后崩溃：只恢复这份 RDB，就回到上午状态。若使用 AOF，恢复进度取决于实际持久成功的位置。AOF 重写不是停止写入后复制原日志，而是把当前状态压成较短的恢复表示并衔接后续写入。

边界与反例：现代 Redis 支持多文件 AOF 与 RDB/AOF 混合表示，别把旧版单文件细节当通则。复制负责副本可用性，持久化负责重启恢复，备份负责误删等灾难恢复，三者不能互相替代。

停一下，自己推：误执行 DEL 后，AOF 持久化成功了，是不是更容易恢复被删的数据？

展开自测解析

持久化成功也会忠实记录删除，重放得到的是已删状态。恢复误删依赖删除前的备份或可保留的历史恢复点，而不是“开启 AOF 就不怕误删”。

理解后，再这样简述：RDB 保存时点状态，AOF 保存恢复序列；选择取决于恢复时间、可接受丢失量与运行开销。

核对原文：Redis：持久化机制。

基础必会 44. Redis 快在哪里，又会被什么拖慢？

先看问题：大量小 GET 很快，但一次查出百万成员可能让别的请求一起卡住。快的是特定工作负载，不是所有 Redis 命令。

原理怎样推出来

常见键值命令直接访问内存中的数据结构，省去了数据库执行复杂连接、计划和磁盘数据读取的很多工作。事件循环与 I/O 多路复用让服务端同时管理许多连接，不必给每个连接独占一个执行线程。

理解经典模型时，可以把普通命令执行看成在主要执行路径上顺序处理：很多短命令排起来很高效，但一个长命令会占住后面请求的机会。网络 I/O、后台持久化与部分实现工作可以在其他线程或进程进行，所以“Redis 只有一个线程”不准确；版本和部署方式也会改变细节。

把它放进一个例子

GET 一个小值与 SMEMBERS 一个超大集合不是同样工作量。返回 100MB 即使查找快，也要花序列化、传输与客户端处理时间。大 key、长 Lua 脚本、fork、内存换页和网络拥塞都可能成为延迟来源。

边界与反例：内存操作不等于每条请求耗时只有纳秒；客户端延迟还包括排队和网络。SCAN 可以分批遍历，但不是固定时点快照，应用要处理遍历期间的变化与可能重复。

停一下，自己推：把 KEYS * 换成 SCAN，就能把 Redis 变成任意规模下稳定的统计数据库吗？

展开自测解析

不能。分批减少一次阻塞时长，但总遍历量仍大，期间数据可能变化。高频统计应考虑提前维护聚合值或换适合该查询的存储方案。

理解后，再这样简述：Redis 对短小内存操作高效；性能排查要看命令复杂度、数据体积、排队、后台工作和网络。

核对原文：Redis：延迟原因与诊断。

项目常用 45. Pipeline、MULTI 与 Lua：少往返和原子执行一样吗？

先看问题：你想先检查任务未完成再改为完成，同时希望少发网络请求。Pipeline 能节省时间，却不把多个命令自动变成同一原子判断。

原理怎样推出来

Pipeline 把命令批量发送以减少网络往返，没有“其他客户端不能插入整个批次”的保证。MULTI/EXEC 排队后执行事务中的命令，WATCH 可监测键变化并在冲突时使 EXEC 不执行；它不是带任意自动回滚的关系数据库事务。

Lua 在 Redis 端把读取、判断与修改放进脚本执行，脚本执行期间不与普通命令交错，因此适合单一存储里的条件状态转换。原子执行不等于脚本报错后自动撤销已写命令，需在写入前验证参数和类型。

把它放进一个例子

if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0

原子比较持有者再删除锁，避免 GET 与 DEL 之间别人换了锁。Redis 的原子边界不包含随后发送的 HTTP 指令或 DB 提交。

边界与反例：长脚本可能阻塞服务，脚本必须短且有界；Cluster 的键范围与脚本声明规则也要遵守。Pipeline 失败后不能盲目断言所有命令都没执行。

停一下，自己推：Lua 已标记任务 DONE，下一步外部发送失败，Redis 会自动回滚 DONE 吗？

展开自测解析

不会。需要业务状态协议、持久待办或补偿，原子范围不能跨脚本外部资源。

理解后，再这样简述：Pipeline 减少往返，事务与脚本提供各自执行边界；Redis 原子操作不能替代跨系统协议。

核对原文：Redis：Lua 执行与原子性；Redis：事务。

项目常用 46. 复制、Sentinel、Cluster：高可用与容量分别怎么做？

先看问题：一台 Redis 挂了要切换，数据太多又想拆到多台；读副本还可能看到旧数据。这三个需求不能用一个“上集群”概括。

原理怎样推出来

复制让副本追随主节点数据，常见复制路径存在异步窗口，因此故障切换或读副本要分析延迟与数据丢失风险。Sentinel 主要监控、协调故障转移并帮助客户端发现主节点，不把一份数据自动分片成多份。

Redis Cluster 用哈希槽划分键空间，把不同槽分给多个主节点，并结合副本与故障转移。客户端需理解槽路由和 MOVED/ASK 等重定向，跨键命令与事务常要求相关键在同一槽；hash tag 可控制相关键落槽，但可能产生热点。

把它放进一个例子

读请求返回设备旧状态，不一定是缓存更新逻辑错，也可能读到了落后的副本。单键热点即使有很多分片，那个 key 的主要压力仍在它所属节点，不能靠分片数无限加速。

边界与反例：高可用不是绝对不丢，分片不是每条操作自动并行；主从切换对锁、会话和幂等状态的影响要按具体用途分析。

停一下，自己推：Sentinel 有三个节点，业务数据是否自动变成三等份？

展开自测解析

不是。Sentinel 做监控与选主，不是数据分片；数据拓扑取决于被监控的 Redis 主从部署。

理解后，再这样简述：复制提供副本，Sentinel 协调主从高可用，Cluster 划分键空间；一致性与热点不能忽略。

核对原文：Redis：复制；Redis：Cluster。

7. 锁 / Redisson：从 Redis 锁原理到 Java 实现

原生租约 → Redisson 使用 → 可重入与看门狗 → 故障与业务保护。

前三步处理锁的协作；最后一步把保护落实到业务资源，不能省略。

项目常用 47. 分布式锁：有锁为什么还会重复执行？

先看问题：两个服务实例都想调度同一机库，进程内 synchronized 管不到另一台机器。大家需要竞争同一个共享锁。

原理怎样推出来

单个 Redis 实例上的常见加锁是 SET lock:dock:7 token NX PX 10000：不存在才创建，并同时设置租约，避免进程崩溃后永远不释放。token 是本次持有者的唯一标识；释放时必须用 Lua 原子比较 token 再删除，不能先 GET 再 DEL。

租约会到期，业务却不一定结束。A 停顿超过 10 秒，锁过期后 B 获取锁开始处理，A 恢复后仍可能继续操作。续租减少正常长任务的过期，却挡不住无限长停顿。锁只是一种协调机制，最终资源还需要拒绝失效持有者的手段。

把它放进一个例子

-- 数据库内的原子状态约束，示意
UPDATE dock SET status = 'BUSY'
WHERE id = 7 AND status = 'IDLE';

检查受影响行数，只有成功抢到状态的事务才能继续。在更严格的资源协议里，可使用单调递增 fencing token（栅栏令牌），让下游拒绝旧令牌；前提是下游真的检查它。不要把一个随机锁 token 当作 fencing token。

边界与反例：Redis 异步复制下，主从切换可能丢失刚写的锁；这题讨论原生租约锁；Redisson 的续租、副本确认与资源端保护在后续题分别分析。数据库约束只保护其事务内的数据，下发设备指令等外部副作用仍需业务幂等与状态协议。

停一下，自己推：A 的锁过期后 B 已加锁，A 用无条件 DEL 释放，会发生什么？

展开自测解析

A 会删除 B 的锁，让第三个请求也可能进入。原子比较持有者 token 可避免误删，但不能阻止 A 已经过期后继续执行业务。

理解后，再这样简述：锁要考虑获取原子性、租约、持有者校验与故障；强正确性靠资源端约束和幂等共同完成。

核对原文：Redis：分布式锁与复制风险。

项目常用 48. Redisson 怎么用：waitTime、leaseTime、finally 各管什么？

先看问题：原生 SET NX 只是竞争一个键。Java 项目还要处理等待、可重入、续租和持有者校验；Redisson 的 RLock 把这些组织成锁 API。

原理怎样推出来

getLock 返回指定名字的分布式锁对象，名字决定哪些请求相互竞争。lock() 与不同 tryLock 重载分别提供阻塞、等待上限和租期等语义。waitTime 是最多等多久获取，leaseTime 是成功获取后锁的固定有效时长，二者不是同一个超时。

只有获取成功才进入临界区，并在同一持有者上下文中释放。同步 RLock 的所有权关联客户端身份与线程；其他线程不能随意 unlock。拿到锁以后真正需要保护的业务操作必须还在保护范围内，不能提交异步任务后马上解锁。

把它放进一个例子

RLock lock = redisson.getLock("dock:" + dockId);
boolean acquired = lock.tryLock(2, TimeUnit.SECONDS);
if (!acquired) {
    throw new BusyException("机库正在调度");
}
try {
    dispatchWithStateGuard(); // 同线程调用，配合业务状态约束
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

示意使用不显式指定租期的重载，通常走看门狗续租；方法需处理/声明 InterruptedException，BusyException 与业务函数代表项目自己的接口。若选 tryLock(2,10,SECONDS)，则最多等 2 秒，获得后固定租期 10 秒。服务共享 RedissonClient，不能每次请求创建客户端。

边界与反例：isLocked 只说明有人持锁，不能作为自己解锁的依据。isHeldByCurrentThread 校验也不是与下一步 unlock 组成一个原子业务操作；异常、丢锁和续租失败仍应按项目协议处理。示例不是外部指令 exactly-once 的证明。

停一下，自己推：拿锁后 supplyAsync 下发设备指令，立即退出 finally，为什么锁可能没保护到指令？

展开自测解析

异步执行可能发生在解锁之后，且换了线程。要把需要保护的动作与完成条件安排在明确的持有者与生命周期内；长期外部动作更要用持久状态协议，而不是无限延长锁。

理解后，再这样简述：选锁名与粒度，区分等待上限和租期，成功获取后在明确生命周期里释放；框架锁与业务约束配套。

核对原文：Redisson：RLock API。

项目常用 49. 可重入与看门狗：Redisson 到底怎样补上原生锁？

先看问题：同一线程进入外层调度方法，再调用也要拿同一把锁的内层方法，不应该把自己挡死；任务耗时不固定，又不能只拍一个短 TTL。

原理怎样推出来

普通 RLock 的经典实现用 Redis Hash 等信息识别持有者并保存重入次数，获取与释放通过 Lua 等原子路径更新。相同持有者再次进入增加计数，释放减少计数，计数归零才真正释放；其他持有者仍需等待。

常规获取路径未指定正的固定 leaseTime 时，会注册续租。看门狗在有效的续租机制与 Redis 连接条件下延长租约，默认 watchdog timeout 通常为 30 秒且可配置；不要把某版本定时器的每次调用时刻当成绝对准点承诺。指定固定租期的获取路径通常不启用相同的看门狗自动续租。

把它放进一个例子

lock.lock();                  // 通常使用看门狗续租
try { /* 工作 */ } finally { lock.unlock(); }

lock.lock(10, SECONDS);        // 固定租期 10 秒
try { /* 工作 */ } finally { /* 按持有者状态与丢锁策略释放 */ }

两种模式不能混为一谈：固定租期下，工作做 15 秒就可能在第 10 秒后失去锁。可重入也要匹配释放次数，不能内外拿两次却只释放一次。

边界与反例：看门狗不是“业务线程活着就绝对永不丢锁”。客户端崩溃、长时间暂停、网络故障或续租失败，都要考虑租约到期后的旧持有者行为。源码和默认配置要按实际 Redisson 版本核对。

停一下，自己推：同一线程连续 lock 两次，再 unlock 一次，其他客户端应立刻拿到吗？

展开自测解析

通常不应。重入计数还剩一次；需要匹配第二次释放，或者由失败/租约等边界结束持有。

理解后，再这样简述：可重入管理同一持有者的计数，看门狗管理不定时长的租约；固定租期与自动续租要分开。

核对原文：Redisson：RedissonLock 获取、续租与重入实现。

项目常用 50. 锁过期、故障转移与 fencing：框架保护到哪一步？

先看问题：A 拿锁后暂停，租约到期，B 拿锁并完成新的状态更新。A 恢复后仍认为自己可以下发指令，怎样让旧执行者被拒绝？

原理怎样推出来

这个问题不只是误删锁：即使释放时严格核对持有者，A 在恢复后仍可能执行外部动作。数据库状态/版本约束可让旧请求修改失败；资源端若支持单调的 fencing token，可记录已经接受的最高令牌并拒绝更旧令牌，从而把持有者判断延伸到真正受保护的资源。

也不要把原生 Redis 锁复制窗口不加区分地套给所有 Redisson 版本。当前参考指南描述了默认开启的副本同步检查，可降低锁未复制即返回成功的故障窗口；具体配置、拓扑与版本须核对。它解决的复制确认问题，与长暂停后旧执行者继续写是不同问题。

把它放进一个例子

时刻 1：A 获取 token=41，然后长暂停
时刻 2：B 获取 token=42，资源接受并记录 42
时刻 3：A 恢复发送 token=41，资源因 41<42 拒绝

只有资源真的比较令牌才有效。普通 RLock 的随机持有者标识不等于单调 fencing token；Redisson 提供的 fenced 锁能力也要结合版本与可执行校验的下游。

边界与反例：锁只协调遵守同一协议的调用者；无校验的 HTTP/设备接口不会自动获得 fencing。核心业务还需幂等键、状态机与可恢复记录。公平锁、MultiLock、RedLock 等属于按场景追问，不要求入门阶段全部背源码。

停一下，自己推：数据库拒绝了旧 token，但指令在检查前已经发给设备，数据库校验还能撤回它吗？

展开自测解析

不能。校验应在真正副作用的边界执行，或让设备/下游支持幂等与令牌协议；不同系统的动作顺序仍有窗口。

理解后，再这样简述：续租、复制确认和资源端 fencing 分别处理不同风险；正确性需要按真正副作用边界证明。

核对原文：Redisson：可靠性与 fencing。

8. JVM：内存、回收与类型身份

基础是判断内存与对象存活，类加载隔离是进一步追问。

基础必会 51. JVM 内存：方法、对象和类信息分别住哪里？

先看问题：递归过深、对象持续积压、加载太多类，都可能让 Java 服务出错，但它们耗尽的不是同一种内存。

原理怎样推出来

调用方法要保留参数、局部变量、计算过程和返回位置，这些组成栈帧，进入当前线程的 JVM 栈；每个线程还需要自己的程序计数器。对象实例与数组在共享堆中，局部变量保存的引用可以指向堆里的同一个对象，所以“局部变量在线程栈里”不代表引用对象也线程私有。

方法区是规范里的概念，保存类结构等运行时信息；HotSpot 在 JDK 8+ 主要用本地内存中的 Metaspace 保存类元数据。堆、元空间、直接内存、线程栈都会影响进程内存，容器限制也不会只计算 Java 堆。

把它放进一个例子

void submit() {
    Task task = new Task();
    queue.add(task);
}

submit 返回后栈帧消失，但 queue 仍引用 task，对象不会因为方法结束就回收。递归没有终止条件可能触发 StackOverflowError；队列不断积压任务可能导致 Java heap space；类加载器被长期引用可能导致元空间增长。

排查先辨认错误与增长区域，再结合 GC 日志、线程状态、堆对象和引用链。抓 heap dump 前要考虑暂停与文件大小，dump 也可能包含业务数据；不能把工具命令当成已经完成的诊断。

边界与反例：元空间仍可 OOM；静态字段相关对象也不能笼统说都住元空间。Eden/Survivor 比例、晋升年龄和大对象分配路径随收集器与配置变化，不是 JVM 统一规格。

停一下，自己推：把 -Xmx 设为容器内存上限，为什么仍可能被容器终止？

展开自测解析

堆之外还有元空间、线程栈、直接内存、代码缓存和其他本地开销，进程总量可能超限制。要为这些区域留空间并观察实际使用。

理解后，再这样简述：栈承载方法调用状态，堆承载共享对象，方法区承载类信息；先分清增长区域再诊断。

核对原文：JVM 规范：运行时数据区域。

基础必会 52. GC：对象没人要了，怎样回收才划算？

先看问题：回收器既要找出不再使用的对象，又要尽量减少对业务的打断。不同算法是在时间、额外空间与碎片之间取舍。

原理怎样推出来

GC 从栈上的引用、类静态引用、JNI 等根出发做可达性分析：能沿引用找到的对象要保留。两个对象互相引用，如果从根都到不了，仍可一起回收，所以循环引用本身不构成 Java 内存泄漏。

标记清除留下可用空洞，但可能碎片化；复制把存活对象搬到另一片空间，省掉逐个清理死对象的成本，却需要目标空间；整理把存活对象集中起来，减轻碎片但要付移动成本。年轻对象通常死得快，复制少量幸存者常划算，这就是分代思想的原因。

G1 把堆划成 Region，以疏散复制等机制回收选定区域；部分标记工作可并发，年轻代和混合回收仍有暂停。MaxGCPauseMillis 是规划目标，不是每次停顿的硬上限。CMS 适合了解老系统背景，已在 JDK 14 移除，现代选型要按实际 JDK 看。

把它放进一个例子

创建一万个临时对象，九千九百个已不可达：复制只需搬那一百个幸存者。反过来，若大部分对象长期存活，每次大量搬迁就昂贵。队列泄漏时对象一直从根可达，GC 无论多勤快都不能替应用删掉它们。

边界与反例：并发 GC 不等于零暂停，换收集器也修不好仍被引用的对象泄漏。先看分配率、回收后占用和停顿，再谈参数；暂停目标与吞吐、CPU、堆余量有取舍。

停一下，自己推：Full GC 后堆占用一周内持续上涨，直接增加 GC 次数能治好吗？

展开自测解析

若上涨来自仍可达的无用对象，不能。要检查主要对象类型与 GC Roots 引用链，找长期持有它们的缓存、集合、监听器或类加载器。

理解后，再这样简述：GC 先判断可达性，再按存活比例与暂停目标选择回收策略；理解算法成本比背收集器步骤更有用。

核对原文：Oracle：G1 回收模型与暂停目标；CMS 移除与历史优化变更。

进阶追问 53. 类加载与双亲委派：同名类为什么可能不是同一个类？

先看问题：两个插件都带了 com.example.Task，却希望互不干扰。JVM 除了类名，还需要知道是谁加载了这个类。

原理怎样推出来

加载取得类的字节表示；链接包括验证、准备和解析；初始化执行类初始化代码。准备与初始化要分开：普通静态字段先有默认值，再执行赋值和 static 块；常量变量有专门规则，解析也不必机械地理解成所有符号都在初始化前一次完成。

ClassLoader 的常见加载策略是先委托父加载器，父找不到再自己找。这样应用通常复用平台已有类，减少重复定义与类型冲突。“父”主要是委托关系，不是 Java 类继承关系。一个运行时类型的身份由二进制名与定义它的加载器共同决定。

把它放进一个例子

插件加载器 L1 与 L2 各自定义同名 Task，名字相同仍是两种类型，强制转换可能报 ClassCastException。插件隔离需要这样做，但跨边界交互的接口应由共享父加载器定义，否则接口本身也会分裂。

线程上下文类加载器让平台代码按约定发现应用提供的 SPI 实现；部分容器使用不同的委托顺序实现隔离。这些是加载策略调整，不是 JVM 的类型身份规则失效。

边界与反例：双亲委派是常见类加载策略，不能说任何 JVM 实现和自定义加载器都不可改变。JDK 8 的扩展加载器与 JDK 9+ 的平台加载器名称也有版本差异。

停一下，自己推：两个插件的 Task 都打印为同一个全限定名，能据此判断可以互相强转吗？

展开自测解析

不能。还要比较定义它们的类加载器和真实的类型继承关系；名字相同不足以确定运行时类型身份。

理解后，再这样简述：加载、链接、初始化负责不同工作；委托促进类复用，而类身份还包含定义加载器。

核对原文：JVM 规范：加载、链接与初始化。

9. 消息队列：交付、重复与顺序

项目使用消息队列时，要把确认、失败恢复与业务效果接起来。

项目常用 54. Kafka 与 RabbitMQ：先问要怎样消费数据

先看问题：监控事件想保存几天、随时重放；发邮件任务希望被一个消费者处理后确认完成。两者都异步，但消费语义不同。

原理怎样推出来

Kafka 的核心是分区追加日志，消费者用 offset 表示读到哪里；一个组的进度不等于另一个组的进度，消费也不直接删除消息，保留策略决定数据生命周期。因此它很适合多订阅者、历史重放与流处理。

RabbitMQ 的经典队列模型经 exchange 按规则把消息路由到队列，消费者确认后消息可从队列移除，适合围绕任务交付、路由和确认组织业务。RabbitMQ 也有 stream 等能力，所以不是“永远不能重放”的绝对二分。

把它放进一个例子

同一份设备事件要被统计、告警、审计三个系统独立回放，可以考虑 Kafka 的不同消费者组。一个异步通知要按类型路由给对应工作队列，可以考虑 RabbitMQ exchange 与队列。最终还要比较团队已有运维、顺序范围、可靠性、延迟和容量要求。

边界与反例：“Kafka 百万、RabbitMQ 万级”没有消息大小、复制、确认、硬件和批量条件就没有比较意义。TTL+死信的经典延迟方案还可能受队头等行为影响，不能直接称为精确任意延迟调度器。

停一下，自己推：Kafka 同一个组里 10 个消费者，某 topic 只有 3 个分区，能都同时分担这 3 个分区的消费吗？

展开自测解析

在经典消费者组分区分配模型下，最多 3 个消费者各持有分区，其余没有该 topic 分区可处理。提高并行度需考虑分区数，同时评估键内顺序与运维成本。

理解后，再这样简述：先比较日志重放与队列交付的消费模型，再结合路由、顺序、延迟和已有运维选型。

核对原文：Kafka：日志、分区与消费设计。

项目常用 55. 消息不丢：要跨过哪几个崩溃窗口？

先看问题：订单数据库提交成功，服务还没把事件发出去就崩溃；或者消费者先确认消息，再写数据库时崩溃。这两头都可能丢业务。

原理怎样推出来

第一段是业务提交到生产发送。本地消息表（outbox）把业务记录和待发送事件写在同一个数据库事务里；后台发送成功再标记，超时可重试。这样进程即使崩溃，也有待办记录可恢复。

第二段是 Broker 接收与保存。RabbitMQ publisher confirm 表明 Broker 按相应队列规则接纳了发布，不代表消费者已经处理；未路由消息还要按 mandatory/returns 等机制检查。持久消息与持久队列不能代替发布确认和副本策略。

第三段是消费处理与确认。先提交业务，再 ack 或提交消费进度；若提交后确认前崩溃，下次会重复，所以可靠交付必须与幂等一起设计。Kafka 可结合 acks=all、min.insync.replicas 与合理副本数，但它们保护的范围仍不包含任意外部业务副作用。

把它放进一个例子

DB 事务：写订单 + 写 outbox → COMMIT
发送器：读 outbox → 发布 → 等确认 → 标记发送成功
消费者：执行幂等业务 → COMMIT → ack / 提交 offset

发送器得到超时，不知道消息是否已接收，因此要重试且允许重复。失败后的补偿需要记录、可控退避、告警和处理入口，不能无限 requeue 形成忙循环。

边界与反例：“保证不丢”必须说明故障范围、保存期限与恢复机制；超期删除、磁盘损坏或错误人工操作不由一句确认配置解决。不要混用 RabbitMQ ack 与 Kafka offset 的具体 API。

停一下，自己推：生产端收到 confirm 后，可以断言邮件已经发给用户了吗？

展开自测解析

不能。它说明的是 Broker 发布接纳，邮件任务还可能等待消费或处理失败。业务完成要由消费结果或业务状态确认。

理解后，再这样简述：按业务提交、Broker 接纳、消费完成三段逐个封闭崩溃窗口，并接受重试会带来重复。

核对原文：RabbitMQ：发布确认与消费确认的范围。

项目常用 56. 幂等：去重记录和业务执行为什么要一起看？

先看问题：你先用 Redis SETNX 记下“处理过”，随后扣款前崩溃。重试看到记录直接跳过，结果钱没扣，但消息也没再处理。

原理怎样推出来

幂等要求同一个业务操作重复到达，最终业务效果仍像执行一次。需要稳定的业务幂等键，而不是每次重试重新生成一个 id。去重记录只记录“见过”，不能单独证明“完成”。

数据库内业务可把幂等记录与业务修改放在同一事务：插入唯一的事件键，执行修改，一起提交。首次执行失败则一起回滚；重试可再执行。若首次已提交，唯一约束会识别同一事件。冲突后的事务如何结束要遵循数据库与框架规则，别 catch 后继续在失效事务里写。

把它放进一个例子

BEGIN
INSERT INTO processed_event(event_id) VALUES (稳定事件键); -- 唯一约束
UPDATE account SET balance = balance - 100 WHERE id = 7;
COMMIT
-- 外部确认在提交成功后

这是数据库内效果的示意，余额校验等业务规则仍要执行。设备下发、支付网关等外部副作用无法被此事务自动回滚，应把同一幂等键传给支持幂等的下游，或使用可恢复状态机和结果查询。

边界与反例：终态保护适合拒绝不合法的重复状态流转，不自动等于所有外部动作只发生一次。Redis 去重还要分析 TTL、持久性、重启与业务事务间的窗口；Kafka 的 exactly-once 能力也有处理范围。

停一下，自己推：改成先扣款再 SETNX，就能解决上面的崩溃问题吗？

展开自测解析

不能。扣款后记录前崩溃，重试又会扣一次。两个动作的顺序都留下窗口，关键是把相关效果置于一个原子边界或让下游接受同一个幂等键。

理解后，再这样简述：幂等围绕稳定业务键与效果原子性设计；登记、处理中、完成以及失败恢复必须分清。

项目常用 57. 顺序、重试与死信：为什么失败消息不能无限重回队列？

先看问题：一条设备“启动”消息失败被重试，后面的“停止”已经成功，最后迟到的启动又执行了。可靠投递与业务顺序必须一起分析。

原理怎样推出来

消息系统的顺序保证通常有范围：Kafka 经典消费模型主要围绕分区顺序；RabbitMQ 队列交付顺序与多消费者、并发处理、重入队等组合后，完成顺序也会改变。需要同一设备状态有序时，应按业务键组织串行处理或让版本/状态机拒绝过时事件。

重试应区分临时网络故障和永久参数/权限错误，有限次并退避。死信承接按规则失败或过期等消息，是隔离和恢复入口，不是“放进去就解决”。需要告警、原因与可追踪的重放流程，重放仍须幂等。

把它放进一个例子

临时故障 → 有界重试与退避
多次失败/不可恢复 → 失败记录或死信 → 告警与处理
再次重放 → 使用相同业务键，校验状态/版本

TTL+死信的延迟方案要检查具体队列过期行为；同一键严格顺序与延迟重试的取舍必须明确，不能只背一个“按 key 分区”。

边界与反例：重试可能导致后续消息越过失败消息，多个消费线程也可能乱序完成。把所有失败立即 requeue 会形成热循环，挤占健康消息与服务容量。

停一下，自己推：把同设备消息放同一分区，消费者再交给线程池并发处理，就能保证完成顺序吗？

展开自测解析

不能。读取有序不代表并发业务完成有序；需串行化该键处理，或用版本/状态协议约束最终效果。

理解后，再这样简述：顺序按业务键与处理完成定义，重试要有界可观测，死信要接上恢复与幂等。

核对原文：RabbitMQ：死信机制；Kafka：消费与顺序模型。

进阶追问 58. Kafka 为什么快：批量到底省了什么？

先看问题：一条 100 字节事件单独发一次，每次都要付协议、系统调用和网络往返成本。把很多事件打包，单位事件成本就能下降。

原理怎样推出来

分区日志追加写使数据布局更顺序，操作系统 page cache 帮助吸收和复用 I/O。批量发送把许多小事件摊在一次请求里；压缩减少网络与存储字节，代价是 CPU。分区则把写入和读取工作分散到多个执行单元。

合适的明文传输路径可利用 sendfile 等减少用户态数据复制与上下文切换，常称零拷贝；不是整个机器没有任何复制。TLS 加密等路径可能改变这一优化，实际性能仍由磁盘、网络、复制与消费者处理能力共同限制。

把它放进一个例子

把 1,000 条小事件分别发送，与打成几个 batch，后者付的请求固定成本更少。等待攒批会增加少量延迟，linger.ms 与 batch.size 是吞吐和延迟的取舍；不能只增大批次而不看尾延迟。

边界与反例：顺序写也不意味着消息已立即持久到介质，page cache 与磁盘持久性要区分。更多分区可能提高并行度，也会增加资源、协调和顺序管理成本。

停一下，自己推：生产端攒批更大，端到端延迟会一定下降吗？

展开自测解析

不一定。吞吐可能提高，但低流量时等批次的时间反而增加；消费端排队与业务处理时间也可能主导总延迟。

理解后，再这样简述：Kafka 用顺序日志、缓存、批量压缩和分区并行降低单位消息成本，同时在吞吐与延迟间取舍。

核对原文：Kafka：批量与高效数据传输。

10. HTTP / 工程：协议、安全与服务治理

HTTP 与资源授权属于基础；微服务和部署细节按岗位与项目深入。

基础必会 59. HTTP、状态码与接口幂等：超时到底代表什么？

先看问题：POST 创建任务超时，用户点了重试，后台出现两条任务。HTTP 没给你拿到响应，并不说明服务端没执行。

原理怎样推出来

HTTP 描述方法、状态码、头与正文等语义。GET 表达读取且应保持安全语义；PUT、DELETE 等方法有协议层的幂等语义，重复请求的预期效果与一次相同，不代表每次响应必须相同。POST 通常不自带这样的业务去重承诺。

状态码区分请求解析与权限、资源、业务/服务故障等结果，具体映射要保持接口一致。超时是调用方未及时取得结果；处理可能已提交，因此创建、支付或设备命令需稳定幂等键与结果查询，而不是无条件重新生成操作。

把它放进一个例子

创建任务时客户端保留同一请求键，服务端用唯一约束/状态记录识别重试并返回既有结果。查询不存在可用 404，未认证与无权限应分清，过量请求可按接口约定使用 429 并明确重试策略。

边界与反例：幂等不意味着授权可省，也不意味着所有 POST 都不允许实现幂等。盲目把失败统一成 200 加一个字符串，会让客户端与监控更难可靠判断结果。

停一下，自己推：第一次 DELETE 返回成功，第二次资源已不存在，响应不同是否必然违反幂等？

展开自测解析

不必然。幂等关注预期效果：资源保持不存在；响应可反映不同的当前状态。具体 API 仍要定义一致的契约。

理解后，再这样简述：方法和状态码表达协议契约，超时需要业务结果确认，重试依赖幂等与明确错误语义。

核对原文：RFC 9110：HTTP 语义。

基础必会 60. 身份、权限与输入校验：知道你是谁，就允许访问所有 id 吗？

先看问题：登录用户把 URL 里的任务 id 换成别人的，参数格式仍合法。如果只做登录检查，就可能跨用户或租户读到数据。

原理怎样推出来

认证确认身份，授权判断该身份能否对该资源做该动作，校验判断输入格式、范围与业务前置条件。三者互补：有效 token 不说明能访问任意设备，正整数 id 不说明资源归当前租户。

服务端从可信身份上下文推导用户/租户，再在查询或业务检查中限制资源范围，不把请求体的 userId 当作身份事实。SQL 值参数绑定、动态字段白名单、日志脱敏与错误信息限制都是信任边界的具体工作。

把它放进一个例子

SELECT ... FROM task
WHERE id = ? AND tenant_id = ?;
-- tenant_id 来自已验证身份及服务端授权上下文

还要验证该用户在租户内有对应动作权限。缓存键和异步事件也应携带正确隔离维度，不能缓存 A 的结果后给 B 复用。

边界与反例：此处只覆盖后端基础边界，不等于完整安全方案。会话/token 保存与撤销、浏览器 CSRF/CORS、密码存储等要按认证架构继续设计。

停一下，自己推：前端隐藏“删除”按钮，后端还需要权限检查吗？

展开自测解析

需要。用户可绕过界面直接构造请求，服务端必须独立执行动作与资源授权。

理解后，再这样简述：身份、资源权限与输入合法性分开验证，数据查询和缓存都保持隔离范围。

核对原文：Spring Security：授权架构。

基础必会 61. TCP 三次握手与关闭：在确认什么？

先看问题：网络里可能有延迟、丢包和旧报文。建立连接要协商双方初始序列号并确认新的连接，关闭还要处理两个独立方向的数据。

原理怎样推出来

客户端 SYN 带自己的初始序列号；服务端 SYN+ACK 带服务端序列号并确认客户端；客户端 ACK 确认服务端序列号。这样双方都能确认对端已收到自己的建连信息，减少把旧 SYN 当成完整新连接的风险。

TCP 是全双工，一端发送 FIN 表示自己不再发送，不代表对方也没数据了。对方可先确认，再发送剩余数据，最后自己发 FIN。因此常见关闭过程有四步；ACK 和 FIN 也可能合并，不能断言每次必有四个独立报文。

把它放进一个例子

建立：C SYN(x) → S SYN(y), ACK(x+1) → C ACK(y+1)
关闭：A FIN → B ACK → B FIN → A ACK
                       ↑ B 可以在发 FIN 前继续发送数据

TIME_WAIT 帮助处理最后确认丢失后的 FIN 重传，并让旧连接报文有时间消退；它并不直接证明服务器代码泄漏。CLOSE_WAIT 表示已收到对端 FIN、本地还没完成关闭，大量长期滞留时应查应用是否忘记关闭或卡在处理流程中。

边界与反例：TCP 提供有序字节流，没有业务消息边界；一次 write 不对应一次 read。SSE 是 HTTP 事件流格式，其重连和业务事件恢复仍需上层设计，不能都归因于 TCP 保证。

停一下，自己推：对方已发 FIN，本端还能继续发送待发数据吗？

展开自测解析

可以，只要本端发送方向仍未关闭。FIN 关闭一个方向的发送，体现半关闭语义；最终双方都完成关闭才结束连接。

理解后，再这样简述：握手同步序列号与连接状态，关闭分别结束两个方向；连接状态用于定位问题，但不直接替代业务诊断。

核对原文：RFC 9293：TCP 连接与关闭。

基础必会 62. HTTPS：怎样知道对方是谁，又怎样保密？

先看问题：只把数据加密给某个公钥还不够：如果这个公钥来自攻击者，你保密地把密码送给了错误的人。身份认证和加密要同时解决。

原理怎样推出来

常见 HTTPS 以 TLS 在连接上建立安全通道。客户端验证服务端证书链、目标域名与有效期等，确认公钥属于预期身份；密钥协商使双方建立会话秘密；之后使用对称认证加密保护应用数据的机密性与完整性。

常见 TLS 1.3 完整握手中，ClientHello 与 ServerHello 带临时密钥交换参数，双方通常用 (EC)DHE 形成共享秘密；服务端通过证书相关签名认证，Finished 验证握手。证书公钥主要参与认证，不是“永远把预主密钥用 RSA 公钥加密发送”。后者是旧版 TLS 的一种握手方式。

把它放进一个例子

客户端：我支持这些算法，附临时密钥份额
服务端：选择算法，附临时份额、证书与身份认证
双方：导出密钥，验证握手
后续：用对称认证加密传应用数据

临时密钥交换可提供前向保密：以后服务器长期私钥泄露，不应直接解密过去已录制的会话；前提是采用相应协议且临时秘密未泄露。

边界与反例：TLS 1.2、1.3、会话恢复与 PSK 模式流程不同；HTTP/3 还以 QUIC 承载，不是所有 HTTPS 都先走普通 TCP。TLS 保护传输，不能修复 SQL 注入、越权或业务端点泄露。

停一下，自己推：为了测试方便关闭证书验证，只保留加密，还能防止中间人读取密码吗？

展开自测解析

不能可靠防止。攻击者可分别与两端建立加密连接，冒充服务器；加密到谁必须靠身份验证确认。

理解后，再这样简述：HTTPS 同时需要身份认证、密钥建立和数据保护；讲流程要声明 TLS 版本及握手类型。

核对原文：RFC 8446：TLS 1.3。

项目常用 63. 微服务组件：一次请求分别由谁保护？

先看问题：订单服务地址会变化，下游可能变慢，入口也可能突然被大量请求打满。注册中心、网关、限流与熔断处理的是不同故障。

原理怎样推出来

服务发现维护“服务名对应哪些可用实例”，调用方据此选址；配置中心管理可动态分发的参数。网关集中处理入口路由与过滤，不能代替下游自己的容量保护。

限流限制某段时间内允许进入的工作量，防止过载；熔断在依赖持续失败或过慢时暂时停止尝试，避免请求耗尽线程，再经过探测恢复。超时限制单次等待，舱壁隔离避免一个依赖占光所有资源，几种机制可以配合。

把它放进一个例子

设备服务变慢：订单服务的独立调用池限制并发，超时释放等待，熔断减少继续访问。入口限流则防止订单服务本身被过量请求压垮。Nacos 可承担发现和配置，Gateway 承担路由，具体容错框架要看项目实际选型。

边界与反例：不要用一句“AP/CP”概括整个组件的所有接口与版本。重试会放大流量，非幂等请求更不能无条件重试；降级返回旧数据也须满足业务语义。

停一下，自己推：下游已经处理了扣款，但返回超时，自动再重试一次有什么风险？

展开自测解析

可能重复扣款。超时表示未拿到结果，不等于业务未执行。需要稳定幂等键、结果查询或可恢复状态协议。

理解后，再这样简述：发现解决找谁，网关解决入口，超时与隔离控制等待，限流与熔断控制过载和故障传播。

进阶追问 64. Pod、Deployment、Service：谁重建，谁接流量？

先看问题：Pod 重新创建后 IP 可能变化。调用方既需要稳定访问入口，也需要后台有人持续把副本恢复到期望数量。

原理怎样推出来

Pod 是一起调度的容器组，容器共享该 Pod 的网络空间，并可使用配置的卷；它承载一次运行实例。Deployment 通过 ReplicaSet 等控制器维护期望副本并组织滚动更新，不是直接给调用方提供固定 IP。

Service 依据选择器等方式关联后端端点，常以稳定名称和 ClusterIP 提供访问入口；后端 Pod 可以变化。readiness 表达实例是否适合接业务流量，liveness 表达是否需要重启容器，startup 给慢启动应用额外启动时间。

把它放进一个例子

发布三个副本的新版本，Deployment 按 maxSurge 与 maxUnavailable 限制新旧副本切换。新 Pod 已 Running 却未 Ready，通常不会作为普通 Service 的可用后端。旧 Pod 终止时还要处理摘流量传播、优雅退出与进行中的请求。

边界与反例：不是所有 Service 都有 ClusterIP，比如 headless Service；未配置 selector 的 Service 也不同。探针不能替代真实业务可用性设计，多副本也不自动解决数据库迁移兼容问题。

停一下，自己推：把数据库暂时断开定义为 liveness 失败，会有什么问题？

展开自测解析

可能让所有实例反复重启，加剧故障。依赖不可用是否影响 readiness、是否需要重启，必须分别判断；进程还活着不等于它能服务，反之暂时不能服务也不一定该重启。

理解后，再这样简述：Pod 承载实例，Deployment 维护副本和发布，Service 提供稳定入口，探针负责不同的健康语义。

核对原文：Kubernetes：Service 与后端端点。

11. 线上排障：从现象找到真正消耗与等待

使用证据排查 CPU、内存与接口延迟，再验证修复。

CPU 低却超时要找等待，GC 后存活持续涨要找持有者；不同现象走不同证据路径。

项目常用 65. CPU 高：先看哪条线程在做什么？

先看问题：进程 CPU 接近满核，可能是业务计算、死循环、锁自旋或频繁 GC。直接改线程池参数无法回答原因。

原理怎样推出来

先核对是哪个进程、多少核、持续多长、哪个业务时段，再找热点线程与线程栈。Linux 上可按进程观察线程 CPU，必要时把系统线程 id 转为与 dump 匹配的表示，再在多份线程 dump 中定位热点栈；也可使用可控的 JFR/采样剖析。

持续同一业务栈可能是大循环或重计算；GC 线程繁忙要结合分配率和 GC 日志；RUNNABLE 也可能正在 native I/O，不应只按一个状态判断忙算。多次采样比偶然一份堆栈更可靠。

把它放进一个例子

top -H -p PID                 # Linux：找热点线程
jcmd PID Thread.print -l      # 结合线程与锁信息
# 再对照业务请求、GC 日志和多次采样

CPU 200% 在某些工具中表示约两核用量，并非“超过机器极限”。容器 CPU 限额与 throttling 也可能让服务变慢，应同时看宿主和配额。

边界与反例：上述 top 是 Linux 场景；Windows 需相应进程/线程监控工具。诊断命令要有权限，采样与 dump 都有开销，先控制时长、文件量与敏感数据暴露。

停一下，自己推：CPU 很低却接口大量超时，还应主要找计算热点吗？

展开自测解析

不应只找 CPU 热点。可能在连接池、网络、锁或队列等待，应沿请求耗时定位阻塞资源。

理解后，再这样简述：关联进程、线程、堆栈、GC 与请求负载，先定位消耗路径再改算法或容量。

核对原文：JDK：jcmd 诊断。

项目常用 66. 内存涨与频繁 GC：先分清“分配多”还是“留住多”

先看问题：堆呈锯齿上升后回落，可能是正常分配回收；每次 GC 后的底线持续上涨，则可能有存活对象积累。两者不应同样处理。

原理怎样推出来

先看进程总内存、堆、元空间、直接内存与线程数，确认哪个区域增长。结合 GC 日志看分配速度、暂停、回收后存活占用；大量短命对象可能使年轻代频繁回收，长期无用对象被集合持有则会抬高存活基线。

堆直方图帮助找主要对象类型；heap dump 与引用链帮助回答是谁持有它们。缓存无限增长、积压任务、未释放监听器或 ThreadLocal 绑定都是候选原因，必须用证据确认，而不是看到某类多就宣布泄漏。

把它放进一个例子

现象 A：每轮 GC 后回到相近占用 → 先查分配与回收成本
现象 B：GC 后基线持续涨 → 查长期持有者和业务积压
现象 C：堆不大，RSS 很高 → 查堆外、线程与其他本地内存

若队列积压来自下游慢，清对象只治表面，还要解决接纳速率、超时、失败恢复与容量。

边界与反例：heap dump 可能暂停并生成大文件，内容可能含凭证与业务数据；先评估空间与影响。别每次高占用都手动 Full GC，收集器不能回收仍被引用的对象。

停一下，自己推：增加 Xmx 后故障从每天变成每周，是不是证明泄漏已解决？

展开自测解析

没有。只是可能延后达到上限；仍需比较存活基线与引用链，确认积累来源是否消失。

理解后，再这样简述：按区域、分配率、回收后存活量和引用持有者排查，再验证修复是否阻断持续积累。

核对原文：JDK：诊断与堆观察；Oracle：G1 观察与模型。

项目常用 67. 接口慢：沿一条请求拆掉等待，而不是见慢就加缓存

先看问题：接口 2 秒，SQL 只用了 20ms。剩余时间可能在排队、连接获取、锁、远程调用或响应传输，优化 SQL 不能覆盖全部。

原理怎样推出来

先用请求关联 id/trace 与分段指标把耗时拆开：入口排队、线程池、连接池、DB 执行与锁等待、外部服务、序列化和传输。看 p50/p95/p99 与错误率、并发和吞吐，平均 100ms 不表示尾部用户都快。

定位最慢段后，区分单次服务时间变长和排队增多。下游连接池已满时，增加上游工作线程可能只制造更多等待；超时应形成总请求预算，而不是每一层各等几秒后叠加成几十秒。

把它放进一个例子

总计 2000ms
连接池获取 1500ms + SQL 20ms + 远程 350ms + 其他 130ms
优先追问：连接被谁持有？事务多长？下游容量与并发匹配吗？

验证修改前后使用相似数据、负载与请求类型，对照分段耗时、扫描量、排队和错误，而不是只看一次成功请求。

边界与反例：诊断采样和日志也有开销，限制高频大字段记录。重试、扩大线程池与延长超时都可能放大故障，先明确瓶颈和失败恢复。

停一下，自己推：线程池排队多，直接扩大到十倍，为什么可能让 DB 更慢？

展开自测解析

若 DB 已达容量，大量额外并发增加连接竞争、锁等待和资源切换，总吞吐未必上升，尾延迟可能更差。

理解后，再这样简述：按真实请求拆耗时与容量，优化最慢环节并以相似条件验证整体结果。

核对原文：OpenTelemetry：分布式 traces。
