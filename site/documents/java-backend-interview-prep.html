2. MySQL（P0）

索引、事务、锁、慢 SQL——小厂必问，往深挖三层的部分。

P0 1. 为什么用 B+ 树做索引，而不是 B 树、哈希或二叉树？

  • 对比二叉 / 红黑树：数据量大时树太高，而树高就等于磁盘 IO 次数，B+ 树矮胖（3 层可撑约 2000 万行）。
  • 对比哈希：哈希等值查询 O(1) 很快，但不支持范围查询、排序和最左前缀匹配。
  • 对比 B 树：B 树的非叶子节点也要存整行数据，InnoDB 一页 16KB 能放的键就少、扇出小、树更高；且范围查询需要中序遍历回溯。
  • B+ 树两个关键设计：非叶子节点只存键不存数据，单页能放约 1170 个键（bigint 8B + 页指针 6B），树更矮；叶子节点存全部数据且用双向链表串联，范围查询和排序只需顺序扫描。

P0 2. 联合索引的最左匹配原则？

  • 索引 (a,b,c) 的排序规则：先按 a 排，a 相同按 b，b 相同按 c——像字典先按首字母再按次字母。
  • 能走索引：where a=?、a=? and b=?、a=? and b=? and c=?（条件顺序无所谓，优化器会重排）。
  • 不能走：where b=? 或 b=? and c=?——缺了 a，b 在整个索引里是无序的，无法定位。
  • 范围之后失效：where a>? and b=? 只有 a 列走索引，因为 a 是范围匹配后，结果集里 b 不再有序（MySQL 5.6+ 的索引条件下推 ICP 能部分缓解）。
  • order by 同样遵循最左连续：where a=? order by b,c 可以免掉 filesort。

P0 3. 什么是回表、覆盖索引？

  • 聚簇 vs 二级索引：主键索引（聚簇）叶子节点存整行数据；二级索引叶子节点只存索引列 + 主键值。
  • 回表：select * where name=? 走 name 索引拿到主键后，还要回聚簇索引再查一次整行——多一次树查找。
  • 覆盖索引：查询的列和条件列全部包含在二级索引里，不需要回表；explain 的 Extra 显示 Using index。
  • 实践：高频查询建联合索引做覆盖；少写 select *，只取需要的列。

挂靠项目：「调度任务列表查询（机库 + 任务状态 + 时间）就是这么建联合索引的，状态和时间放在机库 ID 后面，列表页不回表。」

P0 4. 事务隔离级别和 MVCC？

  • 三个并发问题：脏读（读到未提交数据）、不可重复读（同事务两次读同一行结果不同，针对 update）、幻读（两次读行数不同，针对 insert/delete）。
  • 四个级别：读未提交 → 读已提交 RC（解决脏读）→ 可重复读 RR（InnoDB 默认，解决不可重复读）→ 串行化。
  • MVCC 三要素：行记录隐藏字段（trx_id 最近修改事务、roll_pointer 指向旧版本）；undo log 版本链；ReadView（活跃事务列表）。
  • 可见性判断：版本的事务 id 小于 ReadView 里最小活跃事务 id → 可见；大于最大已分配 id 或仍在活跃列表里 → 不可见，沿版本链往回找。
  • RC 与 RR 的区别就在 ReadView 的生成时机：RC 每次 select 都新建（所以能看到别人新提交的，造成不可重复读）；RR 只在事务第一次 select 时生成并复用 → 可重复读。RR 下的幻读靠 next-key lock（当前读）基本解决。

P0 5. 行锁、间隙锁、临键锁？

  • Record Lock（记录锁）：锁住单条索引记录。
  • Gap Lock（间隙锁）：锁住两条记录之间的开区间，阻止其他事务在区间内插入——RR 级别解决幻读的手段，RC 级别没有。
  • Next-Key Lock（临键锁）：记录锁 + 间隙锁，左开右闭区间，是 RR 下当前读的默认加锁单位；唯一索引等值命中已存在记录时可退化为纯记录锁。
  • 重点（生产事故来源）：InnoDB 的行锁加在索引上。update 没走索引会全表扫描，把所有记录都锁上，近似锁全表——所以更新条件必须命中索引。
  • 意向锁（IS/IX）是表级锁，只用来快速判断表内是否存在行锁，不和行锁冲突。

P0 6. 一条慢 SQL 怎么优化？

  • 定位：慢查询日志（slow_query_log、long_query_time）找到嫌疑 SQL。
  • 分析：explain 四看——type（至少到 range，ALL 全表扫要处理）、key（是否命中索引）、rows（扫描行数）、Extra（出现 Using filesort / Using temporary 要警惕，Using index 是覆盖索引，好）。
  • 索引层：按查询建联合索引并遵循最左匹配；覆盖索引免回表；索引列上避免函数、运算、隐式类型转换（字符串列传了数字）。
  • SQL 层：深分页改游标 where id>? limit n 或延迟关联（先查 id 再回表）；只查需要的列；小表驱动大表。
  • 架构层：读写分离、冷热分离、加缓存、异构到 ES、大事务拆小。

挂靠项目：按「先说定位手段，再说一个自己优化过的例子」的结构答，任何一条列表查询加索引的经历都可以展开讲。

3. Redis（P0）

缓存三件套、一致性、分布式锁——每题都能挂到项目上。

P0 7. 缓存穿透、击穿、雪崩？

  • 穿透（查不存在的数据）：请求的 key 在缓存和数据库都不存在，每次都打到 DB（典型是恶意伪造 id）。对策：缓存空值（短 TTL）、布隆过滤器前置拦截、接口层参数校验和限流。
  • 击穿（单个热点过期）：某个热 key 过期瞬间，大量并发同时回源。对策：互斥锁重建（setnx 保证一个线程查库、其他等待或返回旧值）；逻辑过期（不设物理 TTL，值里存过期时间，过期后异步重建）；核心热点直接不设过期 + 后台更新。
  • 雪崩（大面积失效）：大量 key 同时过期，或 Redis 整体宕机。对策：TTL 加随机值打散；哨兵 / 集群保证高可用；多级缓存；限流降级兜底。
  • 记忆口诀：穿透是「不存在」，击穿是「单个热点」，雪崩是「大面积」。

P0 8. 缓存一致性：先更新数据库还是先删缓存？

  • 主流方案 Cache Aside：读——先读缓存，miss 则查库并回填；写——先更新数据库，再删除缓存。
  • 为什么是删不是更新：并发双写时更新缓存容易乱序覆盖产生脏数据；删除是幂等的，下次读自动回源。
  • 为什么先库后缓存：先删缓存的话，「删除后-更新前」窗口期有读请求会把旧值回填。可以延迟双删缓解：先删、更新库、延迟几百毫秒再删一次。
  • 极小概率的不一致仍有：读请求恰好在更新前查库、在删除后回填。要求强一致就上分布式锁串行化，或 canal 订阅 binlog 异步删缓存，日常用 TTL 兜底即可。

P0 9. 分布式锁：SETNX 和 Redisson 的区别？

  • 裸 SETNX 的坑：setnx 和 expire 两条命令不原子（setnx 后宕机 → 永久死锁），要用 set key value nx ex 一条命令解决。
  • 剩下的坑：业务执行超过锁过期时间，锁失效后被别的线程拿到，自己释放时删掉了别人的锁 → 锁的 value 存线程唯一标识，释放前用 Lua 脚本校验再删。
  • Redisson 帮你做好了：加锁用 Lua（hash 结构，天然可重入）；看门狗机制——默认锁 30 秒，后台每 10 秒检查业务没执行完就自动续期；主从切换丢锁问题对应的 RedLock 方案争议大，多数场景不用。

挂靠项目（重点题，背熟）：「机库调度里我用 Redisson 做调度锁，但没有只依赖它——Redis 锁挡住大部分并发，真正保证不重复分配的是数据库条件更新（update ... where status='待分配'，影响行数为 0 就说明被别人抢了）。Redis 是性能优化，DB 约束才是正确性兜底，锁粒度收到单个机库避免互相阻塞。」

P0 10. RDB 和 AOF？

  • RDB：某时刻的全量快照。bgsave fork 子进程基于写时复制生成；文件小、恢复快；丢两次快照之间的数据（分钟级）。
  • AOF：追加记录每条写命令。appendfsync 三档：always 最安全最慢、everysec 默认（最多丢 1 秒）、no 交给系统。文件大、恢复慢；AOF 重写用当前状态生成最小命令集来压缩体积。
  • 4.0+ 混合持久化：重写时 RDB 全量做头 + 后续 AOF 增量，恢复快、丢失少，推荐开启。
  • 选型：纯缓存场景可以只 RDB 甚至不持久化；不允许丢数据的用 everysec 或混合。

P0 11. Redis 为什么快？

  • 纯内存操作：内存访问是纳秒-微秒级，磁盘是毫秒级，差几个数量级。
  • 高效数据结构：SDS（O(1) 取长度、二进制安全、空间预分配）、跳表（zset，O(logN) 且范围查询友好）、listpack、小整数集合 intset。
  • 单线程执行命令：无锁竞争、无线程上下文切换，实现还简单。
  • IO 多路复用（epoll）：单线程也能监听海量连接（Reactor 模型）。
  • 6.0 的 IO 多线程：只是读写 socket 和协议解析用了多线程，命令执行仍是单线程——不改线程模型，保持兼容。

4. 并发（P0）

线程池是必考之王，流程要能画出来。

P0 12. 线程池七大参数和执行流程？

  • 七参数：corePoolSize 核心线程数、maximumPoolSize 最大线程数、keepAliveTime + unit 非核心线程空闲回收时间、workQueue 任务队列、threadFactory 线程工厂、handler 拒绝策略。
  • 执行流程（对照上图）：核心线程未满 → 创建核心线程；满了 → 入队；队列满 → 创建非核心线程（直到 max）；达到 max → 执行拒绝策略。注意「先入队再开非核心」，很多人答反。
  • 四种拒绝策略：AbortPolicy（默认，抛异常）；CallerRunsPolicy（提交线程自己执行，天然反压限流）；DiscardPolicy（静默丢弃）；DiscardOldestPolicy（丢队头最老的）。
  • 参数怎么配：CPU 密集型 N+1；IO 密集型 2N，或按 QPS × 平均耗时（秒）估算；队列必须有界，防 OOM。
  • 为什么不用 Executors 快捷方法：FixedThreadPool / SingleThreadExecutor 用无界队列会堆积 OOM；CachedThreadPool 最大线程数是 Integer.MAX_VALUE。手动 new ThreadPoolExecutor。

P0 13. synchronized 和 volatile 的区别？

  • 从三性看：原子性、可见性、有序性。
  • synchronized：三者都保证（互斥 → 原子；解锁前刷回主内存 → 可见；监视器锁 happens-before → 有序）。JDK 1.6 后有锁升级：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁，只能升不能降。
  • volatile：只保证可见性（写后立即刷主内存，其他 CPU 缓存行失效）和有序性（内存屏障禁止指令重排），不保证原子性——i++ 是读-改-写三步，volatile 挡不住并发覆盖。
  • volatile 典型场景：状态标志位（while(!stop)）；双检锁单例的实例字段（防止对象初始化指令重排，别的线程拿到半初始化对象）。

P0 14. ConcurrentHashMap 怎么保证线程安全？

  • 1.8 的方案：Node 数组 + 链表 + 红黑树；空桶用 CAS 插入，非空桶 synchronized 只锁该桶的头节点——锁粒度细到一个桶。
  • 树化条件：链表长度 ≥ 8 且数组长度 ≥ 64（否则先扩容）；退化阈值 6。
  • 扩容：支持多线程协助迁移，每个线程认领一段桶（stride）。
  • size()：baseCount + CounterCell 分散计数（LongAdder 思想），结果是近似值。
  • 对比：1.7 是 Segment 分段锁（并发度 = 段数）；HashTable 是全表一把锁。key 和 value 都不许 null——并发下 get 返回 null 有「不存在」和「值就是 null」的二义性。

5. JVM（P0）

内存区域、GC、类加载——答不出排查思路就说工具链。

P0 15. JVM 运行时内存区域？

  • 线程私有：程序计数器（记录字节码行号，唯一不会 OOM 的区域）；虚拟机栈（每个方法一个栈帧：局部变量表 / 操作数栈 / 动态链接 / 返回地址；递归过深 StackOverflowError，-Xss 调整）；本地方法栈（native 方法用）。
  • 线程共享：堆（新生代 Eden : S0 : S1 = 8:1:1 + 老年代）；方法区（类元信息、运行时常量池、静态变量；1.8 起由永久代改为元空间 Metaspace，使用本地内存，不容易再 OOM）。
  • 对象分配路径：优先在 Eden 的 TLAB（线程私有分配缓冲，避免并发竞争指针）分配；大对象直接进老年代；Minor GC 后年龄默认到 15 晋升老年代（还有动态年龄判定）。
  • 加分项——排查工具链：CPU 高 / 内存涨 / 卡顿三类问题，用 jstat -gcutil 看 GC 频率、jmap dump 堆、jstack 看线程栈，线上用 arthas。没实操过就说「我知道的排查路径是……」。

P0 16. GC 算法和垃圾收集器？

  • 对象判定：可达性分析——从 GC Roots（栈上引用、静态变量、常量、JNI 引用、活跃线程）出发不可达即垃圾。引用计数法有循环引用问题，JVM 不用。
  • 三大算法：标记-清除（简单但有碎片）；标记-复制（新生代用它，Eden + 两块 Survivor 轮流倒腾，空间换时间）；标记-整理（老年代用，移动对象消灭碎片，停顿更久）。
  • CMS：并发标记清除。初始标记（STW 短）→ 并发标记 → 重新标记（STW）→ 并发清除。低停顿但有浮动垃圾、内存碎片，并发失败会退化为 Serial Old 单线程整理。
  • G1（JDK 9 起默认）：堆切成等大的 Region，Eden / Survivor / Old 不再物理连续；整体上是标记-整理、Region 之间是复制，无碎片；可以设 -XX:MaxGCPauseMillis 停顿目标，按收益优先回收垃圾最多的 Region；大对象用专门的 Humongous Region。
  • ZGC：着色指针 + 读屏障，停顿亚毫秒级——说得出名字和特点就够了。

加分答法：「我们服务跑的是 G1，日常关注 Full GC 频率和单次停顿，频繁 Full GC 就先查大对象分配和内存泄漏。」

P0 17. 类加载过程和双亲委派？

  • 五个阶段：加载（字节流 → 内存中的 Class 对象）→ 验证 → 准备（静态变量分配内存并设零值，final 常量例外）→ 解析（符号引用转直接引用）→ 初始化（执行 <clinit>：静态变量赋值 + static 块，JVM 保证线程安全，所以静态内部类单例成立）。
  • 双亲委派：收到类加载请求先委托父加载器，父加载器找不到才自己加载。层级：Bootstrap（核心类库）→ Platform → Application → 自定义。
  • 两个作用：防止核心类被篡改（自己写的 java.lang.String 永远加载不到）；保证同一个类只被加载一次（类的唯一性由「类加载器 + 全限定名」决定）。
  • 打破它的场景：JDBC 的 SPI（线程上下文类加载器）、Tomcat 的 webapp 隔离（先自己加载）、热部署。

6. Spring（P1）

生命周期、循环依赖、事务失效——事务失效是小厂最爱。

P1 18. Bean 的生命周期？

  • 主线：实例化（构造方法）→ 属性填充（@Autowired 注入）→ Aware 回调（BeanNameAware / ApplicationContextAware）→ BeanPostProcessor 前置处理 → 初始化（@PostConstruct → InitializingBean.afterPropertiesSet → init-method）→ BeanPostProcessor 后置处理 → 单例入池使用 → 销毁（@PreDestroy → DisposableBean → destroy-method）。
  • 关键一句：AOP 代理对象就是在「后置处理」阶段由 AnnotationAwareAspectJAutoProxyCreator 生成的——面试说到这一句就超出预期了。

P1 19. 循环依赖和三级缓存？

  • 三级缓存：一级 singletonObjects（成品单例）；二级 earlySingletonObjects（提前曝光的早期对象）；三级 singletonFactories（对象工厂）。
  • 流程：A 实例化后先把自己的工厂放进三级缓存 → 填充属性时发现要 B → 创建 B → B 注入 A 时从三级缓存的工厂里拿到 A 的早期引用（若 A 需要代理，工厂生成的就是代理对象）→ B 完成 → A 拿到 B 继续走完生命周期。
  • 为什么要工厂不直接放对象：把「要不要提前生成代理」这个决定延迟到真正发生循环依赖那一刻，不破坏正常生命周期里代理该在后置处理生成的顺序。
  • 解决不了的：构造器注入的循环依赖（对象都还没建出来）、prototype 作用域、@Async 代理对象的循环依赖。

P1 20. Spring 事务失效的场景？（小厂最爱，背全）

  • 本质：声明式事务底层是动态代理，一切绕过代理或配置错误的场景都失效。
  • 方法不是 public；
  • 自调用：同类里 this.methodB() 没走代理对象 → 拆到另一个 Bean，或用 AopContext.currentProxy()；
  • 异常被 try-catch 吞掉了，事务管理器感知不到；
  • 抛的是受检异常——默认只回滚 RuntimeException 和 Error，要加 rollbackFor = Exception.class；
  • 对象不是 Spring 管理的（自己 new 出来的）；
  • 多线程里调用——事务绑定在 ThreadLocal 的数据库连接上，新线程不在同一事务；
  • 传播行为配置错误（如 NOT_SUPPORTED 会挂起事务）。

P1 21. IOC 和 AOP？

  • IOC 控制反转：对象的创建和依赖装配从代码里的 new 交给容器，依赖注入 DI 是实现方式。价值：解耦、便于测试（注入 mock）、统一管理生命周期。
  • AOP 面向切面：把横切关注点（事务、日志、权限、审计）抽成切面织入。核心概念：切点 Pointcut（在哪切）+ 通知 Advice（前置 / 环绕 / 后置 / 异常 / 返回）+ 切面 Aspect。
  • 实现：有接口用 JDK 动态代理，没接口用 CGLIB 子类代理；Spring Boot 默认 CGLIB。

挂靠项目：「Action 指令的审计日志就是用 AOP 环绕通知统一记录的，业务代码零侵入。」

7. Java 基础（P1）

HashMap 和 String 不可变，出现率极高但答好的人不多。

P1 22. HashMap 底层原理？1.7 和 1.8 的区别？

  • 1.8 结构：数组 + 链表 + 红黑树。链表长度 ≥ 8 且数组长度 ≥ 64 才树化（否则先扩容），节点数 ≤ 6 退化回链表。
  • 定位桶：hash 值高 16 位与低 16 位异或（扰动，减少碰撞），再 (n-1) & hash——这就是容量必须取 2 的幂的原因：等价取模但更快，且扩容迁移只有两个去处。
  • 扩容：负载因子 0.75，超过阈值容量翻倍。1.8 迁移时判断 hash & oldCap：等于 0 留原位置，等于 1 挪到「原位置 + oldCap」，不用重算 hash。
  • 1.7 的经典问题：头插法在并发扩容时会让链表成环，造成死循环；1.8 改成尾插解决。但 HashMap 依然线程不安全，并发场景用 ConcurrentHashMap。

P1 23. String 为什么设计成不可变？

  • 怎么实现的：final 类 + private final 的字符数组 + 不提供任何修改方法。
  • 字符串常量池：不可变才能放心共享同一份字面量，节省内存。
  • hashCode 缓存：第一次算完缓存起来，作 HashMap 的 key 时高效。
  • 安全性：路径、类名、URL 参数如果是可变的，中途被改会造成安全漏洞。
  • 线程安全：天然线程安全。顺带说清三者：String 不可变；StringBuilder 可变非线程安全（单线程拼接用）；StringBuffer 可变且方法加 synchronized（老 API）。

8. 消息队列（P1）

简历上 Kafka 和 RabbitMQ 都写了，选型题必来。

P1 24. Kafka 和 RabbitMQ 怎么选型？

  • 共同解决的问题：解耦、异步、削峰。
  • Kafka：分布式顺序日志，分区水平扩展，顺序写 + 零拷贝，吞吐百万级；支持消息回溯重放，流处理生态（Kafka Streams / Flink）。适合日志采集、埋点、大数据管道。
  • RabbitMQ：AMQP 协议，exchange（direct / topic / fanout）路由灵活，单机万级吞吐、延迟低；支持优先级、TTL + 死信队列做延迟队列。适合业务解耦、异步通知、复杂路由场景。

挂靠项目（必被问）：「告警外发在亚信时走 Kafka 中转 Topic——消息量大、日志性质、要高吞吐；无人机平台的业务异步补偿用 RabbitMQ——业务消息，需要灵活路由和重试。按消息量和路由复杂度选型。」

P1 25. 消息怎么保证不丢？

  • 生产端：开 confirm 确认 + 失败重试；更可靠的是本地消息表——业务数据和消息记录写同一个事务，定时任务扫表补偿。
  • Broker：Kafka 设 acks=all + min.insync.replicas>=2、副本因子 3；RabbitMQ 交换机 / 队列 / 消息都设持久化。
  • 消费端：关自动 ack，业务处理完再手动 ack；失败 nack 重回队列或进死信 + 告警人工介入。
  • 本质：三段都保证后得到的是「至少一次」投递，代价是可能重复——所以必须配下一题的幂等。

P1 26. 重复消费怎么办？

  • 前提认知（答出这句就赢一半）：只要保证不丢就必然可能重复（网络超时重发），重复无法在投递层消灭，只能做消费端幂等。
  • 手段一：数据库唯一约束——业务唯一键建唯一索引，重复插入报错捕获即可。
  • 手段二：Redis 去重——setnx 记录 messageId / 业务键，处理前先判断。
  • 手段三：状态机条件更新——update ... set status='已处理' where status='待处理'，影响行数为 0 说明已处理过。

挂靠项目（重点题，背熟）：「我们 Action 协议的回调就是幂等的——messageId 贯穿指令接收、执行、结果查询全链路，Redis + Lua 做原子状态流转，终态保护：已经是终态的指令再来回调，Lua 那一步直接拒绝，不会重复执行。」

P1 27. Kafka 为什么快？

  • 顺序写磁盘：消息只追加到分区日志末尾，磁盘顺序写接近内存随机写的速度，且先落 page cache。
  • 零拷贝（sendfile）：消费者拉取时数据从页缓存直接送到网卡，不经过用户态两次拷贝。
  • 批量 + 压缩：生产端攒批发送（linger.ms + batch.size），配 lz4 / zstd 压缩，摊薄网络和 IO 开销。
  • 分区并行：分区是最小并行单位，消费者组内消费者各自认领分区。
  • 稀疏索引：.log 分段 + .index 稀疏索引，按 offset 快速定位。

9. P2 速览

过一遍留印象即可，每题能说出两句就达标。

28. Spring Cloud 组件？

  • Nacos：注册中心 + 配置中心二合一；临时实例走 AP（心跳），持久实例走 CP（Raft）；配置变更实时推送。
  • Gateway：基于 WebFlux + Netty 的网关，路由（predicate 谓词匹配）+ 过滤器链，替代阻塞模型的 Zuul1。
  • 熔断限流（Sentinel）：熔断是错误率 / 慢调用比例超阈值后快速失败，防止雪崩，半开状态试探恢复；限流是按 QPS / 线程数控制入口。

挂靠项目：「平台本身就是 Spring Cloud 微服务，Nacos 做注册和配置。」

29. MyBatis：#{} 和 ${}、缓存？

  • #{}：预编译参数占位（?），值按参数传，天然防 SQL 注入，默认用它。
  • ${}：字符串直接拼进 SQL，只能用于表名、列名、order by 字段这些没法参数化的位置，必须白名单校验。
  • 缓存：一级缓存 SqlSession 级默认开启；二级缓存是 namespace 级，多表关联时容易脏读，分布式下还有节点间不一致问题，一般不用，要缓存上 Redis。

30. K8S：Pod / Deployment / Service？

  • Pod：最小调度单元，一到多个容器共享同一 Pod IP 和存储卷；多容器是为 sidecar（日志收集、代理）和主容器同生共死。
  • Deployment：管理 ReplicaSet 控制副本数，负责滚动更新（maxSurge / maxUnavailable）和回滚；Pod 挂了自动重建（自愈）。
  • Service：给一组 Pod（按标签选中）提供稳定的虚拟 IP 和 DNS 名做负载均衡——Pod IP 随时会变，Service 解决「找谁」的问题。类型：ClusterIP 集群内 / NodePort 端口映射 / LoadBalancer。
  • 实操：kubectl get pods / logs -f / describe；readiness 探针没过就把 Pod 摘出流量。

挂靠项目：简历写了 K8S，说得出自己服务怎么发布、怎么看日志就及格。

31. 三次握手四次挥手 + 32. HTTPS？

  • 三次握手：SYN → SYN+ACK → ACK。为什么三次：双方都要确认「我能发、你能收」；两次的话旧的失效 SYN 到达服务端会建出僵尸连接。
  • 四次挥手：FIN → ACK → FIN → ACK；主动关闭方最后等 2MSL 的 TIME_WAIT：保证最后的 ACK 丢了能重发，也让旧连接的报文自然消亡。排查衍生题：大量 TIME_WAIT 是短连接频繁（正常现象）；大量 CLOSE_WAIT 是自己代码没关连接。
  • HTTPS：TCP 之后走 TLS——客户端发随机数 + 加密套件 → 服务端发随机数 + 证书 → 客户端验证证书链（CA 签名、域名、有效期），生成预主密钥用证书公钥加密发过去 → 双方用两个随机数 + 预主密钥导出对称会话密钥，之后对称加密通信。为什么混合：非对称安全但慢，只用来协商密钥；对称快，用来传数据。
