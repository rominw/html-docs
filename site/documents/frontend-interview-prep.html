2. HTML 与 CSS

先建立语义、布局、响应式和键盘可用性。

基础必会 1. 语义 HTML：按钮和链接为什么不能只看外观？

先看问题：

一个 div 加点击事件看着像按钮，键盘用户却无法正常聚焦触发，辅助技术也不知道它的职责。

原理怎样推出来

元素语义同时决定默认交互与可访问性信息。button 用于动作，a 用于导航，表单、标题与区域表达结构；使用正确原生元素可获得许多默认行为，再按需求补样式和说明。不要仅用视觉相似代替功能契约。

把它放进一个例子

<button type="button">重新加载</button>
<a href="/tasks">查看任务</a>

边界与反例：按钮在表单中的默认提交行为需明确 type；真实链接应有可用目标，避免只用 # 伪装动作。

停一下，自己推：给 div 加 role="button" 就完成了吗？

展开自测解析

没有。仍要实现焦点、键盘触发、禁用等行为，通常先选原生 button。

理解后，再这样简述：语义让结构和交互可被浏览器、用户及辅助技术识别。

核对原文：对应官方文档或方法原文。

基础必会 2. 可访问性：鼠标能用为什么还不够？

先看问题：

弹窗视觉正常，但键盘焦点跑到背景，错误只用红色，输入框没有标签。

原理怎样推出来

用户可能用键盘、屏幕阅读器或放大界面。每个控制有可识别名称与状态，焦点顺序合理、焦点可见，弹窗打开/关闭有焦点管理，错误信息通过文本关联字段。ARIA 补充语义，不替代原生行为。

把它放进一个例子

<label for="task-name">任务名称</label>
<input id="task-name" aria-describedby="name-help">
<p id="name-help">请输入可识别的名称</p>

边界与反例：不要只靠颜色表达成功失败，也不要无依据去掉焦点轮廓。测试要包含键盘路径和合适辅助工具。

停一下，自己推：不可点击的按钮只改灰色，键盘和程序还能触发吗？

展开自测解析

可能。禁用状态与业务守卫要真正实现，并说明用户该如何继续。

理解后，再这样简述：名称、状态、焦点与错误反馈共同构成可用性。

核对原文：对应官方文档或方法原文。

基础必会 3. 盒模型与 overflow：宽度为什么超出容器？

先看问题：

卡片 width=100%，再加 padding 和 border，页面出现横向滚动。

原理怎样推出来

content-box 的 width 主要约束内容，外加内边距和边框；border-box 把这些纳入指定尺寸。布局还受最小内容宽度、长文本、图片与子元素影响，overflow 只是处理溢出，不自动修好尺寸来源。

把它放进一个例子

* { box-sizing: border-box; }
.card { width: 100%; }
.code { max-width: 100%; overflow: auto; }

边界与反例：隐藏溢出会切掉重要内容或焦点，应把需要横向滚动的表格放独立容器，避免页面级滚动。

停一下，自己推：统一 border-box 后长 URL 仍可能撑宽吗？

展开自测解析

可能。内容最小尺寸和断行规则仍要处理，必要时 min-width:0 与适合的换行。

理解后，再这样简述：尺寸包含关系和内容约束先看清，再处理溢出。

核对原文：对应官方文档或方法原文。

基础必会 4. 层叠、继承与优先级：为什么后写 CSS 没生效？

先看问题：

新规则在文件末尾，颜色仍被旧选择器覆盖；到处加 !important 又使维护更难。

原理怎样推出来

样式决策还涉及来源、重要性、层、选择器优先级与顺序，并非单纯后写覆盖。继承只针对相应属性与上下文，布局尺寸不都继承。明确组件作用域与令牌，减少过度具体选择器和全局泄漏。

把它放进一个例子

先在开发者工具看最终计算值及被覆盖规则，再判断是选择器、内联样式、层还是变量来源，而不是盲目追加更强规则。

边界与反例：!important 不修复样式职责冲突；使用层叠层时还要理解层顺序与重要声明行为。

停一下，自己推：父元素 color 改了，子元素显式 color 是否仍一定跟随？

展开自测解析

不一定。子元素自己声明的有效值会决定结果，不能仅看父级。

理解后，再这样简述：层叠先确定有效声明，继承再补对应属性，排查以计算样式为证据。

核对原文：对应官方文档或方法原文。

基础必会 5. Flex 与 Grid：一维和二维分别解决什么？

先看问题：

工具栏按行分配空间，报表卡片按行列对齐，两种布局不一定都用手工百分比宽度。

原理怎样推出来

Flex 主要组织一条主轴和交叉轴，适合工具栏与一维排列；Grid 定义行列轨道，更直接表达二维关系。flex-basis、收缩、最小尺寸会影响最终宽度，Grid 的 minmax 可表达可伸缩轨道。

把它放进一个例子

.toolbar { display: flex; gap: 12px; }
.toolbar > * { min-width: 0; }
.cards { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); }

边界与反例：不是所有子元素都该无条件收缩或隐藏。绝对定位也不是通用布局替代。

停一下，自己推：flex:1 的文本列为什么仍可能挤出容器？

展开自测解析

其自动最小尺寸可能受内容约束，需检查 min-width、断行与相邻固定元素。

理解后，再这样简述：先选排列维度，再处理轨道、收缩和内容最小宽度。

核对原文：对应官方文档或方法原文。

基础必会 6. 响应式：小屏不只是把所有内容缩小

先看问题：

桌面三列和长表格直接缩到手机，字太小、按钮难点、关键动作离屏。

原理怎样推出来

根据可用空间改变布局与信息组织：媒体查询、弹性尺寸、合理图片与独立滚动容器配合。断点应由内容何时失效决定，触控、键盘与字体放大都要可用；不要靠页面整体横滚弥补每个模块布局。

把它放进一个例子

窄屏卡片改单列，关键操作保留清晰入口；宽表格在表格容器滚动，正文继续正常换行。

边界与反例：隐藏某列不等于用户不需要该信息，必要时提供详情入口。检测 user-agent 不等于掌握真实视口与能力。

停一下，自己推：只有 390px 截图正常，就代表响应式完成了吗？

展开自测解析

不够。还要看中间宽度、缩放、长内容、横屏和交互。

理解后，再这样简述：响应式让任务在不同约束下仍可完成，断点按内容检验。

核对原文：对应官方文档或方法原文。

项目常用 7. 层叠上下文与定位：z-index 很大为什么还被挡住？

先看问题：

弹窗 z-index=99999，却被另一块区域覆盖；sticky 元素也跟着意外容器滚动。

原理怎样推出来

z-index 在对应层叠上下文内比较，不跨所有祖先全局排序；定位、transform、opacity 等可能建立新上下文。fixed/absolute/sticky 的参考和滚动祖先也不同，需检查祖先结构，不只加数值。

把它放进一个例子

开发工具查看弹窗祖先是否创建上下文；按组件库约定把遮罩放在正确层级，保留焦点与背景交互管理。

边界与反例：Portal/Teleport 可改变 DOM 所在位置，但框架事件和状态关系仍有自己的规则。

停一下，自己推：给弹窗不断加 z-index，能跨越祖先被压住的上下文吗？

展开自测解析

不保证。必须处理它所在上下文的排序或结构。

理解后，再这样简述：层级属于上下文，定位依赖祖先与滚动边界。

核对原文：对应官方文档或方法原文。

基础必会 8. 表单与校验：前端校验为什么不能替代服务端？

先看问题：

用户绕过页面直接发请求，或提交后收到服务端字段错误；前端只弹“失败”无法恢复。

原理怎样推出来

前端校验减少误操作并提供即时说明，服务端独立验证权限、范围与一致性。保留输入、对应字段错误、提交状态和重复点击处理，让失败可修复。加载、空、错误和成功都应有明确状态，而不只设计正常截图。

把它放进一个例子

提交名称时先检查必填，服务端返回名称冲突则保留数据并关联到名称字段；超时后按请求身份确认结果，避免盲目重建。

边界与反例：禁用按钮只是交互措施，不能保证服务端幂等；验证码、隐藏字段也不是可信身份。

停一下，自己推：提交超时后立刻清空表单，会影响什么？

展开自测解析

用户丢失输入且不知道是否成功，应保留可恢复状态与结果确认方式。

理解后，再这样简述：表单设计覆盖完整状态与恢复，前后端各自守边界。

核对原文：对应官方文档或方法原文。

3. JavaScript / TS

从对象与回调行为走到事件、类型和模块。

基础必会 9. 对象、数组与不可变更新：复制外层够吗？

先看问题：

组件直接修改 props 或共享嵌套对象，另一处界面被悄悄改了，状态追踪也不清晰。

原理怎样推出来

JS 对象以引用共享，const 不冻结成员；展开复制通常是浅层。框架状态应按契约更新对应层级，不随意修改外部输入；内容相等、引用相等和身份都影响观察与优化。

把它放进一个例子

const next = { ...state, device: { ...state.device, name: "新名称" } };
// 仅在确实修改的层级创建新对象

边界与反例：JSON 复制可能丢类型或改变值，不是通用深复制；更大复制也可能付出性能成本。

停一下，自己推：复制 state 后改 next.device.name，device 仍共享会怎样？

展开自测解析

旧 state.device 也可能变化，破坏“上一份快照”的预期。

理解后，再这样简述：清楚数据所有权与复制深度，更新保护状态快照。

核对原文：对应官方文档或方法原文。

基础必会 10. 闭包与 this：事件回调读的是什么？

先看问题：

点击回调里的数据不是最新，或传出的对象方法丢了 this。两种问题都来自调用环境。

原理怎样推出来

闭包访问创建环境的绑定；框架每轮渲染还可能创建新的局部快照。普通函数 this 取决于调用方式，箭头捕获词法 this，bind 固定接收者。先确定希望读取当前状态还是特定时点，再选参数、更新函数或受控引用。

把它放进一个例子

把方法作为回调时可明确 bind；延迟回调需要最新计数时使用框架规定的更新方式，而不是假定闭包会自动变成当前值。

边界与反例：不能把 React 渲染快照与所有 JS 闭包统一成“永远读旧值”；具体绑定是否被重赋要分析。

停一下，自己推：给箭头函数 call(other) 就能改 this 吗？

展开自测解析

不能按普通函数方式改它的词法 this；它仍读取创建时外层环境对应的接收者。

理解后，再这样简述：回调的绑定、快照与接收者分别分析。

核对原文：对应官方文档或方法原文。

基础必会 11. 浏览器任务、微任务与渲染：Promise 为什么也能卡 UI？

先看问题：

连续排 Promise 回调，页面输入和绘制不及时；给计算套 Promise 并没变快。

原理怎样推出来

JavaScript 当前任务执行完后处理相应微任务，浏览器在合适机会更新渲染；长任务或持续排微任务会推迟输入与绘制。Promise 不把同步计算自动移到 worker，requestAnimationFrame 是与渲染时机配合的回调，不是免费计算线程。

把它放进一个例子

console.log("A");
Promise.resolve().then(() => console.log("B"));
console.log("C"); // 此普通脚本 A、C、B

边界与反例：不要把每个 timer 都视为一次必然绘制；后台页、设备和调度环境会改变机会。

停一下，自己推：递归 queueMicrotask 做百万步计算，就不会阻塞交互吗？

展开自测解析

仍可能连续占住微任务处理，需分块让出或采用 worker 等方案。

理解后，再这样简述：异步队列不等于计算并行，交互需要有界工作与让出机会。

核对原文：对应官方文档或方法原文。

基础必会 12. 事件传播与委托：为什么点击子元素也触发父处理？

先看问题：

列表每行绑监听，动态新增忘了绑定；点击按钮却误执行整行跳转。

原理怎样推出来

展开自测解析

基础必会 15. 防抖与节流：减少调用怎样避免丢掉正确结果？

先看问题：

搜索每次按键都请求，滚动每次事件都重算；减少次数却不能让旧请求覆盖新结果。

原理怎样推出来

防抖等一段安静时间后执行，适合延后连续输入；节流限制一段时间内执行频次，适合持续事件。前沿/尾沿、参数、接收者与取消规则需明确。它们控制发起频率，不保证已发请求的完成顺序，所以仍配请求身份或取消。

把它放进一个例子

function debounce(fn, ms) {
  let timer;
  function wrapped(...args) {
    clearTimeout(timer);
    const context = this;
    timer = setTimeout(() => fn.apply(context, args), ms);
  }
  wrapped.cancel = () => clearTimeout(timer);
  return wrapped;
}

边界与反例：示意实现为尾沿执行。组件需要稳定函数身份并在结束时 cancel；保存、支付等操作不能只靠防抖保证服务端幂等。

停一下，自己推：防抖后已发出的 A 请求，比后来 B 还晚返回，会自动被忽略吗？

展开自测解析

不会。防抖没有证明完成顺序，结果与错误状态仍需按当前请求身份校验。

理解后，再这样简述：防抖/节流控制频率，生命周期、顺序与副作用另外保证。

核对原文：对应官方文档或方法原文。

基础必会 17. HTTP 缓存：no-cache 与 no-store 差在哪里？

基础必会 18. 同源与 CORS：后端 curl 成功，浏览器为何拒绝？

项目常用 21. 请求竞态：旧搜索结果为什么覆盖了新结果？

5. React / Vue

状态、身份与副作用是框架学习的主线。

基础必会 23. React 状态快照与更新队列：连点三次为什么只加一？

先看问题：

一个回调连续 setCount(count+1) 三次，以为每次都会读取刚更新后的 count。

原理怎样推出来

一次渲染提供当次状态快照，回调读取的是该快照；setState 排队请求后续更新，不直接改当前局部变量。基于前值的连续更新可用更新函数，React 再按队列应用；渲染应保持纯，副作用不随意写在渲染过程。

把它放进一个例子

setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);
// 依序基于前一更新结果

边界与反例：更新函数应纯，不在里面发请求；开发检查和并发渲染可能再次调用相关代码，不能依赖恰好一次。

停一下，自己推：setCount 后立刻 console.log(count)，必然看到新值吗？

展开自测解析

不必然，它仍是当前渲染的局部快照，观察下一次状态需按生命周期。

理解后，再这样简述：状态是渲染快照，更新队列表达转换，不等于原地赋值。

基础必会 24. React Effect：什么时候真的需要副作用？

原理怎样推出来

不是，它可能继续观察旧设备。先表达正确同步关系再优化。

停一下，自己推：Context 的 value 每次都新建大对象，消费者会如何受影响？

展开自测解析

可能收到更新并重渲染，需按依赖与实测成本组织，而不先盲目 memo。

理解后，再这样简述：按状态来源、拥有者与寿命设计共享，不把缓存问题伪装成全局变量。

核对原文：对应官方文档或方法原文。

进阶追问 28. memo、useMemo 与编译优化：为什么不是加了就更快？

先看问题：

到处包 memo，仍因新对象 props 重渲染，维护却更复杂。

原理怎样推出来

优化依赖正确的状态与稳定输入语义，memo/useMemo 等可减少特定重复工作，但比较、缓存与依赖维护也有成本。框架编译优化随版本和配置改变，不要求把每个表达式手工缓存。先用 profiler 找真正昂贵路径。

把它放进一个例子

若列表重渲染由父组件无关状态引起，检查数据结构和 props 身份，再局部验证缓存是否降低耗时；便宜计算无需增加复杂依赖。

边界与反例：memo 是性能机制，不作为副作用只执行一次或业务正确性的依赖。

停一下，自己推：只比较 id 的自定义 comparator 忽略 name，可能怎样？

展开自测解析

组件可能错过名称更新并显示旧数据；比较策略必须覆盖真实读取输入。

理解后，再这样简述：测量先行，优化不改变正确契约。

核对原文：对应官方文档或方法原文。

基础必会 29. Vue ref 与 reactive：解构后为什么不更新？

先看问题：

把 reactive 对象的普通数值属性解构到局部变量，以为它还自动关联原对象。

原理怎样推出来

Vue 3 通过响应式代理/引用等机制追踪读取与触发更新。ref 用 value 访问，模板有对应解包规则；reactive 对象属性访问通过代理，解构普通值会得到当时的值，失去对应访问路径。需要维持连接可用 toRef/toRefs 或按原对象访问。

把它放进一个例子

const state = reactive({ count: 0 });
const { count } = toRefs(state);
state.count++;
// count.value 随对应字段变化

边界与反例：数组、集合、嵌套引用和 props 编译转换的解包规则并不完全一样，按项目版本核对。

停一下，自己推：把 state 直接换成一个未响应式处理的普通对象，旧引用自动跟随吗？

展开自测解析

不保证。对象身份与引用绑定已经改变，需保持正确响应式拥有者。

理解后，再这样简述：追踪发生在响应式访问上，解构与替换按值和身份分析。

核对原文：对应官方文档或方法原文。

基础必会 30. computed、watch 与 watchEffect：计算和副作用如何分开？

先看问题：

计算筛选总数却用 watch 多存一份状态，或在 computed 里发网络请求。

原理怎样推出来

computed 根据响应式依赖表达派生值并缓存，getter 应保持纯；watch 观察明确源，适合副作用；watchEffect 自动跟踪同步执行中读取的依赖，异步回调首个 await 后读取不一定被同样追踪。异步副作用仍须清理与竞态控制。

把它放进一个例子

const doneCount = computed(() => tasks.value.filter(t => t.done).length);
// 网络同步用对应 watch 与清理协议，而不是 computed 副作用

边界与反例：深度 watch 可能有成本，也不一定提供独立旧快照；不靠增加 deep 修复所有状态设计。

停一下，自己推：watchEffect await 后才读 deviceId，它必然成为依赖吗？

展开自测解析

不必然。要按追踪边界显式选择 watch 源或在同步阶段读取。

理解后，再这样简述：派生计算保持纯，观察副作用管理依赖、取消与结果身份。

核对原文：对应官方文档或方法原文。

项目常用 31. Vue 生命周期与组件契约：事件、props 和清理谁拥有？

先看问题：

组件直接改父传的 props，或卸载后定时器仍更新状态。

原理怎样推出来

props 表达外部输入，组件通过事件等约定请求拥有者更新；双向模型也有其 prop/event 契约。生命周期管理订阅、定时器与 DOM 资源，卸载时清理，DOM 更新后读取需使用相应 nextTick/生命周期时机。

把它放进一个例子

任务行发出 rename 事件，父或数据层处理保存并回传结果；行组件结束时释放监听和未需要的工作。

边界与反例：组件契约应包含禁用、加载、错误和可访问性，不只一个 value 字段。跨实例持久业务不能放组件内。

停一下，自己推：调用 nextTick 就能保证服务端结果已经返回吗？

展开自测解析

不能，它针对框架更新队列相关时机，不是任意网络/业务完成。

理解后，再这样简述：输入输出与资源所有权清楚，DOM 时机不等于业务时机。

核对原文：对应官方文档或方法原文。

项目常用 32. 构建、代码拆分与 Tree Shaking：bundle 小了就一定快？

先看问题：

一次加载全部页面代码，首屏慢；拆成很多小块后又多次瀑布请求。

原理怎样推出来

打包解析依赖图，拆分将按需功能延后加载，tree shaking 在符合静态分析与副作用规则时消除不用代码。策略还要看网络往返、缓存、执行和关键路径，不能只看压缩字节。预加载等提示也要按真实优先级使用。

把它放进一个例子

把低频报表路由延迟加载，公共依赖按缓存需求组织；在网络和性能记录中确认首屏关键路径少了什么。

边界与反例：依赖的 side effects 与模块格式影响消除能力，动态导入错误要有恢复界面；不能提前拆碎所有组件。

停一下，自己推：总字节少了，但关键块串行下载五次，用户一定更快吗？

展开自测解析

不一定，关键路径往返可能更长，要比较实际用户指标。

理解后，再这样简述：拆分控制加载时机，静态消除减少无用代码，最终验证关键路径。

核对原文：对应官方文档或方法原文。

基础必会 33. 路由、URL 与权限：刷新为什么 404？

先看问题：

客户端跳转正常，复制详情链接到新窗口却 404，筛选又无法分享。

原理怎样推出来

浏览器 URL 与服务端资源路由要一致，SPA history 路由通常需要托管端正确回退，同时避免把真实 API/不存在资源全部吞掉。可分享状态适合进入 URL 并解析校验；路由守卫改善交互，但服务端仍授权资源。

把它放进一个例子

任务列表的筛选与页游标可编码 URL，详情刷新由托管返回正确入口，再请求已授权数据；不存在任务显示清晰错误。

边界与反例：URL 可能出现在日志和分享中，不放密钥与敏感明文。客户端“无法进入页面”不阻止直接 API 调用。

停一下，自己推：统一所有路径返回 index.html 就完成了吗？

展开自测解析

不一定，会误处理静态资源/API 与真正 404，回退规则要明确范围。

理解后，再这样简述：URL 是导航与分享契约，客户端和托管规则配套。

核对原文：对应官方文档或方法原文。

项目常用 34. SSR、SSG 与 Hydration：服务端 HTML 为什么还要 JS？

先看问题：

SSR 页面首屏有内容，按钮仍要等待脚本；服务端与客户端随机值不同还出现 hydration 不匹配。

原理怎样推出来

SSR 按请求生成 HTML，SSG 在构建或对应预生成阶段得到页面；客户端 hydration 将事件与框架状态接到已有结构。初始输出需兼容，浏览器专有 API 不直接在服务端执行。缓存、个性化与数据获取位置共同决定策略。

把它放进一个例子

静态说明页可预生成，用户任务页面需要按身份获取数据；时区、随机数与客户端条件输出要避免造成不一致，交互错误有恢复。

边界与反例：SSR 不自动减少全部 JS，也不让服务器忽略授权或缓存隔离；完整框架边界按版本看。

停一下，自己推：把用户 A 的 SSR HTML 放公共缓存，可能发生什么？

展开自测解析

如果缓存键/策略没隔离，可能向 B 暴露数据，服务端渲染仍需正确权限与缓存。

理解后，再这样简述：生成、数据和交互接入分开，保证初始一致与身份隔离。

核对原文：对应官方文档或方法原文。

基础必会 35. 前端测试：为什么截图正常还会坏？

先看问题：

正常状态截图没有发现重复提交、键盘无法触发、旧请求覆盖和刷新路由失败。

展开自测解析

不够，还需检查名称、可操作性、结果与失败反馈。

理解后，再这样简述：测试围绕用户任务与结果，浏览器和系统边界有对应证据。

项目常用 36. 组件与设计系统：复用的是样式还是交互契约？

先看问题：

多个页面都有弹窗和表格，各自处理焦点、错误和加载，结果行为不一致。

原理怎样推出来

复用组件要定义输入输出、状态、键盘、焦点、错误与响应式行为，令牌统一基础视觉。业务规则保留在合适层，不把所有页面差异塞成几十个布尔参数。先复用已有组件体系，再根据真实重复需求提炼。

把它放进一个例子

确认框明确危险动作、取消、处理中与失败恢复；表格明确排序、选择、空状态与长内容，不能只复用一组颜色。

边界与反例：抽象会引入维护成本，一个只用一次的特殊流程可直接实现，不能以“以后可能”推动通用化。

停一下，自己推：两个弹窗外观一样，就一定能用同一业务组件吗？

展开自测解析

不一定，任务与状态契约可能不同；可共享基础层而保留业务流程。

理解后，再这样简述：组件复用稳定契约，设计令牌与业务职责分别组织。

核对原文：对应官方文档或方法原文。

基础必会 37. LCP、INP、CLS：性能指标分别对应哪种用户感受？

先看问题：

平均加载很快，用户却说首屏慢、按钮卡或页面跳动，三个症状不能只看一个秒数。

原理怎样推出来

LCP 观察主要内容显示时机，INP 观察交互响应，CLS 观察意外布局变化；指标定义与采集有条件，现场数据与实验室数据覆盖不同环境。先确定哪个体验问题，再按资源、长任务和布局路径定位。

把它放进一个例子

大首屏图片迟到查 LCP 关键资源；点击等待查长任务与状态更新；图片未预留空间导致跳动查 CLS。记录相应分布和真实设备，而不只本机一次测速。

边界与反例：不同指标不是完整可用性与业务成功率；不要仅为过分数隐藏重要内容。

停一下，自己推：CLS 很好，就代表表单提交不会卡吗？

展开自测解析

不代表。布局稳定与交互延迟是不同维度，需分别观察点击响应、等待和相应性能路径。

理解后，再这样简述：指标连接具体用户感受，现场分布与剖析形成证据。

核对原文：对应官方文档或方法原文。

项目常用 38. 性能定位：网络、JS 和渲染怎样分段看？

先看问题：

页面慢，先加 memo 或 CDN，却没确认瓶颈在下载、解析、请求瀑布还是大列表渲染。

原理怎样推出来

使用网络与性能记录拆下载、脚本执行、布局绘制和数据等待，再关联真实用户指标。请求数量、压缩字节与缓存不是同一成本；状态更新范围与长任务也要看。一次只改证据指向的环节，再以相似环境比较。

把它放进一个例子

网络快而主线程忙，查脚本与渲染；数据请求串行，查依赖与并发；首屏图片迟，查资源优先级与尺寸。

展开自测解析

不能，应覆盖对应用户环境和分位，分清缓存与负载条件。

理解后，再这样简述：先分段定位，优化验证控制环境与工作量。

项目常用 39. 长列表与虚拟化：少 DOM 后还要保证什么？

项目常用 40. 错误边界、发布与恢复：新版 chunk 404 怎么处理？
