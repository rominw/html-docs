1. 什么是状态机

一句话理解：状态机把"什么状态下允许发生什么"从散落各处的 if/else，收拢成一张事先定义好的表。

核心思想：一个事物在任意时刻，只能处于有限个状态中的一个；当"事件"发生时，按事先定义好的规则从当前状态跳到下一个状态；除了这些规则，状态不允许以任何其他方式变化。

直观例子：红绿灯

  • 状态：红、绿、黄 —— 有限个
  • 事件：计时器到
  • 流转规则：绿 → 黄 → 红 → 绿，循环往复

你永远不会看到"灯同时是红和绿"，也永远不会看到"红灯跳过黄灯直接变绿"——因为规则不允许。把这种确定性用到软件里，就是状态机。

形式化定义（五元组）

教科书上写作 M = (S, Σ, δ, s₀, F)，含义并不神秘：

  • S：有限状态集（如 待处理/执行中/已完成）
  • Σ：事件（输入）集合
  • δ：转移函数，当前状态 × 事件 → 下一状态
  • s₀：初始状态（任务刚创建时是"待处理"）
  • F：终态集合（"已完成""已取消"，转出永不发生）

2. 五个核心概念

状态、事件、转移、动作、守卫——所有状态机相关讨论都由这五个词构成。

概念英文含义巡检任务中的例子
状态State事物当前所处的模式RUNNING 执行中
事件Event触发变化的输入设备回调"无人机到达起飞点"
转移Transition状态 + 事件 → 新状态RUNNING + 到达起飞点 → TAKEOFF
动作Action转移发生时执行的副作用转入 RUNNING 时下发任务给机库、推送 WebSocket 通知
守卫Guard转移的前置条件，不满足则不转移电量 > 20% 才允许 WAITING → RUNNING

Mealy 机：动作挂在"转移"上

每次转移时做一次性的事（发一条消息、写一行日志）。工程实践中绝大多数业务状态机都是 Mealy 型。

Moore 机：动作挂在"状态"上

进入某个状态后持续表现出某种行为（状态对应一个界面、一种输出）。硬件控制（如红绿灯本体）更常见。

3. 状态图与转移表

无论用什么语言实现，第一步永远是先把流转画出来、写成表——图和表就是转移函数 δ 本身。

看图就能问出关键问题（这正是状态图的价值）：取消只能从"待处理"进入，还是"执行中"也能取消？FINISH 是终态吗、终态之后还允许任何转出吗？到达起飞点后如果设备故障，走哪条边？WAITING 是初始状态，即任务刚创建时的状态。

4. 隐式状态机：最常见的反面形态

很多系统"其实已经是状态机"，只是转移规则没有定义在任何地方——它们散落在各个 Service 的 if/else 里。

症状一：枚举只定义了状态集 S，没有定义转移 δ

public enum MissionStatusEnum {
    WAITING(0, "待处理"),
    RUNNING(1, "执行中"),
    TAKEOFF(21, "到达起飞点"),
    LAND(29, "到达降落点"),
    DRONE_BACK(4, "飞机落库"),
    DOCK_RESET(5, "机库复位"),
    IMAGE_UPLOAD_COMPLETED(6, "图片上传完成"),
    FINISH(2, "已完成"),
    CANCEL(3, "已取消");
    // ……只有状态集合 S，"哪些流转合法"没有定义在任何地方
}

症状二：判断"处于哪一组状态"的 if 链散落各处

// 某个设备回调处理里的典型判断：哪些状态算"已结束"全靠人脑记
if (config.isFinishExeOdm()
        && DRONE_BACK != mission.getStatus()
        && DOCK_RESET != mission.getStatus()
        && FINISH != mission.getStatus()
        && IMAGE_UPLOAD_COMPLETED != mission.getStatus()) {
    // ……
}

问题一：无人能回答全貌

"状态 X 能不能变成状态 Y"的答案散落在几十个文件里，只能靠通读代码或线上踩坑才能知道。

问题二：加状态要改 N 处

新增一个状态（例如为"断点续飞"增加回补状态），所有判断"任务是否结束"的 if 链都要挨个排查，漏一处就是线上 bug。

问题三：并发不安全

"取消"和"图片上传完成"两个回调同时到达，都读到旧状态、都判断自己合法、都去更新——已取消的任务又"活"了。

判断标准：当 status != A && status != B && status != C 这种"判断当前是否处于某一组状态"的代码出现超过两处时，就该引入状态机了。状态机的解法就是把 δ 从代码角落里提出来，显式写成一张表，让非法流转在物理上不可能发生。

5. Java 实现的四种姿势

由浅入深：枚举内聚 → 表驱动 → 状态模式 → 框架。绝大多数场景前两种就够用。

5.1 枚举内聚式：把"下一步能去哪"放进枚举 零依赖 · 首选起步

改动最小，一眼看清全部流转。局限：表达不了"事件"和"守卫"维度。

public enum MissionStatusEnum {

    //                                          合法的下一步（终态集合为空）
    WAITING(0, "待处理",        EnumSet.of(RUNNING, CANCEL)),
    RUNNING(1, "执行中",        EnumSet.of(TAKEOFF, LAND, FINISH, CANCEL)),
    LAND(29, "到达降落点",      EnumSet.of(DRONE_BACK)),
    DRONE_BACK(4, "飞机落库",   EnumSet.of(IMAGE_UPLOAD_COMPLETED, DOCK_RESET)),
    IMAGE_UPLOAD_COMPLETED(6, "图片上传完成", EnumSet.of(DOCK_RESET)),
    DOCK_RESET(5, "机库复位",   EnumSet.of(FINISH)),
    FINISH(2, "已完成",         EnumSet.noneOf(MissionStatusEnum.class)),
    CANCEL(3, "已取消",         EnumSet.noneOf(MissionStatusEnum.class));

    private final int type;
    private final String desc;
    private final Set<MissionStatusEnum> nextStates;

    MissionStatusEnum(int type, String desc, Set<MissionStatusEnum> nextStates) {
        this.type = type;
        this.desc = desc;
        this.nextStates = nextStates;
    }

    /** 状态转移的唯一入口，业务代码必须经过它 */
    public MissionStatusEnum transferTo(MissionStatusEnum target) {
        if (!nextStates.contains(target)) {
            throw new IllegalStateException(
                desc + " 不允许流转到 " + target.desc);
        }
        return target;
    }
}

于是第 4 节那条四行 if 链变成一行：mission.transferTo(DOCK_RESET)。非法流转直接抛异常——在物理上不可能发生，而不是靠程序员记得写判断。

5.2 表驱动式：把 δ 写成数据 工程上最实用

引入事件枚举后，转移规则变成一张真正的表：规则与执行彻底分离，看一张表就能评审全部流转逻辑。

public enum MissionEvent {
    DISPATCH, REACH_TAKEOFF, REACH_LAND, DRONE_DOCKED,
    IMAGE_UPLOADED, DOCK_RESET_DONE, USER_CANCEL
}

public final class MissionStateMachine {

    private static final Map<MissionStatusEnum, Map<MissionEvent, MissionStatusEnum>> TABLE =
        Map.of(
            WAITING,    Map.of(DISPATCH, RUNNING, USER_CANCEL, CANCEL),
            RUNNING,    Map.of(REACH_TAKEOFF, TAKEOFF, REACH_LAND, LAND, USER_CANCEL, CANCEL),
            LAND,       Map.of(DRONE_DOCKED, DRONE_BACK),
            DRONE_BACK, Map.of(IMAGE_UPLOADED, IMAGE_UPLOAD_COMPLETED,
                               DOCK_RESET_DONE, DOCK_RESET),
            IMAGE_UPLOAD_COMPLETED, Map.of(DOCK_RESET_DONE, DOCK_RESET),
            DOCK_RESET, Map.of(DOCK_RESET_DONE, FINISH)
        ); // FINISH / CANCEL 不在表中 = 终态，任何事件都转不出去

    private MissionStateMachine() {}

    /** 返回目标状态；表中不存在即为非法转移 */
    public static MissionStatusEnum fire(MissionStatusEnum current, MissionEvent event) {
        MissionStatusEnum next = TABLE
            .getOrDefault(current, Map.of())
            .get(event);
        if (next == null) {
            throw new IllegalStateException(
                "状态[" + current + "]收到事件[" + event + "]无合法流转");
        }
        return next;
    }
}

5.3 状态模式（GoF）：每个状态一个类 状态行为差异大时

当各状态不只是流转不同，而是同一操作在不同状态下行为完全不同时使用。缺点是类多，状态多而行为简单时不划算。

public interface MissionState {
    void onEvent(MissionContext ctx, MissionEvent event);
}

public final class RunningState implements MissionState {
    @Override
    public void onEvent(MissionContext ctx, MissionEvent event) {
        switch (event) {                    // 只需处理本状态关心的事件
            case REACH_TAKEOFF -> ctx.setState(new TakeoffState());
            case USER_CANCEL   -> { /* 先召回无人机，再转入取消态（动作） */ }
            default -> throw new IllegalStateException("执行中不接受事件 " + event);
        }
    }
}

public final class FinishedState implements MissionState {
    @Override
    public void onEvent(MissionContext ctx, MissionEvent event) {
        // 终态：任何事件一律拒绝，任务不可能"复活"
    }
}

5.4 框架：Spring StateMachine 超复杂长流程才用

状态多到几十个、出现子状态（如"执行中"内部又分阶段）、或流程横跨数天与多个服务时，才值得引入框架。它提供层次状态、转移监听器、持久化与恢复（StateMachinePersister）等能力。不建议一上手就用框架——表驱动能解决八成问题，且人人看得懂。

选型速查

场景特征推荐实现理由
流转简单、无事件维度枚举内聚零依赖、零学习成本，规则跟着枚举走
事件多、规则需要集中评审表驱动规则即数据，一张表覆盖全部流转
各状态下行为差异巨大状态模式面向对象封装，新增状态不改旧状态

6. 生产环境最佳实践

写对转移表只是及格线；真正的坑在并发、持久化、幂等这些"写代码之外"的地方。

6.1 并发转移：用条件更新（CAS）兜底 最重要

转移表只保证"逻辑上合法"，但两个线程可能都读到 WAITING 然后各自转移。落库时永远用条件更新，这是分布式环境下最可靠的状态转移方式：

-- 条件更新（CAS）：影响行数为 0，说明状态已被并发请求改走
UPDATE mission
SET status = #{newStatus}, update_time = NOW()
WHERE id = #{id} AND status = #{oldStatus};
int rows = missionDao.compareAndSwap(missionId, current, next);
if (rows == 0) {
    // 状态已被别人改走：重查当前状态，再决定重试、忽略还是报错
    return handleConflict(missionId, event);
}
// rows == 1 才继续执行动作：发消息、写日志、推进下游

口诀：状态机（逻辑合法）+ 条件更新（物理互斥）= 完整方案，两者缺一不可。

6.2 持久化与恢复

状态必须落库。服务重启后从库里恢复当前状态继续推进，而不是重置。批次表 + 子任务表 + 产物表构成"可恢复的持久化状态机"，是长周期异步任务的标配。

6.3 幂等

事件可能重复到达（MQ 至少一次投递、设备重发回调）。同一事件第二次到来时，若当前状态已"消化"过它，应安全忽略而不是报错或重复流转——转移表天然帮你判断：重复事件在表中查不到合法流转，走忽略分支即可。

6.4 终态封闭

FINISH、CANCEL 这类终态的 next 集合必须为空，任何事件都转不出去。"已取消的任务又活了"这类事故的根源就是终态没有封闭。

6.5 流转审计

单独记录每一步流转 (from, event, to, operator, time)。设备回调乱序、重发常态化的场景下，能完整回放问题是救命的能力。

流转日志表参考结构

CREATE TABLE mission_status_log (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,

);

7. 落地检查清单与适用边界

引入状态机前先对照这两张清单，避免过度设计，也避免漏掉关键防线。

落地检查清单

  • 状态和事件先画图、写表、评审，再动手写代码
  • 转移规则只有一处定义（枚举 next 或转移表），禁止散落 if
  • 所有转移经过唯一入口（transferTo / fire）
  • 落库一律条件更新（CAS），返回 0 行视为冲突处理
  • 终态 next 集合为空，任何事件不可转出
  • 重复事件幂等：已消化的事件直接忽略
  • 状态持久化 + 重启恢复，不靠内存续命
  • 流转写审计日志，出问题可回放
  • 新增状态时：图 → 表 → 单测三处同步改

什么时候不需要状态机

  • 状态只有两三个、流转毫无约束（如启用/停用开关）——直接写就行
  • 纯 CRUD 的简单字段，没有并发修改与审计诉求
  • 取值是连续数据而非离散模式（如温度、进度百分比）——那不是状态机要解决的问题

适用判断一句话：状态数有限（通常 < 20）、流转有严格约束、存在并发修改、需要审计回放——满足两条以上，状态机就开始回本了。

8. 练习

检验是否真正掌握：三道题分别对应画图、实现和守卫/动作。

  • 补图：为"断点续飞"场景新增"任务创建回补"与"已接收"两个状态，它们应该出现在状态图的哪条路径上？画出修改后的完整流转。
  • 实现：用表驱动方式实现 fire()，并为每个状态编写非法转移的单元测试——终态收到任何事件必须抛异常。
  • 思考：用户取消事件在"已到达降落点、无人机还在空中"时应该允许吗？如果允许，取消动作里无人机怎么处理？——这正是守卫（Guard）和动作（Action）的用武之地。
