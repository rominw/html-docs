1. 什么是状态机

一句话理解：状态机把"什么状态下允许发生什么"从散落各处的 if/else，收拢成一张事先定义好的表。

核心思想：一个事物在任意时刻，只能处于有限个状态中的一个；当"事件"发生时，按事先定义好的规则从当前状态跳到下一个状态；除了这些规则，状态不允许以任何其他方式变化。

直观例子：红绿灯

  • 状态：红、绿、黄 —— 有限个
  • 事件：计时器到
  • 流转规则：绿 → 黄 → 红 → 绿，循环往复

你永远不会看到"灯同时是红和绿"，也永远不会看到"红灯跳过黄灯直接变绿"——因为规则不允许。把这种确定性用到软件里，就是状态机。

形式化定义（五元组）

教科书上写作 M = (S, Σ, δ, s₀, F)，用音乐播放器一对照就不神秘：

  • S：有限状态集 = { 停止、播放中、已暂停 }
  • Σ：事件集 = { 播放、暂停、停止 }
  • δ：转移函数（当前状态 × 事件 → 下一状态），下一节展开成 3×3 的表
  • s₀：初始状态 = 停止（打开播放器时必然处于这里）
  • F：终态集合 = ∅ —— 播放器没有"到此为止"的状态；而业务状态机（如订单的"已完成/已取消"）通常有终态，这是两类状态机最直观的差别

2. 五个核心概念

状态、事件、转移、动作、守卫——所有状态机相关讨论都由这五个词构成。继续用播放器建立直觉。

概念英文含义播放器中的例子
状态State事物当前所处的模式PLAYING 播放中
事件Event触发变化的输入用户按下"暂停"键
转移Transition状态 + 事件 → 新状态播放中 + 按下暂停 → 已暂停
动作Action转移发生时执行的副作用暂停时记住播放进度；恢复播放时从进度续播，而不是从头开始
守卫Guard转移的前置条件，不满足则不转移在线流媒体场景：缓冲就绪，才允许从暂停恢复播放

播放器的完整转移表（δ）

当前状态 \ 事件播放暂停停止
停止播放中（从头播放）非法：没有可暂停的内容忽略
播放中忽略已暂停停止
已暂停播放中（从进度续播）忽略停止

3 个状态 × 3 个事件，这就是一台完整的状态机。注意两种"没有转移"的区别：忽略（重复事件，幂等处理）与非法（逻辑错误，应当报警）——这个区分第 6 节讲幂等时还要用到。另外注意"播放"事件在停止态和暂停态下目标状态相同、动作不同（从头播 vs 续播），这就是 Mealy 机。

Mealy 机：动作挂在"转移"上

每次转移时做一次性的事：按暂停时"记住进度"，按播放时"从头或续播"。工程实践中绝大多数业务状态机都是 Mealy 型。

Moore 机：动作挂在"状态"上

进入状态后持续表现出某种行为："播放中"持续解码出声，"暂停中"持续定格画面。硬件控制（红绿灯本体）更常见。

3. 状态图与转移表：电商订单

播放器太小，承载不了守卫、终态与并发这些真实问题。从本节起换用电商订单生命周期作为贯穿全文的主力例子——先画图、再写成表，图和表就是转移函数 δ 本身。

看图就能问出关键问题（这正是状态图的价值）：已支付的"取消"带守卫——必须尚未发货；待支付的取消可能来自用户点击，也可能来自支付超时定时器，事件不只来自用户操作；COMPLETED 是终态，若产品要求"确认收货后 7 天无理由退货"，就得把"已收货"与"已完成"拆成两个状态——终态选在哪里，本身就是设计决策。

转移表（转移函数 δ 的表格形式）

当前状态 \ 事件支付成功发货确认收货申请退款退款成功驳回申请取消
PENDING_PAYMENT 待支付PAID—————CANCELLED
PAID 已支付—SHIPPED————CANCELLED（守卫：未发货）
SHIPPED 已发货——COMPLETEDREFUNDING（守卫：限 N 天内）———
REFUNDING 退款中————REFUNDEDSHIPPED（回退）—
COMPLETED / CANCELLED / REFUNDED终态：表中不存在任何条目，任何事件都无合法流转

表中"—"表示该组合非法：收到该事件应当拒绝、忽略或报警，而不是"顺手改一下状态"。守卫是转移前的附加条件，写在单元格里只是便于评审，工程上由代码在触发转移前校验（见 5.3）。

4. 隐式状态机：最常见的反面形态

很多系统"其实已经是状态机"，只是转移规则没有定义在任何地方——它们散落在各个 Service 的 if/else 里。

症状一：枚举只定义了状态集 S，没有定义转移 δ

public enum OrderStatusEnum {
    PENDING_PAYMENT(0, "待支付"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货"),
    COMPLETED(3, "已完成"),
    CANCELLED(4, "已取消"),
    REFUNDING(5, "退款中"),
    REFUNDED(6, "已退款");
    // ……只有状态集合 S，"哪些流转合法"没有定义在任何地方
}

症状二：判断"处于哪一组状态"的 if 链散落各处

// 散落在各处的判断：哪些状态算"已完结"、哪些还能退款，全靠人脑记
if (COMPLETED != order.getStatus()
        && CANCELLED != order.getStatus()
        && REFUNDED != order.getStatus()) {
    // ……这里到底允不允许退款？读代码的人不知道，写代码的人过俩月也不知道
}

问题一：无人能回答全貌

"已发货的订单能不能取消"的答案散落在几十个文件里，只能靠通读代码或线上踩坑才能知道。

问题二：加状态要改 N 处

新增一个状态（例如"部分退款"），所有判断"订单是否已完结""是否可退款"的 if 链都要挨个排查，漏一处就是线上 bug。

问题三：并发不安全

用户点"取消"和支付网关回调几乎同时到达，两个请求都读到"待支付"、都判断自己合法、都去更新——已取消的订单被改成已支付。

判断标准：当 status != A && status != B && status != C 这种"判断当前是否处于某一组状态"的代码出现超过两处时，就该引入状态机了。状态机的解法就是把 δ 从代码角落里提出来，显式写成一张表，让非法流转在物理上不可能发生。

5. Java 实现的四种姿势

由浅入深：枚举内聚 → 表驱动 → 状态模式 → 框架。绝大多数场景前两种就够用。

5.1 枚举内聚式：把"下一步能去哪"放进枚举 零依赖 · 首选起步

改动最小，一眼看清全部流转。局限：表达不了"事件"和"守卫"维度。

public enum OrderStatusEnum {

    //                                        合法的下一步（终态集合为空）
    PENDING_PAYMENT(0, "待支付",  EnumSet.of(PAID, CANCELLED)),
    PAID(1, "已支付",             EnumSet.of(SHIPPED, CANCELLED)),
    SHIPPED(2, "已发货",          EnumSet.of(COMPLETED, REFUNDING)),
    REFUNDING(3, "退款中",        EnumSet.of(REFUNDED, SHIPPED)),
    COMPLETED(4, "已完成",        EnumSet.noneOf(OrderStatusEnum.class)),
    CANCELLED(5, "已取消",        EnumSet.noneOf(OrderStatusEnum.class)),
    REFUNDED(6, "已退款",         EnumSet.noneOf(OrderStatusEnum.class));

    private final int type;
    private final String desc;
    private final Set<OrderStatusEnum> nextStates;

    OrderStatusEnum(int type, String desc, Set<OrderStatusEnum> nextStates) {
        this.type = type;
        this.desc = desc;
        this.nextStates = nextStates;
    }

    /** 状态转移的唯一入口，业务代码必须经过它 */
    public OrderStatusEnum transferTo(OrderStatusEnum target) {
        if (!nextStates.contains(target)) {
            throw new IllegalStateException(
                desc + " 不允许流转到 " + target.desc);
        }
        return target;
    }
}

于是散落的判断收敛成一行：order.getStatusEnum().transferTo(CANCELLED)。非法流转直接抛异常——在物理上不可能发生，而不是靠程序员记得写判断。

5.2 表驱动式：把 δ 写成数据 工程上最实用

引入事件枚举后，转移规则变成一张真正的表：规则与执行彻底分离，看一张表就能评审全部流转逻辑。

public enum OrderEvent {
    PAY, SHIP, CONFIRM, APPLY_REFUND, REFUND_APPROVE, REFUND_REJECT, CANCEL
}

public final class OrderStateMachine {

    private static final Map<OrderStatusEnum, Map<OrderEvent, OrderStatusEnum>> TABLE =
        Map.of(
            PENDING_PAYMENT, Map.of(PAY, PAID, CANCEL, CANCELLED),
            PAID,            Map.of(SHIP, SHIPPED, CANCEL, CANCELLED),
            SHIPPED,         Map.of(CONFIRM, COMPLETED, APPLY_REFUND, REFUNDING),
            REFUNDING,       Map.of(REFUND_APPROVE, REFUNDED, REFUND_REJECT, SHIPPED)
        ); // COMPLETED / CANCELLED / REFUNDED 不在表中 = 终态，任何事件都转不出去

    private OrderStateMachine() {}

    /** 返回目标状态；表中不存在即为非法转移。守卫（如"退款限 N 天内"）在调用前校验 */
    public static OrderStatusEnum fire(OrderStatusEnum current, OrderEvent event) {
        OrderStatusEnum next = TABLE
            .getOrDefault(current, Map.of())
            .get(event);
        if (next == null) {
            throw new IllegalStateException(
                "状态[" + current + "]收到事件[" + event + "]无合法流转");
        }
        return next;
    }
}

5.3 状态模式（GoF）：每个状态一个类 状态行为差异大时

当各状态不只是流转不同，而是同一操作在不同状态下行为完全不同时使用。守卫在这种写法里最自然。缺点是类多，状态多而行为简单时不划算。

public interface OrderState {
    void onEvent(OrderContext ctx, OrderEvent event);
}

public final class ShippedState implements OrderState {
    @Override
    public void onEvent(OrderContext ctx, OrderEvent event) {
        switch (event) {                    // 只需处理本状态关心的事件
            case CONFIRM      -> ctx.setState(new CompletedState());
            case APPLY_REFUND -> {
                if (!ctx.withinRefundWindow()) {     // 守卫：发货后 N 天内
                    throw new IllegalStateException("已超过可退款时限");
                }
                ctx.setState(new RefundingState());
            }
            default -> throw new IllegalStateException("已发货状态下不接受事件 " + event);
        }
    }
}

public final class CompletedState implements OrderState {
    @Override
    public void onEvent(OrderContext ctx, OrderEvent event) {
        // 终态：任何事件一律拒绝，订单不可能"复活"
    }
}

5.4 框架：Spring StateMachine 超复杂长流程才用

状态多到几十个、出现子状态（如"已发货"内部又分拣货/出库/运输）、或流程横跨数天与多个服务（如订单履约全链路）时，才值得引入框架。它提供层次状态、转移监听器、持久化与恢复（StateMachinePersister）等能力。不建议一上手就用框架——表驱动能解决八成问题，且人人看得懂。

选型速查

场景特征推荐实现理由
流转简单、无事件维度枚举内聚零依赖、零学习成本，规则跟着枚举走
事件多、规则需要集中评审表驱动规则即数据，一张表覆盖全部流转
各状态下行为差异巨大、守卫多状态模式面向对象封装，新增状态不改旧状态
层次状态 / 超长流程 / 跨服务Spring StateMachine框架自带持久化恢复、监听器、子状态

6. 生产环境最佳实践

写对转移表只是及格线；真正的坑在并发、持久化、幂等这些"写代码之外"的地方。

6.1 并发转移：用条件更新（CAS）兜底 最重要

转移表只保证"逻辑上合法"，但用户点"取消"和支付网关回调几乎同时到达时，两个请求都读到"待支付"、都判断自己合法。落库时永远用条件更新，这是分布式环境下最可靠的状态转移方式：

-- 条件更新（CAS）：影响行数为 0，说明状态已被并发请求改走
UPDATE orders
SET status = #{newStatus}, update_time = NOW()
WHERE id = #{id} AND status = #{oldStatus};
int rows = orderDao.compareAndSwap(orderId, current, next);
if (rows == 0) {
    // 状态已被别人改走：重查当前状态，再决定重试、忽略还是报错
    // 典型场景：取消请求 vs 支付回调赛态，CAS 保证只有一方成功
    return handleConflict(orderId, event);
}
// rows == 1 才继续执行动作：扣库存、发短信、推进下游

口诀：状态机（逻辑合法）+ 条件更新（物理互斥）= 完整方案，两者缺一不可。

6.2 持久化与恢复

状态必须落库。服务重启后从库里恢复当前状态继续推进，而不是重置。批量退款、批量发货这类长周期异步任务的标准形态：批次表 + 子任务表构成"可恢复的持久化状态机"。

6.3 幂等

支付网关的重复通知（至少一次投递）、用户双击按钮、MQ 重发——同一事件第二次到来时，若当前状态已"消化"过它，应安全忽略而不是重复流转。转移表天然帮你判断：已支付状态再次收到 PAY，表中查不到合法流转，走忽略分支即可。

6.4 终态封闭

COMPLETED、CANCELLED、REFUNDED 这类终态的 next 集合必须为空，任何事件都转不出去。"已取消的订单又变成已支付"这类事故的根源就是终态没有封闭。

6.5 流转审计

单独记录每一步流转 (from, event, to, operator, time)。支付回调乱序、重发、运营人工改单常态化的场景下，能完整回放问题是救命的能力。

7. 落地检查清单与适用边界

引入状态机前先对照这两张清单，避免过度设计，也避免漏掉关键防线。

落地检查清单

  • 状态和事件先画图、写表、评审，再动手写代码
  • 转移规则只有一处定义（枚举 next 或转移表），禁止散落 if
  • 所有转移经过唯一入口（transferTo / fire）
  • 落库一律条件更新（CAS），返回 0 行视为冲突处理
  • 终态 next 集合为空，任何事件不可转出
  • 重复事件幂等：已消化的事件直接忽略，不报错不重放
  • 状态持久化 + 重启恢复，不靠内存续命
  • 流转写审计日志，出问题可回放
  • 新增状态时：图 → 表 → 单测三处同步改

什么时候不需要状态机

  • 状态只有两三个、流转毫无约束（如启用/停用开关）——直接写就行
  • 纯 CRUD 的简单字段，没有并发修改与审计诉求
  • 取值是连续数据而非离散模式（如温度、进度百分比）——那不是状态机要解决的问题

适用判断一句话：状态数有限（通常 < 20）、流转有严格约束、存在并发修改、需要审计回放——满足两条以上，状态机就开始回本了。

8. 练习

检验是否真正掌握：三道题分别对应画图、实现和守卫/并发。

  • 补图：电商常把"确认收货"与"已完成"拆开（已收货 → 待评价 → 已完成，评价完成才终态）。把"已收货""待评价"补进第 3 节的状态图与转移表；想一想：终态从"收货即完成"变成"评价后完成"，哪些已有代码的假设会被打破？
  • 实现：用表驱动方式实现 fire()，并为每个状态编写非法转移的单元测试——终态收到任何事件必须抛异常；PAID 收到取消事件必须先过"未发货"守卫。
  • 思考：用户点"取消"和支付回调几乎同时到达，CAS 之后必有一方失败——失败的那一方该怎么处理？重试、报错还是静默忽略？另外，"退款中"买家主动撤销退款申请，应该回到哪个状态（回退边）？需要定义什么新事件？
