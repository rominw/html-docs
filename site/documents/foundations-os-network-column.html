01CPU 很快，程序为什么仍会被内存拖慢？

记忆关键词： 局部性 · 缓存层级 · 工作集 · 延迟与带宽

先这样回答：CPU 执行指令的速度不等于获取数据的速度。缓存利用时间和空间局部性减少昂贵访问；程序是否快，取决于工作集、访问模式和实际瓶颈。

机制与边界

顺序遍历连续数组通常更容易利用缓存行与预取；追逐链表指针需要等待下一地址，可能形成串行依赖。缓存容量、关联冲突和并发访问都会影响命中率，不能只根据算法的大 O 比较真实耗时。

延迟描述一次访问等待多久，带宽描述单位时间搬多少数据。多核扫描大数组可能耗尽内存带宽；增加线程不能让共享带宽无限增长。

例子与时序：同样访问一百万个元素，数组顺扫与随机索引可能有不同缓存行为；这是待测的机制假设，不是固定倍数的性能承诺。

追问接答：“缓存越大越快？”还要看访问延迟和工作集。“把所有数据预加载？”会竞争容量，也增加分配与生命周期成本。

如何验证：固定数据量与业务结果，分别测顺扫、乱序和多线程；同时记录吞吐、CPU、缓存未命中与内存带宽，避免只比较一次耗时。

02两个线程改不同变量，为什么也可能互相拖慢？

记忆关键词： 独立变量 · 同一缓存行 · 一致性争用 · 布局/分片

先这样回答：这可能是伪共享：逻辑上独立的可写数据处在同一缓存行，不同核反复争取写入所有权。没有共享业务变量，也可能共享硬件一致性粒度。

机制与边界

假设两个热点计数器落在同一条缓存行，核 A 改第一个、核 B 改第二个，缓存行会产生一致性通信与所有权转移。真实共享是争同一个逻辑对象，伪共享则是数据布局造成的额外争用。

可尝试按线程分片、降低共享写频率或隔离热点字段，但会增加空间、汇总成本与布局依赖。常见缓存行大小不能直接当作所有架构、所有运行时对象布局的保证。

例子与时序：每线程累加本地计数，最后汇总，可以减少共享写；运行中的分片总和未必是同一时刻的原子快照，不能直接用于严格额度裁决。

追问接答：“加 volatile 就能修复？”可见性不会消除缓存行争用。“字段填充一定有效？”要验证真实布局与优化结果。

如何验证：用相同工作量比较相邻计数、隔离布局与分片；检查编译优化、核数和实际布局，不能把无竞争的单线程结果当证据。

03缓存一致性、内存屏障、语言内存模型是一回事吗？

记忆关键词： 单位置一致性 · 跨位置顺序 · 编译器 · 发布关系

先这样回答：缓存一致性协调同一位置的观察，内存顺序还涉及多个位置、编译器和处理器。应用要依赖语言规定的同步关系，不能拿某台机器上的观察替代正确性证明。

机制与边界

发布一个对象包含“写数据，再发布可见标志”。读取方应通过相应同步手段观察发布，再使用数据。没有正确关系，跨位置观察可能不符合源码直觉；编译器也可以作不改变单线程语义的优化。

屏障限制某类访问重排或观察顺序，不自动把整个业务动作变成原子操作。Java volatile、C/C++ 原子、内核屏障属于不同契约层，不能逐字照搬；要从所用语言与 API 推导。

例子与时序：读取方先读数据、后检查发布标志，可能已经错过保护该次读取所需的顺序。改变代码顺序后“暂时没出错”，也不是反例不存在的证明。

追问接答：“CPU 缓存一致就不需要锁？”不成立，跨变量不变量与读改写仍需同步。“屏障会把所有缓存都清空？”不是通用模型。

如何验证：画出发布方写入、同步动作、读取方观察和数据读取的关系；使用对应语言的并发测试工具，明确压力测试只辅助验证，不替代模型证明。

04count++ 为什么不是原子操作？原子指令又为什么不是事务？

记忆关键词： 读 → 算 → 写 · 丢失更新 · 原子边界 · 多字段不变量

先这样回答：count++ 是读改写组合，多个线程可能覆盖结果。原子类或指令保护指定操作，但两个原子字段各自安全，不等于它们之间的业务约束也安全。

机制与边界

A、B 都读到 10，各算出 11 并写回，最后是 11 而非 12。锁可覆盖整段临界区，原子读改写可裁决某个状态位置；关键是把需要同时成立的条件纳入同一保护边界。

从余额 A 扣款和给 B 加款，是跨状态的不变量。分别对两个字段做 CAS，不能自动得到全部成功或全部回滚；还要考虑失败恢复、死锁与外部副作用。

例子与时序：库存条件扣减要把“库存足够”和“减一”合成一个裁决；若先读取再原子覆盖固定结果，仍可能丢失更新。

追问接答：“64 位读写不撕裂就足够？”不撕裂不是复合原子。“所有问题都用 CAS？”竞争重试、ABA 和跨对象约束仍要处理。

如何验证：手算两个参与者的读写交错，再明确采用原子读改写或锁后的线性化点；单次运行碰巧得到正确总数不能证明无竞态。

05程序、进程、线程和协程分别是什么？

记忆关键词： 程序是代码 · 进程是资源环境 · 线程是执行流 · 协程由运行时调度

先这样回答：程序是静态代码与数据，进程是运行中的资源环境，线程是执行流。协程把可挂起的执行上下文交给运行时管理，但最终仍需要操作系统线程执行指令。

机制与边界

同进程线程共享地址空间、文件描述符等资源，各自保存执行上下文与栈。进程通常有独立地址空间，仍可通过共享映射或 IPC 通信；隔离不是“不可能共享”。

协程是否可迁移、如何调度以及阻塞调用如何处理，取决于运行时。await 暂停后续执行，不自动使 CPU 密集代码并行，也不保证任何阻塞调用都能释放底层线程。

例子与时序：一个事件循环处理一千个等待中的网络请求，不代表一千个 CPU 任务在同时执行；一个长时间 JSON 转换仍可能拖住同线程的其他回调。

追问接答：“多进程一定比线程慢？”要看隔离、IPC 和工作量。“协程都是栈复制？”实现可用不同策略，先说明运行时。

如何验证：分别增加等待时间与纯计算量，观察并发数、线程数、事件循环延迟和 CPU；不要把等待并发与计算并行混成一个数字。

06系统调用、用户态/内核态切换和上下文切换有什么区别？

记忆关键词： 权限边界 · 内核执行 · 任务切换 · 保存状态 · 缓存影响

先这样回答：系统调用让当前执行流请求内核服务，不必然换成另一个任务。上下文切换是调度到不同执行任务，需要保存与恢复状态；两种成本会相互影响，却不是同一件事。

机制与边界

read、write、socket 等接口进入内核执行相关操作；数据已经可用时，调用可能返回而不发生任务切换。若要等待 I/O，调度器可以让别的任务运行，之后再恢复等待者。

任务切换会处理寄存器、栈与调度状态；跨地址空间切换还涉及映射上下文。TLB、缓存和分支预测受到的影响随硬件与路径变化，不是每次都把全部缓存清空。

例子与时序：读内存中的缓存数据和等待远端报文，虽然都可能经过 read，产生的等待与切换行为不同。优化要先确认时间花在内核工作、调度还是业务处理。

追问接答：“一次系统调用等于两次线程切换？”错误。“减少 syscall 一定更快？”批处理可能增加等待、内存与延迟。

如何验证：结合系统调用采样、上下文切换速率与线程栈，比较相同吞吐下的变化；采样或跟踪本身有开销，先在受控环境观察。

07CPU 低但负载高，或者机器空闲却被限速，怎么解释？

记忆关键词： 可运行 · 不可中断等待 · load 非 CPU% · 配额 · throttling

先这样回答：Linux load average 不是 CPU 使用率：它包含可运行任务及部分不可中断等待。容器还可能受 CPU 配额限制，宿主机有空闲不代表该容器有可用预算。

机制与边界

可运行不等于正在运行，线程可能排队等 CPU；不可中断等待常与内核等待路径相关，但不能只凭 D 状态就断定某块磁盘故障。需要结合 I/O、调用栈与持续时间定位。

CPU 配额限制在时间窗口内可消耗的执行预算，权重则影响竞争时的分配。cpu.stat 的节流统计、祖先限制和部署策略要一起看，不能套一个“核数×线程数”公式。

例子与时序：服务有 32 个忙碌线程，但容器仅获约 2 核预算，更多线程可能增加排队与切换；持续限速会拉长延迟，即使宿主机总 CPU 不高。

追问接答：“load 超过核数一定报警？”要看是否持续及等待来源。“线程 RUNNABLE 就正在烧 CPU？”语言运行时状态与 OS 状态也不能直接一一对应。

如何验证：同时记录 CPU 使用、可运行队列、切换、I/O 等待及 cgroup 节流；以同负载调整单个限制，验证尾延迟与节流是否同向变化。

08fork、exec、IPC 和优雅退出，怎样连成完整生命周期？

记忆关键词： 创建 → COW → 替换映像 → 通信 → 停受理 → 排空/恢复

先这样回答：fork 创建子进程，Linux 常以写时复制避免立即复制全部私有页；exec 替换当前进程的程序映像。运行后通过 IPC 协作，退出前还要处理受理、在途任务和结果恢复。

机制与边界

COW 将复制成本推迟到相关私有页被写时，页表与任务结构仍有成本；共享映射另有语义。多线程进程 fork 后，子进程只保留调用线程，继承的锁状态使 exec 前可安全调用的操作受到限制。

管道、Unix socket、共享内存等有不同边界与同步成本，共享内存不会附赠互斥。优雅退出通常先停止接收新任务，再在预算内排空、记录未知结果和释放资源；SIGKILL 不能指望 finally 收口。

例子与时序：父进程写时复制快照期间持续修改大量页，可能增加实际内存；服务被强制终止后，远端已完成的退款并不会被本地退出自动撤销。

追问接答：“exec 会启动新 PID？”不是通常语义。“发送 SIGTERM 就一定优雅？”还取决于处理器、超时和编排器的强杀行为。

如何验证：在测试环境观察创建、写入与退出的资源变化；分别测试排空成功、排空超时和强制终止，核对已受理任务是否有可查询结果。

09互斥锁、信号量、条件变量分别保护什么？

记忆关键词： 锁保临界区 · 信号量保许可 · 条件变量等谓词 · 醒后重查

先这样回答：互斥锁保护共享状态的临界区，信号量管理一定数量的许可，条件变量用于等待受锁保护的业务条件。唤醒只表示可以重新检查，不是业务条件已经永久满足。

机制与边界

消费者发现队列空，应在持锁检查后使用条件等待；等待操作按其契约释放锁，返回前重新获得锁。使用循环重查，因为有虚假唤醒，也可能被其他消费者先取走数据。

信号量可限制远端调用并发，但所有入口都必须遵守，异常路径也须归还许可。锁的范围应覆盖同一个不变量，不能一处写字段 A、一处只锁字段 B。

例子与时序：库存剩一件，两个等待线程都被唤醒；第一个取得锁后消费库存，第二个醒来仍应发现库存为空并继续等待，而不是凭通知再扣一次。

追问接答：“notify 等于交出锁？”不是。“信号量限制线程总数？”只限制遵守该许可协议的操作范围。

如何验证：测试虚假/重复通知、多个消费者争同一资源、异常归还与超时；核对许可数和业务状态都不会漂移。

10CAS、自旋、ABA 与版本号有什么关系？

记忆关键词： 比较并交换 · 失败重试 · ABA · 版本绑定 · 竞争成本

先这样回答：CAS 原子比较当前值与预期值，匹配才更新。它能构建某些无锁算法，但业务仍要处理重试、状态历史和资源生命期；看到 A 不代表从未变化过。

机制与边界

A→B→A 后，只比当前值的 CAS 可能成功，却无法察觉中间发生过变化。把版本与状态放在同一原子比较边界，可区分历史；分两次读取版本和值则重新引入竞态。

自旋适合预计很短、竞争有限的等待；长时间无效重试会占 CPU。算法还要处理节点回收、版本回绕和进展保证，不能把“用了 CAS”直接称为整套系统无锁。

例子与时序：任务状态再次回到 READY，不代表它还是第一次的任务版本。迟到执行者应比较任务版本与持有身份，避免覆盖新一轮结果。

追问接答：“版本号解决所有问题？”还需原子绑定和寿命管理。“高竞争就继续自旋？”可改退避、分片或锁，取舍要实测。

如何验证：刻意安排 A→B→A，再让旧观察者提交；验证原子版本校验会拒绝。记录竞争下的失败重试、CPU 与吞吐。

11死锁、活锁、饥饿怎样区分？

记忆关键词： 等待环 · 重试无进展 · 长期拿不到 · 资源图 · 进展指标

先这样回答：死锁是相关任务相互等待而无法推进，活锁是持续动作却没有有效进展，饥饿是某个任务长期得不到资源。它们的现象、证据与修复方法不同。

机制与边界

常见死锁讨论关注互斥、占有并等待、不可抢占、循环等待；实际排查要画线程持有与等待的资源图。统一锁顺序、缩短持锁范围或失败时释放资源，才是针对依赖环的措施。

双方检测冲突后同时退让、又同时重试，可能形成活锁；退避与明确裁决帮助打破同步重试。资源总被高优先级任务抢走则可能饥饿；单个任务等待时长比系统总吞吐更能暴露它。

例子与时序：A 持锁 X 等 Y，B 持 Y 等 X，是等待环；两个客户端反复撤销彼此的预约而无人完成，是有动作但无进展。

追问接答：“超时即可恢复？”超时能退出等待，不自动回滚已发生的副作用。“公平锁绝无饥饿？”还要看调度和旁路获取策略。

如何验证：重复抓取等待栈，画资源依赖；同时监控重试次数、任务完成数和最大等待时间，区分忙碌与真实进展。

12线程、协程都便宜了，为什么还必须限制队列与并发？

记忆关键词： 到达率×停留时间 · 在途数量 · 下游上限 · 有界排队 · 受理语义

先这样回答：执行上下文更便宜，不会让数据库、带宽、内存和远端容量无限增长。并发限制与队列容量应由完整链路的资源预算决定，而不是只看线程是否创建得出来。

机制与边界

在稳定系统的平均量关系下，在途数量约为到达率乘停留时间。每秒 200 个请求、平均停留 0.5 秒，约有 100 个在途请求；这不是直接设成 100 个线程的公式，也不描述突发和 P99。

请求变慢会增加在途量，重试又抬高实际到达率。队列必须有长度与等待预算，过载时明确拒绝、降级或持久受理；仅把同步等待改成无界异步队列，只是换个位置积压。

例子与时序：数据库只有 30 个连接，放入一万个协程查询不会得到一万个数据库并发；大量等待者还会保留参数、缓冲和超时状态。

追问接答：“池最大 10 就是下游硬上限？”提交线程执行或旁路调用可突破；限制必须放在共享调用边界。“超时后资源都释放？”需要底层协作取消与清理。

13虚拟地址、页表、TLB 和缺页怎样协作？

记忆关键词： 虚拟页 → 地址翻译 → 物理页；TLB 未命中不等于缺页

先这样回答：程序使用虚拟地址，页表描述映射与权限，TLB 缓存地址翻译。TLB 未命中可能通过页表遍历解决；缺页则由内核处理缺少有效映射或权限等情况，二者不能混为一谈。

机制与边界

地址可以拆为虚拟页号和页内偏移，翻译后得到物理页框加偏移。页表存在不代表所有页已经驻留；首次访问匿名页、文件映射和写时复制都有不同处理路径。

缺页不必是错误或磁盘读取：可在已有内存页上建立映射，也可能需要从后备存储读取；非法访问或文件映射异常则可能变成进程信号。大小页、TLB 与 NUMA 优化均有适用条件。

例子与时序：申请一大段地址后只触碰少量页，虚拟大小与驻留大小可能差很多。再逐页写入，内存、缺页和执行时间才可能明显改变。

追问接答：“minor fault 完全没成本？”仍有内核工作。“每次 TLB miss 都读磁盘？”错误。“大页总更好？”还要看碎片、回收与停顿。

如何验证：区分虚拟映射大小、RSS、minor/major faults；对照首次触碰与再次访问，不把文件页已缓存的试验当冷盘结果。

14malloc 成功、RSS 增长与写时复制，为什么不是同一事件？

记忆关键词： 地址保留 · 实际触碰 · RSS · COW · 共享页计量

先这样回答：分配成功不一定立即使相同大小的物理页驻留。实际访问、分配器行为与系统策略决定内存变化；COW 还会在写入时把原来共享的私有页分离。

机制与边界

分配器可复用已有区域或建立新映射，释放给分配器也不保证立刻归还操作系统。因此 RSS 不回落，可能是活对象、碎片、分配器保留或共享/文件映射，不可只凭一条曲线认定泄漏。

fork 后的相关私有页可先共享，某一进程写入时复制。RSS 对共享页的计量不适合直接跨进程相加当物理总量；PSS 按共享比例分摊，但同样应说明口径。

例子与时序：进程释放一批对象后，业务对象数下降而 RSS 仍高；应先查看映射和分配器，再决定是否为无界持有。相反，持续写 COW 页会增加实际内存压力。

追问接答：“malloc 成功说明以后访问都安全？”系统仍可能缺乏资源。“RSS 相加就等于容器用量？”共享、内核与其他计费维度使口径不同。

如何验证：在测试环境记录申请、触碰、释放三个阶段的对象数与 smaps；区分 RSS/PSS 和 cgroup 用量，避免用进程求和替代容器计费。

15Java 堆只用了一半，容器为什么会 OOMKilled？

记忆关键词： 容器总量 · 堆外/线程/文件页 · cgroup 证据 · 非只有 Xmx

先这样回答：容器限制覆盖的内存不只有 Java 活对象。堆、线程栈、直接与原生分配、相关文件页和内核计费都可能影响总量；OOMKilled 与 Java 抛出 OutOfMemoryError 是不同路径。

机制与边界

Xmx 是堆上限，不是整个进程或容器的上限；堆已提交空间与堆使用空间也不同。内存预算要给元数据、代码、线程、缓冲和负载峰值留空间，不能简单把 Xmx 等于容器限制。

cgroup v2 可结合 memory.current、memory.stat 与 memory.events 分析；实际部署也可能使用其他版本与层级。退出码 137 只提示被 SIGKILL 终止的常见编码，还需 OOM 事件证据，手工强杀也可能同码。

例子与时序：慢客户端让输出缓冲积压，活对象可能增长；线程暴涨会增加栈与运行时开销；大量文件 I/O 还会改变文件页计费。三者不能都用“GC 没回收”解释。

追问接答：“NMT 能解释全部 RSS？”只覆盖其可追踪部分。“减 Xmx 必然治本？”可增加余量，但无界缓冲和原生泄漏仍需修复。

如何验证：对齐被杀前的容器用量、事件、堆提交/使用、线程数与原生指标；在受控环境限制单类资源，验证其变化是否解释峰值。

16怎样区分内存泄漏、缓存增长、队列积压和回收压力？

记忆关键词： 持有链 · 业务寿命 · 有界策略 · 流入/流出 · 回收后基线

先这样回答：泄漏要证明不再需要的资源仍持续被持有；缓存可能有用却无界，队列则可能因生产快于消费而积压。它们都能耗尽内存，但修复点不同。

机制与边界

把内存曲线与任务量、缓存条目、队列长度、线程和连接生命周期对齐。回收后基线持续升高是线索，不是根因；需要找到持有者以及本应释放的时刻。

页缓存增长和分配器保留可能具有可回收性；持续回收、换入换出或缺页也会拖慢业务。不要看到 free 很小就立刻认定泄漏，先看可用量、回收压力与服务延迟。

例子与时序：下游慢使请求在队列里保存大图片，消费恢复后内存回落，说明积压是关键；若已完成请求仍被监听器列表永久引用，则要修正注销与寿命管理。

追问接答：“堆里最多的类就是泄漏？”需看支配与引用链。“缓存有 TTL 就一定有界？”到达量、淘汰和过期清理也影响峰值。

如何验证：采样多个时间点的对象/映射与流量，再跟踪持有链；比较停止新增、排空与清理后的基线，避免仅截一张内存图。

机制与边界

例子与时序：事件循环收到可读通知后执行一次 recv 得到半个 JSON，这是正常情况。反复 busy-poll 非阻塞读，也不等于高效异步。

追问接答：“epoll_wait 会阻塞，所以是 BIO？”它可以等多个描述符事件，与每连接单线程等待不同。“有 Promise 就不占线程？”不能如此推出。

18select、poll、epoll 与 LT/ET，关键区别在哪里？

记忆关键词： 监视集合 · 就绪集合 · LT 条件仍在 · ET 状态变化 · EAGAIN

先这样回答：select/poll 在接口和遍历方式上与 epoll 不同；epoll 维护注册与就绪状态，避免每次由调用方重交并扫描全部监视项。规模优势不等于每次调用和事件处理都严格 O(1)。

机制与边界

LT 在就绪条件持续存在时继续报告；ET 按状态变化通知，不能依赖残余数据再次触发。常用正确路径是非阻塞读写并处理到 EAGAIN；大量数据需自行安排后续处理，兼顾公平。

epoll 返回可尝试的操作，不保证数据仍可读或已完成。select 的 fd 集合限制、poll 的数组成本和 epoll 的维护开销都需结合具体平台与活跃比例，不宜仅背“红黑树加链表”。

例子与时序：一次到达 2 KB，只读 1 KB 就回到 ET 等待，剩余数据可能无人继续处理。另一方面，不限量处理一个热点连接，也可能饿死其他连接。

追问接答：“ET 必比 LT 快？”取决于实现与负载。“惊群都消失了？”还要说明共享监听器、线程与事件配置，不能泛化。

如何验证：在 Linux 隔离环境复现短读、EAGAIN、关闭和单连接洪流，记录所有连接的进展；本页没有把这些内核实验当作已运行结果。

19Reactor、Proactor、事件循环和 io_uring，怎样分层理解？

记忆关键词： Reactor 等就绪 · Proactor 等完成 · 业务执行另层 · 支持按操作核对

先这样回答：Reactor 围绕就绪事件分发处理，Proactor 围绕操作完成分发处理。事件循环是执行与调度组织方式；具体 API 能否真正异步、如何回退，要看操作类型、内核与库实现。

机制与边界

Reactor 收到通知后通常由处理者读写；完成模型由提交与完成结果衔接数据状态。但模型名称不保证所有工作都在内核完成，也不保证一个线程不会被业务回调长时间占据。

io_uring 使用提交/完成队列组织请求，具体操作与执行路径随版本和配置变化，可能涉及内部工作线程。不能说它使所有磁盘操作都永不阻塞，或在任何负载下比 epoll 快。

例子与时序：网络收包走事件循环，压缩大文件若也在该线程执行，会拖住其他连接；移到有界计算池仍须安排结果回传与取消。

追问接答：“Node 单线程为什么能读文件？”要区分 JavaScript 回调、系统 I/O 与线程池路径。“把全部业务都异步化？”可能只是把等待转成排队。

如何验证：标出每一步的实际执行线程与队列；比较事件循环延迟、I/O 延迟、业务 CPU 与取消后的遗留工作，而非只比 API 返回速度。

20半包、短写和慢消费者，怎样保证完整消息与有界内存？

记忆关键词： 分帧状态 · 部分读写 · 长度上限 · 累计缓冲 · 背压/恢复

先这样回答：字节流读取块不是业务消息。接收端按协议累计并解析，发送端记录未写完的位置；双方限制帧长度、累计缓冲与等待时间，慢消费者时明确暂停、合并或恢复策略。

机制与边界

长度前缀协议先收够头，再校验长度并等待正文，解析完整帧后继续处理剩余字节。文本协议还要考虑字符跨块、多行与分隔符转义；不能对每个网络块直接 JSON.parse。

TCP 流控约束传输窗口，不阻止应用提前把一百万条消息放进自己的内存队列。背压应贯穿业务生产、框架缓冲与 socket，每连接和全局都要有上限。

例子与时序：两次 write 发出 A、B，接收可能得到半个 A，再得到剩余 A 加完整 B。若正文含中文，字符也可能跨读取块；先处理字节边界，再按协议解码。

追问接答：“write 返回成功等于对方业务成功？”不是。“缓冲超限直接丢最旧？”订单、聊天与遥测有不同丢弃契约，必须按业务决定。

如何验证：把同一报文按每个切割位置喂给解析器，测试多帧、非法长度、EOF 残留与慢消费。本章附可本地运行的字节分帧练习。

可运行练习：四字节长度头 + 原始字节正文

MAX_FRAME = 64 * 1024
MAX_BUFFER = 2 * MAX_FRAME + 8

class Decoder:
    def __init__(self):
        self.buffer = bytearray()

    def feed(self, chunk):
        if len(self.buffer) + len(chunk) > MAX_BUFFER:
            raise ValueError("buffer budget exceeded")
        self.buffer.extend(chunk)
        messages = []
        while len(self.buffer) >= 4:
            size = int.from_bytes(self.buffer[:4], "big")
            if size > MAX_FRAME:
                raise ValueError("frame too large")
            if len(self.buffer) < 4 + size:
                break
            messages.append(bytes(self.buffer[4:4 + size]))
            del self.buffer[:4 + size]
        return messages

    def finish(self):
        if self.buffer:
            raise EOFError("truncated frame")

def frame(payload):
    if len(payload) > MAX_FRAME:
        raise ValueError("frame too large")
    return len(payload).to_bytes(4, "big") + payload

expected = ["你好".encode("utf-8"), b"ok", b""]
wire = b"".join(frame(payload) for payload in expected)
for cut in range(len(wire) + 1):
    d = Decoder()
    assert d.feed(wire[:cut]) + d.feed(wire[cut:]) == expected
    d.finish()
d = Decoder()
actual = []
for value in wire:
    actual += d.feed(bytes([value]))
assert actual == expected
d.finish()

def rejects(error, operation):
    try:
        operation()
    except error:
        return
    raise AssertionError("expected rejection")

rejects(ValueError, lambda: Decoder().feed((MAX_FRAME + 1).to_bytes(4, "big")))
rejects(ValueError, lambda: Decoder().feed(bytes(MAX_BUFFER + 1)))
d = Decoder()
d.feed(wire[:2])
rejects(EOFError, d.finish)
print("All split positions, byte-by-byte input and rejection cases passed.")

机制与边界

用户态缓冲库可先把数据留在进程内，flush 将其交给更下层；常见 write 路径可在页缓存形成脏数据，内核随后回写。不能把这几层都称为一次“落盘”。

fsync 请求同步文件相关数据与元数据，fdatasync 对不影响数据检索的元数据有不同要求；目录项持久化还要考虑目录同步。直接 I/O、映射写与不同文件系统另有约束，不能机械套相同路径。

例子与时序：进程崩溃时 OS 缓存可能仍存在；断电则不同。实验仅杀进程后文件还在，不能据此证明写入已经满足断电恢复目标。

追问接答：“flush 一定是磁盘同步？”取决于库 API。“fsync 一次保证所有文件？”只覆盖相应对象与契约，跨文件业务原子性还需协议。

如何验证：分别设计进程退出与存储故障的恢复目标，核对返回值和恢复内容；把故障边界写清楚，不在生产机器直接做断电实验。

22文件描述符、打开文件状态、inode 和路径是什么关系？

记忆关键词： 路径查找 · inode 对象 · 打开状态 · fd 引用 · 生命周期

先这样回答：路径是查找名称，inode 标识文件系统对象，打开文件状态保存偏移等信息，fd 是进程使用的引用。删除路径不一定立即释放仍被打开的文件，复制 fd 也不一定产生独立偏移。

机制与边界

打开过程解析路径并关联底层对象；dup 或 fork 继承的描述符可引用同一打开文件状态，因而共享文件偏移与部分标志。不同 open 调用通常有各自的打开状态，不能只按文件名判断是否共用偏移。

unlink 去掉目录中的名称，但打开引用仍可继续使用对象；磁盘空间回收要等相关引用释放。socket、管道与普通文件都可表现为 fd，数量泄漏需要追到创建与关闭的责任方。

例子与时序：删除一个正在写入的大日志，目录看不到它，但进程仍持有 fd，磁盘空间可能没有释放。只继续删除路径不解决该打开引用。

追问接答：“close 一个复制 fd 就全释放？”还要看其他引用。“fd 数字一直指同一个连接？”关闭后可复用，异步事件要防旧身份误操作。

如何验证：在隔离环境核对 /proc/PID/fd 与打开对象，观察删除、dup、close 后的变化；不要凭 fd 数量直接认定所有长连接泄漏。

23mmap、sendfile 和零拷贝，究竟减少了哪一步？

记忆关键词： 映射非预加载 · 省用户态搬运 · 缺页成本 · 支持边界

先这样回答：mmap 将文件或其他对象映射进地址空间，sendfile 可减少文件到 socket 路径中的用户态搬运。零拷贝是优化路径的简称，不等于没有 DMA、内核处理、缺页或所有形式的数据复制。

机制与边界

映射后访问仍可能触发缺页；映射本身不保证文件已全部进内存或数据已持久。顺序、随机访问与工作集大小影响映射方案的表现，还要处理映射文件被截断等异常。

sendfile 避免常见 read 到用户缓冲再 write 的往返，但需处理短发送、阻塞/非阻塞与支持条件。加密、压缩、设备与库配置会改变优化能否应用，不固定承诺“四次变两次”。

例子与时序：静态大文件可受益于减少搬运；若业务必须逐字节转换内容，就可能仍需要处理缓冲。Kafka 的吞吐还涉及顺序 I/O、批量与页缓存，不只一个 API。

追问接答：“mmap 就不会 I/O？”错误。“HTTPS 必然不能优化？”要看实际 TLS 与内核路径，不能一刀切。

如何验证：固定文件与吞吐目标，比较 CPU、syscall、缺页、吞吐和首字延迟；冷热缓存分开，记录操作系统与加密配置。

24如何让配置文件替换同时考虑原子可见与崩溃持久？

记忆关键词： 同文件系统临时文件 → 完整写入 → 同步 → rename → 目录同步

先这样回答：原子替换名称与崩溃后保留结果是不同承诺。常见本地文件系统方案是写同文件系统临时文件、同步文件、rename 替换，再按所需持久性同步父目录，并处理每一步错误。

机制与边界

同文件系统 rename 可提供名称替换的原子观察边界，但不能只凭 rename 成功就忽略文件数据与目录项的持久性；跨文件系统也不能直接套该原子替换模型。

读者已打开旧文件可能仍读旧对象，新打开者读新对象，这是不同资源寿命。多个写者还要裁决版本与所有权；文件替换不自动构成数据库、文件和通知的联合事务。

例子与时序：先截断原配置再写新配置，进程中途退出可能留下半文件。临时文件方案应让读者见到完整旧版或完整新版，而不是混合字节。

追问接答：“有 journaling 就不用 fsync？”不是通用保证。“失败后删临时文件即可？”需区分替换是否已发生及读者可见状态。

如何验证：在各步骤设置中断点，检查重启后可见版本、校验和与残留文件；明确文件系统和故障类型，不把名称原子性写成全系统事务。

25从输入 URL 到服务处理，怎样按层追踪？

记忆关键词： URL/名称 → DNS → 路由/连接 → TLS → HTTP → 应用/存储

先这样回答：先区分应用语义、传输、网络与链路层，再沿真实路径追踪。URL 指明协议与资源，DNS 解析名称，路由决定下一跳，连接与 TLS 建立通信和身份边界，应用最后处理业务。

机制与边界

缓存、连接复用、代理、重定向和服务发现会跳过或增加步骤，因此并非每次请求都重新 DNS、TCP、TLS。HTTP/3 使用 QUIC 路径，不能强行套“任何 HTTP 都先 TCP 握手”。

REST 是接口设计风格，JSON 是数据表示，HTTP 是应用协议，TCP 是传输协议，IP 负责寻址与转发。把它们排成互相替代的选项，会混淆约定、封装和实现。

例子与时序：浏览器看到 HTTP 200，只证明某个应用响应了；响应可能来自缓存、网关或错误服务，仍须检查内容、版本和业务状态。

追问接答：“ping 通就能 HTTP 成功？”ICMP、TCP 端口、TLS 和应用是不同检查。“localhost 指同一台宿主机？”网络命名空间可能不同。

如何验证：画出浏览器、代理、负载均衡、服务与存储节点；为每一步标出名称、地址、协议、复用条件和可观察证据。

26DNS 怎样解析？TTL 能保证切换立刻生效吗？

记忆关键词： 本地/递归缓存 · 权威答案 · TTL · 负缓存 · 连接仍可复用

先这样回答：客户端常先问递归解析器，它可使用缓存或沿委派关系取得权威答案。TTL 管理记录缓存寿命，却不能保证所有应用和既有连接在某个瞬间统一切换。

机制与边界

递归解析器承担继续查询的工作，权威服务器给出所负责区域的信息；别把每次浏览器请求都画成亲自访问根、顶级域与权威。解析结果还可能包含别名、多地址、失败或负缓存。

OS、运行时、代理与连接池各自有缓存和重试行为。即使重新解析得到新地址，旧的长连接仍可能复用；更改 TTL 也不能倒退已经缓存记录的有效期。

例子与时序：发布后少量客户端仍访问旧节点，可能是旧 DNS 缓存，也可能只是旧连接。先区分查询结果、实际连接目标与缓存层，再决定是否排空旧节点。

追问接答：“DNS 只用 UDP？”也有 TCP 等路径。“低 TTL 必然解决故障切换？”会增加查询负载，应用复用与失败处理仍要设计。

如何验证：在同一环境分别记录解析器、返回记录与 TTL、运行时缓存和 socket 目标；比较新建连接与复用连接，避免只在自己电脑查一次 DNS。

27同网段与跨网段通信，为什么要先找到下一跳？

记忆关键词： 路由选择 → 下一跳 → 链路地址 → 逐跳转发；目标 IP 非每跳改写

先这样回答：发送端依据路由选择出口与下一跳。IPv4 常用 ARP 解析同链路下一跳的链路地址；跨网段通常先交给网关。IPv6 使用邻居发现，不能把 ARP 画成所有 IP 的共同步骤。

机制与边界

数据经过路由器时链路层封装会按下一链路重新组织，目的 IP 通常仍是最终目标；NAT 等机制才可能改写地址或端口。远端服务器 MAC 不必被客户端提前知道。

可达性还受路由、邻居状态、MTU、防火墙和策略影响。单个端点看见“已发出”，不能证明报文已经跨过每一跳，也不能证明返回路径与去程对称。

例子与时序：客户端访问外部服务时 ARP 查询的可能是网关，而不是远端服务的 IP。只在远端机器上找 ARP 记录，不能据此诊断客户端链路。

追问接答：“路由器每跳都改目标 IP？”不是普通转发语义。“大包超时、小包正常？”应考虑 MTU 与路径问题，也需实际证据。

如何验证：从所在网络命名空间检查路由与邻居，再在测试链路观察收发位置和包长；受限环境里 traceroute 无响应不能独立证明该跳丢业务报文。

28NAT、负载均衡、反向代理与可信身份分别管什么？

记忆关键词： 地址改写 · 四元组 · 转发/终止 · 信任边界 · 业务授权

先这样回答：NAT 改写网络端点，负载均衡选择后端，反向代理可能终止客户端连接后另建后端连接。它们改变路径和观察地址，不自动提供用户身份与资源授权。

机制与边界

TCP 连接常以源/目的地址和端口区分；代理前后的两段连接有各自的状态、超时与缓冲，前端已经断线时后端业务可能仍在执行。NAT 与中间设备还可能回收空闲状态。

Forwarded 或 X-Forwarded-For 等头只能在受控代理链规则下使用；来自客户端的任意同名头不应直接变成可信来源。业务仍须验证实际登录身份、租户、资源和动作权限。

例子与时序：客户端超时、网关连接已关闭，但服务仍提交订单；把网关断线当数据库回滚，会误导重试策略。代理日志中的地址也未必是原始客户端。

追问接答：“TCP keepalive 能保证应用活着？”它与业务健康不同。“来源 IP 合法就有权限？”身份、来源与授权需分别验证。

如何验证：画出每段连接的超时、缓冲与目标；测试空闲回收、客户端断开和伪造代理头，核对真实身份及最终业务结果。

29三次握手到底确认什么？TCP 可靠性怎样建立？

记忆关键词： 双方序号 · SYN/ACK · 字节确认 · 重传 · 有序交付

先这样回答：握手协商连接相关状态并同步双方初始序号，建立双向通信所需的序号空间。传输通过序号、确认与重传等机制恢复缺失并有序交付字节，不承诺任意故障下永久可达。

机制与边界

在常见主动连接路径中，SYN、SYN+ACK、ACK 使双方交换并确认序号。确认号通常指期望的下一字节；累计确认、重复确认和其他协商机制帮助判断已接收范围。

接收端 TCP 可去重与重排传输字节，但应用退出、连接重建和同一业务请求重发是另一层。应用确认也不同于 TCP ACK，不能因握手成功就假定业务已可用。

例子与时序：TCP 重传同一段数据通常不会让同一连接上的应用收到两份相同字节；客户端断线后重新发送整条“创建订单”请求，却可能产生第二次业务执行。

追问接答：“两次握手为什么不够？”按双方状态与旧报文影响推演，不只背“确认收发能力”。“ACK 后数据必已持久？”ACK 的承诺不是数据库提交。

如何验证：在测试环境观察 SYN、ACK、重传与应用记录的时间线；协议序号、请求身份和业务结果分别记录，不用抓包中的 ACK 代替业务证据。

30流量控制、拥塞控制、带宽和 RTT 如何联系？

记忆关键词： 接收窗口 rwnd · 拥塞窗口 cwnd · RTT · 在途容量 · 丢包非唯一信号

先这样回答：流量控制保护接收端容量，拥塞控制调节网络中的发送压力。发送还受到两类窗口、应用供给和路径约束；带宽大不意味着小请求延迟一定低。

机制与边界

接收窗口表达可接收范围，拥塞窗口根据相应算法与反馈演进。对在途数据的约束不能只看其中一个窗口，零窗口也不能简单归因网络带宽不足。

带宽延迟积帮助估计填满路径所需在途量，但 RTT、排队、损失、竞争与算法版本会改变行为。丢包可由拥塞或其他原因产生；应用 P99 还可能主要来自服务排队。

例子与时序：远距离链路带宽很高，却因往返等待和小请求交互而慢；增加带宽未必减少 DNS、握手、数据库和模型首字的等待。

追问接答：“TCP 有流控所以应用不会 OOM？”应用队列仍可无界。“BBR 对所有路径都更好？”版本、公平性与负载需要实测。

如何验证：按同一路径记录 RTT、重传、接收窗口、发送速率与应用排队；一次只改变一项，不把所有延迟变化都叫网络拥塞。

31TCP 粘包拆包，为什么本质是应用分帧问题？

记忆关键词： 字节流 · write/read 不对应 · 长度/分隔符 · 增量解析 · 长度护栏

先这样回答：TCP 不保留应用每次 write 的消息边界。所谓粘包和半包是应用把读取块误当成完整消息；解决方案是协议定义边界并增量解析，不是强行让发送间隔变大。

机制与边界

接收一次可能得到多条消息、部分消息或零字节 EOF 等情况；长度前缀、可转义分隔符和自描述编码是不同分帧方案。应用还要处理最大长度、超时和异常断开。

网络包、TLS 记录、HTTP 帧、业务消息与读取缓冲区是不同层的边界。关闭某种发送合并机制也不会让 read 次数与 write 次数建立可靠一一对应。

例子与时序：发送“3:abc”和“2:de”，接收可分成“3:a”“bc2:”“de”。解析器应输出 abc、de，而不是按三次读取生成三个业务事件。

追问接答：“sleep 一会儿就不会粘包？”不构成协议。“用 JSON 就有边界？”连续 JSON 仍需完整解析规则，换行也要定义转义。

如何验证：复用第 6 章分帧练习，在所有切割位置、多消息与非法长度下验证相同结果；不要仅在 loopback 上测一次正常收发。

32关闭连接、TIME_WAIT 和 CLOSE_WAIT 应该怎样排查？

记忆关键词： 双向半关闭 · 最后 ACK/旧报文 · TIME_WAIT · 应用未关闭的 CLOSE_WAIT

先这样回答：TCP 两个方向可以独立关闭，常见关闭路径中主动关闭方会经历 TIME_WAIT。CLOSE_WAIT 通常表示已收到对端关闭而本地应用尚未完成关闭，两者的责任与治理方式不同。

机制与边界

FIN 表示该方向不再发送字节，另一方向仍可发送；常说“四次挥手”是常见图示，报文可合并且存在同时关闭。TIME_WAIT 保护终止和旧报文处理，规范的 2MSL 与实际系统计时应区分。

大量 TIME_WAIT 可能只是高连接创建率；判断端口耗尽要看源 IP、目标地址/端口、临时端口范围和连接复用。CLOSE_WAIT 持续增长则应追本地 close 与异常清理责任。

例子与时序：每个请求新建短连接会积累 TIME_WAIT；客户端收到 EOF 却忘了关闭对象，则可能堆积 CLOSE_WAIT。二者不能用同一条“调小超时”处理。

追问接答：“TIME_WAIT 一定是客户端？”主动关闭角色由实际路径决定。“关 keepalive 就能修复？”可能让短连接更多，先明确参数含义。

如何验证：连续记录连接状态、创建率、fd 数与实际连接错误；核对主动关闭方和连接池回收，不直接套过时内核参数。

33TCP ACK、HTTP 响应、业务提交，哪个能证明操作成功？

记忆关键词： 字节确认 ≠ 业务提交 · 响应可丢 · 结果未知 · 原请求查证

先这样回答：TCP ACK 不等于业务提交，HTTP 响应的意义也由接口契约决定。服务可能已提交但响应丢失；客户端超时只说明未获得结果，不能据此认定未执行。

机制与边界

可靠受理、执行完成和持久提交是不同阶段；202 Accepted 通常只表示受理。即便返回成功结果，客户端是否实际收到与服务端提交之间仍有故障窗口。

有副作用的操作应绑定稳定请求身份、参数与结果记录；未知时按同一身份查询或受控幂等重试。若远端没有查询/幂等契约，需对账或人工处理，而不是生成新身份再执行。

例子与时序：退款已提交，服务在回包前断线；Agent 不应凭“工具超时”发起新退款。它应保留 actionId，查证原动作的真实结果并向用户展示未知状态。

追问接答：“TCP 不丢包还需要幂等？”传输可靠不覆盖应用重试与崩溃。“HTTP 200 就完成？”需看返回是否只是任务受理。

如何验证：在提交前、提交后回包前和客户端接收后分别注入故障；核对结果查询、同键异参拒绝和真实副作用次数。

34HTTP/1.1、HTTP/2、HTTP/3 分别改善哪种队头阻塞？

记忆关键词： H1 响应顺序 · H2 多路复用/TCP 阻塞 · H3 独立流 · 共享约束仍在

先这样回答：HTTP/2 用帧与流多路复用改善 HTTP/1.1 的应用层排队，但同 TCP 连接丢字节仍影响交付。HTTP/3 用 QUIC 流改善跨流传输阻塞，不代表没有拥塞、排队或头部依赖。

机制与边界

HTTP/1.1 的持久连接不等于任意交错响应；流水线仍有响应顺序约束。HTTP/2 在连接中交错多个流的数据，但底层 TCP 提供单一有序字节流，缺失字节可能挡住后续交付。

QUIC 在流内保留顺序，某一流的缺失数据不必按相同方式阻塞其他流；连接仍共享拥塞控制等资源，HTTP/3 的 QPACK 头部依赖也可能造成等待。UDP 只是承载，不等于 QUIC 不可靠。

例子与时序：大响应与小响应共享连接时，多路复用有助于交错；丢包、服务端 CPU 和业务并发限制仍可能使小响应延迟升高。

追问接答：“HTTP/2 保证请求并行执行？”协议允许交错，后端可串行。“HTTP/3 必须更快？”需看路径、连接复用、版本与服务瓶颈。

如何验证：同路径分别测冷建连、复用、大/小混合与损失条件；确认实际协商协议，避免把缓存命中或后端变化算成协议收益。

35HTTP 安全性、幂等性、缓存与业务去重是什么关系？

记忆关键词： 方法语义 · 同意图效果 · ETag 验证 · no-cache/no-store · 权限维度

先这样回答：安全方法的预期语义不修改目标资源，幂等方法重复执行的预期效果相同；它们不是“请求绝不会产生任何记录”或“业务自动防重”。缓存新鲜度、验证与授权是另一组契约。

机制与边界

GET 可有访问日志等附带效果，但不应把支付当作其资源操作；PUT 的幂等语义也需要服务实现遵守。POST 可通过应用幂等协议支持安全重试，不能仅凭方法名称判断实际副作用。

ETag 等验证器支持条件请求与 304；不带字段参数的 no-cache 表示复用前需要验证，不等于禁止存储，no-store 才表达不应存储的要求。个性化内容还需区分共享/私有缓存及影响表示的维度。

例子与时序：用户权限撤销后，旧页面缓存或旧 ETag 不能替代当前授权；更新订单时可用版本条件拒绝基于旧状态的覆盖。

追问接答：“幂等就每次响应一样？”可不同但预期效果相同。“304 说明当前用户有权看旧内容？”服务应先正确处理授权与表示。

如何验证：用重复请求、同键异参、权限切换和不同表示验证；分别记录缓存命中、重新验证、实际业务效果，避免只看 HTTP 状态码。

36TLS 握手、证书、SNI、ALPN 与 0-RTT 应该记住什么？

记忆关键词： 协商 → 身份验证 → 密钥 → 加密记录；SNI 选站 · ALPN 选协议 · 0-RTT 可重放

先这样回答：TLS 协商安全参数，并按所用模式验证对端身份，再保护传输数据。常见 HTTPS 校验服务器，客户端身份由业务认证或 mTLS 等机制处理；证书验证要检查信任链、名称和有效性，SNI 与 ALPN 分别帮助选择站点和应用协议。

机制与边界

以 TLS 1.3 常见证书握手为语境，双方协商密钥相关材料与协议参数，验证握手并建立保护；会话恢复与 QUIC 等路径有不同交互。通常用协商出的对称密钥保护数据，而不是每个业务字节都用证书公钥加密。

0-RTT 降低部分恢复连接的等待，但 early data 存在重放风险，业务应明确哪些动作可接受重放。TLS 保护这段通信，不保证明文离开终止代理后的链路、日志、模型上下文与数据库都受同样保护。

例子与时序：直接用 IP 访问多站点服务，可能命中错误站点或名称验证失败；排查时应保持实际 hostname、SNI 与验证边界，不用跳过证书验证掩盖原因。

追问接答：“HTTPS 所以不会越权？”认证链路与资源授权不同。“会话恢复等于所有写请求可 0-RTT？”必须按重放风险决定。

如何验证：记录证书链、名称、协商版本与 ALPN；测试过期、错误域名、恢复连接和允许的 early data，核对应用是否重复产生副作用。

37SSE、WebSocket、gRPC 和轮询，如何按需求选？

记忆关键词： 方向 · 频率 · 格式 · 基础设施 · 恢复游标 · 权威查询

先这样回答：先看通信方向、延迟、吞吐、客户端与恢复需求。SSE 适合服务端事件推送，WebSocket 支持双向消息，gRPC 提供 RPC 契约与流模式，轮询可简化状态查询；没有一个协议自动替应用补齐恢复。

机制与边界

SSE 基于文本事件流，空行标记事件边界，id 与重连机制还要配服务端历史才能补发。WebSocket 定义消息与控制帧，业务 ACK、鉴权、离线历史和重连恢复需另设计。

gRPC 能提供接口与消息契约，但浏览器接入、代理、deadline 和流控应核对实际栈。低频任务状态用有界轮询可能更简单；推送只做实时提示，持久任务状态负责查询与恢复。

例子与时序：AI 回答需要区分 token、工具状态与最终结果，连接断线时按 run 和游标恢复；另开一个连接从头启动模型，可能重复工具副作用。

追问接答：“SSE 就是每次 read 一条事件？”网络块不保边界。“WebSocket 已发送说明业务完成？”需定义 ACK 所确认的阶段。

如何验证：验证分块、重连、多实例、事件保留过期、客户端慢读和取消；比较用户感知延迟、结果一致与资源上限，不只测正常连接。

38连接池、各类超时和整体 deadline，怎样避免互相打架？

记忆关键词： 池等待 → DNS/建连 → TLS → 读写；整体预算 · 重试扣账 · 未知结果

先这样回答：连接复用减少建连成本，但池等待也会消耗请求预算。连接、读写、空闲与整体 deadline 的语义不同，必须按实际客户端核对，并让重试与下游调用共享剩余预算。

机制与边界

一个 read timeout 可能限制连续无数据的等待，不一定限制整个响应总时长；某些库的连接超时也不包含池获取或全部解析步骤。命名相似的配置不能跨库照抄。

上游超时不必然取消底层任务或远端操作，取消还需协作与清理。超时、熔断、入口限流和下游隔离分别解决不同问题；多层重试容易放大请求量。

例子与时序：总预算 2 秒，先在池等 1.5 秒，再按原始 2 秒调用下游，会突破整体预算；剩余时间不足时应按契约拒绝继续，而非每层重新起计时。

追问接答：“持续有少量字节就永不超时？”要看是否另设整体预算。“超时就可以换节点重发退款？”先查原请求结果与幂等契约。

如何验证：注入池耗尽、慢 DNS、慢握手、慢读和响应丢失，沿同请求记录预算传播；核对取消后连接、许可与未知动作是否被正确处理。

39服务 P99 暴涨，CPU 高低各有一批实例，如何组织排查？

记忆关键词： 分实例/版本 → 分链路 → 热点/等待 → 止放大 → 灰度验证

先这样回答：先按实例、版本、租户与请求类型分组，区分计算忙、调度受限和资源等待。用指标定位阶段，再用多次栈、采样与 trace 解释原因，不先统一调大线程池。

机制与边界

CPU 高的一组看热点、输入复杂度、GC 与配额；CPU 低而慢的一组看连接池、锁、I/O 与下游。共享重试和流量路由也可能让两组互相影响。

止血优先控制重试、队列与受影响能力的并发，保留健康路径。性能修改要配同负载验证；总 P99 不能用各段 P99 直接相加。

例子与时序：某版本对长文本做高复杂度正则，同时下游慢使另一组等待连接；只扩大线程池会使数据库与内存压力更大。

追问接答：“RUNNABLE 就是 CPU 热点？”还需线程 CPU 证据。“把慢实例摘除即可？”要确认剩余容量能接流量，避免二次过载。

如何验证：保留变更前后同类请求的分段耗时、错误与资源指标；验证 P99、吞吐、质量和受影响范围一起改善。

40容器突然退出，堆却很空，下一步查什么？

记忆关键词： 退出证据 → cgroup 峰值 → 内存分类 → 生命周期 → 有界修复

先这样回答：先确认退出原因，再定位容器计费内存来自哪里。堆曲线平稳只排除了部分问题，不能排除线程、直接内存、文件页、原生分配或其他进程。

机制与边界

对齐容器/节点事件、memory.events 与退出前峰值，区分 OOM、外部强杀和正常退出。再结合 memory.stat、进程映射、线程与运行时指标，避免把不同计量口径硬相加。

检查对象和缓冲的生命期：慢客户端、无界队列、未关闭连接或 native 库都可能留住资源。修复要限制来源和归还路径，调大限制只是一种容量取舍。

例子与时序：图片处理把原始字节、解码图和待发送结果同时留在队列，堆统计只看到其中部分路径；峰值发生在处理重叠时，空闲截图容易漏掉。

追问接答：“重启一次没复现就好了？”生命周期与负载可能尚未触发。“137 就一定 OOM？”还需平台和内核证据。

如何验证：在隔离环境复现峰值负载与慢消费者；检查峰值可控、完成后资源回落，以及强杀后的已受理任务能查询或补偿。

41连接报错“Too many open files”，同时 CLOSE_WAIT 增长，怎么修？

记忆关键词： fd 类型 → 创建/关闭责任 → EOF/异常 → 池回收 → 容量与泄漏分开

先这样回答：先确认哪个进程触及哪类描述符限制，再按 fd 类型和连接状态追创建与关闭路径。CLOSE_WAIT 提示本地关闭责任，但大量正常长连接也会消耗 fd，不能把所有占用都叫泄漏。

机制与边界

重复统计 fd、连接池 active/idle/pending、CLOSE_WAIT 和连接年龄。定位 EOF、异常、取消和正常返回是否都关闭或归还资源，特别检查响应体未消费/未关闭的路径。

提高限制只增加余量，持续泄漏仍会耗尽。若连接确实需要长期存在，还要预算端口、内存、心跳和代理空闲状态，并设明确清理协议。

例子与时序：HTTP 客户端异常分支直接返回而未关闭响应体，连接未归还；池等待变长后又启动重试，导致 fd 与在途请求一起增长。

追问接答：“看到 TIME_WAIT 就是 fd 没关？”不能等同。“kill 掉全部连接？”会破坏在途业务，应先明确影响与恢复方式。

如何验证：对正常、EOF、错误、取消四条路径重复调用并观察资源趋势；修复后在相同负载下 fd 和池占用应稳定。

42“网络超时”如何拆成 DNS、连接、TLS、池等待和服务处理？

记忆关键词： 确定边界 → 记录目标 → 拆阶段 → 同环境复现 → 单因素验证

先这样回答：先知道是哪个 API 的哪类超时。实际请求可能在池等待、解析、建连、握手、发送、服务处理或接收；仅凭异常中有 timeout 无法定位网络层。

机制与边界

将同请求的各阶段时间、目标地址、代理路径、重用连接与重试次数关联起来。服务端未见请求可能发生在应用前，也可能是日志采样或入口不同；要逐跳寻找证据。

在同网络命名空间与相同身份条件下比较解析与实际连接；测试固定解析时仍保留正确 hostname、SNI 与证书验证。网关与服务端日志还需考虑时钟误差。

例子与时序：只有复用连接失败，新建连接正常，可能涉及代理回收空闲状态；直接在笔记本 ping 成功，不能解释容器内的解析或连接行为。

追问接答：“curl 快说明服务没问题？”请求、认证、协议与复用可能不同。“抓不到包就是没发？”还需确认接口、命名空间和捕获范围。

如何验证：分别注入每阶段延迟，看对应指标和错误是否正确归属；确认修复改变了目标阶段，而不是通过绕过 TLS 验证使错误消失。

43AI 流式输出断线、内存涨、页面重复，如何沿整条链路排查？

记忆关键词： run/seq → 解析边界 → 慢消费背压 → 断线恢复 → 副作用查证

先这样回答：把业务任务、生成过程、事件流和网络连接分开。连接断线不等于任务取消，网络块不等于事件，输出快于消费会积压；恢复必须保留原任务身份与结果证据。

机制与边界

核对 UTF-8 解码、SSE 空行边界、run/message/seq、服务端保留与前端已应用游标。重复传输可以通过事件身份去重，遗漏则需补发或明确转为最终状态查询。

检查模型生成、工具调用、网关缓冲和浏览器渲染各自的队列预算。取消要贯穿执行器与资源清理；工具已产生的副作用仍要按动作身份查证，不能因为重新连接就盲目重放。

例子与时序：客户端慢读使网关缓冲增长，超时后重建 run 又重复执行工具；提高超时可能掩盖排队，却让峰值内存与副作用风险更大。

追问接答：“每个 token 都立即 setState？”渲染可批处理，协议仍按事件解析。“连接收到 done 就绝对成功？”done 的任务语义须由业务契约定义。

如何验证：测试分块、慢读、重复/缺口、保留过期、换实例和工具成功后断线；同时验证最终正文、真实副作用与内存上限。

能否讲清这四个反例？

  • epoll 已通知可读，应用仍没拿到一条完整消息。
  • 服务已完成退款，客户端却因回包丢失显示超时。
