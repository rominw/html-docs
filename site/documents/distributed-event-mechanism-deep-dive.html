0一句话本质

它把「跨服务发事件」伪装成「调本地方法」，把「收远程事件」伪装成「写一个普通 Spring @EventListener」。中间靠 Spring Cloud Stream + RabbitMQ 搬运，靠启动时的一次反射「偷梁换柱」把两条路接通：

  • 发送方只认识 eventProducer.send(event) 一个方法；
  • 接收方只写普通 @EventListener，感知不到事件来自本机还是另一台机器；
  • 桥是两条固定的 RabbitMQ 主题（组事件 / 广播事件），全平台所有业务事件都挤在这两条主题上，靠 JSON 里的类型字段区分。

2事件模型：三个基类定乾坤

分水岭规则（全文最重要的一句话） 继承 AbstractEvent（经 Group/Broadcast）→ 走分布式，只能用 eventProducer.send() 发；直接继承 ApplicationEvent → 纯本地，用 applicationEventPublisher.publishEvent() 发。两套发送口不能混用——混用的后果是事件无声落空（原因见 §6）。
事件基类语义
OrderFinishedEvent、OrderPaidEvent、NoticeMessageEvent、BindingChangedEvent…GroupEvent跨服务，组内竞争消费
PushMessageEventBroadcastEvent跨服务，全实例广播
ConfigChangedEvent、ViewRefreshEvent、StatsUpdatedEvent…ApplicationEvent纯进程内，不走 MQ

3发送链路：eventProducer.send(event) 之后发生了什么

// EventProducer.java（骨架，逻辑完整保留）
@Retryable(value = {EventProduceException.class},
           maxAttemptsExpression = "${event.retry.maxAttempts:3}",
           backoff = @Backoff(delayExpression = "${event.retry.delay:1000}"))
public void send(AbstractEvent event) {
    try {
        String topic = (event instanceof GroupEvent)
            ? eventProperties.getGroupEventTopic()        // 默认 "groupEventTopic"
            : eventProperties.getBroadcastEventTopic();   // 默认 "broadcastEventTopic"
        String json = JSON.toJSONString(event, SerializerFeature.WriteClassName);
        streamBridge.send(topic, json);                   // ← 唯一出口
        log.info("事件发送，主题：{}，事件：{}", topic, json);
    } catch (Exception e) {
        log.error("事件发送：{}", event, e);
        throw new EventProduceException(e);               // 触发上面的重试
    }
}

@Recover                                          // 重试耗尽后进入这里
public void recover(EventProduceException e, AbstractEvent event) {
    // 空方法：事件被静默丢弃，调用方不会收到任何异常
}

① 路由规则就是“看爹”

instanceof GroupEvent → 组主题；instanceof BroadcastEvent → 广播主题。整个平台只有这两条主题，所有业务事件挤在一起，靠 JSON 里的类型字段区分——这就是源码注释里“下游订阅方按 @type 区分”的含义。

② 序列化：WriteClassName 与 @type

fastjson 的 WriteClassName 会在 JSON 里写入 "@type":"com.xxx.event.OrderFinishedEvent"，消费端靠它还原具体类型。两条硬约束：

  • 消费方 classpath 必须有同名同类路径的事件类——公共事件放契约包，模块私有事件放双方都依赖的公共业务模块；
  • 消费端用的是 fastjson SupportAutoType（按类型名实例化对象），依赖其白名单机制，有历史安全包袱。

③ StreamBridge：运行时动态发送

StreamBridge.send(topic, json) 是 Spring Cloud Stream 3.x 的动态发送入口：第一个参数当 destination，现场建一条到 binder 的通道，不需要预声明任何输出绑定。（框架里预配置的 groupEventProducer-out-0.* 属性实际是摆设，发送路径不经过它。）

可靠性账本（发送侧） 失败 → 重试 3 次（间隔 1s）→ 全部失败进入空的 @Recover → 方法正常返回。调用方完全无感知，事件凭空消失，唯一线索是 catch 块里的 error 日志。

④ 一个 @type 字段，两条硬约束

先回答“为什么要有 @type”：全平台所有事件挤在同一条主题上，消费端从 MQ 拿到的只是一个 String（SCS 绑定声明的是 Consumer<String>）。要把字符串还原成具体事件对象，类型信息只有两个来源——消息外的元数据（header / topic），或者消息自己携带类型。框架选了后者：类型的说明书跟着消息走。这一选择直接决定了两条绕不开的约束。

硬约束一：消费方 classpath 必须有同名同类路径的事件类，否则事件无声丢失。@type 的值只是一个字符串，反序列化时 fastjson 在消费方的 JVM 里执行等价于 Class.forName("...") 的动作——跟发送方无关。这一步要成功，类必须存在、全限定名一模一样（挪过包就对不上）；之后 event.getClass() 精确匹配分发 handler，也要求两边加载到同一个类身份。而失败后果特别隐蔽——看消费端源码：

} catch (JSONException e1) {
    // 消费方没有这个事件类 / JSON 不合法 → 落到这里 → 什么都不做，消息被 ACK 丢弃
}

类缺失不是报错，是凭空消失——连日志都没有。所以事件类的存放位置只有两种合理选择：跨服务共享的事件放独立的契约包（谁用谁依赖）；平台私有的事件放被收发双方共同依赖的公共业务模块。反过来推论：事件类的包名在这个体系里不是内部实现细节，而是线上协议的一部分——挪包、改名、删类都是单方面撕毁协议，且撕毁方式是无声丢消息。

硬约束二：必须在不可信输入上开 fastjson autoType。“让 JSON 自己指定要实例化哪个 Java 类”就是 autoType——fastjson 2017–2020 年一连串反序列化 RCE 漏洞正是这个能力被恶意利用（构造恶意 @type 指向 JNDI gadget 类远程加载恶意代码）。fastjson 的闸门一路演进：默认关闭 + 黑名单（1.2.25 起）→ expectClass 机制（@type 目标必须是指定预期类型的子类）→ safeMode 彻底禁用 @type。本框架必须开 SupportAutoType，安全底气来自一个细节：parseObject(message, AbstractEvent.class, ...) 的第二个参数把 AbstractEvent 设为预期类型，fastjson 会校验 @type 指向的类必须是它的子类才放行——相当于“只准实例化事件子类”的运行时白名单。但这道闸的前提是所用 fastjson 版本没有已知绕过漏洞，安全性押在版本上。

设计取舍 单主题 + @type 的收益：发送端一个 send() 通吃所有事件、新增事件零配置。代价：类型以字符串形式在线上流转（类必须两边同名同路径存在），且必须在消息上开 autoType（安全依赖闸门与版本）。若改成“每个事件一条 destination”或“类型放消息头由消费方映射”，两条约束都消失，但加事件要动配置——典型的把灵活性代价转嫁给部署与安全。

4中间层：Spring Cloud Stream 到底在替你做什么

先把 Spring Cloud Stream（SCS）这个最让人迷糊的点讲透：SCS 是消息中间件适配层。你的代码面对“绑定名 / destination / 消费者组”这套抽象，底下由 binder（rabbit binder 或 kafka binder）翻译成具体中间件的操作。框架只用了 SCS 三个能力：

4.1 函数式消费绑定

@Bean public Consumer<String> groupEventConsumer(EventHandler h)     { return h::handle; }
@Bean public Consumer<String> broadcastEventConsumer(EventHandler h) { return h::handle; }

SCS 规则：spring.cloud.function.definition 里登记的函数 Bean 自动创建输入绑定，绑定名是 BeanName-in-0（如 groupEventConsumer-in-0），之后从 broker 拉消息喂给这个函数。业务代码里一行绑定配置都不用写。

4.2 EventConfigInitializer —— 一切绑定的出生地

它在容器刷新前运行，往 Environment 最前面插一个属性源，等价于替你写下这些配置（每行都是源码原意）：

spring.cloud.function.definition = groupEventConsumer;broadcastEventConsumer
    # 强行插到定义最前，且会保留用户已有的函数定义

# —— 组事件 ——
spring.cloud.stream.bindings.groupEventConsumer-in-0.destination = groupEventTopic
spring.cloud.stream.bindings.groupEventConsumer-in-0.group = ${event.group-name:${spring.application.name}}   # ← 关键！

# —— 广播事件 ——
spring.cloud.stream.bindings.broadcastEventConsumer-in-0.destination = broadcastEventTopic
# ↑ 注意：广播的 in-0【没有设 group】—— 这就是广播的全部实现手法

spring.cloud.stream.binders.rabbit.type = rabbit     # binder 类型钉死为 RabbitMQ

4.3 Group 与 Broadcast 的语义差异 = 两行配置的差别

落到 RabbitMQ 上是两种队列拓扑：

Group 事件（组 = 应用名）Broadcast 事件（不设组）
队列每服务一条持久化队列，名为 groupEventTopic.应用名，绑到 exchange每实例一条匿名、独享、auto-delete 队列
投递同组实例共享队列 → Rabbit 轮询 → 一条消息只被一个实例消费（服务内负载均衡）每实例自己的队列各得一份 → 所有实例都收到；实例下线队列自动删除
跨服务不同服务组名不同 → 各有一条队列 → 各得一份。准确表述：“每服务一份，服务内竞争”天然全量
适用业务处理（数据落库、状态机流转）实例本地持有状态时的推送（SSE 长连接、本地缓存刷新）
一个仓库里看不到的环节 starter 同时依赖 rabbit 和 kafka 两个 binder；多 binder 共存时 SCS 需要 spring.cloud.stream.default-binder 才能确定路由。这类开关在配置中心里（本仓库的本地配置文件只有应用名）。从平台侧证（web 服务还有裸 @RabbitListener 的旁路消费者）看，事件链路跑在 RabbitMQ 上。

4.4 groupEventConsumer 与 handle() 是怎么对上的：命名约定三重奏

常见追问：groupEventConsumer 是怎么跟 EventHandler.handle() 关联起来的？答案是命名约定 + 方法引用，没有任何显式注册。三样东西靠同一个名字串起来：

东西值谁提供的
函数 BeangroupEventConsumer（Consumer<String>，Bean 的值是 eventHandler::handle 方法引用）EventConfiguration 的 @Bean 方法名
输入绑定名groupEventConsumer-in-0SCS 按「BeanName + "-in-0"」约定拼出
绑定属性 keybindings.groupEventConsumer-in-0.destination=groupEventTopicEventConfigInitializer 按同一条约定拼出

属性 key 里的绑定名和 SCS 从 Bean 名推导出的绑定名字面相等，SCS 由此知道“这条 destination 的消息要喂给这个 Bean”。运行时一条消息进来后的调用链：

RabbitMQ 队列 groupEventTopic.<应用名>
  │  rabbit binder 的 listener container 线程拉到一条消息
  ▼
SCS 找到绑定对应的函数 Bean：groupEventConsumer
  │  按绑定的 content-type=application/json 把 payload 转成 String
  ▼
groupEventConsumer.accept(json)      ← Consumer<String> 的唯一方法
  │  这个 Bean 的值就是 eventHandler::handle 方法引用
  ▼
eventHandler.handle(json)            ← Bean 被 @EnableRetry 代理，@Retryable 在此生效

两个容易忽略的点：

  • 组/广播的区分不在 handler 层。groupEventConsumer 与 broadcastEventConsumer 两个 Bean 指向同一个 handle()。handle() 不知道消息来自哪条队列，反序列化后 instanceof 只用来选该用哪条 SpEL 过滤表达式；“组消费还是广播”完全由绑定层的队列拓扑决定，handler 只是所有消息的公共漏斗。
  • 重试发生在 Rabbit listener 线程上。@Retryable 是同步阻塞重试（同线程试 3 次），一条毒消息最坏占用 listener 线程约 3 秒；@Recover 空方法兜底保证 accept() 总是正常返回、消息照常 ACK，队列不会堵死——代价是静默丢弃。

5消费链路：消息如何“变回”本地事件

Rabbit listener 线程收到消息后，依次经过四站（对应图 1 右列）：

// EventHandler.handle(json)（骨架）
@Retryable(value = {EventConsumeException.class}, maxAttemptsExpression = "...:3", ...)
public void handle(String message) {
    try {
        AbstractEvent event = JSON.parseObject(message, AbstractEvent.class, Feature.SupportAutoType);
        if (!this.hasListeners(event)) return;          // 本进程无监听器 → 直接 ACK 丢弃
        String el = (event instanceof GroupEvent)
            ? eventProperties.getGroupEventConsumeExpression()      // 可选 SpEL，根变量 #event
            : eventProperties.getBroadcastEventConsumeExpression();
        if (!this.matchesExpression(el, event)) return; // 不匹配 → 丢弃
        eventMulticasterFacade.publishEvent(event);     // → 本地异步多播
    } catch (JSONException e1) {
        // 脏消息：无声放过（连日志都没有）
    } catch (Exception e) {
        log.error("事件处理：{}", message, e);
        throw new EventConsumeException(e);             // 触发重试
    }
}
@Recover public void recover(EventConsumeException e, String message) { /* 空：重试耗尽后 ACK 丢弃 */ }

① SpEL 过滤：实例级开关

配置了 group-event-consume-expression（如 #event.level == 'HIGH'）就在派发前求值，不匹配即丢；没配则全放行。可以用来做“某些实例只处理某类事件”的灰度。

② hasListeners：快速跳过

启动时登记的“本进程监听了哪些事件类”列表里找不到（含子类型匹配）就立刻返回，消息被 ACK 丢弃——这是全平台事件挤两条主题还不至于拖垮每个消费者的第一道闸。

③ 线程模型：两段式

  • Rabbit listener 容器线程只干“反序列化 + 提交多播”，干完立刻返回去拉下一条；
  • 业务监听器在框架自定义线程池里跑：event- 前缀，默认 core 5 / max 10 / queue 20，CallerRunsPolicy——池满时退化为 listener 线程自己执行，形成天然背压；
  • 监听器抛异常由 EventErrorHandler 接住，只打日志，不影响 ACK。
可靠性账本（消费侧） 消费失败 → 重试 3 次（同一条消息、同一个线程内）→ 进入空的 @Recover → 方法正常返回 → binder 认为消费成功 → 消息 ACK 掉。没有死信、没有落库、没有告警。JSONException（反序列化失败）更是被单独 catch 后无声放过。

6最“魔法”的一步：为什么写 @EventListener 就能收到远程事件

EventListenerProcessor（实现 SmartInitializingSingleton，在所有单例实例化完、容器刷新收尾时执行）干了四件事：

  1. 拿到 Spring 默认的 ApplicationEventMulticaster（就是正常 publishEvent() 用的那个）；
  2. 用反射调它的私有方法 getApplicationListeners()，枚举出全部监听器；
  3. 逐个解析它监听的事件类型：@EventListener 方法 → 反射读 ApplicationListenerMethodAdapter 的私有字段 declaredEventTypes；ApplicationListener<T> 接口 → 解析泛型；
  4. 只要事件类型是 AbstractEvent 的子类，就把该监听器从默认多播器上摘除，挂到框架自定义多播器上；其余监听器原地不动。

于是形成严格分水岭：

分布式事件（Group / Broadcast 子类）本地事件（直接继承 ApplicationEvent）
监听器挂在哪仅框架自定义多播器仅 Spring 默认多播器
到达路径MQ → EventHandler → 自定义多播器（异步）publishEvent() → 默认多播器（同步）
用错的后果对分布式事件调 publishEvent()：走默认多播器，但监听器已被摘走 → 事件无声落空；对本地事件调 send()：类型不对 / 白跑一趟 broker
三个推论 ① 分布式 @EventListener 永远异步（线程池执行）；② 哪怕同进程自己发给自己，也至少绕 broker 一圈，且发送实例不一定是消费实例（组内轮询）；③ 写成 ApplicationListener<GroupEvent>（监听基类）会收到所有组事件，需自行按类型分发——业务侧普遍用「分发器 + 策略 handler 表」来承接（见 §7 链路 A）。

7两条真实链路走读

链路 A · Group 事件：跨服务业务协作

  1. admin 服务处理一次绑定关系变更 → eventProducer.send(new BindingChangedEvent(...))；
  2. → groupEventTopic exchange → 路由到持久化队列 groupEventTopic.admin-service（同服务多实例轮询，单实例消费）；
  3. → 事件分发器 BizEventDispatcher（ApplicationListener<GroupEvent>，收到所有组事件）按 getClass() 精确匹配 handlerMap；
  4. → 命中的策略 handler 执行（清理关联的周期任务与派生数据）。未注册的事件类型打 debug 日志跳过。

另一个典型：OrderPaidEvent（支付完成）被 两个 handler 同时注册（开票、积分）——“一个事件多订阅者”的常规实现方式。

链路 B · Broadcast 事件：为什么必须广播

  1. 某个业务服务为在线用户产出一条实时消息 → send(PushMessageEvent)（Broadcast）；
  2. → broadcastEventTopic exchange → 每个 web 服务实例的匿名队列各得一份；
  3. → 各实例的 @EventListener 各自查自己手上有没有该用户的 SSE 长连接，有就推送。

用广播的原因：SSE 长连接可能连在任意实例上，负载均衡会把同一用户的请求打到不同机器。只有“每个实例都收到、各自查本地连接表”才能保证送达——这正是广播事件的存在意义：消费的是实例本地状态。

顺带一提该平台的另一条旁路：web 服务还有一个裸 @RabbitListener 的前端消息消费者，收到消息后再转成广播事件走事件框架分发出去——两套机制在同一进程里接力。

8坑与边界

#坑说明
1尽力而为的可靠性发送端、消费端都是“重试 3 次后空 @Recover 吞掉”。没有死信、没有补偿、调用方无感知。排障只能搜日志关键字（事件发送 / 事件处理）。
2顺序无保证派发进线程池后乱序执行；组事件在服务多实例间轮询，跨实例也无序。
3单点汇聚全平台两类事件各挤一条主题。hasListeners 能挡掉无关消费，但监听基类的监听器每条组事件都会进。
4组名 = 应用名服务改名会让新旧实例分属两个组、事件各消费一份——发版改名要小心。想让两个服务都收到组事件，靠的正是它们应用名不同。
5autoType 既是协议又是风险事件类的包名是协议的一部分，重命名/挪包会让对端反序列化失败，且以 JSONException 被静默吞掉。
6本地通信也依赖 broker没有本地短路，自己发给自己也过 MQ；MQ 抖动时同进程通信同样受影响。
7线程池默认偏小core 5 / max 10 / queue 20，饱和后退化为 listener 线程执行（背压生效，但吞吐受限），需按消费能力调参。

9追问与排障 FAQ

Q1 · 自己发给自己，也要走 MQ 吗？

要。没有本地短路：send() 一定上 broker，消息再从队列回来。而且组事件在同服务多实例间轮询，发送实例自己未必是消费实例。同进程通信用组事件，成本 = 一趟 broker 往返；MQ 抖动时同进程通信同样受影响。

Q2 · 我的 @EventListener 收不到事件，按什么顺序查？

  1. 事件基类对吗？必须继承 GroupEvent / BroadcastEvent（经 AbstractEvent）。直接继承 ApplicationEvent 的是本地事件，永远收不到 MQ 来的消息。
  2. 发送方式对吗？分布式事件必须 eventProducer.send()。对它调 publishEvent() 会走默认多播器，而监听器已被迁走 → 无声落空（§6 分水岭）。
  3. 消费方 classpath 有这个类吗？没有的话反序列化抛 JSONException 被静默吞掉、消息 ACK 丢弃，连日志都没有（§3 ④）。
  4. 监听器类型能匹配吗？hasListeners 按“监听类型与事件类可赋值”判断；监听具体类的监听器收不到兄弟类型事件。
  5. SpEL 过滤配了吗？配了 consume-expression 且不匹配会被丢弃（表达式求值异常也按不匹配处理）。
  6. 组名对吗？消费组默认 = spring.application.name，服务改名会让新旧实例分属两组、各消费一份。

Q3 · 怎么确认事件有没有发出去 / 有没有被消费？

两头都有 info 日志：发送成功打「事件发送，主题：…，事件：…」；进入派发打「事件处理：…」。发送失败是 error「事件发送：…」，消费异常是 error「事件处理：…」。注意反序列化失败（类缺失 / 脏消息）没有任何日志。队列情况看 Rabbit 管理台：组队列名 = groupEventTopic.应用名；广播队列是每实例一条匿名队列，实例下线即消失。

Q4 · 广播事件在实例离线时会不会丢？

会。广播队列是匿名的 auto-delete 队列，实例不在线就没有这条队列，消息自然错过，且不补偿——广播语义只保证“在线实例都收到”。需要离线补投的场景应该用组事件（持久化队列）。

Q5 · 有顺序保证吗？

没有。消费侧派发进线程池后乱序执行；组事件在多实例间轮询，跨实例也无序。同一业务键需要顺序时，要么在监听器里按业务键串行化，要么换用带分区键的机制。
