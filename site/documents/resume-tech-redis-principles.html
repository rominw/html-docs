典型应用场景

调度锁、Lua 状态转移、messageId、终态保护与回调幂等共同影响 Action 生命周期。沿租约与执行结果，识别 Redis 的原子范围和外部系统边界。

本篇核心问题

能在进程暂停、锁过期、重复回调、主从切换和缓存回填交错中判断哪些不变量仍成立。

阅读方式：先用记忆关键词复述机制，再推演例子的失败窗口，最后明确验证对象。场景用于解释技术取舍；练习能证明什么、不能证明什么，见版本与验证范围。

版本与验证范围：Redis 原子性讨论限定在相应实例和操作范围；Cluster 多键要求、持久化和故障切换另行讨论。模型练习不执行 Redis 或 Lua。

2. Redis 的“单线程、原子”为什么不能直接推出业务正确？

从机制到边界，再用具体交错检验结论。

记忆关键词：命令串行 · 单次边界 · 组合竞态 · 脚本预算

核心结论

常见核心命令执行路径的串行性避免命令互相穿插，但一次 GET 与后续 SET 之间仍可插入别的请求。原子操作保护特定 Redis 状态，不覆盖多系统事务。

拆开机制与保证范围

A GET 到空闲，B 也 GET 到空闲，随后两人 SET 占用，最后只留下一个值却可能已经发了两次设备指令。问题不在单条 SET 是否原子，而在“读条件、判断、写状态”没有被放入同一个受保护边界。

Lua 把适当的读写条件放到服务端执行，减少网络往返并防止其他命令插入。但长循环、大量扫描或复杂计算会占用该执行路径，拖慢其他请求。Redis 的网络 I/O、后台持久化等可以有其他线程或进程，不能把整个系统一概称为只有一个线程。

脚本原子执行不等于 SQL 式失败回滚。若脚本先成功写一个键，后续命令因类型或参数出错，不能依赖自动撤销前面的写入。应在写入前完成可做的参数、状态和类型检查，并使执行长度有界。

场景推演：一个状态转移先写 DONE 再给错误类型的字段累加，后半段抛错。应用收到错误却不能直接认定状态没有改变，应查询并审视脚本的写前校验。

进一步思考：“MULTI 就能读值后分支？”排队执行与交互式读判定不同。“Lua 报错就可无脑重试？”需先判断实际修改与稳定动作身份。

如何验证：在隔离 Redis 中注入参数和类型错误，检查错误前后的键；量测脚本耗时和延迟影响。纯状态模型只验证业务规则，不能验证服务器回滚语义。

3. messageId、回调幂等与终态保护怎样组成一个状态机？

从机制到边界，再用具体交错检验结论。

记忆关键词：身份绑定 → 合法迁移 → attempt → 终态单调 → 查证

核心结论

同一业务动作必须有稳定身份并绑定租户与请求内容，状态转移只接受合法前置条件。重复和迟到回调不能覆盖终态，也不能把其他尝试的结果写进当前动作。

拆开机制与保证范围

先定义生命周期：PENDING → RUNNING → SUCCEEDED/FAILED；UNKNOWN 可表达未获知外部结果，而不是假装失败。哪些终态可修正、通过谁修正，都要显式规定。若系统允许对账修正，应使用独立受审计路径，不能放开普通回调随意覆盖。

messageId 解决关联，eventId 解决某次回调去重，attempt 或执行代次解决重试轮次。它们可以不同；只检查 messageId 可能让上一轮晚到的 FAILED 覆盖这一轮 RUNNING。请求摘要还用于拒绝同键异参，避免拿旧成功结果响应新的执行意图。

Lua 中检查当前状态、版本和代次后再写新状态，必要时同时记结果与事件序号。重复事件返回已存在结果；非法迁移返回可解释原因。去重记录到期后，旧消息可能再次进入，因此保留期要覆盖重投和业务查证需求，不能随意套短缓存 TTL。

场景推演：成功回调先到，失败回调迟到。如果迁移只按“最后一条消息”覆盖，状态会退回失败；终态保护和代次校验使这类交错可解释。

进一步思考：“两个相反终态都来了怎么办？”终态保护只能保证不随意改写，还需查证权威执行事实。“收到重复就丢弃？”可返回既有结果并留下必要审计。

如何验证：枚举事件顺序、重复事件、旧 attempt、同键异参和缺失记录；核对合法迁移与真实结果。下方模型验证终态和身份规则，不证明设备只执行一次。

4. Redisson 锁和 watchdog 能否消除“两个持有者都执行”？

从机制到边界，再用具体交错检验结论。

记忆关键词：租约 · 续期 · 暂停 · 所有权 · 资源端资格

核心结论

租约限制锁在 Redis 的有效时间，watchdog 在符合条件的路径上续期。网络中断、长暂停和切换仍可能让旧执行者恢复后继续行动，所以资源端必须有最终资格检查。

拆开机制与保证范围

显式 leaseTime 和 watchdog 使用路径要按 Redisson 版本及调用方式区分；不要把固定租期和无限续约混为一谈。释放锁也应确认所有者，避免 A 超时后删掉 B 新取得的锁。所有权正确只解决释放对象，不解决 A 已在外部执行的问题。

A 暂停超过租期，B 获锁并提交，然后 A 恢复。A 本地以为持锁，其下游写入是否被拒绝取决于下游契约。数据库条件更新可以保护当前版本/状态；fencing token 是另一类单调资格，必须由真正受保护的资源检查旧令牌，而不只是日志里记录。

若设备只提供无身份的“执行起飞”接口，Redis 锁不能单独创造精确一次副作用。需要设备或权威服务支持动作身份、条件资格和结果查询；不具备时，应明确可达到的保证和 UNKNOWN 查证流程。分布式锁是控制竞争的一层。

场景推演：A 用旧版本占用机库被数据库拒绝，此时不能继续下发。如果先发指令后查资格，数据库保护已经来不及阻止真实副作用。

进一步思考：“租期设很长？”减小误过期概率，却延长故障占用。“每次操作前检查锁？”检查与外部写之间仍有窗口，关键是资源端原子资格。

如何验证：暂停持锁进程、阻断续约与模拟切换，观察旧执行者是否被权威资源拒绝；只测解锁没有异常，不能验收双持有风险。

5. 缓存失效为什么仍会出现旧值回填？

从机制到边界，再用具体交错检验结论。

记忆关键词：读旧快照 → 写新版本 → 删除缓存 → 迟到回填

核心结论

Cache-aside 减少读取成本，但删除缓存不是同步屏障。一个早已读到旧值的请求可以在删除之后把旧数据写回，TTL 只是限制某些旧值保留时间。

拆开机制与保证范围

典型交错：A 读缓存未命中并查到 v1；B 提交 v2 并删除缓存；A 随后回填 v1。整个流程每条命令都成功，缓存仍过时。延迟双删可以缓解某些时间窗口，但延迟不构成对所有暂停和重试的严格证明。

先确定允许的旧数据窗口与权威读取路径，再选择版本化回填、失效事件、短 TTL 或直接查询。若用“只接受较新版本”的门槛，必须考虑删除后门槛是否也丢失；空缓存不应意味着任意旧请求重新取得写入资格。

缓存键还应包含租户和影响结果的权限/参数维度。负缓存与 TTL 抖动可分散回源，但权限变更、删除标记和真实结果查询不能被简单的“命中即正确”覆盖。资源抢占不能以缓存值作为最终判断。

场景推演：大屏允许几十秒滞后，可以在响应中注明数据时刻并采用受控刷新；机库是否可分配则必须回到权威条件更新。不同数据不应共享同一种新鲜度要求。

进一步思考：“先删后写数据库更好？”也会出现交错窗口。“所有缓存加锁？”锁范围、过期和下游等待仍需处理，先定需要的保证。

如何验证：人为固定 A 的旧读取，等 B 提交并失效后再释放 A 回填；验证旧值可见窗口与拒绝旧版本的规则，并覆盖权限切换。

6. Redis 已返回成功，为什么切换后还可能丢状态？

从机制到边界，再用具体交错检验结论。

记忆关键词：执行确认 · AOF/RDB · 复制进度 · 切换 · 未知结果

核心结论

命令受理、持久化和副本确认不是同一时点。RDB、AOF 与复制配置改变恢复窗口；客户端成功响应不能单独证明所有故障后的状态都保留。

拆开机制与保证范围

RDB 按快照恢复，AOF 按追加日志及 fsync 策略恢复；写入追加缓冲、写文件与完成持久同步有不同边界。策略需要按实际版本、存储和配置核对，不能把 everysec 当成在任何故障下最多只丢固定一秒的硬保证。

常见 Redis 复制是异步的。主节点写入后副本尚未追上就切换，新主可能缺少近期写入。WAIT 等机制可等待某种副本确认，但其确认范围不能被扩大成跨全部故障的强一致事务。锁、幂等记录和缓存的数据价值不同，恢复策略也应不同。

如果 Action 已执行但 Redis 幂等记录丢了，重试可能再次执行。需要把关键业务结果放在足够可靠的权威存储或外部执行协议里，Redis 可以作为状态缓存与协调层。TTL 到期时，应转为查询/对账或明确过期结果，而不是生成新动作伪装“从未发生”。

场景推演：设备执行成功后服务写了 SUCCEEDED，客户端回包丢失，随后 Redis 故障切换丢记录。客户端再次使用同一身份时，应查权威执行结果，不能因 Redis 没键就再次起飞。

进一步思考：“开 AOF 就不用对账？”存储持久化不覆盖外部调用窗口。“不存在等于没受理？”也可能是过期、淘汰或恢复缺失。

如何验证：在隔离环境核对 fsync、复制进度、故障后键与权威业务事实；分别模拟成功响应丢失和状态记录缺失，验证 UNKNOWN 恢复。

7. 热键、Lua 多键和内存淘汰如何改变设计？

从机制到边界，再用具体交错检验结论。

记忆关键词：hash slot · 单点热点 · 有界集合 · 数据价值 · 观测

核心结论

分片扩大总体容量，但同一热键仍落在特定分片。Lua 多键操作需满足相应 Cluster 约束，内存淘汰也可能删除业务以为永久存在的去重状态。

拆开机制与保证范围

Redis Cluster 将键分到 hash slot，合适的 hash tag 可让需要原子操作的多个键同槽。把全部租户或任务都放进一个 tag，虽然简化多键脚本，却可能制造单分片热点；键的原子范围与分布负载需要一起设计。

回调集合、流式缓冲和结果历史应有数量、大小和生命周期上限。长脚本、大值读写与高基数集合会增加执行和网络成本；热门聚合查询可以缓存、分批或合并刷新，但合并后要保留每个请求的授权范围。

maxmemory 与淘汰策略是契约的一部分。普通缓存允许丢失，幂等/终态记录若被淘汰却当作不存在，会损坏执行保证；最好分清权威事实与可丢缓存。监控命令延迟、脚本耗时、热点分布、eviction 和回源压力，而不只看 Redis 总 QPS。

场景推演：一个全局 Action 大 Hash 持续增长，所有回调争同一热点，清理又扫描大量字段。按必要业务原子范围拆分，并给结果保留和旧事件查证留明确路径。

进一步思考：“加节点能均分热键？”单键不会自动拆开。“给每个键相同短 TTL？”可能同时回源，也可能让迟到重投失去去重证据。

如何验证：核对脚本涉及的所有键是否同槽，压测实际热点与大小分布；触发淘汰和迟到回调，验证关键状态不会因缓存缺失而重执行。

8. 动手验证与故障推演

先推导预期，再运行；如果结果相反，回到机制与边界。

状态模型练习：重复、迟到和旧轮次回调不能改写终态

Python 3 标准库模型，通过事件排列验证状态不变量；它不调用 Redis，不模拟复制、租约或外部设备副作用。UNKNOWN 保留待查证含义。

保存为 practice.py，用 python practice.py 运行。

from itertools import permutations

def apply(state, event, current_attempt=2):
    attempt, target = event
    if attempt != current_attempt:
        return state
    if state in {"SUCCEEDED", "FAILED"}:
        return state
    allowed = {
        "PENDING": {"RUNNING"},
        "RUNNING": {"SUCCEEDED", "FAILED", "UNKNOWN"},
        "UNKNOWN": {"SUCCEEDED", "FAILED"},
    }
    return target if target in allowed.get(state, set()) else state

for order in permutations([(2, "SUCCEEDED"), (1, "FAILED"), (2, "SUCCEEDED")]):
    state = "RUNNING"
    for event in order:
        state = apply(state, event)
    assert state == "SUCCEEDED"
assert apply("SUCCEEDED", (2, "FAILED")) == "SUCCEEDED"
assert apply("RUNNING", (1, "SUCCEEDED")) == "RUNNING"
assert apply("RUNNING", (2, "UNKNOWN")) == "UNKNOWN"
payload_by_id = {}

def accept_identity(key, digest):
    existing = payload_by_id.get(key)
    if existing is not None and existing != digest:
        raise ValueError("same identity with different payload")
    payload_by_id[key] = digest

key = ("tenant-a", "message-1")
accept_identity(key, "payload-digest-a")
accept_identity(key, "payload-digest-a")
try:
    accept_identity(key, "payload-digest-b")
except ValueError:
    pass
else:
    raise AssertionError("changed payload must be rejected")
assert payload_by_id[key] == "payload-digest-a"
print("terminal, duplicate, attempt and identity model passed")
