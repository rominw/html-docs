2. Kafka 和 RabbitMQ 应先按什么职责比较？

从机制到边界，再用具体交错检验结论。

记忆关键词：可重放日志 · 分区与组 · 路由队列 · 消费位置

先这样回答

Kafka 的常见模型是有保留期的分区日志和消费位置，RabbitMQ 的常见工作队列模型是交换机路由到队列再投递。先比较重放、路由、确认和负载组织，不把名称变成速度排名。

拆开机制与保证范围

Kafka 日志中的记录在保留契约内可被不同消费组独立读取，某个组推进 offset 不意味着其他组失去数据。分区是顺序和常见消费并行的重要范围；分区数量、键分布与保留策略共同约束容量和恢复。

RabbitMQ 发布到 exchange，按类型、binding 和 routing key 等路由到队列；普通工作队列中的消费者通常竞争处理投递。队列类型与 Streams 提供的能力不同，不能说 RabbitMQ 一概无法重放或所有队列都具备同一复制保证。

告警中转可能需要独立下游消费与回放，任务分发可能需要灵活路由、确认和重试；这些是需求推导，不是给简历项目强行补不存在的架构。选型还要核对消息大小、延迟、保留、运维和异常恢复。

项目推演：同一告警要给统计与外发系统独立读取，两套消费位置便于各自恢复；同一执行任务由一组 worker 竞争处理，则要关注资格、确认与幂等。

继续追问：“Kafka 更快所以全部换？”须比较业务契约。“一个 Topic 对应一个业务事务？”传输组织不自动等于事务边界。

如何验证：画出谁保留记录、谁拥有消费位置、谁决定路由和谁提交副作用；在隔离环境验证多个组/队列、回放与消费者故障的行为。

3. Publisher confirm、consumer ack 与数据库提交差在哪一步？

从机制到边界，再用具体交错检验结论。

记忆关键词：发送受理 · Broker 契约 · 消费完成 · 本地提交

先这样回答

发布确认覆盖发布者与 broker 的相应交互，消费确认覆盖投递与消费者；二者独立。业务提交何时完成由消费者自己的资源与协议决定。

拆开机制与保证范围

连接写入成功只说明某些字节被本地发送路径接受，未证明 broker 保存。发布确认的意义还与队列类型、持久化和复制配置有关。消息未路由到目标队列也需要相应 return/路由处理，不能看到 confirm 就自动认为业务队列存在。

消费者先 ack 再写数据库，ack 后崩溃会留下“消息已处理但效果未发生”的缺口；先提交数据库再 ack，崩溃会导致重投。后者配合原子去重和业务提交，通常更容易实现可靠恢复，但不能因此声称没有重复投递。

MQ 消息和 SQL 事务属于不同提交系统。outbox 保护发布意图，消费去重表与业务更新在同一数据库事务中保护消费效果；如果消费者还调用设备，仍有下一层不确定窗口，不能把数据库幂等扩展为设备幂等。

项目推演：任务状态已提交，消费者尚未 ack 就退出。重投后检查相同 eventId 的已完成记录并返回，而不是重新建任务或生成新的下发身份。

继续追问：“自动 ack 可以省代码？”减少代码但可能改变失败保证。“durable queue 就绝不丢？”还要消息持久、确认、复制和故障模型。

如何验证：在 broker 接受、confirm 接收、业务提交与 ack 之间各断开一次，分别核对消息记录、重投次数和实际业务效果。

4. 为什么同分区顺序仍不保证应用完成顺序？

从机制到边界，再用具体交错检验结论。

记忆关键词：分区读取顺序 · 异步执行 · 连续前缀 · 业务版本

先这样回答

日志顺序、交付顺序、开始处理顺序和副作用完成顺序是四个概念。应用把消息并行派发后，必须自己管理同一业务键的顺序和安全提交位点。

拆开机制与保证范围

同一业务键稳定进入同一分区，有助于建立顺序范围；多个生产者的业务因果、分区数变更和键分配策略仍需讨论。分区里先记录 A 后记录 B，不代表设备先完成 A 后完成 B。消费者线程池可以让 B 先执行完。

Kafka 提交的是下次应读取的位置。收到 offset=102 的完成回调时，如果 100/101 尚未完成就提交 103，重启会跳过缺口。应推进已安全处理的连续前缀，而不是简单取已完成消息的最大 offset。重平衡时还需限制旧拥有者的迟到写入。

任务状态可用业务版本或合法状态转移拒绝旧事件；要求同键严格串行时，可以按键组织执行并对热点做预算。RabbitMQ 的多消费者、重投和优先级等也会改变观察到的顺序，不能仅用“队列先进先出”概括完成语义。

项目推演：100、101、102 同时被提交到池中，102 最先完成。安全重启位置仍为 100；等 100 完成才到 101，最后 101 完成后才可到 103。

继续追问：“单线程消费就全部有序？”外部副作用、重试与多个来源仍需明确。“按最大时间戳更新？”时钟和因果并不天然一致，优先用业务版本契约。

如何验证：下方模型验证所有完成排列得到同一安全前缀；真实 broker 还需测试重平衡、旧 worker 回调和分区变化，核对业务状态。

5. Kafka 的幂等生产与事务为何不等于任意业务 exactly-once？

从机制到边界，再用具体交错检验结论。

记忆关键词：生产序号 · Kafka 事务 · read_committed · 外部边界

先这样回答

幂等生产解决特定生产重试造成的日志重复；Kafka 事务可以覆盖 Kafka 输出与相应位点。它们不自动覆盖任意数据库、设备或 HTTP 副作用。

拆开机制与保证范围

生产者重发因确认丢失而产生的同一发送，可由支持的幂等协议识别；应用重建一条“语义上相同”的新业务消息，未必落入同一协议身份。业务 eventId 与生产者内部序号不应混为一谈。

从 Kafka 消费再向 Kafka 生产时，可在相应事务内提交输出和消费位置，配合 read_committed 读取已提交结果。事务身份、超时、失败与客户端配置仍有契约，消费者看到控制边界与阻塞行为也需要纳入理解。

若在事务中先调用设备起飞，再 Kafka 事务失败，Kafka 不会把已起飞设备“回滚”。跨外部系统的精确一次效果，需要外部资源共同支持稳定身份、去重或原子位点与结果提交。没有共同协议时，表达可证明的范围比背口号更有用。

项目推演：告警经 Kafka 中转后调用外部平台，外部成功但回包丢失。Kafka 中转事务正确也不能判断外发未执行，应使用外发身份和平台查询协议。

继续追问：“开启事务还能少做幂等吗？”先看副作用全部在哪个系统。“read_committed 读不到未提交就绝对实时？”还受事务进展、消费位置与服务负载影响。

如何验证：分别测试生产确认丢失、事务中止、消费者隔离和外部成功后断线；用日志记录与外部业务事实双重核对。

6. 重试、死信和异步补偿为什么必须有预算与语义？

从机制到边界，再用具体交错检验结论。

记忆关键词：可重试分类 · 指数退避 · 毒消息 · UNKNOWN · 对账

先这样回答

重试只对仍有价值且可安全再次尝试的失败有用；死信保存待处理记录，补偿产生新的业务动作。三者都不能替代失败分类与真实结果查询。

拆开机制与保证范围

输入契约错误、永久拒绝与资源暂时不可用应分开。每次重试消耗并发与 deadline，退避和抖动降低同步冲击；次数、总时间和队列大小必须有限。结果未知时先查证，不能把它塞进普通“失败后重做”策略。

死信交换是再发布和路由过程，目标不可用、配置或队列类型会影响安全保证；不是给任意消息一个永不丢失的保险箱。毒消息重放前要修复原因、保留原身份并审核范围，避免批量重放重新触发真实执行。

补偿是与原动作关联的新动作，如释放保留资源，不是时间倒流。释放本身也会失败或被重复投递，需幂等且只针对自己持有的资格。对账任务读取权威结果并推进未收敛状态，保留可解释的异常，而不是无限重试到日志消失。

项目推演：任务超时可能已经下发。补偿立即释放机库后新任务占用，旧任务却仍在执行，形成资源冲突；必须先确认设备状态和保留资格的真实含义。

继续追问：“进死信就闭环？”还要责任、查证与恢复。“重试成功即最终正确？”要核对有没有重复效果和错释放。

如何验证：覆盖永久错误、长时间不可用、确认丢失和死信目标故障；记录每个身份的尝试预算、查证结果及补偿结果。

7. Prefetch、lag 和消费者线程池如何形成背压？

从机制到边界，再用具体交错检验结论。

记忆关键词：未确认预算 · 拉取预算 · 内存大小 · 下游容量

先这样回答

broker 的消费控制只能限制特定传输范围。应用内部队列、线程池和下游调用仍需预算，否则只是把积压从 broker 搬进进程。

拆开机制与保证范围

RabbitMQ prefetch 限制相应消费范围内的未确认消息数量，配置作用域与客户端/协议模式要核对。消息大小差异很大时，数量上限不等于字节内存上限；消费者收到后再放入无界队列，依然可能 OOM。

Kafka lag 表示某个消费位置与日志进展的差距，但位点提前提交会掩盖应用内部未完成积压。还需看 poll、执行、提交、队列与下游时间；处理过久可能影响组成员资格，配置并行处理时要遵守客户端线程与重平衡契约。

消费速度应受真实下游容量约束，批处理改善吞吐但会增加单批内存和重试放大。停机时先停止接收新工作，再等待有界在途任务，正确提交或保留未完成消息；不能在退出钩子里无条件 ack 全部。

项目推演：consumer lag 很低，进程却堆了数万条异步任务：位点已经推进到队列尾，但业务结果尚未提交。这是确认协议错误，不是 Kafka 消费能力很强。

继续追问：“提高 prefetch 一定提速？”到达下游瓶颈后只会积压。“多加消费者一定均衡？”热点分区、键和资源容量仍限制并行。

如何验证：慢化数据库或模型调用，验证未完成条数和字节有上限；停机重启后核对未提交消息不会被跳过，已完成效果不会重复。

8. 练习：从能讲到能反驳自己的假设

先说预期，再运行；如果结果相反，回到机制与边界。

位点模型练习：乱序完成只能推进连续前缀

Python 3 标准库模型，假设一个分区从 offset=100 开始处理、最多跟踪三个在途位置。不连接 Kafka，不模拟重平衡或数据库提交。

保存为 practice.py，用 python practice.py 运行。

from itertools import permutations

class Completion:
    def __init__(self, start, end):
        self.next_offset, self.end = start, end
        self.done = set()

    def finish(self, offset):
        if offset < self.next_offset:
            return self.next_offset
        if offset >= self.end:
            raise ValueError("not in admitted range")
        self.done.add(offset)
        while self.next_offset in self.done:
            self.done.remove(self.next_offset)
            self.next_offset += 1
        return self.next_offset

progress = Completion(100, 103)
assert progress.finish(102) == 100
assert progress.finish(100) == 101
assert progress.finish(101) == 103
assert progress.finish(101) == 103
for order in permutations([100, 101, 102]):
    progress = Completion(100, 103)
    seen = set()
    for offset in order:
        seen.add(offset)
        committed = progress.finish(offset)
        assert all(x in seen for x in range(100, committed))
    assert progress.next_offset == 103
print("all completion orders preserve the safe prefix")
