1. 从工程场景建立原理地图

Spring Boot · Spring Cloud · Spring MVC · MyBatis-Plus

典型应用场景

Spring Boot／Cloud 服务通过 MyBatis-Plus 访问数据库，并用配置表组织业务接入。从请求进入到代理、事务和远程调用，逐层分析框架执行路径与业务边界。

本篇核心问题

能画出请求进入、代理拦截、SQL 执行、事务提交与外部调用的顺序，并解释哪个注解在哪个路径才生效。

阅读方式：先用记忆关键词复述机制，再推演例子的失败窗口，最后明确验证对象。场景用于解释技术取舍；练习能证明什么、不能证明什么，见版本与验证范围。

版本与验证范围：容器与事务以 Spring Framework 6.2 的常见代理模式为基线；Boot、Cloud、MyBatis-Plus 的具体版本和插件顺序需以项目依赖为准。配置练习只推演版本切换。

2. Spring 容器和 Boot 自动配置，分别解决什么问题？

从机制到边界，再用具体交错检验结论。

记忆关键词：定义 → 实例化 → 注入 → 初始化 → 后处理 → 发布

核心结论

容器管理对象及其依赖和生命周期，Boot 自动配置根据类路径、属性和已有 Bean 等条件补充定义。启动成功不说明某个预期 Bean 或代理一定生效。

拆开机制与保证范围

容器先拥有 Bean 定义，再按依赖关系创建和注入对象，随后执行初始化和后处理；最终对外提供的引用可能是代理。不要把对象构造完成、初始化完成和代理可被外部调用混成一个时点，尤其不要依赖初始化方法内的自调用触发事务。

自动配置的条件决定是否装配，应用自定义 Bean 常会使某些默认配置退让。这个行为随具体配置类而定；排查应查看条件报告、实际 Bean 类型与来源。把“加了 starter”当成启用全部能力，会忽略缺少属性、类或显式排除等条件。

Spring MVC 常见请求路径是过滤器和 DispatcherServlet、映射与参数处理、控制器及异常/返回值处理。AOP 拦截 Bean 方法与 HTTP 过滤器处在不同层次，鉴权、日志、事务和流式响应资源不能只靠一个注解覆盖全部路径。

场景推演：自定义一个同类型连接 Bean 后，默认装配可能退让；HTTP 接口仍可启动，但真正连接的地址与操作者预期不同。需要查运行时对象而不是只看配置文件。

进一步思考：“单例就是线程安全？”单例只说明作用域。“循环依赖能启动就可以接受？”还要检查早期引用、构造依赖与代理完整性。

如何验证：通过条件评估报告和 Bean 清单核对实际配置；分别覆盖属性缺失、自定义 Bean、初始化失败和请求异常路径。

3. @Transactional 为什么会失效？该从哪里追？

从机制到边界，再用具体交错检验结论。

记忆关键词：调用经过代理 · 方法可拦截 · 事务管理器 · 异常规则

核心结论

先确认运行时调用是否经过事务代理，再检查事务管理器、资源绑定和回滚规则。默认代理模式下，同一对象的自调用不会新增一次事务拦截。

拆开机制与保证范围

外部调用代理对象时，拦截器在进入目标方法前获取或加入事务，返回或抛错后处理提交与回滚。this.inner() 调到目标自身，绕过了这层新增拦截；如果外层已有事务，inner 仍可能在该事务中执行，但它自己的传播设置未因此生效。

回滚规则与异常传出路径有关。常见默认对 RuntimeException 和 Error 回滚，checked exception 通常需配置；如果代码吞掉异常，代理可能看到正常返回。必须按实际版本、全局设置与业务回滚规则核对，不能只看注解存在。

普通命令式事务往往绑定当前线程，新开的线程不会自动继承同一连接与事务；响应式事务使用另一套上下文机制。远程 HTTP、MQ 和 IoT 调用也不是 JDBC 本地事务的参与者。代理修复解决的是拦截范围，不是分布式原子性。

场景推演：外层方法直接调用同类的 REQUIRES_NEW 方法，期望审计独立提交却没有新事务；修复为外部经过独立 Bean 的代理调用后，还需测试两个事务的真实失败语义。

进一步思考：“private 方法能不能加注解？”注解可写不等于当前代理能拦截。“改 public 就够？”还得经过代理且匹配事务配置。

如何验证：从代理入口发起集成测试，分别抛运行时/受检异常、吞异常和切线程，观察数据库提交结果与连接边界；纯模型练习不能证明事务注解有效。

原始资料 03 · 可运行练习与自测

4. REQUIRED、REQUIRES_NEW 与连接池有什么关联？

从机制到边界，再用具体交错检验结论。

记忆关键词：逻辑事务 · 物理连接 · rollback-only · 挂起与资源预算

核心结论

REQUIRED 通常加入现有物理事务；REQUIRES_NEW 使用独立物理事务并挂起外层资源。传播模式既改变回滚关系，也改变连接占用与锁等待。

拆开机制与保证范围

多个 REQUIRED 逻辑范围可能共享同一事务。内部范围标记 rollback-only 后，外层即使捕获异常并继续，最终也可能得到 UnexpectedRollbackException；外层正常返回并不能改变物理事务已不可提交的事实。

REQUIRES_NEW 的独立提交可用于某些审计需求，但外层持有连接时，内层还需要另一条连接。所有请求都持有外层连接并等待内层连接，会使池子耗尽。内层还可能尝试获取外层已经持有的数据库锁，因此“独立”不等于没有依赖。

NESTED 常基于保存点，在同一物理事务内局部回滚，支持与语义取决于事务管理器和驱动。不能把它等同独立持久提交，也不能用传播名称证明审计已跨外层失败存活。先给出业务意图，再选资源契约。

场景推演：假设连接池容量为 N，N 个请求各持有外层连接并进入 REQUIRES_NEW，内层全都等连接。增加 HTTP 线程会增加等待者，无法凭空生成数据库容量。

进一步思考：“扩大连接池就解决？”还要核对数据库容量和锁关系。“回滚失败日志也被回滚？”应明确日志要保留的提交边界，不能随意嵌套事务。

如何验证：设置有限池容量，在隔离数据库中观察 active/pending、事务 ID 和锁等待；覆盖内层失败、外层失败和 rollback-only，而不只测成功路径。

原始资料 04 · 可运行练习与自测

5. MyBatis-Plus 如何把方法变成 SQL？插件为何不能当业务保证？

从机制到边界，再用具体交错检验结论。

记忆关键词：MappedStatement → 参数绑定 → 拦截器 → SQL → 影响行数

核心结论

MyBatis 执行映射语句并绑定参数，MyBatis-Plus 在此基础上提供 CRUD 与插件。真正保护数据的是最终 SQL、数据库约束和影响行数的处理。

拆开机制与保证范围

一个 Mapper 调用会选择映射语句，构造参数和 SQL，经过执行器、语句处理及配置的拦截路径，再映射结果。参数绑定与字符串拼接不同：把用户输入放进 ${...} 等直接替换位置，会改变 SQL 结构；动态排序字段需采用允许列表。

乐观锁常把 version 作为更新条件并推进新版本，但只在受支持的操作、参数与插件配置下生效。自定义 SQL、批量路径或遗漏版本条件时，需要自行保证。更新影响行数为零可能意味着版本冲突、状态条件不满足或记录不存在，不能统一当成功。

租户、逻辑删除、分页和乐观锁拦截器改变最终语句，但不能证明所有手写 SQL 和绕过 Mapper 的路径都被保护。插件顺序还会影响分页和其他改写。二级缓存、连接和事务生命周期也应按 MyBatis/Spring 的整合方式理解。

场景推演：机库占用使用 UPDATE ... WHERE status=IDLE AND version=oldVersion。两个请求同时执行时，必须由数据库判定只有合格更新获胜，并把零行更新返回为占用失败。

进一步思考：“用了乐观锁就不用唯一约束？”版本保护更新，唯一约束保护不同身份的重复插入。“分页 total 一定便宜？”还要单独检查 count SQL 的成本。

如何验证：查看最终绑定 SQL、租户条件与影响行数；覆盖自定义 Mapper、插件顺序、并发冲突和逻辑删除，避免只看 ORM 返回对象。

原始资料 06 · 可运行练习与自测

6. Spring Cloud 的服务发现、负载均衡、重试和熔断如何串起来？

从机制到边界，再用具体交错检验结论。

记忆关键词：发现目标 · 选实例 · deadline · 重试预算 · 隔离

核心结论

发现和负载均衡选择调用目标，重试重新尝试，熔断控制继续调用的资格。它们处理远程不确定性，不能把超时变成“对方未执行”。

拆开机制与保证范围

实例列表有缓存与更新延迟，客户端连接池还可能复用已有连接。目标已摘除不代表所有旧连接和在途请求立即消失；负载均衡也不能只凭 Pod 数均分真实负载，长连接、热点键与服务时间都会造成偏斜。

每层都配置重试会放大请求：网关、客户端和消费者的尝试可能相乘。一次端到端 deadline 要分配给排队、连接、读写与后续尝试，剩余时间不足时停止。读请求也可能昂贵；执行类请求要绑定稳定动作身份，不能仅以 HTTP 方法判定可重试。

熔断依据采样窗口和配置对后续调用做决策，半开探测需要限量；它既不是事务回滚，也不取消所有在途工作。fallback 应表达真实能力，如“暂时不可查询”，不能把假成功或旧数据伪装成权威执行结果。隔离还需要有界连接、线程和队列。

场景推演：任务下发超时，重试到另一实例。若第二实例生成新动作身份，设备可能再次执行；保留原身份并查询受理/执行结果才能判断下一步。

进一步思考：“熔断后就不堆积？”其他队列和在途请求仍可能存在。“发现健康实例就安全？”健康只说明特定探测，不证明业务容量和任务幂等。

如何验证：模拟摘实例、慢响应、回包丢失和多层重试，核对尝试次数、真实执行次数及总 deadline；分别观察各实例负载和连接复用。

7. “只改接口配置，不改代码”背后需要哪些原理？

从机制到边界，再用具体交错检验结论。

记忆关键词：类型化契约 · 允许列表 · 版本快照 · 原子发布 · 审计

核心结论

配置驱动把变化从代码移到受约束的数据。它仍需要语义校验、版本和发布协议，否则只是把运行时错误与安全边界隐藏进配置表。

拆开机制与保证范围

接口配置可以描述路由、参数映射、返回字段和超时，但必须限定可表达的能力。URL、HTTP 方法、字段路径和模板变量都要按契约校验；不能允许配置任意访问内网、执行脚本或把用户输入变成无约束远程请求。

同一次调用应使用同一配置快照。若路由读取 v2，参数映射却读取 v1，就可能把正确字段发给错误接口。做法是校验整个版本后再整体发布，并在请求开始时捕获快照；在途请求是否使用旧版本，应有明确兼容策略。

Spring 的配置绑定负责把数据转换到类型，不能代替业务语义验证。配置回滚只回滚后续请求的路由，不自动撤销已完成的副作用；审计要把配置版本、请求身份、实际目标和结果联系起来。

场景推演：表单接口 v1 用 departmentId，v2 用 orgCode；如果只更新部分行，用户看起来填表成功，后端却把组织映射错。发布前用固定样例做端到端契约验证。

进一步思考：“做成万能 DSL 更灵活？”表达能力越强，验证和治理成本越大。“热更新要加锁吗？”要保护版本一致性；不可变快照整体替换是一种选择。

如何验证：下方模型练习验证快照不被后续发布改写；真实框架还需测试属性绑定、无效配置拒绝、权限和下游契约，不把模型自检当作集成验收。

8. 动手验证与故障推演

先推导预期，再运行；如果结果相反，回到机制与边界。

模型练习：一次调用只能看见一份配置版本

Python 3 标准库模型。它验证不可变快照的版本绑定，不调用 Spring，也不验证真实热更新、网络请求或事务代理。

保存为 practice.py，用 python practice.py 运行。

from dataclasses import dataclass

@dataclass(frozen=True)
class Config:
    version: int
    route: str
    field: str

def validate(cfg):
    allowed = {("/form/v1", "departmentId"), ("/form/v2", "orgCode")}
    if cfg.version <= 0 or (cfg.route, cfg.field) not in allowed:
        raise ValueError("invalid configuration contract")
    return cfg

active = validate(Config(1, "/form/v1", "departmentId"))
in_flight = active
active = validate(Config(2, "/form/v2", "orgCode"))
assert in_flight == Config(1, "/form/v1", "departmentId")
assert active == Config(2, "/form/v2", "orgCode")
try:
    validate(Config(3, "/form/v2", "departmentId"))
    raise AssertionError("mixed contract accepted")
except ValueError:
    pass
print("snapshot isolation and invalid contract rejection passed")
