1. 定位：Boot 是什么、不是什么

它是脚手架和默认答案，不是另一套框架。

它不是

不是 Spring 的替代品。容器还是 IoC，增强还是 AOP，ApplicationContext 还是那一个——Boot 没有重写内核。

它是

四件事的打包：starter 依赖管理（版本对齐）+ 自动装配（条件化默认配置）+ 内嵌容器（jar 直接跑）+ 生产特性（Actuator、指标、健康检查）。

一句话

Boot 把"一个典型 Spring 应用应该配什么"写成了条件化的默认答案——你不配就给你默认的，你配了就尊重你的（@ConditionalOnMissingBean）。

三部曲导航：① IoC 篇：容器、Bean 生命周期与循环依赖 · ② AOP 篇：BeanPostProcessor、动态代理与拦截器链 · ③ Boot 篇（本篇）。本篇两处回到前两篇：自动装配发生在 refresh 的 BeanFactoryPostProcessor 阶段（IoC 篇第 5 节），AOP 代理发生在最后的单例实例化阶段（AOP 篇第 5 节）。

2. @SpringBootApplication 拆解

一个注解三个身份，每个都有独立职责。

@SpringBootConfiguration   // 就是 @Configuration：主类也是一个配置类
@EnableAutoConfiguration   // ★ 自动装配总开关（下一节主角）
@ComponentScan             // 扫描主类所在包及子包的 @Component
  • @SpringBootConfiguration：身份是配置类，所以主类里的 @Bean 一样生效；它单独起名是为了在测试和嵌套配置场景里可被识别；
  • @ComponentScan：默认扫主类所在包——这就是"启动类要放根包"的原因：放错了，你的 Service 就扫不到；
  • @EnableAutoConfiguration：唯一的"魔法"入口，其余两个都是普通 Spring 能力。

高频考点：三个注解各自能干什么可以独立追问；但"自动装配"只由 @EnableAutoConfiguration 负责——很多候选人把 @ComponentScan 扫 Bean 也说成自动装配，这两条是完全不同的注册路径（扫描 vs 配置类 import）。

3. 自动装配全链路（主菜）

从注解到 BeanDefinition 的完整路径，条件过滤是灵魂。

常用条件注解含义典型用途
@ConditionalOnClass类路径存在某类才生效引了 tomcat 依赖才装配 Tomcat——"有什么依赖就配什么"的实现基础
@ConditionalOnMissingBean容器里没有该 Bean 才生效用户自己配了就用用户的——"可覆盖的默认值"，Boot 可定制性的核心
@ConditionalOnProperty配置项满足条件才生效spring.datasource.url 存在才配数据源；开关式装配
@ConditionalOnWebApplication是 Web 环境才生效Servlet / Reactive 环境分叉

衔接前两篇：自动配置类最终以配置类身份进入容器，在 refresh() 的 invokeBeanFactoryPostProcessors 阶段被解析（IoC 篇的"改配方"阶段）；它们内部的 @Bean 再在最后的单例实例化阶段创建实例——AOP 代理就挂在那一环。三部曲在这里闭环。

4. 启动流程：SpringApplication.run

Boot 的壳（run）包着 Spring 的芯（refresh）。

主类是入口

prepareContext 阶段把主类注册为配置类；refresh 解析它时才触发 @ComponentScan（扫你的 Bean）和 @EnableAutoConfiguration（装默认 Bean）——两条注册路径从此并行。

Tomcat 在 onRefresh 创建

不是"启动完再开服务器"：ServletWebServerApplicationContext 覆写 onRefresh，容器刷新到一半就把内嵌 Tomcat 建好、端口监听起来。

Runners 是业务钩子

容器完全就绪后执行，常用来做启动预热、缓存加载、延迟任务的触发入口——拿得到完整的容器，又早于对外服务。

面试高频陷阱："自动装配发生在启动的哪一步？"——不是 main 方法一进来，而是 refresh 的 invokeBeanFactoryPostProcessors（解析主配置类时）。答出这个位置，说明你把 Boot 的壳和 Spring 的芯真正接上了。

5. Starter：原理与自定义

starter = 依赖聚合 + 自动装配入口，没有任何新机制。

官方 starter 在做什么

  • 依赖聚合：把某场景需要的一组依赖（含版本）打包成一个坐标，比如 spring-boot-starter-web 拉 Spring MVC + Jackson + Tomcat；
  • 版本对齐：父 POM / BOM 统一管版本，你只挑场景不挑版本——"约定优于配置"的依赖层体现；
  • 空壳设计：很多官方 starter 本身没有代码，只是依赖清单；真正的装配逻辑在 spring-boot-autoconfigure 里。

自定义 starter 四步

// 1. 建模块：xxx-spring-boot-starter（依赖 autoconfigure 模块）
// 2. 写属性类
@ConfigurationProperties(prefix = "xxx")
public class XxxProperties { ... }

// 3. 写自动配置类
@AutoConfiguration
@ConditionalOnClass(XxxService.class)
@EnableConfigurationProperties(XxxProperties.class)
public class XxxAutoConfiguration {
    @Bean @ConditionalOnMissingBean
    public XxxService xxxService(XxxProperties p) { ... }
}
// 4. 登记：META-INF/spring/org.springframework.boot
//        .autoconfigure.AutoConfiguration.imports 写入配置类全名

检验标准：别人引你的 starter + 在 yml 里写 xxx.* 就能改变行为，配自己的 @Bean 就能整体替换——做到这两点，说明条件装配的两面（默认值 + 可覆盖）都用对了。

6. 配置体系与内嵌容器

外置配置怎么加载、两种绑定注解怎么选。

维度@ConfigurationProperties@Value
绑定方式批量：一个前缀绑定整组字段单个：一个表达式一个值
松散语法支持（user-name/userName/USER_NAME 互通）需精确匹配
表达式 / SpEL不支持支持（#{...}）
校验 / 元数据支持 JSR-303 校验、IDE 提示（配置元数据文件）无
绑定时机都发生在 Bean 生命周期内：@ConfigurationProperties 由 ConfigurationPropertiesBindingPostProcessor（一个 BPP，见 IoC/AOP 篇）在初始化前绑定；@Value 在属性填充阶段注入

配置优先级（外置覆盖内置）

命令行参数 > SPRING_APPLICATION_JSON > 环境变量 > application-{profile}.yml > application.yml > @PropertySource / 默认值。原则：越靠外、越贴近部署环境的越赢。

profile 多环境

spring.profiles.active 激活；同一配置项，激活的 profile 文件覆盖默认文件——测试 / 预发 / 生产一份代码多套配置。

内嵌容器

ServletWebServerFactoryAutoConfiguration 按 classpath 选容器（默认 Tomcat，换 Undertow 只要换依赖）；onRefresh 创建、finishRefresh 启动。可执行 FatJar 由 Boot 的 Launcher 引导，java -jar 直接跑，不再需要外置 Tomcat。

7. 面试口述简记卡片

每张 30~60 秒。B1 和 B4 是高频中的高频。

B1 · Spring Boot 自动装配原理 ≈60s · 高频

@EnableAutoConfiguration 通过 @Import 引入 AutoConfigurationImportSelector，它的 selectImports 读取所有 jar 里 META-INF/spring 目录下的 AutoConfiguration.imports 文件——旧版本是 spring.factories——拿到一百四十多个自动配置类的全量候选，先去重和按 exclude 排除，再经过 @Conditional 家族过滤：OnClass 判断类路径有没有依赖、OnProperty 判断配置开关、OnMissingBean 判断用户有没有自己配，条件不满足的直接淘汰，剩下的以配置类身份注册成 BeanDefinition，里面的 @Bean 在单例实例化阶段创建。整个过程发生在 refresh 的 invokeBeanFactoryPostProcessors 阶段，也就是解析主配置类的时候。一句话：自动装配就是"按条件装配的默认配置"，用户配置优先由 OnMissingBean 保证。

B2 · @SpringBootApplication 三个组成 ≈30s

拆成三个注解：@SpringBootConfiguration 本质是 @Configuration，说明主类自身是一个配置类，里面的 @Bean 一样生效；@ComponentScan 默认扫描主类所在包及子包，这是启动类要放根包的原因；@EnableAutoConfiguration 是自动装配总开关。注意扫描和自动装配是两条独立的注册路径：前者注册你写的组件，后者注册框架的默认配置，别混为一谈。

B3 · SpringApplication.run 启动流程 ≈45s

分六步：第一，构造 SpringApplication 时推断应用类型，加载 ApplicationContextInitializer 和监听器；第二，准备 Environment，把 application.yml、命令行参数、环境变量、profile 都装进环境；第三，按应用类型创建 ApplicationContext 并 prepareContext，把主类注册为配置类；第四，调 refresh——解析配置类、扫描加自动装配、注册 BeanPostProcessor；第五，refresh 的后半程在 onRefresh 创建内嵌 Tomcat，在 finishBeanFactoryInitialization 实例化所有单例，AOP 代理也在这一步生成；最后执行 ApplicationRunner 和 CommandLineRunner，发布就绪事件。核心记忆点：Boot 的 run 是壳，Spring 的 refresh 是芯。

B4 · 自动装配发生在启动的哪一步 ≈30s

发生在 refresh 的 invokeBeanFactoryPostProcessors 阶段。主类在 prepareContext 时被注册为配置类，refresh 解析它时，@Import 进来的 AutoConfigurationImportSelector 作为配置类解析的一部分被触发，候选清单、条件过滤、注册 BeanDefinition 都在这一个阶段完成；而候选里的 @Bean 真正实例化要等到 finishBeanFactoryInitialization 批量创建单例的时候。区分"注册定义"和"创建实例"两个时机，这题就算答透了。

B5 · @ConditionalOnMissingBean 的作用 ≈30s

它是 Boot"可覆盖的默认值"的实现机制：自动配置类里的 @Bean 加了这个条件，只有容器里不存在同类型 Bean 时才生效。因为用户自定义的配置先被处理，所以用户配了自己的 DataSource 或 RedisTemplate，自动装配就让位。这就是为什么 Boot 给了全套默认配置却不挡着你自己定制——约定优于配置，但配置永远赢过约定。

B6 · 怎么自定义一个 starter ≈40s

四步：建两个模块，一个 autoconfigure 放逻辑，一个 starter 只做依赖聚合；写 XxxProperties 用 @ConfigurationProperties 绑定 xxx 前缀的配置；写 XxxAutoConfiguration，类上 @AutoConfiguration 加 @ConditionalOnClass 判断核心类在不在，@EnableConfigurationProperties 启用属性，里面的 @Bean 加 @ConditionalOnMissingBean 保证用户可覆盖；最后在 META-INF/spring 的 AutoConfiguration.imports 文件里登记配置类全名。检验标准：引入即生效、yml 可调、用户自己配 Bean 能整体替换。

B7 · @ConfigurationProperties vs @Value ≈30s

ConfigurationProperties 是批量绑定，一个前缀对应一组字段，支持松散语法、JSR-303 校验和 IDE 元数据提示，适合结构化配置；@Value 是单值绑定，支持 SpEL 表达式，适合取一两个简单值。绑定时机都在 Bean 生命周期内：前者由 ConfigurationPropertiesBindingPostProcessor 在初始化前完成绑定——它本身就是一个 BeanPostProcessor；后者在属性填充阶段注入。选型原则：成组的配置用前者，零散的单值用后者。

B8 · 配置文件优先级 ≈30s

总原则是外置覆盖内置、越靠近部署环境的优先级越高：命令行参数最高，然后是 SPRING_APPLICATION_JSON、操作系统环境变量、profile 指定的 application-{profile}.yml、默认的 application.yml，再往下是 @PropertySource 和代码默认值。同一个 key，高优先级直接覆盖低优先级而不是报错。profile 机制让一份代码配多套环境，激活的 profile 文件覆盖默认文件，这也是它能生效的原理。

B9 · 内嵌容器怎么启动的 ≈30s

ServletWebServerApplicationContext 覆写了 refresh 里的 onRefresh，在这里根据 classpath 创建对应的 WebServer——classpath 有 tomcat 就建 Tomcat，换 Undertow 只要换依赖，这正是 ServletWebServerFactoryAutoConfiguration 加 ConditionalOnClass 实现的；容器刷新到 finishRefresh 时调用 WebServer 的 start 端口就监听起来。加上 Boot 的 FatJar 和 Launcher 引导，java -jar 直接运行，部署不再依赖外置容器。

B10 · Boot 2.6 为什么默认禁止循环依赖 ≈30s

官方认为循环依赖是设计坏味道，而且三级缓存这套解法有边界（构造器注入和 prototype 本来就解不了），全量默认放开容易掩盖问题，所以 2.6 起 allow-circular-references 默认 false，出现循环直接启动失败。需要打开要显式配置。出现循环依赖时的推荐处理：优先重构，把两个 Bean 互相依赖的公共逻辑下沉到第三个 Bean；临时缓解用 @Lazy 打断一边，注入的是代理，首次调用才真正创建。

使用建议：B1 是 Spring Boot 面试的第一题，务必练到不看稿能说；B4 是区分度题，把"注册定义 vs 创建实例"两个时机分开讲。三部曲收尾：IoC 篇管"对象怎么来"，AOP 篇管"功能怎么增强"，本篇管"配置怎么自动来"——Spring 面试的完整骨架就这三根柱子。
