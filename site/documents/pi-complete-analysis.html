一、项目总览

Pi（@earendil-works/pi-*）是一个开源、可自扩展的 AI 编码智能体 monorepo，由 earendil-works 维护（核心作者 Mario Zechner / badlogic，即 libGDX 的创建者）。它的旗舰产品是 pi——一个交互式 CLI 编码智能体，同时提供了完整的多模型 LLM 接入层、智能体运行时框架、终端 UI 库和远程会话基础设施。

核心组成

pi-coding-agent 应用层

交互式 CLI 编码智能体。提供 read、bash、edit、write、grep、find、ls 七个内置工具，支持交互式 TUI、非交互打印、JSON 事件输出、RPC 远程四种模式。

pi-agent-core 运行时

三层智能体运行时：无状态循环 AgentLoop、有状态封装 Agent、产品级线束 AgentHarness。支持会话分支、上下文压缩、技能系统、29 种细粒度事件。

pi-ai 基础层

统一 38 个 LLM 厂商的接入层。三层架构（Models → Provider → API Module），懒加载避免拉入重依赖，自动模型发现脚本从 models.dev 等数据源生成完整目录。

pi-tui 基础层

差分渲染终端 UI 库。行级 diff 算法只重绘变化区域，flexbox 风格布局引擎，Kitty/Legacy/modifyOtherKeys 三层键盘协议匹配，overlay 浮层系统。

二、架构分层

整个 monorepo 严格分为三层，依赖方向只能从上到下——应用层依赖运行时层，运行时层依赖基础层，基础层之间互不依赖。

↑ 箭头指向被依赖方。pi-coding-agent 作为"聚合者"，向上汇聚了五个基础/运行时包。

分层规则

层包规则
基础层pi-ai / pi-tui / pi-protocol互不依赖，各自独立
运行时层pi-agent-core / pi-client / pi-storage只依赖基础层
应用层pi-coding-agent / pi-server依赖运行时 + 基础层
独立pi-evals评测工具，不参与核心架构

@earendil-works/pi-ai 是整个项目的 LLM 基础设施，统一了 38 个 LLM 厂商的接入。它的设计目标是让上层代码不需要关心"你调用的是 Anthropic 还是 OpenAI"——所有差异在 API 适配层被抹平。

所有 API 适配器都输出统一的 12 种流式事件，上层只需要处理这套协议：

  | { type: "start"; partial: AssistantMessage }

3.3 模型自动发现

scripts/generate-models.ts（2862 行）从 models.dev、OpenRouter、Vercel AI Gateway 三个数据源拉取模型目录，经过合并、去重、手动覆盖后，生成：

  • src/providers/data/*.json — 模型元数据
  • *.models.ts — 类型安全的薄包装
  • models.generated.ts — 聚合入口

懒加载机制

每个 API 适配器都有 .lazy.ts 包装器（仅 4 行），只有在第一次 stream() 调用时才 import() 真正的实现。这样 import @earendil-works/pi-ai 时不会拉入所有厂商的 SDK。

截断安全

当 LLM 响应的 stopReason === "length"（输出被 token 上限截断），所有工具调用一律失败——因为参数可能是不完整的 JSON。失败结果会告诉模型"重新发起调用"。

三层键盘协议匹配：Legacy 转义序列 → Kitty CSI-u → modifyOtherKeys，自动协商最佳协议。StdinBuffer 解决序列分块到达问题（带 10ms 超时）。

可注册的能力

  • registerProvider() — 自定义 LLM 厂商

可订阅的事件（30+）

  • 生命周期：session_start/agent_end
  • 工具：tool_call/tool_result
  • Provider：before_provider_request
  • 输入：input（可拦截）
  • 上下文：context（可修改）

扩展发现路径（按优先级）：

  1. 项目本地：cwd/.pi/extensions/
  2. 全局：~/.pi/agent/extensions/
  3. 显式配置：--extensions 参数

加载使用 jiti 动态导入 TypeScript，支持源码运行、编译 Node.js、Bun 二进制三种模式。

七、pi-protocol — CBOR 传输协议

纯传输层定义，无 I/O 依赖，被 server 和 coding-agent 共用。

CBOR 安全限制

  • 只支持 definite-length（定长），不支持 indefinite-length
  • 不支持 CBOR tags（major type 6）、break marker
  • maxByteLength = 16MB、maxContainerLength = 1M、maxDepth = 64
  • 禁止 -0、循环引用、undefined、Symbol key

八、pi-server — 远程会话服务端

把 coding-agent 包装成可远程连接的会话服务端，支持 Unix Domain Socket 等传输方式。

连接生命周期

  1. 握手：awaitingHello → handshaking → ready（超时 5s）
  2. 就绪：客户端发 RequestEnvelope，服务端执行后回 ResponseEnvelope
  3. 事件推送：服务端主动推 server_snapshot / session_snapshot / session_progress

抽象接口

PiSessionBackend（持久化层）
  ├── listSessions()
  ├── listModels()
  ├── createSession() → PiSessionRuntime
  └── openSession() → PiSessionRuntime

PiSessionRuntime（活跃会话）
  ├── snapshot() / getPhase()
  ├── prompt() / steer() / abort()
  ├── setModel() / setThinking()
  ├── subscribe(event)
  └── dispose()

LiveSessionManager 处理并发打开同一会话的去重（liveSessions Map + openingSessions Promise Map），并在会话空闲时自动 dispose。

  • 禁用 any（除非绝对必要）

  • 多 agent 会话共用同一 cwd，只 stage 自己改的文件（git add <path>）

十二、设计哲学

1. 关注点分离到极致

AgentLoop 只管"怎么循环"，不关心状态怎么存。Agent 只管"状态和生命周期"，不关心会话怎么持久化。AgentHarness 只管"产品级功能"，不关心循环细节。每一层都能独立使用。

2. 状态与逻辑分离

核心循环是纯函数，所有状态通过参数传入，所有输出通过 emit 回调发出。这让循环逻辑可测试、可复用。

3. 核心极简，可扩展

不符合核心定位的功能应做成 extension。仓库有 70+ 个扩展示例，涵盖自定义工具、命令、Provider、渲染器、工作流。一行代码可以启动一个 agent（createAgentSession()），也可以完全控制每个细节。

4. 事件驱动而非回调地狱

29 种细粒度事件让扩展可以在不修改内核的情况下实现权限控制、审计、成本追踪、缓存优化、自定义压缩。钩子和通知的区分让"能改"和"只能看"的边界清晰。

5. 供应链信任

从依赖钉版到生命周期脚本禁用，从 shrinkwrap 到 CI audit，每个环节都不盲信外部代码。
