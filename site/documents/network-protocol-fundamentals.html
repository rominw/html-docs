1. 先看地图:所有协议叠成一座楼

不懂分层,协议学习就是一堆散落的知识点;懂了分层,每个协议的怪癖都有了出处。

读图关键:应用层协议(MQTT、Modbus TCP、OPC UA、HTTP)全部叠在 TCP/UDP 之上——底层特性会向上"漏"问题:TCP 不保证消息边界(→粘包)、不保证对端应用活着(→应用层心跳)、网络断了不替你重发业务消息(→应用层 QoS)。本册主线就是把这三个"漏",与工业协议的设计一一对应。

2. IP 与端口:设备的门牌系统

所有上层协议的第一课:消息怎么找到目标。

IP 地址 = 小区地址

  • IPv4:32 位,形如 192.168.1.10,全世界约 43 亿个,已耗尽
  • IPv6:128 位,fe80::1,号称能给地球上每粒沙子发地址;物联网海量设备的主角
  • 公网 vs 内网:设备通常在内网(192.168.x.x、10.x.x.x),经 NAT 网关共享公网出口——这是"设备主动连云"架构的根本原因(MQTT 设备主动出连,云无法主动进内网)

端口 = 门牌号

  • 16 位(0~65535),区分同一台机器上的不同服务
  • 记牢几个"熟面孔":80 HTTP / 443 HTTPS / 1883 MQTT / 8883 MQTT over TLS / 502 Modbus TCP / 4840 OPC UA / 53 DNS
  • 看到端口号就能反推协议——排查"连不上"的第一步永远是 telnet ip 端口 或 netstat

面试视角:"为什么物联网设备都是主动连云平台,而不是平台连设备?"——设备在内网 NAT 之后没有公网地址,外部无法主动进入;所以 MQTT 让设备主动出连并保持长连接,反向指令也走这条已建立的连接。

3. TCP:可靠字节流是怎么炼成的

面试题密度最高的一章——握手、挥手、粘包,三个考点讲透。

3.1 三次握手:建立连接

为什么握手是三次,两次不行吗?

  • 核心目的:让双方都确认"我能发、他能收;他能发、我能收"
  • 两次的问题:服务端无法确认"客户端能收到我的消息";更致命的是历史重复的 SYN(网络里迷路的老连接请求)会被误当成新连接,三次握手让客户端可以用第三次 ACK 否决它

挥手为什么是四次?

  • TCP 全双工,两个方向独立关闭:被动方收到 FIN 后可能还有数据没发完,所以 ACK 先回、FIN 等发完再发——中间的缝隙就是第四次
  • 追问高频:TIME_WAIT 为什么等 2MSL——保证最后的 ACK 可重传 + 让旧报文自然消亡;海量短连接会把 TIME_WAIT 堆成端口耗尽(所以物联网都用长连接)

3.2 可靠性四件套与粘包

可靠是怎么做到的

  • 序号 + 确认:每字节都有编号,收到要回 ACK
  • 超时重传:等 ACK 超时就重发
  • 滑动窗口:一次可发多条,兼顾吞吐;窗口随接收方缓冲自适应 = 流量控制
  • 拥塞控制:感知网络拥堵主动降速(慢启动/拥塞避免)

粘包:TCP 最著名的"坑"

  • TCP 是字节流,没有"消息"边界——发送方三次 write,接收方可能一次 read 全收到(粘),也可能半条(半包)
  • 应用层三种切帧方案:定长 / 分隔符 / 长度前缀
  • 这正是:MQTT 用"剩余长度"、Modbus TCP 用 MBAP"长度"字段的原因;Modbus RTU 串口没长度前缀,只能靠 3.5 字符静默切帧

面试视角高频三连:① TCP keepalive 默认 2 小时才探测,太迟钝 → 所以 MQTT 定义应用层 Keep Alive(如 60s)自己探测;② TCP 断线(拔网线)时对端可能半小时感知不到 → 所以有 MQTT 遗嘱、应用层心跳;③ TCP 的可靠只是"字节送达对方内核缓冲区",对方应用进程崩溃就白搭 → 所以 MQTT 还要应用层 QoS。三连答完,面试官知道你真懂分层。

4. UDP:自由但有代价

没有握手、没有重传、没有顺序——换来的是极致的轻与快。

维度TCPUDP
连接三次握手建立,有状态无连接,拿了就发
可靠性确认+重传+排序,不丢不乱尽力而为,可能丢、可能乱序
头部开销20 字节起固定 8 字节
收发模型字节流(无边界→粘包问题)数据报(一条就是一条,天然有边界)
一对多只能一对一天然支持广播/多播
典型用户HTTP、MQTT、Modbus TCP、OPC UADNS、音视频、DHCP、MQTT-SN、OPC UA PubSub 多播

面试视角:"什么时候用 UDP?"——要低延迟不要重传的(音视频、实时控制);要一对多的(广播/多播,如 OPC UA PubSub 的 UDP 多播模式);包小得亏 TCP 头的(DNS 一问一答)。再补一句:"MQTT-SN 把 MQTT 搬上 UDP,给跑不动 TCP 栈的超弱传感器;可靠性靠应用层 QoS 补"——直接展示两册知识的贯通。

5. HTTP/HTTPS:互联网通用语

网页的语言,也是物联网平台 API 的语言——但很少用于设备侧,原因值得细说。

核心模型

  • 请求/响应:客户端发起,服务端应答,一问一答;服务端无法主动推
  • 方法:GET 读 / POST 建 / PUT 改 / DELETE 删 → REST 风格 API
  • 状态码:200 成功 / 301 重定向 / 404 不存在 / 500 服务器错误
  • 文本协议,头几百字节起步,人可读

版本演进(一句话版)

  • 1.0:每次请求新建连接,贵
  • 1.1:keep-alive 长连接复用,至今主流
  • 2:二进制分帧 + 多路复用,一条连接并行多个请求
  • 3:干脆弃 TCP 改 QUIC(UDP 之上重建可靠),解决队头阻塞
  • HTTPS=HTTP+TLS:非对称交换密钥 → 对称加密通信,证书防冒充——和 OPC UA SecureChannel 同一套思想

5.1 为什么物联网设备不用 HTTP?

维度HTTPMQTT
模型请求/响应(设备只能被问)发布/订阅(设备主动报,平台可推)
开销头几百字节固定头 2 字节
连接短连接为主,反复握手耗电长连接 + 轻量心跳,弱网稳定
服务端下行难(需轮询/长轮询)天然下行(发布到设备订阅的主题)
适用平台侧 API、配置管理、文件下载设备侧数据上报与指令下发

面试视角:"HTTP 和 MQTT 选谁?"的满分答法是分层使用:"设备到平台用 MQTT(省电、弱网、可下行);平台对外提供 REST API 给应用系统(HTTP);文件/固件升级用 HTTPS 下载。我搭过的链路里三者共存。"

6. 两个配角:WebSocket 与 DNS

出场率不高,但各有一个必考点。

WebSocket:HTTP 升级出的全双工

  • 先用一次 HTTP 握手(Upgrade: websocket)"改签",之后变成长连双工通道
  • 解决 HTTP 服务端不能推的痛点:网页实时刷新、在线看板
  • 必考联动:MQTT over WebSocket(端口 8083)——让浏览器里的 JS 也能直连 MQTT Broker,Grafana 类 Web 看板常用

DNS:域名 → IP 的电话簿

  • 浏览器/客户端先问 DNS(udp 53)把域名换成 IP,再发起连接
  • 分层缓存:本机 → 本地 DNS → 根 → 顶级 → 权威;TTL 控制缓存时效
  • 必考点:"改了域名解析为什么没立刻生效?"——各级缓存 + TTL;物联网侧:设备端长连接重连时要重新解析域名,否则换了 Broker IP 还傻连旧地址

7. 总复习:基础 → 工业的六条因果线 + 自测

本册的全部内容,浓缩成六条"因为所以"——面试里随口说出,含金量拉满。

#基础协议特性工业协议的应对(因果线)
1TCP 字节流无边界MQTT 用变长"剩余长度"切帧;Modbus TCP 用 MBAP 长度字段切帧;Modbus RTU 串口没长度,靠 3.5 字符静默
2TCP 只保证"点到点"字节送达MQTT/OPC UA 定义应用层确认(QoS 确认链 / 通知序号重传)保证"端到端"业务可靠
3TCP keepalive 迟钝(默认 2 小时)MQTT 应用层 Keep Alive(如 60s)+ 遗嘱消息,掉线秒级感知
4设备藏在 NAT 内网,外部进不去设备主动出连 Broker 并保持长连接;下行指令复用该连接
5UDP 轻量、可多播但不可靠MQTT-SN 给超弱传感器;OPC UA PubSub 用 UDP 多播做实时分发
6HTTP 头重、单向、短连接设备侧换 MQTT;HTTP 退守平台 API / 文件下载层
