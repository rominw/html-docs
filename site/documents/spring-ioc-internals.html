1. 总纲：IoC 是什么，DI 是手段

先把两个被混用最多的词拆开，再给 Spring 三大件定位。

IoC · 控制反转

思想：对象的创建、装配、生命周期管理权，从应用代码反转给容器。以前是 new + 手工组装，现在是容器按"配方"生产。

DI · 依赖注入

手段：实现 IoC 的主要方式——容器把依赖"递"进对象（构造器 / setter / 字段）。另一种手段是依赖查找（DL），需要主动调 getBean，不推荐。

BeanDefinition · 配方

载体：容器不直接持有类，而是先持有 BeanDefinition（类名、作用域、依赖、初始化方法……），它是 Bean 的"图纸"。

① IoC（本篇）

对象的生产与装配：容器体系、Bean 生命周期、循环依赖、扩展点。

② AOP

功能的动态增强：BeanPostProcessor 挂载、动态代理、拦截器链。见 AOP 篇。

③ Spring Boot

自动装配与快速搭建：约定优于配置、启动流程、starter。见 Boot 篇。

三部曲的关系：IoC 是地基（对象都由容器造），AOP 是建在地基上的增强机制（造的过程中换成代理），Boot 是把两套机制"自动配好"的脚手架。AOP 篇里讲的 BeanPostProcessor 钩子，本质上就是 IoC 生命周期主线上的插件位——本篇把这条主线完整画出来。

2. 容器体系：BeanFactory → ApplicationContext

一个是最小内核，一个是超集门面，最终都落在同一个实现上。

维度BeanFactoryApplicationContext
定位容器顶层接口，只定义 getBean 等基本能力，最小内核BeanFactory 的超集门面，日常用的"容器"就是它
Bean 创建时机懒：第一次 getBean 才触发整套流程启动时（finishBeanFactoryInitialization）批量实例化所有单例
BeanPostProcessor需要手动注册才生效自动注册：refresh 中 registerBeanPostProcessors 统一登记
注解支持默认不懂 @Autowired 等注解自动注册 AutowiredAnnotationBPP 等，注解开箱即用
附加能力无事件发布、国际化 MessageSource、资源加载、Environment、profile
常见实现XML：ClassPathXmlApplicationContext；注解：AnnotationConfigApplicationContext；Boot：AnnotationConfigServletWebServerApplicationContext——它们内部全部组合了 DefaultListableBeanFactory（唯一完整落地实现）

理解要点：ApplicationContext 不是"另一个容器"，而是"BeanFactory + 自动注册扩展点 + 一堆企业能力"的打包。真正的单例池、BeanDefinition 注册表、三级缓存都在 DefaultListableBeanFactory 里——平时说的"容器"，解剖下来就是它。

3. Bean 生命周期主线

从配方到销毁的八步。AOP 篇讲的钩子，全部长在这条主线上。

postProcessMergedBeanDefinition 扫注入点） ② 实例化构造器 / 工厂方法 / 候选构造器钩子 ③ 属性填充 populateBean@Autowired · @Resource · setter（postProcessProperties 真正注入） ④ Aware 回调BeanNameAware → BeanFactoryAware → ApplicationContextAware ⑤ 初始化回调@PostConstruct → afterPropertiesSet → init-method ⑥ 初始化后处理 ★postProcessAfterInitialization —— AOP 在这里包代理 ⑦ 就绪进入单例池 · getBean / @Autowired 拿到的就是它 ⑧ 销毁（容器关闭时）@PreDestroy → DisposableBean#destroy → destroy-method 三级缓存的入场券② 与 ③ 之间：实例化后、注入前，把 ObjectFactory 放入三级缓存 代理的唯一性循环依赖若已提前生成代理，⑥ 复用同一个（earlyProxyReferences） 注入是插件注解注入的语义由 BPP 提供，容器内核不懂 @Autowired

与 AOP 篇的衔接：AOP 只是第 ⑥ 步的插件，注解注入只是第 ③ 步的插件——生命周期主线本身属于 IoC。记住这条主线，所有"XX 注解什么时候生效"的问题都能定位到具体阶段。

4. 循环依赖与三级缓存

Spring 最著名的设计题：三级缓存各存什么，为什么两级不够。

一级 · singletonObjects

成品池：完全初始化好的 Bean。getBean 优先来这里。

二级 · earlySingletonObjects

半成品池：实例化了、但属性填充和初始化没做完的早期引用。

三级 · singletonFactories

工厂池：ObjectFactory。调用它才能拿到早期引用——必要时按需提前生成代理（getEarlyBeanReference）。

为什么两级不够？

  • 三级缓存存的是工厂，不是对象——意义是"代理的按需提前创建"；
  • 若去掉工厂、实例化后直接生成代理放二级：所有 Bean 一出生就提前代理，违背"代理应在 ⑤ 初始化后生成"的设计（保证 @PostConstruct 等回调先作用于原始对象的完整语义）；
  • 工厂 + earlyProxyReferences 缓存保证：不提前（正常路径 ⑥ 才代理）、需要时能提前（循环依赖 ④ 提前）、且全局只生成一次（⑥ 复用）。

哪些循环依赖解不了？

  • 构造器注入：对象都没实例化出来，没有"早期引用"可暴露 → 启动直接报错；
  • prototype：没有缓存池可放，无解；
  • Spring Boot 2.6+ 默认禁止循环依赖（allow-circular-references=false），官方态度：循环依赖是设计坏味道，要开需显式配置；
  • 解法：@Lazy 打断一边（注入的是代理，首次调用才真正创建）、重构下沉公共逻辑。

面试点睛：三级缓存不是"为了解决循环依赖不得不三层"，而是"用工厂层换来了代理创建时机的正确性"——两层也能解决循环依赖本身，但会破坏生命周期语义。能讲出这层权衡，这道题就从背诵题变成了理解题。

5. 扩展点对比：改配方 vs 改成品

两类 Processor 前缀像，作用对象完全不同。

维度BeanFactoryPostProcessor / BeanDefinitionRegistryPostProcessorBeanPostProcessor
操作对象BeanDefinition（配方）：改属性、改作用域，甚至注册新定义Bean 实例（成品）：加工、包装、替换
执行时机容器级一次性：refresh() 的 invokeBeanFactoryPostProcessors，在任何单例 Bean 创建之前Bean 级多次：每个 Bean 创建时都会经过所有 BPP
典型应用ConfigurationClassPostProcessor——解析 @Configuration/@ComponentScan/@Import/@Bean，把配置类翻译成 BeanDefinition；占位符解析 PropertySourcesPlaceholderConfigurerAOP 代理、@Autowired 注入、@PostConstruct、@Async（见 AOP 篇）
一句话改配方——影响所有"还没出生"的 Bean改成品——影响"正在出生"的单个 Bean

通向 Boot 篇的桥：@EnableAutoConfiguration 的自动装配，最终也是在 invokeBeanFactoryPostProcessors 阶段（解析配置类时）把自动配置类注册进容器的——IoC 的扩展点体系是 Spring 一切"配置魔法"的骨架，Boot 只是往骨架上挂了最大的一批插件。

6. 高频概念澄清

三组最容易被问混的概念，一组一句话拆开。

FactoryBean vs BeanFactory

一个是特殊的 Bean（定制生产逻辑的工厂 Bean，& 前缀拿工厂本身），创建复杂对象用——MyBatis 的 SqlSessionFactoryBean、OpenFeign 的客户端都靠它；一个是容器本身。名字对称纯属巧合。

@Configuration full vs lite

full 模式：CGLIB 增强配置类，保证 @Bean 方法互调也走容器（单例）；lite 模式（proxyBeanMethods=false 或 @Component 上标 @Bean）：纯 POJO，方法互调每次 new。Spring Boot 大量用 lite 换启动性能。

作用域与 scope proxy

singleton（默认，单例池）/ prototype（每次新对象）/ request / session。把 request 域 Bean 注入 singleton 时实际注入的是作用域代理，每次调用再路由到当前请求的实例——机制和 AOP 代理同源。

7. 面试口述简记卡片

每张 30~60 秒。主线图在脑子里，卡片只是配词。

C1 · IoC 和 DI 是什么关系 ≈30s

IoC 是控制反转，指对象的创建、装配、生命周期管理权从应用代码反转给容器，它是一种设计思想；DI 依赖注入是实现这个思想的主要手段，容器把依赖通过构造器、setter 或字段递给对象。另一种手段是依赖查找，主动调 getBean，耦合更高所以不推荐。所以 IoC 是目的，DI 是手段，面试常把两个词混着问，拆开答就赢了。

C2 · BeanFactory vs ApplicationContext ≈30s

BeanFactory 是容器顶层接口，定义 getBean 这类基本能力，是最小内核，默认懒加载、不懂注解、BPP 要手动注册。ApplicationContext 是它的超集门面：启动时批量创建单例、自动注册各种 BeanPostProcessor 所以注解开箱即用，还附加了事件发布、国际化、资源加载、Environment 这些企业能力。但它们最终都组合了 DefaultListableBeanFactory——单例池和三级缓存真正住在那里。

C3 · 说一下 Bean 的生命周期 ≈45s

先合并 BeanDefinition，配方就绪；然后实例化，走构造器；接着属性填充，@Autowired 在这一步由 AutowiredAnnotationBeanPostProcessor 完成注入；然后 Aware 系列回调，把容器自身递给 Bean；初始化阶段依次是 @PostConstruct、afterPropertiesSet、init-method；初始化之后是 BeanPostProcessor 的 postProcessAfterInitialization，AOP 就是在这里把 Bean 包成代理；最后进入单例池就绪使用；容器关闭时走 @PreDestroy、DisposableBean、destroy-method 销毁。关键点：注解注入和 AOP 都是生命周期主线上的插件，不是主线本身。

C4 · 三级缓存怎么解决循环依赖 ≈45s

三级缓存分别是一级 singletonObjects 存成品、二级 earlySingletonObjects 存半成品早期引用、三级 singletonFactories 存 ObjectFactory 工厂。A、B 循环依赖时：A 实例化后立刻把工厂放入三级缓存，然后属性填充去创建 B；B 填充时又需要 A，三级查找先查一级没有、二级没有、命中三级工厂，调工厂拿到 A 的早期引用——如果 A 需要 AOP，这一刻按需提前生成代理——并把 A 提升到二级缓存；B 拿着 A 的引用完成初始化进入一级缓存；接着 A 的流程恢复，注入 B、初始化、也进入一级缓存。循环解开。

C5 · 为什么需要三级，两级不行吗 ≈35s

两级其实也能解决循环依赖本身：实例化后直接把对象放二级，B 来取就有。问题出在代理上：Spring 的设计是代理应该在初始化完成后的 postProcessAfterInitialization 里生成，保证生命周期语义完整。如果为了循环依赖把所有 Bean 都在实例化后提前代理，就破坏了这个设计。所以第三级存的是工厂而不是对象——平时不提前，真发生循环依赖、别人来取早期引用时，才通过 getEarlyBeanReference 按需生成代理，再用 earlyProxyReferences 缓存保证全局只生成一次。第三级本质是用工厂层换来了代理创建时机的正确性。

C6 · 哪些循环依赖解不了 ≈30s

三种：构造器注入的循环依赖，因为对象还没实例化出来，根本没有早期引用可以暴露；prototype 作用域，因为没有缓存池，每次都是新对象；还有多例之间通过 @Async 等产生代理循环的场景。另外 Spring Boot 2.6 之后默认直接禁止循环依赖，需要 allow-circular-references 显式打开，官方态度是循环依赖属于设计坏味道。真正的解法是加 @Lazy 打断一边——注入的是代理，首次调用才真正创建——或者重构把公共逻辑下沉。

C7 · BeanFactoryPostProcessor vs BeanPostProcessor ≈30s

一句话：一个改配方，一个改成品。BeanFactoryPostProcessor 操作的是 BeanDefinition，在 refresh 的 invokeBeanFactoryPostProcessors 阶段容器级执行一次，影响的是所有还没创建的 Bean，典型应用是 ConfigurationClassPostProcessor，它负责解析 @Configuration、@ComponentScan、@Import、@Bean，把配置类翻译成 BeanDefinition。BeanPostProcessor 操作的是 Bean 实例，每个 Bean 创建时都会经过，典型应用是 AOP 代理和 @Autowired 注入。自动装配也是在前者阶段挂进来的。

C8 · FactoryBean vs BeanFactory ≈30s

两个名字很像但完全无关。BeanFactory 是容器本身，IoC 的顶层接口。FactoryBean 是一种特殊的 Bean，它本身注册在容器里，但 getBean 拿到的是它 getObject 生产出来的对象，用 & 前缀才能拿到工厂本身。它存在的意义是接管复杂对象的创建过程，比如 MyBatis 的 SqlSessionFactoryBean 生产 SqlSessionFactory，OpenFeign 用它为每个接口动态生成远程调用客户端。可以说 FactoryBean 是容器留给"造对象"这件事的插件位。

C9 · @Configuration 的 full 和 lite ≈30s

full 模式就是默认情况，Spring 会用 CGLIB 增强配置类，让 @Bean 方法互调也走容器逻辑，保证拿到的是同一个单例，代价是启动时多生成一个增强类。lite 模式是 proxyBeanMethods=false，配置类就是纯 POJO，方法互调等于普通方法调用、每次都会 new，但省掉了增强类的生成，启动更快。Spring Boot 的自动配置类大量使用 lite 模式换性能，因为它们内部 @Bean 方法基本不互调。

C10 · 容器启动（refresh）做了什么 ≈45s

核心几步：prepareRefresh 做准备和校验；然后是最重要的 invokeBeanFactoryPostProcessors，解析所有配置类，把组件注册成 BeanDefinition，自动装配也在这一步挂进来；接着 registerBeanPostProcessors，把 AOP、@Autowired 这些处理器注册好；再初始化消息源、事件广播器、注册监听器；Spring Boot 的内嵌 Tomcat 是在 onRefresh 这一步创建的；然后 finishBeanFactoryInitialization，批量实例化所有单例 Bean，AOP 代理在实例化的最后一环生成；最后 finishRefresh 发布容器就绪事件。一句话总结：refresh 前半程搭好基础设施和扩展点，后半程造 Bean。

使用建议：C3 生命周期和 C4 三级缓存是本篇骨架，先背熟这两张；C5 是区分度所在（大多数候选人只会背"三级缓存"答不出为什么）。延伸阅读：AOP 篇（第 3 节有同一条生命周期的 AOP 视角切面）、Boot 篇（C10 的 refresh 在 Boot 里怎么被调起来）。
