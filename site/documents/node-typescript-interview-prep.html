2. JavaScript 语义

从值、对象、作用域与模块开始，别让类型声明掩盖运行时。

基础必会 1. 值与引用：const 为什么挡不住对象变化？

先看问题：

const 声明对象后还能改字段，展开复制后内层标签仍一起变化。绑定和对象是不同层。

原理怎样推出来

const 禁止重新给绑定赋值，不递归冻结对象。对象被多个引用共享时，修改会被其他引用观察到；展开和 Object.assign 等常见复制只复制相应外层属性。需要独立内层数据就明确复制策略，structuredClone 也有支持类型和资源边界。

把它放进一个例子

const a = { tags: ["A"] };
const b = { ...a };
b.tags.push("B");
// a.tags 也是 ["A", "B"]

边界与反例：Object.freeze 通常也是浅层限制，不能把它当所有成员深冻结。复制不自动保证线程/业务协议安全。

停一下，自己推：在函数里把参数 obj 赋成新对象，会改掉调用者变量的指向吗？

展开自测解析

不会。参数保存传入值的副本，修改原对象与重绑参数不同。

理解后，再这样简述：区分绑定、对象与复制深度，const 不是深不可变。

核对原文：对应官方文档或方法原文。

基础必会 2. 相等、转换与空值：==、===、?? 怎么选？

先看问题：

接口参数是字符串 "0"，与数字比较时结果不同；用 || 给 0 设置默认值还会把合法 0 覆盖。

原理怎样推出来

== 包含转换规则，=== 不做同样的跨类型转换；对象比较通常仍按身份。?? 只在 null/undefined 时选择后值，|| 根据真假值选择，会影响 0、空字符串与 false。输入类型要在边界明确解析，不靠宽松比较凑业务正确性。

把它放进一个例子

const retries = 0;
const a = retries || 3;  // 3
const b = retries ?? 3;  // 0
Number.isNaN(NaN);       // true

边界与反例：NaN、对象与浮点另有规则，严格相等也不是任意深层内容相等。金额需要明确精度与单位。

停一下，自己推：空字符串是合法名称时，用 value || "默认" 会怎样？

展开自测解析

它会被替换，丢掉合法值；应按具体缺省规则判断。

理解后，再这样简述：比较和缺省按业务类型定义，不让隐式转换代替校验。

核对原文：对应官方文档或方法原文。

基础必会 3. 作用域与闭包：回调为什么读到旧值或最终值？

先看问题：

循环中用 var 创建回调，执行时都看到循环结束值；服务闭包保存一份旧配置，又一直不更新。

原理怎样推出来

闭包访问创建环境中的绑定，var 的函数作用域与 let 的块/循环绑定不同。闭包可以保留状态，也会延长对象生命周期；到底希望读取最新绑定还是创建时快照，要在设计里明确。

把它放进一个例子

const callbacks = [];
for (let i = 0; i < 3; i++) callbacks.push(() => i);
// callbacks.map(fn => fn()) 得到 [0, 1, 2]

边界与反例：捕获引用不等于深拷贝，监听器与缓存中保存闭包也可能留住大对象。

停一下，自己推：把整份请求对象捕获进长期定时器，有什么风险？

展开自测解析

可能长期持有用户数据、连接和大字段，需只保留必要值并清理定时器。

理解后，再这样简述：闭包保持环境访问，范围、快照语义与释放都要明确。

核对原文：对应官方文档或方法原文。

基础必会 4. this 与箭头函数：方法拆出来为什么丢了上下文？

先看问题：

把对象的方法作为回调传给库，函数内部 this 不再是原对象。

原理怎样推出来

普通函数的 this 由调用方式决定，方法调用与直接函数调用不同；bind 可固定接收者，call/apply 显式指定。箭头函数没有同样的独立 this，而是读取外层词法环境，不能当作“所有方法的万能替代”。

把它放进一个例子

const service = {
  name: "dock",
  getName() { return this.name; }
};
const callback = service.getName.bind(service);
// callback() 返回 "dock"

边界与反例：严格模式、ESM/CJS 顶层环境不同；箭头作为对象字段未必读取该对象自身。

停一下，自己推：给箭头函数 call(other)，就能把 this 改成 other 吗？

展开自测解析

不能按普通函数的方式改变其词法 this。

理解后，再这样简述：回调传递前确定接收者，普通调用与词法捕获分开。

核对原文：对应官方文档或方法原文。

基础必会 5. 原型与对象属性：输入对象合并有什么边界？

先看问题：

从 JSON 接受配置再随意合并进对象，可能覆盖关键字段或影响原型相关属性。

原理怎样推出来

对象属性查找可沿原型链进行，own 属性与继承属性不同。class 以原型相关机制组织实例方法，方法不会为每个实例都复制一份。处理不可信数据时明确允许字段，使用合适的键存储与自有属性判断，拒绝任意深合并改变内部结构。

把它放进一个例子

例如请求只允许 name、timeout 两个业务字段，逐个验证后构造配置；任意键值映射可评估 Map，而不是把输入全部铺到权限对象上。

边界与反例：JSON 能解析只证明格式合法。原型污染、危险键与业务字段覆盖仍需要边界设计。

停一下，自己推：用 for...in 遍历，是否只包含对象自己的属性？

展开自测解析

不一定，会涉及可枚举的继承属性；按需要选 Object.keys/entries 与自有属性检查。

理解后，再这样简述：属性来源与原型规则要分清，不可信输入按字段契约接入。

基础必会 6. ESM 与 CommonJS：导入成功为什么还会在部署失败？

先看问题：

本地构建输出 ESM，生产却按 CommonJS 启动；同一扩展名在不同 package 配置下有不同含义。

原理怎样推出来

CommonJS 与 ESM 有不同导入/导出与加载语义，文件扩展名、package.json 的 type、依赖 exports、编译目标共同决定路径。ESM 的绑定与解析方式不能全部照搬 require；互操作支持随 Node 版本演进，需要对实际产物测试。

把它放进一个例子

// package.json: { "type": "module" }
import { readFile } from "node:fs/promises";
// .cjs 明确走 CommonJS；.mjs 明确走 ESM

边界与反例：不应把新版同步 require 部分 ESM 的能力一概说成永远不支持，也不能假定 top-level await 与全部包都可混用。

停一下，自己推：tsconfig 指定了路径别名，Node 就一定能在运行时找到它吗？

展开自测解析

不一定。编译器路径解析与运行时解析要通过构建、包配置或对应加载方案接起来。

理解后，再这样简述：源代码、编译产物和运行时模块规则必须一致。

核对原文：对应官方文档或方法原文。

基础必会 7. 错误传播：try/catch 为什么没捕获异步失败？

先看问题：

在 try 块里调用异步函数但没有 await，Promise 后来拒绝，catch 已经结束。

原理怎样推出来

try/catch 捕获当前执行链中的抛出；在 async 函数里 await 被拒绝的 Promise，可把拒绝带入该链。返回、等待与处理各有用途，必须明确谁拥有失败结果。把所有错误转成 null 会让调用者失去失败语义。

把它放进一个例子

async function load() {
  try {
    return await fetchDevice(); // 项目接口
  } catch (error) {
    throw new Error("读取设备失败", { cause: error });
  }
}

边界与反例：EventEmitter 的 error 事件等还有自己的契约；未处理拒绝的进程行为需按版本/参数理解，不能依赖它“只是打印”。

停一下，自己推：finally 返回成功结果，原来的失败还能被调用者看到吗？

展开自测解析

可能被覆盖，清理逻辑不应无意改变原有错误与返回。

理解后，再这样简述：异步错误要有人等待和处理，保留失败与原因。

核对原文：对应官方文档或方法原文。

3. TypeScript

类型表达契约，边界验证保证真实输入。

基础必会 8. TypeScript 与运行时：as 为什么不验证 JSON？

先看问题：

fetch 的 JSON 被断言为 Device，缺少 id 的输入却照样运行到数据库。

原理怎样推出来

TypeScript 主要在编译期检查，类型注解与多数断言不会生成输入验证代码。as 表达编译者承担类型判断，不会补字段、改内容或检查范围。网络、文件、消息等信任边界先当未知数据验证，再得到可依赖类型。

把它放进一个例子

const raw: unknown = JSON.parse(text);
// 验证对象、字段、范围之后再构造 Device
// const device = raw as Device 并未完成验证

边界与反例：静态类型也不自动校验权限、金额或数据库约束；schema 库要明确转换与严格规则。

停一下，自己推：编译通过后，接口一定不会返回缺字段对象吗？

展开自测解析

不一定。运行时外部数据可违背声明，边界验证与契约测试仍必要。

理解后，再这样简述：类型系统检查代码契约，实际输入靠运行时验证。

核对原文：对应官方文档或方法原文。

基础必会 9. any、unknown、never：分别表达哪种信任？

先看问题：

any 让访问所有字段都通过，错误直到运行时出现；unknown 则要求先判断。

原理怎样推出来

any 关闭相应检查并容易向调用链传播；unknown 表达不知道是什么，先缩窄才使用；never 表达不会产生正常值的路径，可用于穷尽检查。三者不能为了让编译通过而随意互换。

把它放进一个例子

function message(value: unknown): string {
  if (typeof value === "string") return value;
  throw new Error("需要字符串");
}

边界与反例：unknown 到可靠领域类型还需更完整结构判断；双重断言不是安全解析。

停一下，自己推：把异常捕获参数改成 any，能证明 error.message 总存在吗？

展开自测解析

不能。JavaScript 可以抛任意值，需要检查或规范化错误表示。

理解后，再这样简述：用 unknown 表达边界，用缩窄建立证据，never 检查不可能遗漏。

核对原文：对应官方文档或方法原文。

基础必会 10. strict、空值与可选字段：没有值和没有字段一样吗？

先看问题：

设备名称可缺省，但代码直接调用 toUpperCase；PATCH 中“未传”和“清空”也被混为一谈。

原理怎样推出来

strictNullChecks 把 null/undefined 的可能性带入类型检查。可选字段表达属性可能缺失，业务应定义缺失、null 和合法空值的差异；配置 exactOptionalPropertyTypes 等可影响赋值约束。缩窄应符合真实条件，而不是用 ! 强行跳过。

把它放进一个例子

function title(name: string | null): string {
  return name === null ? "未命名" : name.toUpperCase();
}

边界与反例：编译配置必须实际被构建/CI 使用；非空断言不生成运行时检查。

停一下，自己推：PATCH 名称未传、传 null、传 ""，都应清空吗？

展开自测解析

由接口契约定义，不能因为 JavaScript 都可能是假值就同样处理。

理解后，再这样简述：空值语义先定义，再由类型配置和判断保证一致。

核对原文：对应官方文档或方法原文。

基础必会 11. 联合类型与判别字段：状态机怎样避免无效组合？

先看问题：

用多个可选字段表示任务结果，可能出现 status=success 却没有 result，或者 failed 却带成功内容。

原理怎样推出来

判别联合让每种状态有自己的字段，按字面量状态缩窄后访问对应值。switch 配合 never 检查可帮助新增状态时暴露未处理分支；它不替代数据库的合法状态转换。

把它放进一个例子

type Result =
  | { status: "ok"; value: number }
  | { status: "error"; reason: string };
function read(r: Result) {
  return r.status === "ok" ? r.value : r.reason;
}

边界与反例：来自网络的状态仍需解析；类型表达静态可表示状态，不自动保证转换时序和权限。

停一下，自己推：新增 cancelled 状态后只用 else 处理所有非 ok，会发现遗漏吗？

展开自测解析

未必。需显式分支或穷尽检查，避免把取消误当失败。

理解后，再这样简述：把状态和所属数据一起建模，用缩窄表达分支证据。

核对原文：对应官方文档或方法原文。

项目常用 12. 泛型与约束：保留关系，不制造任意保证

先看问题：

函数输入某类型就应返回同类型，写成 any 丢掉关系；无约束泛型却想访问 .id。

原理怎样推出来

泛型表达输入、输出或成员间的类型关系，extends 约束说明必要结构。若实现不能保证任意 T，不能用断言伪装成 T；泛型名称也不会在运行时验证对象。

把它放进一个例子

function getId<T extends { id: string }>(value: T): string {
  return value.id;
}

边界与反例：泛型不等于必须创建高度通用 API。简单具体类型能表达需求时，避免额外参数与深层条件类型。

停一下，自己推：函数内部返回固定空对象，却声明返回任意 T，合法吗？

展开自测解析

4. 事件循环与异步

基础必会 15. 事件循环：一个慢回调为什么拖住其他请求？

先看问题：

服务是异步 HTTP，但某个回调解析巨大数据或做长循环，其他请求都迟迟得不到处理。

原理怎样推出来

主要 JavaScript 回调在事件循环线程执行，I/O 完成后回调仍需排队执行；部分底层工作由系统或 libuv 线程池等处理。异步接口不意味着回调计算在另一核。长回调阻塞就绪工作与超时处理，任务需要小而有界。

把它放进一个例子

读取文件的异步等待可让循环处理其他连接，但随后 JSON.parse 的巨大输入和同步计算仍在调用线程占时间。

边界与反例：事件循环阶段顺序与 libuv/Node 版本有细节变化，不要靠背所有阶段替代识别阻塞路径。

停一下，自己推：CPU 计算加上 async 关键字，就会自动后台执行吗？

展开自测解析

不会。async 改变结果与等待表达，不搬移同步计算。

理解后，再这样简述：事件循环重叠 I/O 等待，回调里的 CPU 工作仍必须控制。

核对原文：对应官方文档或方法原文。

基础必会 16. Promise 与 await：执行和等待分别什么时候发生？

先看问题：

new Promise 里的日志立刻出现，then 的日志稍后出现；await 后的代码被误认为永远开了新线程。

原理怎样推出来

Promise 的 executor 在构造时同步执行，兑现后的反应回调通过相应微任务机制调度。await 暂停当前 async 执行链，后续作为异步恢复，不是线程创建。Promise 包裹阻塞计算不会减少循环占用。

把它放进一个例子

console.log("A");
Promise.resolve().then(() => console.log("B"));
console.log("C");
// 同一普通脚本里：A、C、B

边界与反例：示意限定当前普通脚本；嵌入其他模块或调度上下文时不把相对序列无限推广。

停一下，自己推：new Promise(() => heavyLoop()) 为什么还卡住？

展开自测解析

executor 同步跑，heavyLoop 没被搬到 worker 或分片调度。

理解后，再这样简述：Promise 表示异步结果，await 表示等待链，不自动平行计算。

核对原文：对应官方文档或方法原文。

基础必会 17. all、allSettled 与顺序 await：失败策略怎么选？

先看问题：

读取三份独立信息，希望并发；其中一份失败时，有的接口要整体失败，有的允许部分结果。

原理怎样推出来

顺序发起并 await 通常串行等待；先发起多个再等待可重叠。Promise.all 在任一拒绝时让聚合拒绝，但不自动取消其他工作；allSettled 等全部结束并给各结果状态，适合显式处理部分成功。

把它放进一个例子

const results = await Promise.allSettled([loadA(), loadB()]);
for (const r of results) {
  if (r.status === "fulfilled") use(r.value);
  else recordFailure(r.reason);
}

边界与反例：并发组合要配超时与上限，不能一次展开十万请求；不同结果是否可混用由业务定义。

停一下，自己推：all 抛异常后另一个扣款 Promise 一定没执行吗？

展开自测解析

不一定，它可能仍在跑或已完成；需要取消/结果查询和业务协议。

理解后，再这样简述：组合方式表达失败策略，生命周期和副作用仍需管控。

核对原文：对应官方文档或方法原文。

项目常用 21. Stream 与背压：消费者慢时数据存在哪里？

原理怎样推出来

缓存要定义陈旧容忍与删失败/回填竞态；Redis 租约锁需要原子获取、持有者校验释放和到期后的业务处理。Node 的分布式锁依赖须核对拓扑与续租规则，不靠框架名字承诺绝对互斥。DB 条件更新、唯一约束与幂等保护业务效果。

把它放进一个例子

缓存只加速设备信息，任务 NEW→RUNNING 使用 DB 原子条件更新；锁降低争抢但恢复和重复回调仍靠持久状态。

边界与反例：缓存淘汰、主从延迟与锁长暂停各是不同窗口；不能把缓存 TTL 当“保证至少存这么久”。

停一下，自己推：Redis 先 SETNX 标记完成再执行，执行前崩溃会怎样？

展开自测解析

重试可能被跳过而业务未完成；去重记录与真实效果须有原子或可恢复协议。

理解后，再这样简述：共享存储提供协调，正确性由状态与副作用边界证明。

核对原文：对应官方文档或方法原文。

项目常用 29. 队列与幂等：可靠后台任务怎样确认？

先看问题：

返回 202 后任务只存在内存，重启丢失；消费者执行成功但 ack 丢失，任务又来了。

原理怎样推出来

持久任务/消息记录让重启可恢复，DB 业务与待发送事件可通过 outbox 同事务保存。消费在业务提交后确认，确认前崩溃会重复，因此按稳定业务键幂等，失败重试有界并有告警与恢复入口。

把它放进一个例子

任务 id 固定，状态与尝试记录持久；重复收到消息读既有结果或执行合法条件转换，外部命令携带同一幂等身份。

边界与反例：队列库的重复、租约和确认配置各不同，Promise/定时器不等于可靠任务基础设施。

停一下，自己推：先 ack 再业务，进程立刻崩溃，后续能凭什么恢复？

展开自测解析

若没有独立持久业务待办，就可能无法知道该补什么；确认时机需与恢复协议一致。

理解后，再这样简述：持久记录、确认与幂等组合解决崩溃窗口。

核对原文：对应官方文档或方法原文。

类型检查、行为测试、指标与发布分别提供证据。

基础必会 30. 依赖与环境：lockfile 为什么重要？

先看问题：

同一 package.json 在两台机器装到不同小版本，启动出现差异；开发的 node 版本还与生产不一样。

原理怎样推出来

版本范围允许安装解析变化，lockfile 记录具体依赖图，CI 使用对应可重复安装方式并匹配 Node/包管理器。环境配置按边界校验，私密值与公开构建参数分开，ESM/CJS 与原生依赖也要测试实际产物。

把它放进一个例子

npm ci
# 执行项目的 typecheck、test、build
# 用生产启动命令运行构建产物

边界与反例：lockfile 不保证远程资源、系统库与所有安装脚本安全；依赖更新需要验证兼容与来源。

停一下，自己推：把 .env 整份打包进前端产物，是否因为变量名是 SECRET 就安全？

展开自测解析

不安全。浏览器产物可读取，真正密钥应只在受保护服务端使用。

理解后，再这样简述：锁定依赖、运行版本与配置，共同实现可复现交付。

核对原文：对应官方文档或方法原文。

项目常用 31. 测试与契约：类型通过后还要测什么？

先看问题：

类型检查保证方法接收 string，却没发现重复创建、权限越界或 Promise 拒绝无人处理。

原理怎样推出来

类型检查覆盖静态关系，行为测试检验结果、边界与副作用。纯逻辑用小测试，HTTP/DB 用受控集成和契约测试，外部服务替身模拟失败窗口；异步测试必须等待实际完成，假时钟不应掩盖取消与资源清理。

把它放进一个例子

验证同一幂等键两次只产生一份效果，失败可重试，未授权用户不能读取任务；再看连接与监听是否释放。

边界与反例：mock 内部每个步骤不等于证明行为，压测和真实外部故障仍属不同证据。

停一下，自己推：测试函数没 await 异步断言，为什么可能假通过？

展开自测解析

测试可能在失败产生前已结束，需返回/等待正确 Promise 并校验资源结束。

理解后，再这样简述：静态、行为、集成与容量验证各自承担不同证据。

核对原文：对应官方文档或方法原文。

项目常用 32. 事件循环延迟、CPU 与内存：怎么区分等待和阻塞？

先看问题：

平均响应不差，p99 很高；可能是长回调、连接池排队、GC 或外部慢调用。

原理怎样推出来

结合事件循环延迟、CPU、堆/外部 Buffer、队列与请求分段定位。CPU profile 找计算热点，heap 观察长期持有者，event loop delay 反映调度被推迟；RSS 与 JS 堆并不等同。几种信号需关联同一时段与负载。

把它放进一个例子

循环延迟高且 CPU 高，查同步热点；CPU 低但连接获取耗时高，查池容量与长事务；堆回收后基线增长，查监听、缓存与积压。

边界与反例：剖析有开销且可能含敏感数据，不直接在生产无限采集。一次请求快不证明尾部问题解决。

停一下，自己推：把内存限额加倍后晚几天崩溃，泄漏就修复了吗？

展开自测解析

没有，可能只是延迟达到上限，仍要看长期存活基线与引用关系。

理解后，再这样简述：按计算、调度、等待和持有者拆分症状再验证。

核对原文：对应官方文档或方法原文。

基础必会 33. 日志与错误响应：怎样找到一条请求的全链路？

先看问题：

异步日志交错，没有请求 id，消息回调也只打印“失败”，无法重现。

原理怎样推出来

记录关联 id、稳定业务键、阶段、尝试号与原因，指标观察耗时分位和错误，trace 展开跨服务步骤。用户响应不暴露内部路径、SQL 或密钥；记录失败也不能把错误吞成成功。

把它放进一个例子

从 API 接收、DB 提交、消息发布到设备回执都串同一业务键，保留阶段和耗时；身份证明与 token 不全量打印。

边界与反例：采样、保留和告警门槛按业务设计；traceId 来自外部不等于授权身份。

停一下，自己推：HTTP 全是 200，就能证明业务成功率为 100% 吗？

展开自测解析

不能。可能把失败包装进正文、后台未完成或指标漏采，应检验真正业务结果。

理解后，再这样简述：观测连接真实效果，错误保留原因并限制信息暴露。

核对原文：对应官方文档或方法原文。

项目常用 34. 优雅关闭与发布：进程退出前还能保证什么？

先看问题：

部署直接 kill，连接中断，消息消费和后台任务停在中间。

原理怎样推出来

接收退出信号后停止接新工作，以有界时间等待/取消正在处理任务，释放连接与监听，保存可恢复记录。容器 readiness、停止路由传播和终止时限要配套；新旧版本的表、消息与配置需要兼容。

把它放进一个例子

HTTP server 停止接新连接，任务消费者停止领取，已经提交但尚未确认的工作靠幂等重投恢复。长设备动作保存在业务状态，而非无限等待进程。

边界与反例：关闭成功不是任意外部操作都完成；OOM/强制终止时也可能没有清理机会，可靠性必须依赖持久记录。

停一下，自己推：把所有 SIGTERM 都改成忽略，是安全发布方案吗？

展开自测解析

不是。会妨碍部署并可能被强制终止，应该设计有限收尾与恢复。

理解后，再这样简述：有限收尾与持久恢复一起支撑发布，不能只依赖 finally。

核对原文：对应官方文档或方法原文。
