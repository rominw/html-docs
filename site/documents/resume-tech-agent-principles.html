典型应用场景

本篇核心问题

能把模型建议、工具协议、可信身份、执行状态与用户反馈分开，解释工具调用为什么不是模型直接拥有业务权限。

2. LLM 生成答案时，Attention、token 与 KV cache 各做什么？

从机制到边界，再用具体交错检验结论。

记忆关键词：token 化 → Q/K/V → 上下文关联 → 下一 token → 缓存

核心结论

常见自回归语言模型根据已有上下文估计下一 token 的分布。Attention 组织上下文信息，KV cache 重用部分推理中间结果；它们都不把生成内容自动变成事实或授权。

拆开机制与保证范围

token 不等于一个汉字或单词。输入先映射为向量表示；Attention 用 Query 与 Key 的关联形成权重，再组合 Value，模型据此更新表示。以经典形式看，softmax(QKᵀ/√d)V 描述按相似关系加权汇聚，不是查一个固定问答表。模型架构的具体变体需分别核对。

生成阶段逐步扩展上下文，KV cache 避免为历史 token 重复计算某些 Key/Value，换取显存与管理成本。prefill 和逐 token decode 的资源特征不同，长上下文、并发会话和输出长度都会影响延迟与容量；不能只按 token 单价理解服务预算。

推理时向上下文补一份新资料，通常是改变本次条件输入，不是即时更新模型权重。模型可以产生流畅但无证据的描述，结构化输出也只约束部分格式；业务字段、身份、坐标和执行资格仍需应用验证。

场景推演：模型说“已完成航线下发”，但没有 Action 的受理与结果证据；这只是生成文本。界面应按执行协议展示真实状态，而不是从自然语言判断成功。

进一步思考：“降低 temperature 就无幻觉？”不能创造缺失事实。“上下文很长就等于记住全部？”还受注意力使用、截断和模型能力影响。

如何验证：用固定事实题、缺失信息题和伪造工具结果分别评估；测首 token、后续生成和总资源，区分回答正确率与真实动作成功率。

3. RAG 与 Dify 知识检索为什么必须拆分评估？

从机制到边界，再用具体交错检验结论。

记忆关键词：解析/切块 → 召回 → 重排 → 权限证据 → 生成

核心结论

RAG 把检索到的证据放进生成上下文，Dify 可以组织相关工作流。检索找到资料与模型正确使用资料是不同阶段，权限也不能交给模型自己判断。

拆开机制与保证范围

文档先解析、切块和建立索引；块太小可能丢掉表格、标题与限定条件，太大则增加噪声和上下文预算。向量召回寻找语义近似，关键词检索保留精确术语；混合召回和重排用于形成更合适的候选，不意味着相似度分数就是事实正确概率。

Dify 检索配置可在知识库与节点等层次影响候选和重排，实际策略取决于版本与配置。评估要分别看证据召回、排序、引用忠实和回答完整性，不以“回答看起来合理”证明检索命中了正确资料。

租户、文档 ACL、版本、删除和数据时效应在检索边界处理。先检索所有秘密再让模型拒绝泄露，会把秘密提前放进不应拥有的上下文。检索到的文本也可能含恶意指令，应作为数据与证据，不把它提升为工具授权。

场景推演：OA 表单知识块遗漏“仅海外机构适用”这一限定，模型套用到其他机构。修复应追到解析、切块和适用元信息，而不是只改最后的提示词。

进一步思考：“TopK 更大总更好？”噪声、成本和引用冲突会增加。“Embedding 就能精确命中编号？”精确字段往往需要关键词或结构过滤。

如何验证：建立带证据位置、版本和权限的题集，覆盖找不到资料、旧资料、表格和越权候选；分别记录检索、重排与生成阶段的失败。

4. Agent loop 与持久工作流应该怎样分工？

从机制到边界，再用具体交错检验结论。

记忆关键词：建议 → 校验 → 执行 → 观察 → 再决策 · 持久边界

核心结论

Agent 用模型根据观察提出下一步，工作流用明确的状态与恢复协议组织长期执行。智能规划适合可变决策，可靠执行仍需要稳定身份和受控状态机。

拆开机制与保证范围

一个常见循环包含上下文组装、模型响应、工具候选、应用执行和结果回填；下一轮看到的是新的观察。模型决定会受上下文、采样和外部数据影响，不能像确定性工作流那样直接重放代码并希望得到同一命令序列。

长任务可以把规划建议固化成经过校验的版本化动作，再交给业务状态机或持久工作流执行。恢复时读取既有动作与结果，避免仅凭聊天历史重新规划并重复副作用。Agent 会话、执行 run 和任务身份可以不同，应显式关联。

循环还需工具次数、模型成本、总 deadline、取消和人工接管预算。重复错误可能只是模型不断换说法调用同一工具；返回结构化错误、可恢复状态和既有动作身份比无限追加文本更有助于收敛。

场景推演：Agent 提出“重新起飞获取缺失数据”，但上一动作结果未知。执行层先查询旧动作，而不是因为新一轮模型有新理由就重新下发。

进一步思考：“用 Temporal 就能重放模型输出？”通常应把模型调用作为外部执行并记录结果。“聊天记录存下来了就能恢复？”还需业务动作和资源事实。

如何验证：在模型调用、工具执行和结果回填之间中断，检查恢复是否保留原动作；统计重复建议、工具预算和真正业务效果。

5. MCP 的 tools、JSON Schema、annotations 与授权分别管什么？

从机制到边界，再用具体交错检验结论。

记忆关键词：能力发现 · 参数结构 · 元信息提示 · 身份与资源授权

核心结论

MCP 提供可协商的工具等能力与调用协议。Schema 描述结构，annotations 描述提示性元信息；服务端仍必须验证参数、身份和业务资源权限。

拆开机制与保证范围

Tools 的发现与调用允许客户端向模型呈现能力，再由应用执行调用。readOnlyHint、destructiveHint 等不应作为不可绕过的安全证明，尤其面对不可信服务端元信息。MCP 允许具有副作用的工具，“查询走 MCP、执行走 Action”是业务架构选择。

参数满足 JSON Schema 不代表 resourceId 属于当前用户，字符串格式正确也不代表坐标和设备状态有效。授权应从可信连接或服务上下文取得主体，按实际资源校验；不能接收模型给出的 userId 就直接按该用户身份查询。

stdio 与 Streamable HTTP 有不同传输和认证语境，HTTP 规范的授权流程不能无条件套到所有本地进程。请求 ID 用于协议关联，不自动成为业务幂等键；重连、重试和长任务需要自己的状态与结果协议。

场景推演：查询工具接受 regionId，模型填了另一用户的区域。Schema 合法，服务仍应在当前可信用户范围查找；“只读”工具也可能泄露数据。

进一步思考：“工具返回 isError 就不是协议错误？”工具业务错误与协议层错误有不同含义。“调用 tools/call 成功就业务完成？”还要看返回内容和任务语义。

如何验证：测试同租户、跨租户、无权资源、同键异参、工具业务错误和传输中断；固定阅读规范版本，并核对实际 client/server 的协商版本。

6. Spring AI 的工具适配层为什么应保留可信 ToolContext？

从机制到边界，再用具体交错检验结论。

记忆关键词：模型参数与服务上下文分离 · 显式校验 · 执行策略

核心结论

Spring AI 帮助描述与执行工具调用，但应用拥有实际执行逻辑。可信主体、会话和权限应来自服务上下文，而不是从模型可填写的工具参数推断。

拆开机制与保证范围

工具描述和输入结构帮助模型选择调用，适配器把参数转换给业务函数，结果可能回到模型继续推理。自动循环或显式执行方式取决于具体 API 和配置；启用工具后必须理解调用发生在哪个路径，哪些环节可以校验或拒绝。

ToolContext 可携带应用提供的上下文，设计时把模型可见参数与可信 user/tenant/session 分开。模型参数只描述它想查询或操作的资源，业务服务再用可信主体校验资格。上下文不发送给模型的特性也不替代日志脱敏和工具返回数据控制。

工具结果要结构化地区分成功、未找到、拒绝、暂时失败和未知，避免所有异常转成一段“调用失败”字符串。输出内容也要限制大小、字段与敏感信息；模型看见完整原始堆栈并不会因此更可靠，反而可能暴露内部数据。

场景推演：查询最佳视角只要求模型填写 sceneId；服务从 ToolContext 取得当前用户，再限定资产范围。若把 userId 作为模型必填参数，模型可填任意主体。

进一步思考：“@Tool 已生成 Schema 就不用手工校验？”业务语义仍需校验。“returnDirect 等于结果可信？”它改变返回路径，不改变业务事实。

如何验证：从实际工具调用入口覆盖上下文缺失、跨用户参数、异常、超大结果和敏感返回；检查上下文及日志，不能只直接调用 Java 方法。

7. OpenClaw 的 Skill、Channel 与会话路由各是什么层？

从机制到边界，再用具体交错检验结论。

记忆关键词：Skill 教方法 · Tool 给能力 · Channel 运载 · Session 隔离

核心结论

Skill 提供使用能力的指导，工具提供实际调用，Channel 组织输入输出和路由，会话保存相应上下文。指导文档不会自动成为不可绕过的授权规则。

拆开机制与保证范围

Skill 中可以描述业务步骤、前置条件和何时调用工具，OpenClaw 的加载与 gating 决定相应指导何时可见；真正危险操作应由应用端的参数验证与确认流程约束。不能仅在 Markdown 写“必须确认”就认为所有执行路径已经被保护。

Channel 需要把用户、租户、会话、任务与事件路由建立可信关联。客户端自报 sessionId 不能自动获得读取该会话的资格；相同会话名、不同用户的上下文不能混在一起。传输连接重建也不应导致后台任务身份改变。

上下文注入需区分可信元信息、用户输入和工具/检索数据。旧会话记忆可能过时，工具结果里的指令可能是注入内容；执行资格仍在当前授权边界重新检查。分清业务适配层与框架运行时，才能定位哪个组件处理会话、工具调用和副作用。

场景推演：用户切换场景后旧 SSE 回调仍到达，如果仅按全局 sessionName 写界面，旧结果可能出现在新场景；应以可信会话及 run 身份路由和校验。

进一步思考：“Skill 越多能力越强？”会增加选择、上下文与维护成本。“会话隔离就是用户隔离？”还需权限和存储/路由维度真正匹配。

如何验证：覆盖同名会话、用户切换、重连、旧结果与恶意工具文本；核对加载版本和实际执行拦截，不把文档约定当成权限测试。

8. 高风险 Action 的人工确认究竟应该确认什么？

从机制到边界，再用具体交错检验结论。

记忆关键词：不可变动作快照 · 授权主体 · 有效期 · 当前资格 · 幂等

核心结论

确认应绑定确定的动作、参数、目标和版本，执行时再核对当前资格。只确认“允许继续”不能证明随后变更的任务仍获授权。

拆开机制与保证范围

先构造待审动作：包含租户/主体、操作类型、目标资产、关键参数、资源版本与有效期。把规范化快照与确认记录关联，UI 展示同一快照；模型或客户端后续改参数应要求新的确认，而不能沿用先前批准。

确认后到执行前，天气、资源占用或权限可能变化。确认表示用户接受当时展示的动作，执行资格仍需当前校验；版本不符或状态变化应拒绝/重新确认。需要受审计的确认消费和稳定 messageId，避免重复点击形成两个新动作。

确认记录与外部副作用也有提交窗口。业务受理状态、真正执行和结果返回必须分开，未知结果保留原身份查证。前端禁用按钮只是交互措施，真实重放、参数篡改和并发由服务端协议处理。

场景推演：确认 A 区域的航线后，客户端提交了 B 区域；服务按动作快照发现不一致并拒绝。即便区域不变，资源版本过时也不能直接执行。

进一步思考：“确认一次可批准整段对话？”应明确授权范围，不能无限扩大。“同 messageId 重试都返回成功？”只有已有可查证结果才能返回相应状态。

如何验证：下方模型验证篡改、过期、版本变化和重复提交；真实验收还需服务端原子受理、权限、外部幂等和结果未知恢复。

9. 空间资产按名称引用，为何要讲坐标语义、身份和版本？

从机制到边界，再用具体交错检验结论。

记忆关键词：名称不是 ID · 场景/租户 · CRS/单位 · 高程基准 · 快照

核心结论

名称帮助人和模型选择资产，执行需要确定的资产身份、坐标语义和版本。字符串匹配成功不代表位置、权限和当前有效性正确。

拆开机制与保证范围

同名区域可能出现在不同用户或场景，应在可信范围内解析并返回确定 assetId/version；歧义时要求选择，不能让模型随意挑一个。执行引用用稳定身份或快照，名称后续修改不应悄悄改变已确认动作的目标。

GeoJSON 等协议明确坐标轴和参考系的约定，常见位置以经度、纬度顺序表达，第三维还涉及高程语义。实际设备接口可能使用不同坐标或高度基准，需显式转换和验证。度、米、相对地面高与参考椭球高不能因为都叫 altitude 就混用。

最佳视角除点位还可能含方向、俯仰、变焦及场景元信息；教学文档只解释契约，不提供真实飞控参数。资产删除、权限变更和新版本出现后，旧确认应按明确政策拒绝或重新确认，不能靠自然语言“还是那里”绕过检查。

场景推演：模型选到“北区”，UI 显示的是同名另一场景。先返回可核对的 assetId、场景与坐标基准，再构造确认快照，防止名称歧义进入执行。

进一步思考：“经纬度看着正常就可用？”轴序、参考系和权限都可能错。“数据库更新坐标即可热生效？”要考虑在途任务引用的版本。

如何验证：用固定虚构点位测试轴序、单位、基准、同名资产和版本变化；真实空间与飞控正确性须用项目契约和隔离验证，不能用模型回答代替。

Action 模型练习：批准的快照不可被改成另一个动作

Python 3 标准库模型。确认与执行在单进程中演算，不模拟数据库事务、真实用户认证、网络重放或设备执行。时间由测试显式传入。

保存为 practice.py，用 python practice.py 运行。

from dataclasses import dataclass

@dataclass(frozen=True)
class Proposal:
    user: str
    action: str
    asset: str
    version: int

approved = Proposal("user-a", "inspect", "asset-a", 3)
accepted = {}

def accept(message_id, proposal, user, now, expiry, current_version):
    if proposal != approved or user != approved.user:
        raise ValueError("approval mismatch")
    if message_id in accepted:
        return accepted[message_id]
    if now >= expiry or current_version != proposal.version:
        raise ValueError("approval expired or resource changed")
    accepted[message_id] = proposal
    return proposal

for proposal, user, now, version in [
    (Proposal("user-a", "inspect", "asset-b", 3), "user-a", 9, 3),
    (approved, "user-b", 9, 3),
    (approved, "user-a", 10, 3),
    (approved, "user-a", 9, 4),
]:
    try:
        accept("message-1", proposal, user, now, 10, version)
        raise AssertionError("invalid approval accepted")
    except ValueError:
        pass
assert not accepted
assert accept("message-1", approved, "user-a", 9, 10, 3) == approved
assert accept("message-1", approved, "user-a", 11, 10, 4) == approved
assert len(accepted) == 1
print("approval binding, expiry, version and repeat lookup passed")
