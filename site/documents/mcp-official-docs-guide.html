1. MCP 是什么

一个连接 AI 应用与外部系统的开放标准——官方的比喻是「AI 应用的 USB-C 接口」。

解决 N×M 集成问题

没有统一协议时，N 个 AI 应用 × M 个数据源/工具需要 N×M 套定制集成；MCP 把它变成 N+M：应用实现一次客户端，服务方实现一次服务器。

连接什么

数据源（本地文件、数据库）、工具（搜索引擎、API、计算器）、工作流（专门化的提示模板），让 AI 能拿到关键信息并执行任务。

广泛的生态

Claude、ChatGPT、VS Code、Cursor 等客户端均已支持，官方还维护参考服务器实现、多语言 SDK 与 Inspector 调试工具。

官方文档的板块结构

  • Learn（概念）：介绍、架构总览、服务器/客户端概念、版本机制——回答「MCP 是什么、怎么运转」。
  • Develop（开发）：本地/远程服务器接入、构建服务器与客户端的实操教程、客户端最佳实践、SDK 清单。
  • Security（安全）：OAuth 授权教程、安全最佳实践（攻击面与缓解）、本地服务器安全三篇。
  • Tools（工具）：MCP Inspector（Web/CLI/TUI/mcpdo 四种形态）与调试指南。
  • Specification（规范）：按版本冻结的协议本体，含变更日志与废弃特性注册表。

边界很重要：MCP 只定义「上下文如何交换」的协议——它不规定 AI 应用如何使用 LLM、如何管理上下文。宿主的智能编排完全在协议之外。

2. 核心架构：宿主、客户端与服务器

客户端-服务器架构 + 双层协议设计，2026-07-28 版起彻底无状态。

三种参与者

  • MCP Host（宿主）：AI 应用本体（如 Claude Code、VS Code），负责协调并管理一个或多个 MCP 客户端，掌控整体用户体验。
  • MCP Client（客户端）：协议层组件，由宿主为每个服务器实例化，维护与对应服务器的专属连接并获取上下文。
  • MCP Server（服务器）：向客户端提供上下文的程序，与运行位置无关——本地 stdio 服务器通常服务单个客户端，远程 Streamable HTTP 服务器通常服务大量客户端。

两层协议

  • 数据层（内层）：基于 JSON-RPC 2.0 的交换协议——发现（server/discover）、服务器特性（tools / resources / prompts）、客户端特性（elicitation）、工具类特性（通知、进度）。
  • 传输层（外层）：负责通道与安全——连接建立、消息成帧、授权。对上层屏蔽细节，让同一套 JSON-RPC 消息跑在 stdio 或 HTTP 之上。

无状态是本版的底色：处理一个请求所需的全部信息都包含在请求自身之中。服务器不得从先前请求（哪怕同一连接上的）推断上下文；需要跨请求的状态必须用显式句柄（如购物车 ID）由客户端每次携带。一个打开的 stdio 进程不是「会话」，连接身份不能当作会话连续性的依据。

3. 2026-07-28 版重大变更

这是 MCP 迄今最大的一次协议重构：去会话、去握手、全部元数据随请求走。

4. 协议消息与 _meta 元数据

一切围绕 JSON-RPC 2.0 的三种消息展开，元数据全部内联在 _meta 里。

Request（请求）

带字符串或整数 id（不允许 null，且不得与在途请求撞号）、method、可选 params。客户端发给服务器以发起操作。

Response（响应）

成功时回 result（必须含 resultType 字段，支持多态结果）；失败时回 error（code + message + 可选 data）。

Notification（通知）

单向消息，无 id，接收方不得回复。用于进度、日志、订阅流上的变更事件。

_meta 保留键方向作用
io.modelcontextprotocol/protocolVersion客户端 → 每请求（必填）声明本请求使用的协议版本，如 "2026-07-28"
io.modelcontextprotocol/clientCapabilities客户端 → 每请求（必填）声明与该请求相关的能力（elicitation 等）；缺必填字段即畸变请求，服务器以 -32602 拒绝
io.modelcontextprotocol/clientInfo / serverInfo双向（建议携带）自报的实现名与版本，仅用于展示/日志/调试
io.modelcontextprotocol/logLevel客户端 → 每请求（可选）为该请求设置最低日志级别（Logging 特性，已废弃）
io.modelcontextprotocol/subscriptionId服务器 → 订阅流通知把通知关联到打开它的 subscriptions/listen 请求
progressToken客户端 → 请求为该请求开启进度通知（见第 6 节）
traceparent / tracestate / baggage双向W3C 格式的 OpenTelemetry 链路上下文透传

错误码体系

  • 通用协议错误沿用 JSON-RPC 2.0：-32700（解析错误）、-32600～-32603（无效请求/方法/参数/内部错误）。
  • -32020 HeaderMismatch：HTTP 头与请求体不匹配。
  • -32021 MissingRequiredClientCapability：请求依赖客户端未声明的能力。
  • -32022 UnsupportedProtocolVersion：版本不支持，data.supported 列出可用版本供重试。
  • 资源不存在从 -32002 改为 -32602；客户端仍应兼容旧码。

JSON Schema 约定

  • 工具输入/输出 schema 未带 $schema 时默认按 2020-12 方言解释，实现必须支持。
  • 不得自动解引用指向网络 URI 的 $ref；校验失败应显式拒绝而非静默放行。
  • 对 anyOf/oneOf/allOf 等组合关键字设置深度/数量/时间预算，防止恶意 schema 拖垮校验器（DoS）。
  • 规范本体是 TypeScript schema（仓库中的 schema.ts），JSON Schema 由其自动生成。

身份字段不可信：clientInfo 与 serverInfo 是发送方自报的，协议不校验。实现不应据此改变行为，更不应据此做安全决策。另：_meta 键名采用「反域名前缀/名称」格式，第二段为 modelcontextprotocol 或 mcp 的前缀（如 io.modelcontextprotocol/）保留给协议与官方扩展。

5. 服务器原语：Tools / Resources / Prompts

三种积木按「谁来控制」区分——模型控制、应用控制、用户控制。

原语控制方定位典型例子协议方法
Tools模型（Model）可执行函数：查库、调 API、改文件。模型根据上下文决定何时调用，可要求用户确认搜索航班、发消息、建日历事件tools/list、tools/call
Resources应用（Application）只读数据源，作为上下文提供给模型：文件内容、库表结构、API 文档读文档、访问知识库、读日历resources/list、resources/templates/list、resources/read、订阅更新
Prompts用户（User）预制指令模板，需用户显式触发；可引用资源与工具组成完整工作流计划一次度假、总结会议、起草邮件prompts/list、prompts/get

Tools 要点

  • 命名：1–128 字符、大小写敏感、仅 A-Za-z0-9_.-、服务器内唯一；聚合多服务器时客户端应加前缀消歧。
  • Schema：inputSchema 必填（无参数时推荐 {"type":"object","additionalProperties":false}）；outputSchema 可选，配 structuredContent（任意 JSON 值）返回结构化结果，兼容起见应同时在 text 块里给序列化 JSON。
  • 两类错误：协议错误（未知工具、畸变请求）走 JSON-RPC error；工具执行错误（参数校验失败、业务失败）用 isError: true 的正常结果返回，让模型能自我纠正后重试。
  • 有状态工具：协议无会话，跨调用状态用显式句柄——create_basket 返回 basket_id，后续调用携带；句柄要高熵、不透明、绑定期限，并按「名称而非能力」做每次鉴权。
  • 确定性顺序：tools/list 应按稳定顺序返回，便于客户端缓存并提高 LLM 提示词缓存命中率。

Resources 与 Prompts 要点

  • URI 标识：每个资源有唯一 URI 与可选 MIME 类型；https:// 仅用于客户端可自行抓取的资源，file:// 不必对应物理文件系统，可自定义 scheme。
  • 资源模板：RFC 6570 URI 模板（如 weather://forecast/{city}/{date}）实现参数化查询，参数可接自动补全。
  • 注解：audience（user/assistant）、priority（0–1）、lastModified 帮客户端过滤与排序上下文。
  • 内容：文本（text）或二进制（blob，base64）；工具结果可回 resource_link 或内嵌 resource。
  • Prompts 形态：参数化模板 + messages（role 为 user/assistant，内容可为文本/图像/音频/资源链接）；常以斜杠命令、命令面板等 UI 暴露。
  • 变化通知：三者都在能力中声明 listChanged，经 subscriptions/listen 推送列表变化。

人在回路：信任与安全上应始终有能拒绝工具调用的人。应用应清晰展示暴露给模型的工具、调用时给出可见指示、对敏感操作弹确认。工具注解（annotations）来自服务器，除非可信来源否则视为不可信输入——名称与描述本身就是模型会读的指令。

6. 客户端原语与多轮往返（MRTR）

服务器需要用户输入或 LLM 补全时，不再主动发请求，而是「把请求装进结果里」。

MRTR 机制

  • 仅 tools/call、resources/read、prompts/get 三个请求可返回 InputRequiredResult。
  • inputRequests 是「键 → 请求对象」的映射，值只允许 elicitation/create、sampling/createMessage、roots/list 三种；不得发给客户端未声明支持的能力。
  • requestState 是只对服务器有意义的 opaque 字符串（可 base64 JSON、加密 JWT、序列化二进制）；客户端必须原样回带、禁止解析或修改。
  • 重试是新请求：JSON-RPC id 必须不同；缺信息时服务器应再次返回 InputRequiredResult 而不是报错。
  • 服务器可以多次循环请求输入，但不得假设客户端一定会重试。

requestState 安全红线

  • 它经客户端之手，必须按攻击者可控输入处理：一旦影响鉴权、资源访问或业务逻辑，必须做完整性保护（HMAC 或 AEAD）并拒绝校验失败的值。
  • 防重放应在受保护载荷中绑定：认证主体（跨用户拒收）、短 TTL、原请求标识（方法名 + 关键参数摘要）。
  • 「至多消费一次」的语义（如一次性核销）必须由服务器侧自行保证，协议不提供单次性。

Elicitation：服务器向用户要信息（当前唯一的活跃客户端原语）

  • form 模式（带内）：用受限 JSON Schema 子集（扁平对象 + string/number/boolean/枚举，format 支持 email/uri/date/date-time，支持 default 预填）描述要收集的结构，客户端据此渲染表单并校验。刻意不支持嵌套对象，换取一致的客户端体验。
  • url 模式（带外）：给一个 URL 让用户自己去开——交互数据不过客户端、不进 LLM 上下文，适合凭据录入与第三方 OAuth（服务器此时同时是 MCP 客户端的资源服务器、第三方服务的 OAuth 客户端）。
  • 三动作响应模型：accept（提交数据）/ decline（明确拒绝）/ cancel（直接关闭）；url 模式的 accept 只代表用户同意打开，完成与否由服务器从 requestState 或自身存储判断。
  • 隐私与反钓鱼：密码、API key、访问令牌、支付凭据禁止走 form 模式；客户端必须显示完整 URL、取得明确同意后才打开、不得预取；服务器必须核实打开 URL 的用户与发起请求的用户是同一人（如 connect 页核对会话 cookie 与 MCP 授权的 sub 一致），否则存在账户接管式钓鱼。
  • 能力声明：客户端在每请求的 clientCapabilities.elicitation 声明 form/url 子模式；空对象等价于仅 form。

Sampling（已废弃）

服务器借宿主的 LLM 做补全（sampling/createMessage，走 MRTR），带 modelPreferences（cost/speed/intelligence 权重）、systemPrompt、maxTokens，设计上全程人工审批。新实现应直接对接 LLM 提供商 API。

Roots（已废弃）

客户端用 file:// URI 列表告知服务器工作边界（roots/list）。它是协调机制而非安全边界——「应尊重」而非「必须强制」。新实现改用工具参数 / 资源 URI / 服务器配置传递路径。

订阅与通知（subscriptions/listen）

  • 过滤器：toolsListChanged / promptsListChanged / resourcesListChanged / resourceSubscriptions（URI 数组）。
  • 服务器第一条消息必须是 notifications/subscriptions/acknowledged，其 notifications 字段反映实际接受的子集。
  • 流上每条通知带 subscriptionId（即 listen 请求的 JSON-RPC id），多订阅可并发、可分路。
  • 服务器主动收摊时应回一个正常响应作为优雅结束；传输断开则客户端可重连；stdio 重连后必须重发 listen。
  • 通知是尽力而为，客户端仍应配合轮询/TTL 保证新鲜度。

进度与取消

  • 进度：请求带 progressToken，服务器以 notifications/progress 回报 progress（必须递增，可浮点）、可选 total 与 message；只在相关请求的响应流上发。
  • 取消：Streamable HTTP 上直接关掉该请求的 SSE 响应流即为取消信号；stdio 上发 notifications/cancelled 引用请求 id。服务器端取消仅用于订阅流收摊。
  • 超时：双方应对所有请求设超时；可按进度通知重置计时，但必须保留最大超时上限。

7. 传输层：stdio 与 Streamable HTTP

同一套 JSON-RPC 消息，两种官方通道；帧格式与取消语义各不相同。

维度stdioStreamable HTTP
形态客户端把服务器作为子进程启动，stdin/stdout 通信服务器是独立进程，暴露单个 MCP 端点（如 https://example.com/mcp）接受 POST
成帧换行分隔的 JSON-RPC，消息内不得含换行每条消息一个 HTTP POST；响应为单个 JSON 或该请求作用域内的 SSE 流
方向约束stdout 只许协议消息且禁止服务器发请求（服务端→客户端交互全部走 MRTR）；日志写 stderr客户端只 POST 请求/通知（通知回 202）；服务器不得在流上发独立请求
取消notifications/cancelled + 请求 id关闭该请求的 SSE 响应流
请求元数据全部内联在消息体 _meta，无头层镜像到 HTTP 头：MCP-Protocol-Version（必填，须与 _meta 一致）、Mcp-Method、Mcp-Name；头体不一致回 400 + HeaderMismatch
关闭关 stdin → 等退出 → 超时则 SIGTERM/SIGKILL（Windows 用 TerminateProcess / Job Objects）流结束即请求结束；订阅流可由任一方关闭
授权不走 OAuth，凭据从环境变量取按第 8 节 OAuth 2.1 框架；须校验 Origin 防 DNS rebinding（无效回 403）、本地只绑 127.0.0.1
适用本机进程，零网络开销，性能最优远程/多客户端；支持标准 HTTP 认证与中间件

Streamable HTTP 细节

  • 每个 POST 必须带 Accept: application/json, text/event-stream，两种响应都要能处理。
  • SSE 响应流：先发与该请求相关的通知（进度/日志），最终响应结束流；建议带 X-Accel-Buffering: no 让 nginx 等反代关闭缓冲，静默期发 : 注释行做 keep-alive。
  • 不再支持 Last-Event-ID 断流恢复——断流即失败，以新 id 重发。
  • 未知方法回 404 + -32601（区别于旧 HTTP+SSE 服务器的裸 404）。
  • 长连接通知只能来自 subscriptions/listen 的响应流；请求级通知不进订阅流。

x-mcp-header：参数进 HTTP 头

  • 工具 schema 里给原始类型参数标 "x-mcp-header": "Region"，客户端调用时就会加 Mcp-Param-Region: us-west1，供负载均衡/WAF/网关不解体就能路由。
  • 约束：非空、RFC 9110 token 语法、schema 内大小写不敏感唯一、仅 integer/string/boolean、只能出现在从根纯 properties 链可达的位置（不得穿过 items/组合关键字/$ref）。
  • 非 ASCII/含控制符/首尾空格的值用 Base64 哨兵编码：=?base64?…?=；与哨兵模式撞形的普通值也必须编码。
  • 处理消息体的服务器必须校验头值（解码后）与请求体一致，失败回 400 + -32020。
  • 敏感参数（密码、密钥、PII）不应标注 x-mcp-header——头对链路上中间人可见。

与旧版服务器的互通探测

  • stdio：双时代（dual-era）客户端应先发 server/discover——拿到 DiscoverResult 或现代错误（如 UnsupportedProtocolVersion）即现代服务器；其他错误或超时则回落 initialize 握手。回落不能绑定特定错误码。
  • HTTP：先发一个现代请求，收到 400 时先看响应体——含可识别的现代 JSON-RPC 错误说明对方是现代服务器（按其 supported 版本重试）；体为空或不可识别才回落 initialize，乃至旧 HTTP+SSE（先 GET 等 endpoint 事件）。
  • 时代判定是服务器属性：按进程（stdio）或源站（HTTP）缓存，可在同配置重启间持久化。
  • 只支持现代版的服务器收到旧客户端 initialize 时，应在错误信息中列出自己支持的版本——旧客户端没有前向升级机制，这可能是用户能看到的唯一诊断。

8. 授权（OAuth 2.1）与安全

MCP 服务器即 OAuth 资源服务器；攻击面文档值得整篇读，这里浓缩成可执行的清单。

角色映射

MCP 服务器 = OAuth 2.1 资源服务器；MCP 客户端 = OAuth 客户端；授权服务器独立部署（RFC 8414 / OIDC Discovery 元数据发现）。

依赖的 RFC

OAuth 2.1 草案、RFC 6750（Bearer）、RFC 9728（受保护资源元数据，服务器必须实现）、RFC 8707（resource 指示符，客户端必须实现）、RFC 9207（iss 防混淆）、CIMD 草案。

适用范围

仅 HTTP 传输。stdio 不应走这套流程，凭据从环境获取；双方亦可协商自定义认证。

授权全流程

  • ① 无令牌请求 → 服务器回 401 + WWW-Authenticate（含 resource_metadata URL 与可选 scope 提示）。
  • ② 客户端抓取受保护资源元数据（RFC 9728）→ 得到授权服务器列表与 scopes_supported。
  • ③ 抓授权服务器元数据（先试 OAuth 2.0 再试 OIDC 端点）。
  • ④ 客户端注册：优先 Client ID Metadata Documents（用 HTTPS URL 当 client_id，服务器反抓元数据验证 redirect_uris）；RFC 7591 动态注册已废弃但保留兼容；或预注册。
  • ⑤ 生成 PKCE，带上 resource 参数（服务器规范化 URI，如 https://mcp.example.com/mcp），按 scope 选择策略定 scope，记录期望 issuer。
  • ⑥ 浏览器走授权 → 回调带授权码 + iss；客户端按 RFC 9207 校验 iss 与记录值字符串精确比对（不做大小写/端口/斜杠归一），不匹配不得兑换。
  • ⑦ 换令牌（code_verifier + resource）→ 后续每个请求带 Authorization: Bearer（令牌绝不能进 URL 查询串）。
  • ⑧ 运行中权限不足 → 403 + error="insufficient_scope" + scope="…" → 客户端取「历史已授权 scope ∪ 本次挑战 scope」做 step-up 重新授权，重试有上限。
攻击面一句话机理核心缓解
Confused Deputy（混淆代理人）代理服务器对第三方用静态 client_id，第三方同意 cookie 使恶意动态注册客户端跳过同意页，授权码流向攻击者代理必须在转发第三方授权之前做每客户端同意；state 仅在同意后落 cookie、单次短时效；redirect_uri 精确匹配
Token Passthrough服务器不加校验地把客户端令牌透传给下游 API明令禁止：服务器必须校验令牌受众（audience，RFC 9068/8707）是发给自己的，只接受自己的令牌
SSRF恶意服务器把元数据 URL 指向内网/云元数据端点（169.254.169.254 等），借客户端之手探测客户端强制 HTTPS（环回除外）、封私网/链路本地段、逐跳校验重定向、出网走 egress 代理、防 DNS TOCTOU；CIMD 场景授权服务器同样适用
State Handle 劫持猜到/窃取无状态服务器的状态句柄（购物车 ID、requestState）冒用他人状态句柄≠认证：安全随机、不透明、绑定 user_id:handle、每次调用重新鉴权、有期限
本地服务器失陷本地 stdio 服务器是普通进程，可读环境变量、SSH 私钥、任意出网；恶意启动命令混进配置一键安装前必须完整展示将执行的命令；沙箱/容器运行；高亮危险模式（sudo、rm -rf、敏感目录）
授权 URL 注入javascript: URL 造成 XSS；经 shell 打开 URL 造成命令注入，可叠加 stdio 代理升级为 RCE只允许 http(s) scheme、拒绝 shell 打开 URL、CSP 限制脚本、严格 URL 解析与日志告警
Mix-Up 攻击攻击者控制的授权服务器骗客户端把别家发的授权码发给自己响应 iss 校验（绑定重定向前记录的 issuer）；PKCE 与 resource 参数单独都不够
localhost redirect 冒充CIMD 只能证明域名，不能证明哪个本地进程在监听 localhost 回调授权服务器对仅 localhost 的 redirect_uri 显示额外警告、明示回调主机名

Scope 最小化

  • 渐进式授权：初始只要低风险 scope（如 mcp:tools-basic），高危操作首次触发时按 WWW-Authenticate 挑战递增。
  • 初始挑战无 scope 参数时，回退请求 scopes_supported 全集（由 AS 与用户在同意页裁剪）。
  • 避免通配/大杂烩 scope（*、all）；一次挑战应给全当前操作所需，别挤牙膏式逐个加。
  • 令牌被盗时窄 scope 限制横向爆炸半径、简化撤销、让审计可读。

本地服务器安全清单（官方指南精华）

  • 能远程就别本地：只包远程 API 的服务器在本机运行毫无收益；Streamable HTTP 版不在你机器上跑代码。
  • 装前查来源：可追到真实维护者的仓库、精确包名防抢注、固定版本（容器按 digest 固定整棵依赖树）、优先有签名/证明/SBOM 的产物。
  • 工具定义是运行时输入：安装不是最后一次信任决策——用 Inspector 读一遍工具描述，描述里藏着与功能无关的指令就移除；警惕安装后悄悄改定义的 rug pull。
  • 容器隔离是最高杠杆：第三方服务器进容器跑、只挂必要目录；stdio 语义在容器上不变。
  • 凭据按服务器隔离：用每服务器 env 配置而非全局导出；令牌最小 scope；限文件系统与出网。

两条铁律：① stdio 客户端与服务器共享同一信任域——stdio 不是沙箱，隔离责任在宿主与运维；② 每多装一个服务器，所有服务器共享的模型上下文就多一分被投毒的面（tool poisoning / shadowing）——保持清单最小。

9. 缓存、分页、补全与可观测性

四个横切工具类能力，其中缓存提示是本版新要求。

能力机制要点
缓存（CacheableResult）server/discover、tools/list、prompts/list、resources/list、resources/templates/list、resources/read 的 complete 结果必须带 ttlMs + cacheScopettlMs 是新鲜度提示（类比 max-age）：0/缺失/负值都按立即过期；cacheScope："public" 可被共享缓存跨用户复用，"private" 只能同一授权上下文复用。缓存键 = 方法 + 影响结果的参数；MRTR 重试（带 inputResponses/requestState）的结果禁止缓存。通知到达即失效缓存；TTL 不是轮询间隔
分页四个 list 方法支持不透明 cursor / nextCursor页大小由服务器定；游标必须当黑盒（空串也是合法游标）；无 nextCursor 即结尾；无效游标回 -32602；每页独立缓存、无跨页一致性保证，要快照就从头重拉
补全（completion/complete）对 prompt 参数与资源模板参数提供 IDE 式自动补全，ref/prompt 或 ref/resource 引用目标可带 context.arguments 已填参数做上下文；单次最多 100 条建议，按相关性排序，hasMore 标记更多；客户端应防抖、缓存
日志（已废弃）每请求经 _meta 的 io.modelcontextprotocol/logLevel 开启，服务器在该请求的响应流上发 notifications/message（RFC 5424 八级）未带该字段的请求服务器不得发日志通知；日志是请求作用域的，不进订阅流。迁移：stdio 写 stderr，通用可观测走 OpenTelemetry（配合 _meta 的 W3C trace 上下文透传）

调试入口：stdio 服务器的 stderr 日志会被宿主自动捕获——千万别写 stdout（会污染 JSON-RPC 流，Python 里 print() 是雷区）；HTTP 服务器用自身日志聚合 / OpenTelemetry，配合 curl 与浏览器 DevTools 看请求和 SSE 流。常见坑：客户端拉起的服务器工作目录可能未定义，配置里一律用绝对路径。

10. 版本兼容与开发者生态

版本即日期、兼容靠探测；SDK、Inspector 与示例服务器构成工具链闭环。

版本与兼容模型

  • 版本号 YYYY-MM-DD，表示最后一次破坏性变更的日期；向后兼容的更新不升版本。修订版标记 Draft / Current / Final，当前 Current 为 2026-07-28。
  • Modern（2026-07-28+，每请求元数据）/ Legacy（≤2025-11-25，initialize 握手）/ Dual-era（两者皆支持）三词贯穿全部互通文档。
  • 双时代服务器按开场自动选边：带现代 _meta 的请求按无状态处理；initialize 则进入旧语义，同一端点可并发服务两个时代。
  • 兼容矩阵要点：Modern×Modern 直接工作（discover 可选）；Modern×Legacy 失败（stdio 先探测拿确定性错误）；Legacy×Modern 失败（旧客户端无前向机制）；Dual-era 与谁都能通。

官方 SDK（按支持层级）

  • Tier 1：TypeScript、Python、C#、Go、Rust、Ruby——功能与协议支持最完整。
  • Tier 2：Java。
  • Tier 3：Swift、PHP、Kotlin。
  • 全部 SDK 都支持：创建暴露 tools/resources/prompts 的服务器、构建可连任意服务器的客户端、本地与远程传输、类型安全的协议合规。
  • 官方教程主线：Python SDK 2.0+ 构建天气服务器（get_alerts / get_forecast）与 LLM 聊天机器人客户端；服务器用 MCPServer("name") 起步，客户端用 Client + stdio_client。

MCP Inspector：一个包、四种形态

  • npx @modelcontextprotocol/inspector（Web 图形界面，默认）、--cli（可脚本化、JSON 输出、退出码可进 CI）、--tui（终端 UI）；同核共享传输、配置、OAuth 状态与新旧协议协商。
  • 另附实验性 mcpdo：连一次、按命名连接跑多条命令。
  • 要求 Node ≥ 22.19.0；启动器只认 --web/--cli/--tui 与 -h，其余参数全归各客户端。
  • 密钥（OAuth 令牌、stdio env）优先存 OS 钥匙串，无钥匙串环境落 ~/.mcp-inspector/secrets.json（未加密，除非自带密钥）。

示例服务器与社区

  • 官方参考实现（modelcontextprotocol/servers 仓库）：Filesystem、Git、Fetch 等当前参考服务器，另有归档示例集。
  • 官方集成：Brave Search、Cloudflare、GitHub、GitLab、Google Drive/Maps、PostgreSQL、Puppeteer、Slack 等由服务方维护。
  • 社区实现覆盖 AWS、Kubernetes、浏览器自动化、数据库等长尾场景。
  • 启动姿势：Python 用 uvx mcp-server-git …，npm 用 npx @modelcontextprotocol/server-filesystem ~/Desktop，配置进宿主的 MCP 配置文件。

推荐路径：先用 Inspector 裸测服务器（无模型在环，能逐个看工具/资源/提示与 JSON-RPC 交换），再接宿主配置；客户端侧聚合多服务器时考虑渐进式工具发现而非一次全量加载。规范仓库（github.com/modelcontextprotocol）以 SEP 流程演进，社区可经 GitHub Discussions 与贡献指南参与。
