2. B+ 树、聚簇索引与联合索引如何落到一次查询？

从机制到边界，再用具体交错检验结论。

记忆关键词：页 → 有序键 → 聚簇记录 → 二级主键 → 回表

先这样回答

索引是按特定顺序组织的访问路径。InnoDB 聚簇索引的叶子包含记录，二级索引通常携带主键；查询是否回表和扫描多少项，要看字段、条件与访问计划。

拆开机制与保证范围

树形索引降低定位范围所需的页访问，页内有序和叶子范围扫描利于区间读取。二级索引查到主键后可能再定位聚簇记录，因此宽主键会增加二级索引负担；随机插入也会影响页分裂和写入局部性，不能只说树高很低所以所有 SQL 都快。

联合索引 (tenant_id, status, created_at, id) 建立的是按这些列排序的键空间。能否利用过滤、范围与排序取决于条件形态、选择性和优化器决定。范围后的列仍可能用于过滤或索引条件下推，不能背成“范围后所有列完全失效”。

覆盖索引可减少某些回表需求，但写入要维护更多索引。查询只扫几十条与先扫大量候选再筛出几十条是不同成本；LIMIT 也不保证只读取对应数量。索引设计要从实际谓词、排序、返回列和写入负担共同推导。

项目推演：多租户任务列表按状态和时间翻页。先按 tenant/status 缩小键区间，再用 created_at/id 做稳定游标，通常比深 offset 丢弃大量历史项更易控制。

继续追问：“低基数字段不能建索引？”联合条件和分布会改变价值。“覆盖就一定更快？”还要比较扫描量、页大小和维护成本。

如何验证：用真实分布下的执行计划核对访问路径、扫描行、回表和排序；逐个改变过滤/排序条件，并记录写入代价，而非只看索引命中名称。

3. MVCC 为什么既能减少读写冲突，又不能解决所有竞争？

从机制到边界，再用具体交错检验结论。

记忆关键词：版本链 · Read View · 快照读 · 当前读 · 长事务

先这样回答

MVCC 让某些非锁定读看到一致性版本，而不是让所有读写都免锁。抢占同一资源属于当前状态竞争，需要条件更新、锁或约束参与。

拆开机制与保证范围

旧版本通过 Undo 等机制重建，Read View 决定哪些事务版本对当前读取可见。在常见 RR 一致性读路径中，第一次一致性读确立快照；RC 常按语句建立新快照。事务自身已写入的数据有特殊可见性，因此不能简单描述成整段事务永远只看开始前世界。

SELECT ... FOR UPDATE 与更新语句检查当前可处理的状态并涉及锁。先用快照读看到机库空闲，再无条件 UPDATE，会留下两个请求都做出“可以分配”的竞态；快照看到事实不等于已经取得写入资格。

长事务使旧版本需要保留更久，还可能扩大锁等待或影响清理。分页扫描、业务等待和远程调用如果长期留在同一个事务里，会把服务时间传给数据库。读模型可以允许滞后，执行前置条件则需要明确当前状态检查。

项目推演：A、B 都从各自快照看到 IDLE。真正占用时使用 WHERE status=IDLE AND version=v，数据库更新资格只交给符合条件者；B 的旧观察不会覆盖新的状态。

继续追问：“RR 没幻读所以无需条件？”隔离保证与业务选择资格不同。“所有 SELECT 都走 Read View？”要区分快照读与锁定读。

如何验证：在两个连接中交错普通读、锁定读、提交与更新；记录隔离级别和执行计划。观察长事务、Undo 清理和锁等待，不拿单连接演示冒充并发实验。

4. 条件更新、唯一约束、悲观锁分别保护哪些不变量？

从机制到边界，再用具体交错检验结论。

记忆关键词：当前状态资格 · 唯一身份 · 锁区间 · 影响行数

先这样回答

条件更新保护“仍然符合前置状态”，唯一约束保护“同一身份不能重复创建”，悲观锁组织并发修改。三者可以组合，但各自的保证对象不同。

拆开机制与保证范围

UPDATE resource SET state=BUSY, version=version+1 WHERE id=? AND state=IDLE AND version=? 把判断与更新放到同一数据库语句。应用必须检查影响行数；零行不是成功，也不一定只有版本冲突一种原因。

唯一键如 (tenant_id, request_id) 可以让重复受理发生冲突，但请求键还需绑定载荷摘要，否则同键异参可能被误认作同一动作。多资源一起分配要在事务内保证全成或全退，或使用明确的保留与补偿协议，不能只对每条记录各成功一半。

InnoDB 常按访问的索引记录和范围加锁，锁范围由索引、谓词、隔离级别和执行路径共同决定。死锁可由不同资源访问顺序形成；统一顺序、缩短事务和有限重试比把所有异常吞掉更有意义。缺索引时影响范围可能扩大。

项目推演：一次任务要两个机库。若 A 成功占用第一座后第二座失败，必须回滚本地占用或可靠释放；否则任务未成立却长期占住半套资源。

继续追问：“Redisson 锁后 SQL 还要条件？”租约可能失效，数据库应保留最终资格门槛。“影响 1 行就代表任务下发成功？”只证明这条数据库更新成立。

如何验证：模型练习验证同一旧版本只接受一次更新；真实实验还要并发多连接、覆盖不同索引与失败回滚，核对全部资源是否泄漏。

5. Redo、Undo、Binlog 与 outbox 如何解释提交后发消息？

从机制到边界，再用具体交错检验结论。

记忆关键词：恢复日志 · 历史版本 · 复制日志 · 同事务意图

先这样回答

Redo 支撑 InnoDB 崩溃恢复，Undo 支撑回滚与版本重建，Binlog 用于复制等链路。它们并不自动让数据库更新和任意外部 MQ 发送成为同一事务。

拆开机制与保证范围

事务可先在内存页上修改数据，再按日志与提交协议满足持久化要求，脏页不必与客户端提交响应同步写完。实际断电保证受日志刷盘策略、文件系统与设备契约影响；“写了日志”没有交代到哪一层完成。

业务记录提交后再直接发 MQ，会在提交与发送之间留下崩溃窗口；先发 MQ 再提交，又可能向消费者发布一个最终回滚的事实。outbox 把业务事实和发送意图写在同一本地事务中，发送器重试已持久的意图。

outbox 不代表 MQ 与数据库形成一个全局提交。发送成功后标记前崩溃仍会重发；消费者需要稳定事件身份和原子去重处理。也要处理积压、毒消息、投递确认和清理，避免把 outbox 表当成永远增长的附件。

项目推演：资源占用和 ResourceReserved 事件一起提交；发送器发出事件但标记失败，下次重复发。消费者按 eventId 去重，使重复传输不重复创建采集组。

继续追问：“开启 Binlog 就是 CDC 自动可靠？”还需位点、订阅、重放和事件版本协议。“消息发送器标成成功就结束？”要明确成功是 broker 确认还是业务执行。

如何验证：在提交前后、发送前后和标记前后分别中断，检查业务事实、待发意图和消费效果；断电持久性需在隔离真实存储环境验证。

6. 慢 SQL 应该如何从计划走到证据？

从机制到边界，再用具体交错检验结论。

记忆关键词：估算与实际 · 扫描量 · 锁等待 · 缓冲 · 分布

先这样回答

慢查询可能在扫描、排序、等待锁或等待资源。执行计划解释访问路径，运行指标解释真实成本；仅看到“用了索引”不能证明高效。

拆开机制与保证范围

EXPLAIN 展示优化器计划，EXPLAIN ANALYZE 会实际执行支持的语句并给出运行信息。因此应在受控环境和确认副作用的前提下使用，不能把它当免费静态分析。计划中的估算与实际差异常提示统计信息、参数分布或相关性问题。

按租户、状态、时间窗口和分页位置分组，热点租户与多数小租户可能需要不同访问成本。固定缓存命中、数据规模和并发条件再比较，避免一次冷热缓存差异被归因为某个索引。锁等待的改善也不一定来自扫描优化。

先定位延迟分段，再选择最小变化：减少扫描范围、消除非必要返回列、稳定分页或缩短事务。大量加索引会放大写入与存储负担；数据库连接池排队应与 SQL 执行时间分开，池里等三秒不能说 SQL 本身执行三秒。

项目推演：大屏接口整体慢，真正时间花在等待连接，SQL 执行只占少部分。扩大索引没有解决排队，增加连接反而可能使数据库更拥挤。

继续追问：“rows 很小为什么还慢？”可能回表、锁、I/O、网络或并发环境改变。“加缓存就解决？”缓存会引入时效与失效问题，须保留正确性要求。

如何验证：同时记录池等待、数据库执行、锁等待和结果传输；用相同分布的参数验证前后吞吐与尾延迟，保留结果一致性检查。

7. Elasticsearch 的倒排索引、doc_values 与 refresh 是什么关系？

从机制到边界，再用具体交错检验结论。

记忆关键词：词到文档 · 文档到字段值 · segment · 搜索可见

先这样回答

倒排索引用于从词定位文档，doc_values 支撑常见排序和聚合访问；refresh 使某些新写入进入可搜索视图，搜索可见性与持久化不是同一保证。

拆开机制与保证范围

text 字段常经分析器拆成词项，keyword 保留适合精确匹配的值。对名称做全文搜索与对状态做精确聚合，应该使用符合语义的映射；在分析后的 text 上聚合得到的可能是词，不是原始业务标签。

排序和聚合需要高效取得文档的字段值，doc_values 为支持的字段提供这种访问结构。字段类型与可用能力需核对；为 text 开 fielddata 可能显著增加内存，不能把“查询能返回值”当成“适合聚合”的证明。

新写入到可搜索之间常有 refresh 边界。将 refresh 强制频繁触发可能伤吞吐；涉及“写后立刻看”的交互应选明确策略和读取契约。ES 投影还可能比数据库事件落后，因此搜索查无结果不等于权威任务不存在。

项目推演：告警写入数据库后，大屏聚合短时间未显示。先区分事件投影未完成、ES 未 refresh 和 Redis 仍有旧缓存，不直接认定消息丢失。

继续追问：“refresh 等于 fsync？”不是同一层承诺。“ES 与 MySQL 谁替代谁？”先分别讨论权威事务与搜索投影，不跨层比较。

如何验证：核对字段 mapping、分析结果和刷新时序；同一 eventId 记录数据库提交、投影受理、搜索可见与缓存更新的时间。

8. ES terms 聚合与大屏缓存为什么需要“口径”而不只是提速？

从机制到边界，再用具体交错检验结论。

记忆关键词：分片候选 → 全局归并 · 截断/误差 · 时间与权限维度

先这样回答

分片聚合可能先在各分片取有限候选，再全局归并。返回 top buckets 不等于所有类别的完整精确计数；缓存还必须保留筛选、租户和数据时刻。

拆开机制与保证范围

terms 的 size 控制返回桶，shard_size 等参数影响分片候选；按常见文档数排序时可观察 doc_count_error_upper_bound 和 sum_other_doc_count，其他排序的误差语义有不同限制。遗漏候选与被截断桶可能让业务误把 top 列表当全量统计。

要列出全部类别时，可以评估 composite 聚合分页等适合的方案，但分页期间数据变化仍需考虑一致视图。cardinality 等聚合有不同精度契约；不能把所有聚合统称绝对准确。高基数、宽时间窗口和大量桶也会扩大分片与协调节点成本。

Redis 缓存键需包含真正影响结果的租户、权限范围、过滤条件和统计口径版本。TTL 描述缓存保留，不证明来源已经新鲜；结果应能说明统计截至何时、是否近似和刷新状态。不能缓存一次管理员查询再返回给普通用户。

项目推演：某设备类别在每个分片都不进本地前几名，却在全局有很大总量；候选不足可能漏掉它。提高 shard_size 可以改善部分情况，但不能代替对统计需求的明确设计。

继续追问：“sum_other_doc_count 为零就全都精确？”还需看误差、排序和请求条件。“缓存命中率高就成功？”口径错误的快速响应仍是错误结果。

如何验证：用可枚举的小数据跨分片建立精确基准，对比 terms 参数和缓存权限维度；再在大数据验证资源成本，别把单分片正确当成分布式正确。

SQL 模型练习：旧版本不能重复抢占资源

Python 3 + 标准库 SQLite 内存数据库，只验证条件更新与影响行数。不验证 InnoDB 的 MVCC、间隙锁、死锁和真实并发。

保存为 practice.py，用 python practice.py 运行。

import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("CREATE TABLE resource(id INTEGER PRIMARY KEY, state TEXT, version INTEGER)")
    db.execute("INSERT INTO resource VALUES(1, 'IDLE', 0)")
    claim = """UPDATE resource SET state='BUSY', version=version+1
               WHERE id=? AND state='IDLE' AND version=?"""
    first = db.execute(claim, (1, 0)).rowcount
    stale = db.execute(claim, (1, 0)).rowcount
    assert (first, stale) == (1, 0)
    assert db.execute("SELECT state, version FROM resource").fetchone() == ("BUSY", 1)
    db.execute("CREATE TABLE accepted(tenant TEXT, request_id TEXT, UNIQUE(tenant, request_id))")
    db.execute("INSERT INTO accepted VALUES('tenant-a', 'request-1')")
    try:
        db.execute("INSERT INTO accepted VALUES('tenant-a', 'request-1')")
        raise AssertionError("duplicate identity admitted")
    except sqlite3.IntegrityError:
        pass
print("conditional update and unique identity passed")
