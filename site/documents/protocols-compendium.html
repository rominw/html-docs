PART A · 网络基础篇:所有协议脚下的地基

1. 分层地图:先看懂这座楼

每个协议的怪癖,都能在楼下两层找到出处。

本书主线:底层特性会向上"漏问题"——TCP 不保证消息边界(→ 粘包,催生各协议的切帧设计)、不保证对端应用活着(→ 应用层心跳/遗嘱)、不替你重发业务消息(→ 应用层 QoS)。把这三条因果线刻在脑子里,后面每个协议都是"必然如此"。

2. IP 与端口:门牌系统

消息如何找到目标——以及 NAT 如何决定了物联网的连接方向。

IP = 小区地址

  • IPv4 32 位(192.168.1.10),约 43 亿个已耗尽;IPv6 128 位,物联网海量设备的主角
  • 公网 vs 内网:设备通常在内网(192.168.x/10.x),经 NAT 共享公网出口
  • NAT 的因果线:外部无法主动进内网 → 物联网必然"设备主动出连、长连接保持、下行复用"——MQTT 形态的根本原因

端口 = 门牌号

  • 16 位,区分同机不同服务
  • 熟面孔:80/443 HTTP(S) · 1883/8883 MQTT(明文/TLS) · 502 Modbus TCP · 4840 OPC UA · 53 DNS
  • 排查"连不上"第一步:telnet ip 端口 / netstat -ano 看监听

3. TCP:可靠字节流

面试题密度之王:握手、挥手、粘包三大考点一次讲透底层逻辑。

为什么三次,不能两次?

  • 目的:双方都确认"我能发他能收、他能发我能收"
  • 两次的致命伤:历史重复 SYN(网络里迷路的老请求)会被误当新连接;第三次 ACK 给了客户端否决权
  • 挥手为何四次:全双工两方向独立关,被动方 ACK 与 FIN 之间还要发完剩余数据

可靠四件套 + 粘包

  • 序号+确认 / 超时重传 / 滑动窗口(流控)/ 拥塞控制
  • 粘包:字节流无边界;应用层三解法——定长 / 分隔符 / 长度前缀(MQTT 剩余长度、Modbus MBAP 的设计根源;串口 RTU 无前缀只能 3.5 字符静默切帧)
  • TCP keepalive 默认 2 小时太迟钝 → MQTT 自定义 60s 应用层心跳

面试三连:TCP 可靠只是"字节送到对方内核缓冲区"(点到点),应用进程崩溃照样丢 → 所以 MQTT 要应用层 QoS(端到端);TIME_WAIT 堆积会端口耗尽 → 物联网全用长连接;半包粘包 → 一切应用层协议都要回答"怎么切帧"。

4. UDP:自由但有代价

没有握手、没有重传——换来极致轻快与天然多播。

维度TCPUDP
连接/状态三次握手,有状态无连接,拿了就发
可靠性确认+重传+排序尽力而为,可能丢/乱序
头部20 字节起固定 8 字节
边界字节流(粘包问题)数据报天然有边界
一对多一对一广播/多播原生支持
物联网用户MQTT / Modbus TCP / OPC UAMQTT-SN / OPC UA PubSub 多播 / CoAP / DNS

选型因果:低延迟不要重传(音视频、实时控制)、一对多(PubSub 多播)、包小到亏 TCP 头(DNS)→ UDP;MQTT-SN 把 MQTT 搬上 UDP 给跑不动 TCP 栈的超弱传感器,可靠性由应用层 QoS 补——又一次"传输层不可靠,应用层兜底"。

5. HTTP:互联网通用语

模型、方法、状态码与四代演进——以及它为什么退守物联网平台层。

核心模型

  • 请求/响应:客户端发起,服务端无法主动推
  • 方法:GET/POST/PUT/DELETE → REST;状态码:200/301/404/500
  • 文本协议,头几百字节——比 MQTT 重百倍

四代演进(每代一句话)

  • 1.0 每请求新建连接(贵)→ 1.1 keep-alive 长连接(主流)
  • 2 二进制分帧+多路复用(一条连接并行多请求)
  • 3 弃 TCP 改 QUIC(UDP 上重建可靠),根治队头阻塞

与 MQTT 分工(面试高频):设备→平台用 MQTT(省电/弱网/可下行);平台对外 REST API 给业务系统;固件/文件用 HTTPS 下载。答"分层共存"而非"二选一"。

6. HTTPS / TLS 深度详解:从密码学讲到握手逐消息

本章是"经得住拷打"的重灾区——按"为什么需要"的顺序推导出 TLS 的每一步。

6.1 从 HTTP 的三宗罪推导 TLS 的三个保证

HTTP 明文传输,中间人可以窃听(抄走内容)、篡改(改了你也发现不了)、冒充(假装是服务器)。TLS 对症下药提供三个保证:机密性(加密,看不懂)、完整性(校验,改不了)、真实性(证书,冒充不了)。下面逐步推导:为了同时做到这三点,TLS 的握手为什么长成那样。

6.2 密码学三件套(先补地基,后面全是推理)

对称加密(AES)

加解密同一把钥匙,快(硬件加速,GB/s 级)。致命问题:钥匙怎么安全地给对方?明文寄钥匙等于没加密。

非对称加密(RSA/ECC)

公钥加密只有私钥能解(或反之做签名)。解决"钥匙分发":公钥随便公开。缺点:慢非对称约千倍,只适合传小数据。

哈希与签名(SHA-256)

哈希单向指纹;数字签名=用私钥签哈希,任何人用公钥验证——证明"是他发的且没被改"。

混合加密(一切的核心套路):非对称加密很慢 → 只用它交换一把临时的对称密钥 → 之后全程对称加密。就像用昂贵的挂号信寄一把保险箱钥匙,之后天天往保险箱里塞普通信件。TLS 握手所做的全部事情,本质就是安全地协商出这把对称密钥 + 验明对方正身。

6.3 证书:为什么不能直接发公钥?

如果服务器只是把公钥明文发给你——中间人把它替换成自己的公钥,你后续的"加密"全部对中间人透明。这就是中间人攻击(MITM)。解法:公钥不裸发,由 CA(证书颁发机构)用它的私钥签名担保:

证书 = 你的公钥 + 你的身份信息 + CA 的签名。验证链:操作系统内置根 CA公钥(信任的起点)→ 验中间 CA 证书 → 验网站证书,逐级用上一级公钥验下一级签名。链条尽头是机器里预置的根证书——所以"装来路不明的根证书"等于把整个信任体系交出去。

6.4 TLS 1.2 握手逐消息(RSA 密钥交换版,最经典)

每一步"为什么存在"

  • 两个随机数(R1/R2):防止"双方今天和昨天用了完全一样的密钥";三随机共同决定密钥
  • 套件协商:客户端报家底、服务端挑一个——兼容 20 年代差
  • Finished 是精华:把之前所有握手消息做哈希互验——如果中间人篡改过任何一步(比如换公钥),双方算出的哈希对不上,连接立刻失败。这是"完整性"的收官

TLS 1.3 的三大改进

  • 握手从 2-RTT 降到 1-RTT(ClientHello 就带上密钥材料,消息也更少)
  • 废弃 RSA 密钥交换,只留 ECDHE——为前向保密(见下)
  • 握手消息本身也加密(抓包看不到证书细节);支持 0-RTT 会话恢复(有重放风险,只用于幂等请求)

6.5 前向保密:面试深水区的一道分水岭

RSA 交换的致命伤:预主密钥用服务器公钥加密——如果哪天服务器私钥泄露,攻击者把过去录下的所有密文流量全部解密(流量录制攻击:先存着,等钥匙到手)。

ECDHE(E=临时)的解法:双方每次会话各自生成一次性临时密钥对,用 Diffie-Hellman 算法协商出会话密钥,用完即焚、永不存储。私钥只用来签名证明身份,不再参与加密——即使私钥泄露,历史会话的临时密钥早已销毁,过去的流量永远安全。这就是"前向保密(Forward Secrecy)":过去不因今日的失守而失守。

6.6 与工业协议的三条联动(答出即封神)

MQTT 的 8883

= MQTT over TLS,设备与 Broker 之间就是本章的握手;每设备一张 X.509 证书 = 双向 mTLS(Broker 也验客户端)。

OPC UA SecureChannel

没直接用 TLS,而是在自己的二进制协议里实现了同一套思想(非对称协商对称+签名加密)——2008 年设计时要跨平台跑嵌入式,顺带支持非 TCP 传输;知识点完全互通。

工业现场的自签名证书

内网设备常不买 CA 证书,用自签证书+白名单互信——所以 OPC UA 落地最大成本是证书管理制度,不是协议本身。

面试六连:①握手过程(按上图六步讲)②为什么混用对称与非对称(快慢与分发)③证书链怎么验(根→中间→站点)④中间人怎么防(公钥不裸发+Finished 哈希收官)⑤前向保密(ECDHE 临时密钥,私钥泄露不解历史)⑥HTTPS 绝对安全吗(不防服务端被入侵、0-RTT 重放、客户端信任了恶意根证书)。

7. 三个配角:WebSocket、SSE 与 DNS

凑齐"服务端推送"全家福:轮询、长轮询、SSE、WebSocket——再各带一条因果线。

7.1 WebSocket:HTTP 升级出的全双工

  • 一次 HTTP 握手(Upgrade: websocket)"改签",此后双向自由收发,支持二进制
  • 联动:MQTT over WebSocket(8083)让浏览器 JS 直连 Broker——Web 看板标配

7.3 DNS:域名→IP 的电话簿

  • UDP 53 端口;缓存链:本机→本地 DNS→根→顶级→权威,TTL 定时效
  • 联动:长连接重连必须重新解析,否则 Broker 换 IP 后设备还傻连旧地址

7.2 SSE:HTTP 响应"不结束"的艺术(大模型时代翻红)

原理推导:第 5 章说 HTTP 是"一问一答、答完就散"——但 HTTP 响应允许分块传输且不关闭(chunked)。SSE(Server-Sent Events)就是把这一点用到极致:响应头 Content-Type: text/event-stream,连接永远不结束,服务端有事件就写一段,浏览器原生 EventSource API 接收,断线自动重连(带 Last-Event-ID 请求续传)。本质:仍是 HTTP,只是把"响应"变成了一条单向河流。

报文格式极简到可爱,四种字段 + 空行分隔:

id: 42           ← 事件序号:断线重连时浏览器带 Last-Event-ID: 42,服务端可从断点补发
event: alert     ← 自定义事件类型(可选)
data: 温度过高    ← 数据行(多行 data 会自动拼接)
retry: 3000      ← 建议重连间隔毫秒(可选)
                 ← 空行 = 一条事件结束

为什么 ChatGPT 们清一色用 SSE 而不是 WebSocket?①用户输入是一次普通 HTTP 请求,单向流回就够,不需要双工;②纯 HTTP,现有网关/CDN/负载均衡/鉴权中间件全部直接兼容(WebSocket 的 Upgrade 常被代理卡);③实现极简,curl -N 都能测。"一个字一个字蹦"= 服务端把生成好的 token 逐条 data: 推下来。

维度轮询长轮询SSEWebSocket
延迟取决于间隔低低低
方向客户端拉客户端拉(挂着等)服务端单向推双向

物联网联动:Web 能源看板要实时刷新,三条路——①轮询(傻但零成本);②SSE(服务端算好推给浏览器,轻);③MQTT over WebSocket(浏览器直接订阅设备主题,数据不过中间层)。选型看"谁产生数据":业务服务产出用 SSE,设备数据直达用 MQTT over WS。

PART B · 工业协议篇:MQTT / Modbus / OPC UA

8. 三协议全局图景:分层地盘,不是竞争

一句话定位:Modbus 取数、OPC UA 赋义、MQTT 上云。

9. MQTT:为卫星链路而生的极简主义者

1999 年 IBM 监控沙漠油管,卫星链路按字节计费——一切设计由此推导。

发布/订阅解耦

发布者与订阅者经 Broker 中转、互不相识;换设备加听众零改造。

Topic 分层通配

factory/line1/temp 按 / 分层;+ 精确匹配单层(3 层模式配不上 4 层主题),# 匹配余下全部。

2 字节固定头

HTTP 头几百字节 vs MQTT 最小 2 字节;剩余长度变长编码(7bit/字节,续位标志,上限 4 字节 256MB)。

9.1 QoS 状态机:从"ACK 会丢"推导出四步握手

推导逻辑(比背表格强):QoS1 重复的根因是"接收方单凭一条 PUBLISH 分不清是新消息还是重发"——QoS2 把"确认收到"与"允许投递"拆成两步,双方各记一张状态表(PacketID),任何一步丢包都可安全重走。选型:高频流数据 QoS0、一般业务 QoS1+消费端幂等、计费/指令 QoS2。

9.2 会话、遗嘱、保留与 5.0

三个贴心机制(因果版)

  • 遗嘱 LWT:TCP 断开或 1.5 倍 KeepAlive 超时 → Broker 代发预登记的 offline,掉线秒级感知(will 记得 retain=True,否则快照过期)
  • 保留 Retained:Broker 存每主题最后一条,新订阅者零等待拿快照
  • 持久会话:CleanSession=0 时 Broker 攒离线 QoS≥1 消息,重连补发 = 离线队列

3.1.1 → 5.0 的六项进化

  • 原因码(失败可诊断)/ 消息过期 / 主题别名(省流量)
  • 共享订阅 $share/g/topic(组内负载均衡)/ 流控 / 请求响应
  • Broker 梯队:EMQX(百万连接/集群/规则引擎)、Mosquitto(边缘)、云托管(IoT Core 等)

10. Modbus:寄存器柜子的四十年

1979 年的串口约束,推导出主从、静默切帧、CRC——每个设计都是那个年代的必然。

数据模型:四个抽屉

  • 线圈(1位读写,继电器)/ 离散输入(1位只读,按钮)
  • 输入寄存器(16位只读,测量值)/ 保持寄存器(16位读写,设定值)
  • 功能码:01/02/03/04 读四类;05/06 单写;0F/10 批写;异常=功能码+0x80(01非法功能/02非法地址/03非法数据/04从站故障)
  • 寻址大坑:文档 1-based(40001 起)vs 协议 0-based,换算减基数

RTU → TCP:一次"搬家手术"

  • RTU:地址+功能码+数据+CRC16(多项式 0xA001/初值 0xFFFF/低字节在前);帧间 3.5 字符静默切帧
  • TCP:CRC 丢弃(TCP+链路层已校验——与 MQTT 靠 TCP 同一哲学);地址挪进 MBAP;新增事务 ID 支持多主并发配对
  • MBAP:事务ID(2B)+ 协议ID(2B 恒0)+ 长度(2B,粘包切帧依据)+ 单元ID(1B,为透传串口而留)
  • 野生变体"RTU over TCP"非标,遇网关先确认

实战两大坑:① 32 位浮点占两寄存器,字节序 ABCD/CDAB/BADC 厂商不统一,读出天文数字先怀疑字节序;② 采集三板斧——批量读(FC03 一次最多 125 寄存器)、字节序可配置、慢设备独立超时。CRC 冷知识:pymodbus 返回的是交换后的传输序,手写实现多返回寄存器自然值——两库对账先对字节序约定。

11. OPC UA:Modbus 三个死穴的药方

不会自我介绍 → 信息模型;没有锁 → 安全五层;要不停追问 → 订阅推送。

地址空间:带类型的节点图

8 种 NodeClass(Object/Variable/Method/类型系);NodeId=命名空间+标识符,ns=0 为标准区;Browse 可运行时探索——自描述,不用翻各家手册。

订阅三件套

Subscription → MonitoredItem(采样间隔/死区/队列)→ Notification(带序号可重传);变化才推、毫秒级,对比轮询省带宽省延迟。

安全五层

SecureChannel 加密签名 → X.509 双向认证 → 用户认证 → 节点级授权;策略 None/Basic256Sha256/Aes256…;生产禁 None。自己实现了 TLS 思想(见第 6 章)。

配套规范与 PubSub

  • Companion Specs:DI 设备集成 / PLCopen 控制 / PackML 包装 / Euromap 塑机——同规范两家设备零配置互通,IEC 62541
  • PubSub(Part 14,2015):发布订阅扩展,UDP 多播(TSN 实时)/ MQTT 中转;UA over MQTT = 语义×云连接的联姻
  • 版本类型体系:MQTT 3.1.1→5.0、Modbus 四十年一版、OPC UA 14 个 Part 持续演进;标准组织:OASIS / Modbus.org / OPC 基金会

12. 企业实战:ISA-95 地图与三类中间件

面试聊架构,先亮分层地图再谈中间件——这是"正轨表达"。

MQTT 企业纪律

PART C · 面试冲刺篇:45 题 + 场景 + 话术

13. 46 道高频题速查(按协议分组)

答题结构:一句话结论 → 机制 → "我验证过" → 延伸一个坑。

网络基础 11 题答案要点
① 三次握手为何不是两次双向收发确认 + 防历史重复 SYN(第三次 ACK 可否决)
② 挥手为何四次全双工独立关;被动方 ACK 与 FIN 间还要发完数据
③ TIME_WAIT 与状态排障2MSL:末次 ACK 可重传+旧报文消亡;TIME_WAIT 堆积=短连接太多(改长连接);CLOSE_WAIT 堆积=应用忘了 close()(查代码);SYN_RCVD 堆积=SYN Flood 攻击——netstat 状态名就是排障钥匙
④ TCP 可靠四件套序号确认 / 超时重传 / 滑动窗口 / 拥塞控制
⑤ 粘包与解法字节流无边界;定长/分隔符/长度前缀(带出 MQTT/Modbus 切帧)
⑥ TCP vs UDP 选型可靠有序 TCP;低延迟/多播/超轻 UDP(MQTT-SN、PubSub 多播)
⑦ 输入网址到显示DNS→TCP 握手→(TLS)→HTTP→渲染
⑧ HTTPS 握手见第 6 章六步;混用对称非对称;证书链;Finished 防篡改
⑨ HTTP 演进1.1 keep-alive / 2 多路复用 / 3 QUIC(UDP 重建可靠)
⑩ SSE vs WebSocket单向推选 SSE(HTTP 流式响应、自动重连续传、网关全兼容,LLM 流式输出标配);双向实时选 WebSocket(独立协议、支持二进制)
⑪ NAT 内网下发指令设备主动出连长连接,下行复用
MQTT 12 题答案要点
① vs HTTP发布订阅/2B头/长连接可推;平台 API 层仍共存 HTTP
② QoS 三级0 至多一次;1 至少一次(重发→重复);2 恰好一次(四步+状态表)
③ QoS1 为何重复接收方分不清新消息与 ACK 丢失后的重发
④ QoS2 为何四步拆"确认收到"与"允许投递",PacketID 去重,任何步丢包可重走
⑤ 掉线感知遗嘱 LWT + KeepAlive 1.5 倍超时;will 要 retain
⑥ 最新值保留消息,订阅即推快照
⑦ 通配符+ 单层精确(3层模式≠4层主题);# 只能结尾匹配余下全部
⑧ CleanSession0=持久会话攒离线 QoS≥1 消息重连补发;5.0=Session Expiry
⑨ 3.1.1 vs 5.0原因码/共享订阅/过期/别名/流控/请求响应(说三个)
⑩ 共享订阅$share/g/topic 组内负载均衡,解多后端重复消费
⑪ 百万连接EMQX 集群+LB、Topic 纪律+ACL、TLS 证书、共享订阅、Kafka 削峰
⑫ 积压处理扩消费者、幂等去重、非关键降 QoS

Modbus 10 题(要点)

  • RTU/TCP 区别:MBAP 替地址+CRC、事务 ID 多主、静默 vs 长度切帧
  • 四寄存器 / 功能码 01-10 / 异常 fc+0x80 与异常码 1-4
  • 32 位浮点=双寄存器拼接+字节序坑(ABCD/CDAB)
  • 40001↔0(1-based vs 0-based)/ 从站不能主动 → 轮询与优化三板斧
  • Modbus vs RS-485(协议 vs 物理)/ CRC16 参数与低字节在前

OPC UA 8 题(要点)

  • vs Modbus:语义+安全+订阅三张牌全打
  • vs MQTT:C/S 订阅 vs Broker;控制系统 vs 广域上云,常配合
  • 地址空间/8 NodeClass/NodeId/ns=0;Browse=自描述
  • 订阅三件套+死区/队列/序号;Read 低频配置、订阅高频变化
  • 安全五层+禁 None;DA→UA(COM→跨平台 IEC 62541);PubSub 走 UDP/MQTT
