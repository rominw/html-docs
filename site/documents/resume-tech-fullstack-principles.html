本篇核心问题

2. Vue 响应式到底如何从一次赋值走到视图更新？

从机制到边界，再用具体交错检验结论。

记忆关键词：读取收集依赖 → 写入触发 → 调度 → 渲染 → DOM

核心结论

Vue 3 的响应式通过代理和 ref 等机制跟踪读取与变化，再调度依赖它们的计算与渲染。对象变了、响应式触发了和 DOM 已更新是不同阶段。

拆开机制与保证范围

渲染或 effect 读取响应式属性时形成依赖关系，写入触发相关订阅者。普通局部变量、把原始对象交给未受跟踪的路径，或解构一个基本类型属性，都可能让后续操作不再经过原代理；解构到的对象仍可能保留其内部响应性，应区分绑定与对象。

computed 缓存基于它跟踪的依赖，watch 用于观察变化和产生适当副作用。把远程请求放进计算属性并期望它等价一次受控动作，会混淆“派生值”与“执行协议”。调度批量更新 DOM，赋值后立即测量 DOM 可能读到旧视图，适当时用 nextTick。

流式 token 到达频率可能高于用户需要的渲染频率。可以先累计协议事件再按有界频率更新视图，避免逐 token 重排大段内容；批处理不能丢掉事件序号、终态和错误，UI 优化仍需保留完整业务语义。

场景推演：一个 SSE 回调把 reactive 对象的 status 解构到局部字符串，随后只改局部变量，页面不更新。修复需要保持响应式访问路径，而不是盲目调用强制刷新。

进一步思考：“nextTick 等网络完成吗？”只等待相应 DOM 更新周期。“响应式对象线程安全？”浏览器调度与后端并发是不同问题，异步交错仍会覆盖状态。

如何验证：挂载真实 Vue 测试响应性、DOM 时机和高频流更新；用性能证据看重绘、内存和长任务，不把模型 reducer 自检当作框架测试。

3. TypeScript 类型为何挡不住坏 JSON？怎样建运行时边界？

从机制到边界，再用具体交错检验结论。

记忆关键词：类型擦除 · unknown → 校验 → 判别联合 → 穷尽分支

核心结论

TypeScript 主要在编译时检查类型，网络 JSON 到达运行时仍是外部数据。as 或接口声明不能验证字段，应先校验结构与业务语义，再转换为可处理类型。

拆开机制与保证范围

const event = JSON.parse(raw) as Event 只是告诉编译器相信类型，实际可以缺 id、把 seq 写成字符串或给未知 status。边界应检查类型、必要字段、大小、枚举与范围，拒绝不合契约的输入，避免它污染内部状态。

判别联合如 kind=progress/result/error 可以把不同事件的必要字段关联，分支中依据 kind 缩小类型；穷尽检查提醒新增协议事件未被处理。它帮助内部代码表达不变量，但仍需服务端与客户端同时维护版本契约。

整数序号要考虑 JavaScript 的安全整数范围，超长 ID 应使用字符串等适当协议类型。未知字段是否允许、未知事件是忽略还是触发升级，也应显式设计。格式合法并不说明资源属于当前用户，权限还在服务端判断。

场景推演：服务器改了新状态 CANCELLED，旧客户端把任何非 RUNNING 状态都视作成功。使用判别枚举和明确兼容处理，避免协议升级伪造完成。

进一步思考：“用了类型库就不用验证？”静态声明不是输入验证。“所有未知字段都拒绝？”要根据前后兼容契约选择，不能随意扩大信任。

如何验证：用缺字段、超大序号、未知状态和同名异类型输入测试；下方 reducer 先做运行时检查，再允许更新内部状态。

4. SSE 为什么既不是“每个 chunk 一个 JSON”，也不是可靠事件存储？

从机制到边界，再用具体交错检验结论。

记忆关键词：UTF-8 增量解码 → 行 → 空行事件 → id → 保留协议

核心结论

SSE 定义事件流格式，网络读取块可以在任意字节位置拆分。解析必须跨块保留状态；自动重连只恢复连接，不自动提供业务事件存储与可靠补发。

拆开机制与保证范围

多字节字符可能被拆到两个 chunk，增量 TextDecoder 需要保留未完成字节；随后按 SSE 行、字段和空行事件边界解析。多个 data 行按协议组合，注释可用作心跳，不能把任意网络块直接 JSON.parse 后推断为一个完整事件。

事件 id 和重连时的 Last-Event-ID 帮助表达恢复游标，但服务端要有保留、补发、鉴权和过期处理。无事件可补时应明确转为快照/最终结果查询，而不是返回空流让用户误以为已经追上全部。

原生 EventSource 与 Fetch 流的 API、请求头、方法与错误处理能力不同，选型要由认证和协议需求决定。代理缓冲、压缩、连接限制和超时会改变实时性；心跳证明某段连接活着，不证明业务任务仍在推进。

场景推演：中文字段的一个 UTF-8 字符被拆开，两个事件又合在同一读取块。正确解析仍得到同样事件；按 chunk 切 JSON 会同时出现破字和合包错误。

进一步思考：“收到 done 就能删除任务记录？”先明确 done 表示流结束还是业务终态。“重连会重执行吗？”订阅恢复应复用原 run，不重新创建动作。

如何验证：使用基础能力专栏中的任意字节分块练习建立底层认识，再按 SSE 标准测试多行 data、注释、CR/LF、空事件、断线和保留过期。

原始资料 05 · 可运行练习与自测

5. 断线、重复、乱序和刷新之后，页面如何仍与权威状态一致？

从机制到边界，再用具体交错检验结论。

记忆关键词：任务身份 · 已应用游标 · 缺口检测 · 终态保护 · 快照

核心结论

页面只是权威业务状态的一个投影。按 run 身份与事件序号应用更新，检测缺口、拒绝旧事件，并在无法补发时查询权威快照。

拆开机制与保证范围

requestId/messageId 标识动作，runId 标识执行过程，eventId/seq 标识反馈；职责要按协议定义。连接 ID 变化不应改变这些业务身份。收到旧 run 的回调时先拒绝，避免用户切换场景后被旧结果覆盖。

只有已经完整解析并应用的事件才能推进游标。重复事件可以忽略，缺号则请求补发或切换快照；若是差量协议，直接跳过缺口继续应用会使数据永久缺失。快照的版本和恢复后增量衔接也需建立清晰边界。

终态一般不能被普通进度回退。进度条走到 100% 也不能自行判断执行成功；最终结果要来自约定事件或查询接口。服务端保留过期、用户刷新和换实例时，恢复逻辑应提供可解释状态，不无限重连同一个无法恢复的流。

场景推演：已经应用 seq=7，随后收到 9 而没有 8。先标记需恢复，不应用 9 的差量；恢复获得版本快照后再从对应游标接续。

进一步思考：“只按最后收到的事件更新？”网络时间不等于业务版本。“去重就不需要快照？”去重解决重复，不解决遗漏。

如何验证：下方 reducer 验证身份、缺口和终态保护；真实端到端测试还需覆盖刷新、换实例、快照与流的竞争、过期保留。

原始资料 05 · 可运行练习与自测

6. 请求取消、组件卸载与异步竞态如何处理？

从机制到边界，再用具体交错检验结论。

记忆关键词：生命周期 · AbortSignal · 代次校验 · 清理 · 副作用查证

核心结论

取消本地等待可以释放资源，但不证明服务器没执行。界面还需检查响应属于当前请求/会话代次，并清理连接、监听与缓冲。

拆开机制与保证范围

用户先查 A 再查 B，A 的慢响应可能在 B 后返回。单纯把任意成功响应写到同一对象会倒退界面；捕获请求代次并在更新前比较，或由任务身份管理不同结果。取消旧请求有帮助，代次校验仍是状态保护。

组件卸载需要断开流、移除监听和取消可取消任务。响应式 watcher 内发请求也应明确清理策略，具体 API 随 Vue 版本核对。没有清理的闭包可以继续持有正文与缓冲，长期对话会积累内存和后台工作。

AbortController/Signal 向支持的异步操作传递取消，本地 promise 拒绝不等于撤销远端数据库或设备副作用。查询类请求可以丢弃旧响应；执行类请求应保留动作身份和结果查证，不能因为页面离开就创建一个“从未执行”的假状态。

场景推演：用户切换到 B 场景后，A 场景 SSE 仍写入当前列表。用会话/run 代次拒绝旧更新，并在卸载时清理订阅；若 A 有执行任务，结果仍可稍后查询。

进一步思考：“abort 成功就不用查结果？”执行请求可能已受理。“只加防抖？”减少触发次数，不保证响应顺序与生命周期。

如何验证：人为让早请求晚返回，卸载时持续发送事件，检查不会更新错误场景或持有增长；另测执行成功后本地取消的结果查证。

7. 前后端的权限按钮、会话和幂等键怎样形成完整契约？

从机制到边界，再用具体交错检验结论。

记忆关键词：展示资格 · 服务鉴权 · 确认快照 · 稳定身份 · 状态查询

核心结论

按钮状态是用户提示，真实鉴权、前置条件和幂等受理由服务端执行。界面要表达受理、执行、成功、失败与未知，而不是只用 HTTP 是否报错判断结果。

拆开机制与保证范围

页面可以根据权限隐藏按钮，但直接 HTTP 请求仍可能到达服务端；服务端用可信会话验证主体与资源。客户端自报 userId、缓存的权限或上一次工具结果，都不能替代当前授权检查。

重复点击或网络重试应保留同一动作身份和请求摘要，明确何时是同一动作、何时新建动作。用户修改参数后不应沿用旧确认和旧键；服务端也要拒绝同键异参。查询、重新订阅和再次执行应是不同接口语义。

前端缓存、浏览器缓存和 Service Worker 等各有数据生命周期。权限切换后旧数据不能继续跨用户复用，状态查询结果应保留权威版本与数据时间。SSE 反馈可以加快展示，但不是唯一可恢复的事实来源。

场景推演：HTTP 请求超时后 UI 给“重试”按钮，若点击创建新 messageId 就可能产生第二次副作用。更好的交互先查原动作，确定可重试范围后复用原身份。

进一步思考：“HTTP 200 就执行成功？”可能只是受理。“按钮禁用可防幂等问题？”无法阻止网络重试、多个页面与客户端重放。

如何验证：覆盖手工绕过 UI、重复提交、权限切换、同键异参和回包丢失；核对界面状态与服务端权威结果始终对应。

8. 动手验证与故障推演

先推导预期，再运行；如果结果相反，回到机制与边界。

界面状态练习：坏输入、缺号、旧 run 与终态回退

复制到 Node.js 运行，无依赖。它验证 reducer 的运行时输入和状态规则，不解析完整 SSE，也不验证 Vue 渲染、鉴权或服务端补发。

保存为 practice.cjs，用 node practice.cjs 运行。

const assert = require("node:assert/strict");
const states = new Set(["RUNNING", "SUCCEEDED", "FAILED"]);

function apply(state, raw) {
  if (!raw || typeof raw.run !== "string" ||
      !Number.isSafeInteger(raw.seq) || raw.seq < 1 ||
      !states.has(raw.status)) throw new Error("invalid event");
  if (raw.run !== state.run || raw.seq <= state.seq) return state;
  if (state.needsSnapshot || raw.seq !== state.seq + 1)
    return {...state, needsSnapshot: true};
  if (state.status !== "RUNNING") return state;
  return {...state, seq: raw.seq, status: raw.status};
}

const start = {run: "run-a", seq: 0, status: "RUNNING", needsSnapshot: false};
assert.throws(() => apply(start, {run:"run-a", seq:"1", status:"RUNNING"}));
assert.throws(() => apply(start, {run:"run-a", seq:1, status:"UNKNOWN_NEW"}));
assert.equal(apply(start, {run:"run-b", seq:1, status:"SUCCEEDED"}), start);
let state = apply(start, {run:"run-a", seq:1, status:"RUNNING"});
assert.equal(apply(state, {run:"run-a", seq:1, status:"RUNNING"}), state);
const gap = apply(state, {run:"run-a", seq:3, status:"SUCCEEDED"});
assert.equal(gap.seq, 1);
assert.equal(gap.needsSnapshot, true);
assert.equal(apply(gap, {run:"run-a", seq:2, status:"RUNNING"}).needsSnapshot, true);
state = apply(state, {run:"run-a", seq:2, status:"SUCCEEDED"});
assert.equal(state.status, "SUCCEEDED");
assert.equal(apply(state, {run:"run-a", seq:3, status:"RUNNING"}), state);
console.log("schema, run identity, duplicates, gaps and terminal state passed");
