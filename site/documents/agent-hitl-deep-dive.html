1. 问题定义：HITL 不是 UI，是执行模型

先纠正最常见的误解，再给出本文的分析框架。

Human-in-the-Loop 经常被理解成"危险操作前加个确认弹窗"。这个理解会直接导致错误的设计：弹窗是 UI 层的补丁，而 HITL 真正改变的是执行模型——把 agent 从"一次流式跑完的函数调用"改造为可中断、可跨进程跨天恢复、且在关键节点上把决策权交给人的状态机。做不做这个改造，决定了后面所有的交互设计是真回环还是装饰品。

分析任何 HITL 实现，都可以拆到四个正交维度上。这四维也构成了本文第 3–7 节的行文顺序：

触发（When）

什么条件打断人：动作类别、风险分级、沙箱边界、策略规则、模型置信度。触发设计决定打断频率，直接决定监督是否可持续。

呈现（What）

打断时给人看什么：diff、计划、理由、影响面、先例。呈现设计决定人能否在数十秒内做出正确判断——大多数实现死在这里，而不是死在触发上。

恢复（How）

人的决策如何回注执行：resume 值注入、状态重放、前提重校验。恢复设计决定回环能否异步化、能否在生产环境存活。

审计（Why）

每次打断与决策留痕：谁、在何时、基于什么信息、批准了什么。这是事故复盘与合规的依据，也是"有意义的控制"能被证明的唯一方式。

一个判断标准：如果一个系统无法把"等待人类"变成可持久化的状态（进程重启、隔了一夜之后还能继续），那它的 HITL 只能停留在同步弹窗层面——人必须守在屏幕前，回环覆盖不了真实的审批流程。能不能"暂停并跨天恢复"，是 HITL 工程成熟度的分水岭。

2. 理论底座：自动化层级与「自动化的讽刺」

Agent 领域 2026 年撞上的坑，在四十年的监督控制文献里几乎都有原型。

人机自动化分工不是新问题。Sheridan 与 Verplank（1978）提出 10 级自动化层级（Levels of Automation），Parasuraman、Sheridan 与 Wickens（2000）进一步把它拆成四个阶段——信息获取、信息分析、决策选择、行动执行——每个阶段可以独立设定自动化程度。这套框架几乎可以直接映射到今天 agent 的权限模式上：

自动化层级语义（谁决策 / 谁执行）Agent 领域对应形态
LOA 1–3系统采集、过滤、提示信息；人决策并执行检索与总结型助手：人提问，模型只供信息，不碰执行
LOA 4–5系统给出完整方案建议；人拍板并亲自执行Copilot 形态：代码补全、计划草稿；plan mode 里"计划已就绪，等人放行"也是此档
LOA 6–7系统执行，但须人事先批准，或执行后人可否决当前 agent 的主流档位：动作级审批门、acceptEdits、PR review（事后否决权）
LOA 8–10系统自主执行，事后告知、选择性告知或不告知Full Access / bypassPermissions：全自动 + 沙箱隔离 + 事后审计与抽检

这个谱系揭示了一个常被忽略的事实：permission mode 不是二元开关，而是把系统在 LOA 谱系上整体平移的档位选择器。而三个经典理论预言了这条谱系两端的失败模式：

自动化的讽刺

Bainbridge（1983）：自动化越彻底，剩下的人工环节越难做好——监督者脱离回路、技能退化、警觉性下降。当系统 99% 时间正确，人会在第 100 次审查时睡着。agent 时代的重演就是审批疲劳。

自动化偏见

Skitka 等人的实验结论：人系统性地过度信任自动化输出——倾向接受建议、忽略与自动化结论矛盾的独立证据。映射到 agent：模型在审批请求里附带的"理由"本身就是诱导批准的信号，呈现层必须警惕这一点。

有意义的控制

Santoni de Sio 与 van den Hoven（2018）提出两个条件：tracking（人的意图能有效体现在结果中）与 tracing（任何结果都能回溯到具体的人及其理由）。直接对应 agent 的审计日志设计——没有 tracing，"有人审核过"只是合规话术。

为什么先讲理论：2026 年行业对 agent 治理的实证结论——"人工监督是最先失效的一环"——与 1983 年的预言完全同构。HITL 设计不是新发明，而是把监督控制（supervisory control）工程化到 LLM 系统上：挡在人和 agent 之间的每一个环节，都要按"人的注意力是稀缺且会退化的资源"来设计。

3. 机制一：中断与恢复——把执行物化成状态

一切异步 HITL 的技术核心：不保存调用栈，保存每一步的结果。

函数调用栈活不过进程重启，更活不过"等审批者下班回来"。所以 HITL 的第一步是把执行模型事件溯源化：系统持久化的不是执行过程，而是每一步产生的结果；恢复时重放这些结果，而不是重新执行产生它们的过程。LangGraph 是这个思想在 LLM 编排层的最佳样本：

LangGraph 的具体机制

  • checkpointer：每个超步结束后，把整个图状态序列化到 thread。状态由带 reducer 的 channel 组成，恢复即重放 channel 写入。
  • interrupt()：节点函数内调用即抛出暂停信号，框架持久化状态并把线程标记为等待；重放时同一调用直接返回 resume 值。
  • Command(resume=v)：以人类输入重新拉起线程，包含 interrupt 的节点从头重新执行——因此节点在 interrupt 之前的代码必须可重入、幂等（最佳实践：把 interrupt() 放在节点第一行）。
  • interrupt_before / interrupt_after：编译期声明的图级粗粒度版本，等价于在指定节点边界强制"快照 + 暂停"。

为什么不重跑 LLM

快照存的是每个超步的输出，不是模型调用序列。恢复 = 重放写入，LLM 只在未完成的节点里被再次调用。这与 Temporal 的事件溯源是同一思想：把不确定性围堵在已记录结果的边界之内。代价是任何影响状态的副作用都必须经过持久化通道（channel / event），绕过框架直接改内存状态的代码会在恢复时丢失。

换句话说：HITL 对 agent 框架的真正要求，不是"多了一个问人的按钮"，而是全部状态流动必须可序列化。这是为什么成熟框架都把状态当作一等公民来设计。

两个高频工程陷阱：① 世界漂移——挂起三小时后 PR 基线已变、文件已改，resume 时必须重新校验前提（注入新鲜上下文、重查 precondition），必要时把"已批准"降级为"需重审"；② 副作用重放——节点重入意味着 interrupt 之前发生的副作用会再来一次，写操作要么幂等，要么放在 interrupt 之后。

4. 机制二：策略层——审批判定是纯函数

把"要不要问人"从散落的 if-else 收敛成一个可测试、可评审、可回放的决策函数。

动作级审批的工程形态，是一个纯函数：decide(tool, args, context) → allow | ask | deny。写成纯函数的意义远超代码整洁：可以单测（每个策略规则一组用例）、可以 diff 评审（策略变更像代码变更一样走 PR）、可以全量回放（拿历史动作样本跑一遍新策略，看拦截率变化，避免策略调整引发意外大面积放行或拦截）。主流 coding agent 的权限系统都是这个函数的不同分层实现：

Claude Code 的分层实现

  • 规则来源有优先级：组织托管策略 > 命令行参数 > 项目本地 > 项目共享 > 用户级；deny 规则跨层级压倒一切 allow——企业可以一票否决个人放行。
  • 规则按参数模式匹配：Bash(git push:*) 按命令前缀、Edit(//path) 按路径、WebFetch(domain:…) 按域名，粒度到"哪类命令在哪块地盘上"。
  • permission mode 是档位：default / acceptEdits / plan / bypassPermissions，一次切换整体平移判定输出，而不是逐规则修改。
  • hooks 是强制策略执行点（PEP）：PreToolUse 钩子读入工具调用 JSON，退出码 2 或输出 block 决策即阻断且原因回传模型。工单校验、密钥扫描、变更窗口检查都挂在这里——策略执行不依赖模型"自觉"。

沙箱与审批的职责分离

Codex 代表另一条路线：环境隔离承担结构性安全，审批只处理越出沙箱的例外。沙箱（Linux 上 Landlock/seccomp、macOS 上 Seatbelt、Windows 上 2026 年出现的基于 Microsoft Execution Containers 的实现）限制文件系统与网络；审批策略（untrusted / on-request / on-failure / never）只对"联网、写沙箱外、装依赖"这类越界动作生效。

两个子系统联动后的效果：需要人批的请求数下降，不是因为规则变松，而是危险动作被机制性消除了。这是审批疲劳最重要的结构性解药——用人不可绕过的机制安全，替代依赖人注意力的行为安全。

最大威胁是权限提升，不是误操作：prompt injection 的经典攻击路径就是诱导模型调用"切换到自动批准"的开关，或直接改写 settings 文件。因此判定函数的输入与执行必须完全在模型上下文之外的进程里；模型只能"发起请求"，永远不能"修改判定"。OpenAI Model Spec（2025/2026 版）把权限归入 system / developer 指令层级而不属于对话内容层，是同一思想：权限的修改权本身也要被纳入权限管理。

5. 机制三：异步审批与持久化执行

当审批者从"守在终端前的人"变成"晚些才有空的经理"，等待本身必须成为系统的一等状态。

同步审批（人在终端、秒级应答）用任何机制都能凑合；但真实组织的审批者不在线、在开会、在睡觉。异步 HITL 的全部难点可以归结为一句话：把"等人"变成一个不依赖任何进程存活的状态。长时任务编排引擎（Temporal 为代表）为此提供了最完整的语言级表达：

Temporal 的"人审即普通控制流"

  • workflow 代码必须确定性，一切副作用（发审批卡片、写库、调 API）都通过 activity 执行，activity 结果与外部信号全部进入事件历史。
  • 人审 = 提交审批 activity + Workflow.await：await 一个由 signal handler 置位的标志（审批人点了通过）或一个 durable timer 到期，谁先到谁生效——超时升级链在语言层面就是几个 await 的组合：30 分钟无响应升级到 backup 审批人，再超时落到默认策略（拒绝或降级只读）。
  • timer 由服务端计时：等待可以持续数天，worker 全部下线也不丢；恢复时靠事件历史重放重建 workflow 状态，与 LangGraph 的 channel 重放同构。
维度LangGraph（checkpoint / replay 模型）Temporal（deterministic replay 模型）
状态载体每个超步后的图状态快照（channel 值集合），存于 thread全量事件历史（event history），恢复时重放重建
确定性要求节点可重入；interrupt() 在重放时返回 resume 值workflow 代码整体确定性；副作用必须走 activity
"等人"的实现线程挂起于 interrupt，等下一次带 resume 值的调用拉起Workflow.await(signal) + durable timer，任意时长
计时与升级需外部调度触发超时（自身无长期 timer）服务端 durable timer，worker 可全下线；升级链是一等能力
适用重心LLM 图编排：节点是模型调用与工具，中断点在图语义里长时业务流程：审批 SLA、多级升级、补偿事务是日常

审批的去向也值得专门设计：回环应该发生在人已有的工作流里，而不是要求人盯着 agent 面板。Slack / Teams / 钉钉的消息卡片、Jira 工单、GitHub Environments 的 required reviewers（部署到受保护环境前必须指定人批准）都是这个思路。Cloudflare 在 2026 年的实践文档把 Workflow approvals 与 MCP elicitation 组合起来，代表了这个方向的工程收敛。

审批对象本身也要安全设计：一份批准应绑定动作指纹（工具名 + 归一化参数的哈希）、带过期时间、单次使用——防止批准被重放或挪用到"看起来相似"的另一个动作上。审批信号要走带外通道（卡片按钮、平台 API），绝不能走模型可读写的文本流，否则注入攻击可以伪造"人已批准"。

6. 机制四：协议层——MCP 把「问人」标准化

从此 HITL 不再是每个客户端的私有 UI，而是可组合的协议原语。

HITL 长期以来是每个 host 的私有实现：同样的"问用户一次"，每个客户端自己造一遍弹窗。MCP（Model Context Protocol）在两层把它协议化。sampling 是第一个方向：server 请求 host 代为调用一次 LLM，host 对用户保持透明与可控——这解决"人审模型的输出"。2025-06-18 规范新增的 elicitation 是反方向：server 主动向用户索取结构化输入——这解决"人给 agent 缺的信息"。

elicitation 的关键设计细节

  • schema 刻意收窄：顶层必须是 object，属性仅允许 string / number / integer / boolean（可带 enum），禁止嵌套结构。第一版就这么保守——既保证任何 client 都能渲染成表单，又压缩注入攻击面。
  • 三值响应：accept（带符合 schema 的 content）、decline（用户拒绝本次请求）、cancel（请求本身被撤销）——语义上区分"人说不"和"请求没送达"。
  • 同意是规范强制的：client 在返回 accept 之前 MUST 获得用户明确同意；client 在 initialize 阶段声明 elicitation 能力，不支持就协商不启用。

与 tool approval 的本质差异

  • tool approval 解决"授权"：允许不允许 agent 使用某个能力。判定发生在 host 的策略层（第 4 节那个纯函数），人不一定亲自参与。
  • elicitation 解决"咨询"：agent 缺一个只有人有的信息或决策，回复内容是数据而不是许可。
  • 一个管权限，一个管知识。把两者混在一个"确认框"里，是大多数粗糙实现共同的问题：用户分不清自己是在授权还是在回答问题，两种决策的认知负荷完全不同。

协议化的真正收益："问人"从私有 UI 变成可组合原语后，任何 MCP host——IDE、桌面聊天客户端、手机推送——都能替 server 履行问人义务；审批界面的质量由 host 层竞争决定，而不是每个工具各自造一个弹窗。这和第 5 节的异步审批正交组合：server 发起 elicitation，host 把它路由成一张卡片，几小时后带着答案回来。

7. 交互经济学：审批疲劳是第一失效点

请求速率超过人的阅读吞吐时，监督塌缩为橡皮图章——这已被反复实证。

2026 年 agent 治理领域形成的行业共识相当残酷：人工监督是最先失效的一环（human oversight fails first）。当审批请求的到来速度快于人能阅读的速度，人的行为退化为习惯性点击同意；安全领域已开始直接度量"批准率与实际核验率的背离"作为橡皮图章指标。这与 Windows UAC 的警告疲劳、自动化偏见（automation bias）完全同构——四十年的老问题换了个界面重演。

第一层：降量

allowlist 记忆与跨会话复用；批量审批（一次审一组同类动作）；用一次计划审批替代 N 次动作审批；沙箱结构性消除危险请求。请求越少，每一次越被认真对待。

第二层：提质

diff / 变更预览优于原始命令文本；风险分类与理由前置；展示该类决策的历史与先例（"上三次同类请求都批准了"）；默认值按动作类别设定而非全局一刀切。

第三层：换人

guardian agent 先按策略与先例过滤多数低风险请求，只把高分歧案例上呈人类；配合对人工批准的抽样复核，校准整条监督链。

两个被反复验证的设计事实值得单独强调。其一，审查界面是核心竞争力：PR review 之所以有效，是因为 git diff 是信息密度极高、噪声极低的人审界面——人扫一眼就知道改了什么、为什么改。好的审批 UI 应该向"展示将要发生的变更的 diff"收敛，而不是让人类解析 shell 命令。其二，批次大小决定审查质量：Google 的现代代码审查研究一再显示，小变更、短反馈的审查既快又准；迁移到 agent 审批——每批审的动作组要小到能在一次注意力周期内消化，宁可多批，不要一次倒给人 40 个变更。

最后，审批疲劳必须被度量，不能被感觉到才算数：

  • 审批延迟分布：中位数与尾部（P95）——尾部才暴露"卡在某个审批人"的流程问题。
  • 批准率：按动作类别分桶。某道门长期 >98% 批准，它就不再是门，是仪式——删掉或换成自动化检查。
  • 被拒动作的重试率：agent 被拒后换个说法再请求同一操作的比例——提示注入与"磨到批准"的信号。
  • 阅读时长：审批卡片从展示到点击的间隔。中位数趋近于零的批准，就是橡皮图章的直接证据。

呈现层的隐藏陷阱：模型在审批请求里自动附带的"理由"会触发自动化偏见——人读的是模型的自我辩护，而不是独立判断的依据。成熟的做法是把"模型的理由"与"客观事实"（diff、影响面、策略匹配结果）在视觉上分区呈现，并明确标注前者只是主张。

8. 交付边界模式：事后审查与可逆性矩阵

Coding agent 集体收敛到"全自动 + PR review"不是偶然，是可逆性与审查经济学的必然。

动作级审批把打断次数与动作次数绑成正比，注定撞上审批疲劳。另一条路线把审查点从过程中的 N 个动作，合并到交付边界的 1 次审查：agent 在分支上全自动跑完，人审的只是一个 PR diff。它之所以在 coding 领域成立，靠的是两个环境前提——动作可逆（分支模型提供天然可丢弃的工作空间，错了 revert 即可）与过程安全交给沙箱和 CI（agent 出错也越不了界）。把这组前提一般化，就得到按可逆性与影响面选型的决策矩阵：

动作类别典型示例推荐回环设计
可逆 · 影响局部沙箱内文件编辑、分支上的代码改动、临时环境部署全自动 + 事后 diff 审查；配合 CI 与抽检
可逆 · 影响全局合并主干、部署预发环境、批量重构计划审批一次（审意图与方案），执行全自动，交付再审 diff
不可逆 · 可补偿对外发消息、发布文章、调用付费 API动作级审批；批准绑定动作指纹与过期时间；预留补偿动作（撤回、退款流程）
不可逆 · 不可补偿删除生产数据、付款转账、公开发布法务敏感内容双人复核 + 冷却期；high-stakes 动作值得最重的流程，不应因麻烦而省略

事后审查的隐性成本必须正视：反馈回路拉长后，错误在被发现前可能已在错误前提上堆叠了多层构建（agent 基于错误假设继续写了三小时代码）。所以成熟形态是混合的：关键前置假设用计划审批把关（少数几次、高杠杆），中间过程全自动（沙箱内），交付用 diff 审（一次、完整视角）。三种回环各守一段，而不是用一种回环硬扛全程。

9. 多 Agent 编排中的 HITL：升级的作用域

一个子代理提问时，停掉的应该是它自己，不是整棵调度树。

单 agent 里的"暂停"语义是平凡的；多 agent 系统里它是架构决策。反模式是整树停摆：任何一个 subagent 需要人，orchestrator 就阻塞，所有无关分支陪等。正确的语义是升级只挂起发起者：提问的 subagent park 在那次"问人"的调用上，orchestrator 继续调度其余分支，人回答后作为 tool result 原样送达该 subagent，从断点继续——一次提问的等待成本被限制在单分支内。

正确做法

  • 阻塞范围最小化：只有提问的 subagent 挂起；编排器把"等待人"当成一种普通的慢 tool call。
  • 回答结构化：选项式回答可校验、可路由、可统计；自由文本在并行分发给多个下游时是注入面。
  • 超时与降级路径：提问带超时，超时后该分支按默认策略收敛（跳过/取保守值），不影响其余分支。

常见反模式

  • 全局闸门：任何提问都冻结全部并行度，吞吐塌到串行。
  • 人当垃圾场：每个 subagent 都被允许随手问人，问题不聚合、不排序，人面对的是并发轰炸。
  • 双层橡皮图章：guardian agent 预审后，人只是再点一次"同意"——监督链加长一层，却没有增加任何独立判断。

值得展开的是 guardian（AI 审 AI）模式：用一个监督 agent 对照策略与历史先例给每个动作打风险分，过滤掉绝大多数低风险请求，只把高分歧案例上呈人类。它把"审批吞吐不足"转化为"监督模型校准"问题——但要警惕：对人类呈现的必须是 guardian 的判断依据（命中了哪条先例、分歧在哪），而不只是结论，否则只是把橡皮图章从人手里转移给了模型。这也是 2026 年 agentic 安全产品线（guardian 类工具）的共同设计焦点：policy enforcement + 风险路由 + 完整审计链。

10. 经典开源项目的 HITL 实现方案

六个有代表性的开源实现：各自的回环抽象、代码级 API 与语义取舍。

前面各节讲机制原理，这一节看原理如何落地成"默认选项"。LangGraph 与 Temporal 已在第 3、5 节展开，这里巡礼十个代表性开源实现：先是框架与 SDK 一派，再补充 2025–2026 年爆发的新生代——常驻个人代理与极简 harness。它们对最关键的问题——谁拥有触发回环的权力——给出了从"拓扑保证"到"配置时一次授权"的多种答案，先看全貌：

AutoGen / AG2 —— 人即代理（拓扑端）

  • UserProxyAgent 的三档 human_input_mode：ALWAYS（每轮必问人）、TERMINATE（默认自动，人随时可插入——当前事实主流）、NEVER（纯自动）。档位直接对应第 2 节的 LOA 谱系。
  • 人是对话拓扑中的一等 agent：参与由轮转结构保证，不依赖模型"想起来要问"。
  • 代价：粒度是"轮"而不是"动作"。0.4 重构用 input_func 把输入源抽象出来——控制台、Web UI、消息队列都能充当"人的接口"，人不必守在进程旁；也顺带把早期版本混在代理里的"消息转发"与"代码执行确认"两个职责拆开了。

smolagents 与 CrewAI —— 人即工具 / 任务末反馈（模型自主端）

  • smolagents 的 HumanInputTool：把人封装成普通 Tool，forward() 就是读一行控制台输入——human-as-tool 的教科书实现，agent 像调用搜索一样"调用"人。
  • CrewAI 的 Task 级 human_input=True：任务产出后进入反馈循环，人的反馈作为新输入迭代，放行后才进入下一任务——回环挂在交付边界，天然是第 8 节的 post-hoc 形态。
  • 共同的关键取舍：问不问由模型决定。灵活但不可强制——模型可以选择不问。适合信息补充与偏好澄清，不能承担安全职责。

OpenAI Agents SDK —— 审批即一等运行时中断

  • 工具注册时声明式标记 requires_approval=True；调用发生时 run 暂停，以 ApprovalRequest 中断项交还宿主处理。
  • 应答用 ApprovalResponse 三值语义：approve（执行）/ reject（拒绝并把理由回传模型）/ escalate（上交人工或平台）——把"机器可判的拒绝"与"必须给人的升级"分开。
  • 审批是 session 内可持久化的中断：与第 3 节 interrupt/resume 同构，但"哪个工具要批"成了工具的声明式属性，而非散落在代码里的判断；另可经 ApprovalRequestContext 按参数动态决定（如仅对非白名单域名触发）。

Codex CLI —— 审批与沙箱的二维矩阵

  • 开源（Rust）实现里，审批配置是二维矩阵：approval_policy ∈ untrusted（只自动跑可信只读命令）/ on-request（模型主动要权时问）/ on-failure（沙箱拒绝后再问）/ never；sandbox_mode ∈ read-only / workspace-write / danger-full-access。
  • 经典组合 workspace-write + on-failure：沙箱内自由写，越界动作先被机制拦下、失败后才升级人审——审批请求只在机制已经拦截之后发生，天然低频。
  • 这是第 4 节"用沙箱降低审批量"最清晰的开源参考实现，配置语义可以直接抄进自家系统。

Claude Agent SDK —— hook 即策略执行点

  • 生产 CLI 权限系统的开源封装：permission mode 四档照搬；can_use_tool 回调把 PreToolUse 判定交给宿主程序——传入工具名与入参，返回 allow / deny。
  • hooks 体系让策略在模型上下文之外的进程里执行，退出码或 JSON 决策直接改写回环结果——第 4 节"策略纯函数 + PEP"的官方开源载体。
  • 与 Agents SDK 对照很有启发：一个把审批做成运行时中断（SDK 暂停等你，利于异步化），一个做成同步回调（宿主函数当场判，利于嵌入既有服务）。

组合范式 —— Cloudflare Workflows + MCP elicitation

  • 把第 5、6 节接起来：server 经 elicitation 发起结构化提问（协议层的"问"），durable workflow 的 step 把"等人"变成可跨天的状态（基础设施层的"等"）。
  • 等待走持久化、恢复走 step 重放、提问走协议——这是开源参考里最接近生产级异步审批的形态。
  • 提示了一个选型事实：没有一个单一框架能同时把"问、等、审、计"四件事都做到最好，生产系统几乎必然是组合体。

下面这批是 2025–2026 年才爆发的新生代，与前六个不是同一物种：常驻个人代理把回环从"运行时审批"挪到"配置时授权"，极简 harness 干脆主张"人在场 + 代码可读"就够了。它们各自把第 2 节 LOA 谱系推到了两端：

OpenClaw —— 常驻授权的极端与治理回调

  • 个人常驻代理网关（经 WhatsApp / Telegram 等渠道接入你的数字生活），代表 LOA 8–10 在个人场景的极端形态：不是"每动作审批"，而是一次性授予长期代理权。
  • 安全争议后收敛出分层防护：per-agent 沙箱（Off / Non-main / All 三档）+ 每代理工具 allow/deny（agents.list[].tools.allow/deny）+ shell 命令前缀 allowlist + DM policy（谁可以与代理对话）。注意这些 gate 都在配置期生效，运行期回环反而弱。
  • 每代理独立沙箱与工具策略（full access / read-only / no access）值得借鉴：多 agent 场景按代理分权，而不是全局一刀切——这是第 9 节"升级作用域"在权限维度的对应物。
  • HITL 启示：常驻授权把审批从运行时挪到配置时，第 7 节的疲劳问题被绕过、也被放大——绕过是因为不问了，放大是因为出问题时没人看着，只剩审计与事后介入。

nanobot（HKUDS）—— 极简代码基作为信任机制

  • 超轻量个人代理框架（Python，核心约四千行），WebUI / 终端 / 聊天应用多通道接入，定位 OpenClaw 的极简替代；支持 MCP、Ollama、Docker，自托管。（另有同名 Ruby 前辈——2023 年 icebaker 的极简 agent 框架，思路同源，谈论时注意区分。）
  • 回环形态：人即渠道——代理常驻在聊天应用里，人随时插话就是介入，无需专门的审批机制。
  • 信任模型与 pi 同派：代码少到能读完，本身就是安全机制——你审计的是全部代码，而不是一摞配置矩阵和闭源依赖。
  • 局限同常驻一派：宽授权 + 运行期审批弱，适合个人与自托管，进组织场景需要外挂策略层。

pi —— 极简 harness 的反框架立场

  • Mario Zechner（badlogic，libGDX 作者）2025 年底发布的极简终端 coding agent："harness 而非框架"——极小内核，一切靠扩展；skills 与 Claude Code / Codex CLI 兼容，生态直接复用。
  • 立场：反对把权限、记忆、编排全部内建成黑盒框架；agent 应该小到能读完、贴身可改，用户为自己的工具负责。
  • 回环形态：人在终端旁，同步会话本身就是回环。极简派认为 coding 场景里"人一直在场"是比权限系统更强的安全条件——这当然只对同步单人场景成立。
  • 与框架派构成光谱两端：一端是 LangGraph / Agents SDK 的机制化回环，一端是 pi / nanobot 的"可读代码 + 人在场"信任模型。两端各有其场景，不构成谁对谁错。

AgentScope —— 人即代理的工程化与检查点

  • 阿里通义实验室的多智能体框架（Python 为主，另有 Java 版），1.0 于 2025 年 9 月发布；国内生产采用多——阿里商旅差旅助手、金融智能体底座等案例都跑在它上面。
  • HITL 双层：内置 UserAgent 把人表示为对话中的智能体（与 AutoGen 同派）；Java 版进一步提供工具调用前的人工审核 checkpoint——暂停等确认再执行，即 approval gate 形态。
  • 社区讨论（issue #926）点出的难点很典型：HITL 的关键不在会话内，而在不同部署环境如何获取用户输入——Web、终端、消息渠道的输入管道各自不同。这正是 input_func、MCP elicitation 这类抽象要解决的问题：把"人的接口"从应用代码里解耦出来。

触发权谱系——本节最重要的结论：把这些实现排在一条谱系上：拓扑保证（AutoGen：人是对话图的固定节点）→ 模型自主（smolagents / CrewAI：模型决定何时问）→ 程序强制（Agents SDK / Codex CLI / Claude Agent SDK：声明、策略或回调决定何时问）。安全回环必须落在程序强制一端——只有那里的触发不受模型控制，因而也不受提示注入影响；模型自主端只配承担澄清与偏好收集。另一个耐人寻味的事实：截至 2026 年，主流开源实现无一用"模型自评置信度"触发安全回环，大家不约而同把触发权留在了程序层——这印证了第 11 节对 confidence-based escalation 的保守判断。而新生代补上了谱系的第五种答案——配置时授权（OpenClaw / nanobot：运行期不问，监督退化为审计与事后介入）：它绕开了审批疲劳，也放弃了运行期防线，适合单人自托管场景；一旦进入组织场景，必须叠回程序强制那一端。

自建 Agent 的落地 checklist

  • 从 deny-by-default 起步，用 allowlist 逐步放行，而非反过来。
  • 审批判定写成纯函数；策略变更前用历史动作样本跑回归。
  • 每份批准绑定动作指纹 + 过期时间 + 单次使用，拒绝重放与挪用。
  • 审批信号走带外通道（卡片按钮 / 平台 API），不走模型可读写的文本流。
  • 超时必须有升级链与默认策略（升级到 backup、超时默认拒绝或降级只读）。
  • 节点 / 步骤可重入，副作用幂等；resume 前重验前提（世界已漂移）。
  • 审计日志 append-only：谁、何时、基于什么信息、批准了什么，可整体回放。
  • 度量批准率与阅读时长；长期 >98% 批准的门，删掉或换成机器检查。
  • 能交给机制的不要交给人：沙箱、CI、静态检查先上，人只留不可逆决策。
  • 权限修改权本身入权限：模型永远不能改判定函数与配置。

走向：人在回环中的新位置

  • 人审意图与结果，机器审过程：计划审批守前提，沙箱与 CI 守过程，diff 守交付——人出现在信息密度最高、杠杆最大的两端。
  • 审批成为基础设施：policy as code、MCP elicitation 类协议原语、跨渠道审批中心，HITL 从应用特性下沉为平台能力。
  • confidence-based escalation 前景可期但被有意保持保守：让模型自评"我该问人吗"仍不可靠，主流生产系统仍用规则而非模型自评触发升级——模型判断何时升级，大概率是下一个范式转移点。
