典型应用场景

并行航线规划与任务聚合涉及对象共享、任务准入和结果汇总。沿这条执行链路，分析线程预算、JVM 内存与故障定位。

本篇核心问题

能从一次任务提交追到对象可见性、锁等待、堆中持有关系与容器资源，而不是只背集合和 GC 名称。

阅读方式：先用记忆关键词复述机制，再推演例子的失败窗口，最后明确验证对象。场景用于解释技术取舍；练习能证明什么、不能证明什么，见版本与验证范围。

版本与验证范围：并发 API 以 Java 21 文档为阅读基线；虚拟线程的固定载体问题单独区分 JDK 21 与 JDK 24 之后的变化。练习只验证线程池容量机制。

2. 对象“已经赋值”为什么还不等于“另一个线程可以安全使用”？

从机制到边界，再用具体交错检验结论。

记忆关键词：构造 → 发布 → happens-before → 不变量

核心结论

对象共享的关键是写入与读取之间是否建立规定的可见性和顺序关系。字段赋值先后只是一个线程的程序顺序，不能代替跨线程发布协议。

拆开机制与保证范围

设规划配置有 version 和 regions 两个字段。写线程构建完配置，再经 volatile 引用发布；读线程通过该引用取得快照，才可以把发布前的写入作为同一份初始化结果理解。若构造时 this 逃逸，或发布后继续无同步修改内部集合，“引用可见”也救不了内部竞态。

volatile 的读写关系能用于发布，但 count++ 是读、计算、写三个步骤，仍可丢更新。不可变对象降低同步面；如果快照包含可变列表，需要复制或明确所有权。final 的初始化安全性有特定前提，也不赋予容器内容自动线程安全。

把业务不变量写出来：同一版本的区域和参数必须匹配。正确做法可以是整体替换不可变快照，而不是为每个字段各加 volatile，再希望读者恰好读到同一版本。多字段组合正确性与单字段可见性要分开回答。

场景推演：配置从 v1 切到 v2：逐字段更新时，读者可能读到 v2 的阈值和 v1 的区域；整体快照替换把版本绑定在一个对象身份中。

进一步思考：“加 synchronized 一定解决？”要让读写遵守同一保护协议。“ConcurrentHashMap 放了对象就安全？”发布关系不覆盖随后任意修改对象内容。

如何验证：先列出读写点和所有权，再用固定输入核对是否出现混合版本；压力跑不出错误只能增加信心，不能替代 happens-before 推导。

3. AQS、CAS 和锁队列究竟分别负责什么？

从机制到边界，再用具体交错检验结论。

记忆关键词：状态 CAS · 队列等待 · 唤醒再竞争 · 公平与吞吐

核心结论

AQS 为同步器提供状态管理和排队等待骨架。CAS 争用同步状态，队列组织未成功获取者；唤醒只提供重新尝试的机会，并不直接把业务资源授予线程。

拆开机制与保证范围

以独占锁为例，获取者尝试改变同步状态，失败后可能进入等待队列并挂起。释放者更新状态并推进等待者；公平策略通常约束插队，非公平策略可能让新到线程先竞争。队列存在不等于每种同步器都严格 FIFO，细节还与具体实现有关。

CAS 无法把“查空闲机库、写资源占用、发设备指令”三个外部步骤变成原子事务。即使本地锁正确，另一个服务实例不受它保护。锁的范围、被保护数据和持有时间要先确定，长时间把网络调用包在本地锁内会放大等待。

条件等待也属于协议：在锁内检查谓词，等待释放相应锁，醒来重新竞争并用循环检查谓词。通知与资源状态不是同一对象，虚假唤醒和其他线程抢先消耗资源都要求重新验证条件。

场景推演：两个规划线程都等待“机库可用”。一次通知后第一个线程占用了资源，第二个线程即使醒来仍需重新检查，不能因为收到通知就下发任务。

进一步思考：“CAS 就没有锁等待？”不代表没有竞争和重试成本。“公平必然更好？”应比较尾延迟、吞吐和饥饿风险，不能从名称直接选。

如何验证：记录持锁时长与等待时长，结合线程栈判断 CPU 自旋、park 或下游阻塞；不要只看线程状态名就归因为 AQS。

4. 线程池为什么不能只按“核心数乘二”配置？

从机制到边界，再用具体交错检验结论。

记忆关键词：准入 → 核心线程 → 有界队列 → 扩容 → 拒绝

核心结论

线程池参数决定任务如何等待与被拒绝。预算要由到达速率、服务时间、下游容量和可接受排队共同约束，经验公式只能是测量前的起点。

拆开机制与保证范围

ThreadPoolExecutor 的典型路径是先补核心工作线程，再尝试入队；队列放不下才尝试扩到 maximumPoolSize，仍不行则走拒绝策略。使用无界队列时，最大线程数通常不会帮你处理队列积压，慢任务会把压力转成等待和对象持有。

规划包含 CPU 计算与远程调用时，二者的限制不同。CPU 部分超过可用配额会增加竞争；等待部分可以提高并发，但数据库连接、设备请求和模型额度仍有限。把不同等待类型放入同一个池，还可能使长任务阻塞轻量回调。

CallerRuns 会让提交者执行任务，因此可能阻塞 HTTP 接收线程或事件循环；静默丢弃会破坏结果聚合。拒绝需要变成明确的受理失败或可恢复状态。排队时间必须占用同一总 deadline，开始执行前应确认任务尚有价值。

场景推演：假设 core=2、max=4、queue=2 且所有任务阻塞：前六个可被接收，第七个被拒绝。把 queue 改成无界，会让后续任务堆积而不是自动扩到四线程。

进一步思考：“线程越多吞吐越高？”下游和 CPU 会成为上限。“Future 等待超时即可？”还要处理取消、队列移除和已经执行的动作结果。

如何验证：练习用闩锁固定任务占用以验证容量路径；真实调优再记录排队、执行、拒绝率、CPU 配额和下游并发，避免单次压测得出永久参数。

5. ConcurrentHashMap 的安全范围到哪里为止？

从机制到边界，再用具体交错检验结论。

记忆关键词：单键操作 · 原子更新 · 可变值 · 热点键

核心结论

ConcurrentHashMap 支持并发访问及特定单键原子操作，但不会把多次 get/put 或多个键组成业务事务，也不自动保护取出的可变值。

拆开机制与保证范围

get 后计算再 put 可以覆盖别人的结果。单键计数可使用合适的原子更新方式；compute 类回调要简短，不应在里面做长网络等待。它的具体实现会随 JDK 版本变化，答题先说 API 保证，再深入所用版本的桶、CAS 与锁路径。

父任务聚合需要的不变量可能是“子任务只记一次、总数与状态匹配”。如果分别改 finishedCount 和 status 两个键，中途观察者可能看到不一致。可把聚合状态封成一个不可变值做单键状态更新，或转到数据库事务与事件幂等协议。

大量线程更新同一热键仍有竞争；弱一致遍历不能直接用来证明精确时刻的全部任务已完成。LongAdder 适合某些高竞争统计，但其读取并不是天然的业务结算快照。统计指标与状态机决策应使用不同契约。

场景推演：同一个采集完成回调重送两次，即使 count.merge 是原子的，也可能把同一子任务算两次；需要先按子任务身份去重。

进一步思考：“线程安全集合为何还有竞态？”竞态发生在组合操作和业务身份层。“全局加锁？”可能正确，但应先衡量保护范围与跨实例要求。

如何验证：构造重复回调、不同子任务并发、状态读取与终态写入交错；核对身份集合、计数和终态，而不只验证 map 没抛异常。

6. JVM GC、内存泄漏和容器 OOM 如何建立因果链？

从机制到边界，再用具体交错检验结论。

记忆关键词：GC Roots → 可达性 → 活对象 → 堆外 → 容器计费

核心结论

GC 回收不可达的堆对象，不能替应用删除仍被队列、缓存或会话引用的数据。容器总内存还包含堆外、线程栈和其他计费项，所以调大堆不一定解决 OOM。

拆开机制与保证范围

对象从请求进入任务队列，再被 Future、结果缓存或 SSE 会话持有；请求超时后，如果这些引用未断开，GC 仍把它们视作活对象。这类生命周期缺陷常表现为 GC 后基线逐步上升，和瞬时大量分配造成的频繁 GC 不同。

G1 把堆划分为 Region，并按活对象和回收成本组织回收；并发工作减少某些长停顿，但仍有需要停顿的阶段。暂停目标是调优目标而非硬实时承诺，活对象过多、分配压力和巨型对象都会改变表现。

先区分 heap used/committed、RSS 与容器内存。DirectByteBuffer、原生模型库和线程栈可以在 Java 堆外消耗空间。把 Xmx 贴近容器上限，会挤掉这些预算；更大堆也可能让泄漏更晚暴露而不改变根因。

场景推演：断线后的流式会话没有清理，每个会话仍持有消息和缓冲。Full GC 后占用仍不断增长；重启恢复只说明持有关系被清空，不能证明 GC 算法有错。

进一步思考：“GC 频繁就是泄漏？”要看回收后的活集趋势。“OOM 一定会有 Java 堆转储？”容器外部杀死进程未必留下 JVM 的 OOM 证据。

如何验证：结合 GC 日志、堆转储中的支配关系、线程数量、原生内存与 cgroup 事件；在隔离环境复现会话创建与清理，验证回收后基线稳定。

7. 虚拟线程与 CompletableFuture 分别改变了什么？

从机制到边界，再用具体交错检验结论。

记忆关键词：等待组织 · 载体线程 · 取消协议 · 下游仍有限

核心结论

虚拟线程让许多阻塞等待更便宜，CompletableFuture 组织异步依赖；两者都不增加 CPU 算力，也不替代业务并发、超时和取消协议。

拆开机制与保证范围

虚拟线程由运行时调度到载体线程，适用阻塞方式编写的大量 I/O 等待任务；CPU 密集计算仍占用真实执行资源。JDK 21 中 synchronized 相关固定会限制某些路径，JEP 491 在 JDK 24 改善该问题，其他原生调用路径仍需按版本检查。

CompletableFuture 的某些非 Async 阶段可能由完成前一阶段的线程执行；Async 阶段的执行器选择也需明确。把阻塞数据库调用随手丢到公共池，可能影响其他任务。任务链完成异常和应用自行创建的子任务是否退出，也是不同问题。

取消不是撤销已经完成的远端动作。Future.cancel 的参数和具体实现定义了本地取消行为，不能据此推断设备没有起飞或数据库没有提交。只有动作身份、权威查询与资源清理协议才能处理这种边界。

场景推演：把一万个等待任务换成虚拟线程后，数据库连接池仍只有有限容量；如果没有准入限制，只是把线程瓶颈换成连接等待和更长的任务积压。

进一步思考：“虚拟线程还要池化吗？”通常不以池化虚拟线程控制数量，而是对实际有限资源做准入。“异步后异常会自己打印？”必须消费并记录完成结果。

如何验证：按 JDK 版本观察载体利用、固定事件、连接等待与取消后残留工作；比较相同业务结果和同样下游容量，不能只比较创建线程的速度。

8. 动手验证与故障推演

真实 API 练习：有界线程池的第七个任务为什么被拒绝

Java 21 可用语法，使用标准库；闩锁固定任务生命周期，自检 core → queue → max → reject 的实际路径。它不测吞吐，也不代表线上推荐参数。

保存为 ThreadBudget.java，用 javac --release 21 ThreadBudget.java 编译，再用 java ThreadBudget 运行。

import java.util.concurrent.*;

public class ThreadBudget {
    public static void main(String[] args) throws Exception {
        var release = new CountDownLatch(1);
        var pool = new ThreadPoolExecutor(2, 4, 30, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(2),
                new ThreadPoolExecutor.AbortPolicy());
        Runnable task = () -> {
            try { release.await(); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };
        try {
            for (int i = 0; i < 6; i++) pool.execute(task);
            if (pool.getPoolSize() != 4 || pool.getQueue().size() != 2)
                throw new AssertionError("unexpected capacity path");
            boolean rejected = false;
            try { pool.execute(task); }
            catch (RejectedExecutionException e) { rejected = true; }
            if (!rejected) throw new AssertionError("seventh task admitted");
        } finally {
            release.countDown();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                pool.shutdownNow();
                throw new AssertionError("workers did not finish");
            }
        }
        System.out.println("bounded capacity and rejection passed");
    }
}
