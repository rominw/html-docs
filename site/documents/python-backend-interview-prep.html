2. 语言基础

先理解名字、对象与容器的真实关系。

基础必会 1. 赋值和参数传递：改的是名字还是对象？

先看问题：

调用函数后列表多了元素，却没有变成函数里重新赋的空列表。两条“赋值”改变的对象不同。

原理怎样推出来

Python 名字绑定对象；把列表传入函数后，参数名也绑定同一个对象。修改该对象会被其他引用观察到，重新绑定参数名则只改变函数内部的绑定。不可变对象上的 += 常产生新对象，可变对象的行为要按类型判断。

把它放进一个例子

def change(xs):
    xs.append("A")
    xs = []
    xs.append("B")
items = []
change(items)
assert items == ["A"]

边界与反例：不要把“传引用”理解成函数可以重绑调用方变量。对象可变性、别名和原地操作需要分别判断。

停一下，自己推：把列表放进元组，列表就不可变了吗？

展开自测解析

没有。元组的元素绑定不变，但它引用的列表仍可修改；不可变外壳不递归冻结成员。

理解后，再这样简述：赋值绑定名字，修改共享对象与重新绑定名字不同。

核对原文：对应官方文档或方法原文。

基础必会 2. 浅拷贝与深拷贝：为什么副本仍一起变化？

先看问题：

复制一个“设备列表”，修改副本内某设备的标签，原列表也被改了。你复制了外层，内层仍共享。

原理怎样推出来

浅拷贝创建新的外层容器，但内部元素仍引用原对象。深拷贝按对象图递归复制，并用记忆机制处理重复引用和循环；它不是任意资源都能复制，也不等于可以随便复制数据库连接。

把它放进一个例子

a = [[1], [2]]
b = a.copy()
b[0].append(9)
assert a[0] == [1, 9]
b.append([3])
assert len(a) == 2

边界与反例：需要独立数据时先定义哪些层共享、哪些层复制；深拷贝可能昂贵，自定义类也可改变复制语义。

停一下，自己推：JSON 序列化再反序列化能通用替代 deepcopy 吗？

展开自测解析

不能。它只适合可序列化的数据形态，还可能改变类型、共享关系、日期或精度。

理解后，再这样简述：副本独立程度由复制层级决定，按数据契约选择。

核对原文：对应官方文档或方法原文。

基础必会 3. 相等、身份与哈希：dict 和 set 怎样找元素？

先看问题：

两份内容相同的列表 == 为真，is 却未必为真；字典键又不能直接用普通列表。

原理怎样推出来

== 调用类型的值相等规则，is 判断是否为同一个对象。哈希容器先按 hash 定位候选，再判断相等，相等对象必须有一致的 hash。参与键身份的内容要稳定；tuple 也只有元素可哈希时才可作为这种键。

dict 保存键值映射并保留插入顺序，set 表达唯一成员；顺序并不意味着 dict 按键大小排序。

把它放进一个例子

a, b = [1], [1]
assert a == b and a is not b
key = ("dock", 7)
cache = {key: "ready"}
assert cache[("dock", 7)] == "ready"

边界与反例：不要用小整数或字符串驻留的偶然现象推断所有对象身份。自定义 __eq__ 与 __hash__ 要配套。

停一下，自己推：(1, []) 是元组，为什么仍不能作为普通 dict 键？

展开自测解析

其中的列表不可哈希；外层是元组不消除成员哈希要求。

理解后，再这样简述：内容相等与对象身份分开，哈希键需要稳定且满足契约。

核对原文：对应官方文档或方法原文。

基础必会 4. list、deque 与推导式：把整个操作成本算进去

先看问题：

队列不断 pop(0)，数据越多越慢；把全部文件读进列表再处理，还可能先耗尽内存。

原理怎样推出来

list 适合下标访问和尾部操作，删除头部通常需移动后续元素；deque 支持两端入出，更适合普通队列。推导式构建完整结果，生成器表达式按需产生值，能减少同时保留的数据，但遍历和计算总量不会因此消失。

把它放进一个例子

from collections import deque
queue = deque([1, 2])
assert queue.popleft() == 1
values = (i * i for i in range(3))
assert list(values) == [0, 1, 4]

边界与反例：不要在遍历同一列表时随意删元素导致跳项；生成器通常只能消费一次，若下游要重复读取需明确保存。

停一下，自己推：把列表改为生成器，就能让一个本来 O(n²) 的比较过程变成 O(n) 吗？

展开自测解析

不能。延迟产生主要改变存储与时机，算法嵌套工作量仍需单独优化。

理解后，再这样简述：结构按访问模式选，惰性执行不等于减少全部计算。

核对原文：对应官方文档或方法原文。

基础必会 5. 可变默认参数：为什么第二次调用带着第一次的数据？

先看问题：

函数参数写 items=[]，本来想每次得到新列表，结果请求间共享了同一份累积数据。

原理怎样推出来

默认参数表达式在函数定义时求值，并保存在函数对象上，调用没传该参数时会复用它。用 None 作缺省标记，在函数内部创建容器，才能表达每次独立的需求；如果 None 本身是合法值，可以使用独立哨兵对象。

把它放进一个例子

def add(value, items=None):
    if items is None:
        items = []
    items.append(value)
    return items
assert add(1) == [1]
assert add(2) == [2]

边界与反例：有意缓存状态可以存在，但需要明确生命周期与并发协议，不能把意外共享当优化。

停一下，自己推：默认参数写 datetime.now()，得到的是每次调用时间吗？

展开自测解析

不是。它在定义时求值；当前时间应在调用路径里读取。

理解后，再这样简述：默认值不是每次调用重新计算，动态或可变默认值须显式创建。

核对原文：对应官方文档或方法原文。

基础必会 6. 作用域与闭包：循环里创建的函数为什么都返回最后一个值？

先看问题：

循环生成三个回调，触发后都读到了最终 i，而不是各自创建时的数字。

原理怎样推出来

闭包保存对外层绑定的访问，通常在函数执行时读取值，循环不会为每次迭代自动创建独立作用域。把需要的当前值变成参数或通过工厂绑定，可明确快照语义；nonlocal 修改外层函数绑定，global 指向模块绑定。

把它放进一个例子

callbacks = [lambda i=i: i for i in range(3)]
assert [f() for f in callbacks] == [0, 1, 2]

边界与反例：函数里对名字赋值会影响它是否被视为局部变量，先读后赋可能触发 UnboundLocalError。共享闭包状态也需考虑并发与生命周期。

停一下，自己推：默认参数绑定了一个列表，它的内容以后改变，回调会看到改变吗？

展开自测解析

会。绑定的是对象，不是递归深拷贝；快照需求须定义复制范围。

理解后，再这样简述：闭包读取绑定，创建时捕获和调用时读取要区分。

核对原文：对应官方文档或方法原文。

基础必会 7. 迭代器与生成器：yield 暂停在哪里？

先看问题：

导出百万行数据，希望边取边发送。一次性构造全部行会拉高内存，生成器可保留执行位置逐步产出。

原理怎样推出来

可迭代对象可产生迭代器，next 推进迭代器，结束时抛 StopIteration。含 yield 的函数调用后返回生成器，执行会在产出位置暂停，下次恢复局部状态；资源也可能随暂停被持续持有。

把它放进一个例子

def rows():
    yield "first"
    yield "second"
g = rows()
assert next(g) == "first"
assert list(g) == ["second"]
assert list(g) == []

边界与反例：流式过程要处理提前停止、断开与资源释放；生成器不能替代数据库游标和 HTTP 发送侧的完整生命周期管理。

停一下，自己推：把一个生成器同时交给两个消费者，会各自得到完整副本吗？

展开自测解析

不会。它们可能共享推进同一个迭代状态，需按消费方式创建独立迭代器或明确分流。

理解后，再这样简述：迭代器保存消费位置，生成器保存执行状态；惰性也有资源边界。

核对原文：对应官方文档或方法原文。

基础必会 8. 异常与 finally：捕获失败之后还能继续吗？

先看问题：

保存失败后返回空对象，让上游误认为“数据不存在”；finally 里 return 还覆盖了原异常。

原理怎样推出来

异常应该保留操作失败的语义。只捕获当前层能够恢复或转换的具体异常，用 raise 保留传播，包装时可用 raise ... from ... 保留原因链。finally 用于结束路径清理，不用返回值掩盖错误。

把它放进一个例子

try:
    result = load_data()  # 项目接口，可能失败
except OSError as exc:
    raise DataUnavailable("读取失败") from exc
finally:
    release_owned_resource()

边界与反例：CancelledError 等异常层级和库行为要核对；捕获 BaseException 可能吞掉退出或取消语义。日志和错误响应避免泄露凭证。

停一下，自己推：查询超时后返回 []，能与查询成功零条记录自然区分吗？

展开自测解析

不能。需要错误或明确结果类型，否则会让后续逻辑根据虚假的空结果操作。

理解后，再这样简述：捕获要有恢复依据，清理不覆盖失败，原因链继续可追踪。

核对原文：对应官方文档或方法原文。

基础必会 9. with 与上下文管理器：谁负责释放资源？

先看问题：

函数中途抛异常，文件或连接仍要关闭。把 close 放在成功返回之后会漏掉失败路径。

原理怎样推出来

with 调用进入与退出协议，把资源生命周期绑定到代码块。__exit__ 会获得异常信息，其返回值可决定是否抑制异常；contextlib 提供常用包装。异步资源使用 async with，退出时也可能需要等待。

把它放进一个例子

from pathlib import Path
with Path("input.txt").open(encoding="utf-8") as handle:
    text = handle.read()
# 已尝试关闭，即使读取失败

边界与反例：共享池或传入资源不一定归当前函数关闭；先定义所有权。上下文管理器若抑制异常，应明确外部还会观察到什么结果。

停一下，自己推：with Session() 一定就表示每个操作自动提交吗？

展开自测解析

不一定。关闭会话与事务提交是不同协议，要按 ORM 的 begin/commit 上下文理解。

理解后，再这样简述：上下文协议组织资源进入、退出与异常，所有权和事务仍需明确。

核对原文：对应官方文档或方法原文。

项目常用 10. 装饰器：包装方法怎样保留接口和异常？

先看问题：

统一计时或授权不想每个函数写一遍，但包装后函数名与签名难识别，异步函数也可能没被真正等待。

原理怎样推出来

装饰器在定义时把函数交给包装过程，返回新可调用对象。包装应传播参数、结果与异常，functools.wraps 保存常用元信息；装饰器顺序决定先包装谁。对 async 函数，计时范围需包括 await 期间，不能只计协程对象创建。

把它放进一个例子

from functools import wraps
def tagged(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

边界与反例：认证装饰器只检查身份不等于完成资源授权；包装中的空 catch 可能改变事务与重试。不要通过装饰器偷偷重复调用业务。

停一下，自己推：同步包装直接返回 async fn 的协程对象，业务已经执行了吗？

展开自测解析

通常没有。需要由调用方正确 await，或使用明确的异步包装协议。

理解后，再这样简述：装饰器改变调用入口，保留参数、元信息、异常和异步语义。

核对原文：对应官方文档或方法原文。

基础必会 11. 类、dataclass 与属性：数据对象为什么还要考虑共享？

先看问题：

把 tags=[] 写成类属性，多个实例都共享标签；使用 dataclass 后以为对象就不可变或可以直接哈希。

原理怎样推出来

类属性被实例查找时可共享，实例属性应在各自初始化中建立。dataclass 可生成初始化、比较等方法，但默认不递归冻结对象；可变默认字段用 default_factory 创建。property 用访问协议组织计算与校验，不应把昂贵远程调用伪装成廉价字段。

把它放进一个例子

from dataclasses import dataclass, field
@dataclass
class Device:
    id: int
    tags: list[str] = field(default_factory=list)
a, b = Device(1), Device(2)
a.tags.append("hot")
assert b.tags == []

边界与反例：frozen 主要限制字段重新赋值，成员仍可能可变；生成的 equality/hash 也要符合业务身份。继承和方法解析是进一步追问。

停一下，自己推：一个 frozen dataclass 含 list 字段，就能作为稳定 dict 键吗？

展开自测解析

4. 并发与异步

先区分并发与并行，再处理任务生命周期和容量。

基础必会 16. GIL、线程和进程：并发与并行怎样选？

先看问题：

许多 HTTP 请求在等 I/O，和纯 Python 循环算图像，是两种不同负载。线程数多不表示计算就能用满更多核。

原理怎样推出来

在常规带 GIL 的 CPython 中，同一解释器内的 Python 代码执行受全局解释器锁约束，等待 I/O 或某些释放 GIL 的扩展可让其他线程推进。CPU 密集纯 Python 工作可考虑进程池，代价是进程资源、数据传输与序列化。

把它放进一个例子

例如一批远程读取可用受限线程或 asyncio 重叠等待；纯 Python 大量计算先测算法与进程方案。原生扩展是否释放 GIL 要看实现。

边界与反例：GIL 不等于业务复合操作线程安全。Python 3.13+ 有可选自由线程构建，不能把 GIL 结论套到全部构建，扩展兼容也须核对。

停一下，自己推：共享 dict 做“检查不存在→新增”就因 GIL 一定原子吗？

展开自测解析

不能这样推。复合步骤和副作用需要锁或原子存储协议，运行时内部锁不是业务事务。

理解后，再这样简述：先辨认 I/O 等待与计算，再按解释器构建、库行为和通信成本选并发方式。

核对原文：对应官方文档或方法原文。

基础必会 17. async/await：调用协程为什么不立即跑完？

先看问题：

写 async 函数读取设备数据，直接调用却只拿到 coroutine；在里面 time.sleep 后，所有请求仍一起卡住。

原理怎样推出来

async def 调用产生协程对象，需 await 或调度为任务才能推进。事件循环在可让出执行的 await 处调度其他就绪任务；它不会把阻塞函数自动变成非阻塞。顺序 await 两个调用通常仍顺序等待，创建多个任务才可重叠它们。

把它放进一个例子

async def main():
    async with asyncio.TaskGroup() as group:
        a = group.create_task(fetch("A"))
        b = group.create_task(fetch("B"))
    return a.result(), b.result()

边界与反例：示意的 fetch 必须遵守异步协议，TaskGroup 需要 Python 3.11+。CPU 大循环和同步阻塞 I/O 会占住循环，不能只加 async 关键字。

停一下，自己推：await 一个已经就绪的对象，是否必然让其他任务执行一次？

展开自测解析

不能把 await 当作无条件切换点。它表达等待协议，是否实际暂停取决于对象状态。

理解后，再这样简述：协程是可暂停的执行，事件循环重叠等待；阻塞工作必须独立处理。

核对原文：对应官方文档或方法原文。

项目常用 18. 取消、超时与 TaskGroup：失败后剩余任务谁收尾？

先看问题：

一个聚合请求失败，其他后台子任务仍在跑，继续占连接并把结果写入已失效的请求状态。

原理怎样推出来

任务要有拥有者和结束条件。取消通过 CancelledError 等机制在合适时机传入，清理通常放 finally，清理后保留取消传播。TaskGroup 把子任务生命周期绑定到作用域，部分失败会触发组内协作取消并等待结束；与 gather 的错误策略不同。

把它放进一个例子

例如一个请求启动两个远程查询，作用域退出时都应结束；总超时包住整个组合，单次远程调用也配置连接与读取超时。

边界与反例：协作取消不撤销已提交 DB 或已发设备指令；to_thread 中的阻塞工作也不一定因协程取消就立即停止。

停一下，自己推：捕获取消后无限重试，会影响什么？

展开自测解析

父级可能无法结束，超时和关闭语义被破坏；需有界恢复并尊重取消。

理解后，再这样简述：任务归属、取消清理和副作用恢复一起设计。

核对原文：对应官方文档或方法原文。

项目常用 19. 并发上限与队列：为什么 gather 十万次会出问题？

先看问题：

每个请求很轻，但同时创建十万个任务会占内存、连接和下游限额；“都是异步”没有消除容量。

原理怎样推出来

Semaphore 可限制同时进入某段工作，连接池限制可用连接，有界队列控制等待积压。把输入流分批或由有限 worker 拉取，可避免先创建无限任务；下游慢时要定义排队上限、超时和拒绝/降级。

把它放进一个例子

limit = asyncio.Semaphore(10)
async def bounded(item):
    async with limit:
        return await fetch(item)
# 输入很大时还要限制任务创建/排队量

边界与反例：限执行并发不等于限待执行任务数。并发数须结合平均耗时、尾延迟、连接池与实际压测，不拍一个固定“最优”数字。

停一下，自己推：连接池只有 20，Semaphore 设 1000 就能提高吞吐吗？

展开自测解析

可能只是更多任务等连接。先看瓶颈和允许等待时长，再设置一致容量。

理解后，再这样简述：同时控制执行、排队与下游资源，异步需要背压。

核对原文：对应官方文档或方法原文。

项目常用 20. contextvars：请求上下文为什么不能放普通全局变量？

先看问题：

同一事件循环交错处理多个用户，请求 A 保存当前用户后 await，B 覆盖它，A 恢复时读到 B。

原理怎样推出来

ContextVar 管理上下文中的绑定，适合任务交错时隔离请求信息；set 返回令牌，按作用域用 reset 恢复旧绑定。任务创建通常捕获相应上下文，跨线程、进程和消息需要按实际机制显式传播，不把身份随意信任外部输入。

把它放进一个例子

from contextvars import ContextVar
request_id = ContextVar("request_id", default=None)
token = request_id.set("req-A")
try:
    handle()
finally:
    request_id.reset(token)

边界与反例：上下文隔离不递归隔离绑定的可变对象；日志 traceId 与用户授权事实也不是同一概念。

停一下，自己推：绑定同一共享列表给两个上下文，列表内部就不会互相影响吗？

展开自测解析

不会有这个保证。上下文隔离绑定，列表对象仍共享，需独立对象或同步协议。

理解后，再这样简述：上下文管理绑定范围，资源与身份传播需明确边界。

基础必会 22. FastAPI、Pydantic 与依赖：验证了格式还缺什么？

基础必会 24. SQLAlchemy Session、flush、commit：写进会话就持久了吗？

先看问题：

调用 add 后得到对象，以为数据库已经提交；多个并发任务还共享同一个 Session。

原理怎样推出来

Session 管理工作单元和对象状态，flush 把待变更发送到数据库事务，commit 提交事务，两者不同。发生错误后需按会话状态回滚/结束再继续。普通会话与 AsyncSession 都不应被多个并发执行路径随意共享。

把它放进一个例子

with Session(engine) as session:
    with session.begin():
        session.add(task)
    # 正常退出事务块后提交；异常路径回滚
# 会话资源结束

边界与反例：ORM 不能代替唯一约束和原子条件更新；本地提交也不涵盖消息发布与设备下发。flush 后生成 id 不证明已提交。

停一下，自己推：拿到自增 id 后事务回滚，这个任务一定存在吗？

展开自测解析

不一定。id 分配和持久提交是两回事，间隙也不表示数据丢失。

理解后，再这样简述：会话、刷新和提交是不同层，事务与并发所有权要明确。

项目常用 25. N+1 与懒加载：一页列表为什么查了几十次数据库？

6. 可靠业务

缓存、锁、消息与超时都要有恢复边界。

项目常用 26. HTTP 超时与重试：没拿到响应不等于没执行

先看问题：

外部创建任务接口超时，自动再发一次，结果创建两个任务。

原理怎样推出来

分别设置连接、读取及总请求预算，区分可重试暂时故障与永久错误。重试需有次数和退避，创建/支付等副作用要稳定幂等键或结果查询。连接复用减少开销，客户端资源按服务生命周期管理。

把它放进一个例子

同一业务操作重试保持同一请求键；记录外部状态与超时原因，避免重试层层叠加放大流量。

边界与反例：HTTP 客户端的 timeout 参数含义各不相同；进程取消也不撤销已完成外部操作。

停一下，自己推：返回 500 就可以无条件重试所有 POST 吗？

展开自测解析

不能。服务端可能已执行部分动作，先分析业务幂等与恢复契约。

理解后，再这样简述：超时限制等待，可靠重试依赖业务结果和稳定身份。

核对原文：对应官方文档或方法原文。

项目常用 27. 缓存与 Redis 锁：性能协调怎样接上业务约束？

先看问题：

多个 Python worker 同时回源或调度，进程内锁挡不住另一进程；缓存旧值也可能回填。

原理怎样推出来

Cache Aside 要分析 DB 提交、删缓存失败与旧读回填。Redis 锁使用原子获取带租期、持有者标识与原子校验释放；租期可能先于业务结束，原生复制故障也有窗口。业务正确性仍靠 DB 约束、状态版本、幂等或资源端协议。

把它放进一个例子

设备任务先做原子 NEW→RUNNING 条件更新，检查影响行数；锁可减少争抢，不能把“拿过锁”当作所有外部效果已安全。

边界与反例：TTL 不保证缓存始终正确；续租不自动排除长暂停旧持有者。跨进程锁库的 API/续租方式要按依赖核对。

停一下，自己推：A 锁到期、B 获取后，A 用无条件 DEL 释放，会怎样？

展开自测解析

会误删 B 的锁。原子持有者校验防误删，但旧 A 的业务动作仍要被约束。

理解后，再这样简述：缓存允许的陈旧度和锁协调范围都要落到明确业务协议。

核对原文：对应官方文档或方法原文。

项目常用 28. Celery 与后台任务：进程重启后工作还在吗？

先看问题：

HTTP 返回成功后只 create_task 执行导出，进程重启导致任务消失，用户却以为已经排队。

原理怎样推出来

进程内后台任务适合可接受丢失的小工作；可靠任务需持久任务/消息记录、明确确认与重试，Celery 等系统提供相应组织能力但仍需配置。业务提交到消息发送之间可用 outbox 保存待投递记录，消费者按业务键幂等。

把它放进一个例子

导出接口事务内创建任务，返回任务 id；后台领取任务并更新阶段与失败原因，用户查询结果。重试保持同一业务任务身份。

边界与反例：消息确认配置和任务幂等一起分析，不能简单打开重试就宣称不丢不重。结果保存期限也应明确。

停一下，自己推：先 ack 再执行，进程崩溃后会自动重做吗？

展开自测解析

未必。消息已确认可能不再投递，因此确认必须与业务完成及恢复策略对应。

理解后，再这样简述：持久记录让任务可恢复，确认与重试需要幂等效果配套。

核对原文：对应官方文档或方法原文。

基础必会 29. 事务与幂等：去重标记和业务效果为什么要一起看？

先看问题：

先记录“处理过”，业务写入前崩溃，重试被跳过；先业务后标记又可能重复执行。

原理怎样推出来

同一 DB 内可把唯一业务键记录与业务修改放进同一事务，失败一起回滚。状态条件更新保护合法转换，外部副作用需下游支持同一幂等键或结果查询。原子边界由资源决定，不由 Python 函数边界决定。

把它放进一个例子

回调使用稳定 event_id，事务内插入唯一记录并更新任务；提交后才确认消息。已提交后确认丢失可重投，但业务识别已有结果。

边界与反例：去重 TTL 到期后仍可重放，状态机终态也不自动保护所有设备动作；处理过与处理完成要分清。

停一下，自己推：把 DB 写入和 Redis 标记放同一个 try 块，崩溃窗口就消失吗？

展开自测解析

不会。两套资源没有共同本地事务，要设计恢复记录和业务协议。

理解后，再这样简述：稳定业务键、原子效果和失败恢复共同构成幂等。

核对原文：对应官方文档或方法原文。

7. 排障与交付

用证据区分 CPU、内存、等待与输入风险。

项目常用 30. CPU、内存与延迟：先判断哪种资源出了问题

先看问题：

接口慢可能是大计算，也可能在连接池等；RSS 上涨也不一定全是 Python 活对象。

原理怎样推出来

结合请求分段、CPU、GC/对象、线程与连接指标定位。cProfile 等可找函数热点，tracemalloc 观察 Python 分配，二者不覆盖全部原生库内存与系统等待。回收后基线持续涨应查缓存、队列、引用与业务积压。

把它放进一个例子

若 DB 执行 20ms、连接等待 1500ms，先查连接持有与事务时长；若纯计算占 CPU，先查算法和剖析结果，再选进程并行。

边界与反例：诊断与日志有开销，大对象 dump 可能含敏感数据；不要以一次耗时就宣布优化成功。

停一下，自己推：把缓存无限加大后延迟降低，是否已证明系统可稳定运行？

展开自测解析

没有。还需看长期内存、淘汰、容量与负载，短期收益可能换来积累。

理解后，再这样简述：按资源与链路证据诊断，验证长期与尾部表现。

核对原文：对应官方文档或方法原文。

基础必会 31. 日志与可观测性：异常打印出来为什么还找不到请求？

先看问题：

多 worker 同时输出“执行失败”，没有请求 id、业务键、阶段和堆栈，很难拼出发生了什么。

原理怎样推出来

结构化日志保存时间、级别、关联 id、业务键与阶段，错误保留原因与堆栈；指标看错误率、队列、耗时分位，trace 看跨步骤等待。日志事件和指标回答不同问题，不能把高频完整请求体都记下来。

把它放进一个例子

一次设备命令把接收、持久化、发送、回执与终态按同一业务键串联；记录尝试号与耗时而不记录完整凭证。

边界与反例：日志采样与保留需满足排障需求，敏感字段限制记录；contextvars 中 traceId 不是可信授权依据。

停一下，自己推：错误率为零，所有用户就没有问题吗？

展开自测解析

未必。错误可能被吞、成功结果错误、指标漏采或延迟过高，应结合用户效果和业务校验。

理解后，再这样简述：日志保上下文，指标看整体，链路看耗时，结果需可验证。

核对原文：对应官方文档或方法原文。

项目常用 32. 配置、发布与优雅关闭：收到退出信号怎样收尾？

先看问题：

发布时直接终止进程，正在生成的文件、消费中的消息和 DB 事务可能半完成。

原理怎样推出来

启动阶段建立有归属的客户端与池，配置来自环境并校验必需项。退出阶段先停止接新工作，再以有限时间等待/取消已有任务，关闭资源并保存可恢复状态；worker 数、健康探测、迁移兼容与回滚条件要对应实际部署。

把它放进一个例子

任务长于发布窗口时，应有持久阶段记录供新进程恢复，而不是靠无限等待。发布前确认新旧版本对消息与表结构兼容。

边界与反例：虚拟环境不等于生产容量隔离，健康检查返回 200 不证明依赖和业务全部可用。密钥不写进仓库。

停一下，自己推：旧版程序读不懂新版消息，代码回滚就自动安全了吗？

展开自测解析

不会。协议与数据迁移可能不可逆，发布应预先定义兼容期和恢复方案。

理解后，再这样简述：资源、配置与工作生命周期统一管理，发布考虑兼容与恢复。

核对原文：对应官方文档或方法原文。

基础必会 33. 输入、序列化与文件路径：反序列化不是普通读取

先看问题：

用户上传 pickle 文件或传一个路径，服务直接加载/打开，可能执行不可信内容或越过授权目录。

原理怎样推出来

边界选择数据格式、限制大小与结构，拒绝不可信 pickle 等可触发任意执行的输入。路径解析后验证在授权根目录内，并考虑符号链接与文件类型；SQL 值绑定，动态标识符白名单，身份与资源权限独立检查。

把它放进一个例子

上传数据用明确 JSON/schema 校验，目录内文件服务使用服务端映射的文件 id，而不允许用户提供任意绝对路径。

边界与反例：eval 与字符串拼 shell 不是解析普通用户数据的方式；容器和类型提示不自动消除这些边界。

停一下，自己推：文件名去掉 ../ 就保证所有路径都安全吗？

展开自测解析

不能。编码、绝对路径、平台规则和符号链接等仍可能绕过；用解析后范围验证与文件访问策略。

理解后，再这样简述：只解析明确数据，按资源边界验证权限、尺寸与路径。

核对原文：对应官方文档或方法原文。

基础必会 34. 金额与时间：为什么浮点和无时区时间容易出错？

先看问题：

0.1+0.2 不能按十进制直觉直接判等；跨时区任务“今天”也可能不是服务器当天。

原理怎样推出来

二进制浮点不能精确表示许多十进制小数，业务金额可用最小单位整数或明确精度与舍入的 Decimal，避免先从近似 float 构造。时间要分瞬间、时区和日历规则，存储/接口明确时区，持续耗时使用适合的单调时钟。

把它放进一个例子

from decimal import Decimal
assert Decimal("0.1") + Decimal("0.2") == Decimal("0.3")
# 日期区间按业务时区建立，再转换为查询所用时间表示

边界与反例：Decimal 不替你选舍入规则；夏令时可能造成重复或不存在的本地时间，定时业务须定义歧义处理。

停一下，自己推：用系统 wall clock 相减衡量超时，时间校正会影响吗？

展开自测解析

可能。超时预算宜使用单调计时，业务时间记录仍按明确时区。

理解后，再这样简述：数值精度和时间语义是业务契约，不是格式化细节。

核对原文：对应官方文档或方法原文。

进阶追问 35. 引用计数、循环 GC 与 weakref：没用对象为什么还活着？

先看问题：

缓存、监听器或闭包还保留对象，GC 再勤快也无法替业务判断这些引用是否有用。

原理怎样推出来

常规 CPython 以引用计数等机制管理对象，并用循环垃圾回收处理特定可追踪循环；对象仍被强引用到就不能视为不可达垃圾。weakref 可表达不延长对象生命的关联，但回收时机与支持类型需理解，不是所有缓存都应改弱引用。

把它放进一个例子

查存活对象的持有链：全局缓存→设备对象→大字段。若缓存无限增长，先限制生命周期和容量；两个对象互相引用却无外部可达，才是另一类问题。

边界与反例：Python 语言不承诺全部实现都按同样计数时机运行，不能依赖析构准点关闭资源；with/finally 更明确。

停一下，自己推：删除一个变量后 RSS 未立刻降低，就能证明泄漏吗？

展开自测解析

不能。可能还有引用，也可能内存分配器保留空间或原生库占用，应结合分配与持有证据。

理解后，再这样简述：对象可达性、资源关闭与进程内存回收是不同层。

核对原文：对应官方文档或方法原文。
