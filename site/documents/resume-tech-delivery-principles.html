2. Kubernetes 的控制循环为什么不等于业务事务？

从机制到边界，再用具体交错检验结论。

记忆关键词：期望状态 → 观察 → 协调 → 重建载体 → 业务恢复

先这样回答

控制器不断比较期望与观测状态并尝试协调。它能补足 Pod 等运行对象，但不知道某个设备动作是否成功、某条消息是否已提交业务效果。

拆开机制与保证范围

Deployment/ReplicaSet 等控制器维护相应工作负载数量和版本，Pod 可被替换而产生新身份。应用若只把任务、SSE 游标或去重状态放在旧 Pod 内存，重建后这些业务事实不会自动出现。应把需要恢复的状态交给有合适契约的存储和执行协议。

协调是持续过程，实例创建、调度、拉镜像、启动、探测和端点更新各有时间。配置了三个副本不代表每一时刻都有三个可服务实例；跨故障域、调度约束和依赖故障还会改变可用性。

业务状态机与平台状态不同：Pod Ready 只说明满足所定义的服务资格，任务 SUCCEEDED 需要业务结果证据。把恢复原则放在动作身份、确认与持久状态上，才能在换实例后解释未知结果，而不是靠进程重启“清零”。

项目推演：Pod 在设备已执行、回调未保存时被替换。新 Pod 即使完全健康，也必须查原动作结果；重新创建执行任务会扩大副作用风险。

继续追问：“多副本就绝不丢任务？”还需任务与确认协议。“StatefulSet 名称稳定就保存所有内存？”身份稳定和数据持久不同。

如何验证：在隔离环境删除承载在途任务的 Pod，核对新实例恢复同一业务身份；分别观察控制器对象与实际业务结果。

3. Requests、Limits、线程池和 HPA 怎样形成一个容量模型？

从机制到边界，再用具体交错检验结论。

记忆关键词：调度预算 · CPU 节流 · 总内存 · 指标时滞 · 下游容量

先这样回答

requests 参与调度与某些资源指标计算，limits 限制运行资源。线程与队列的预算需适配容器和下游，HPA 增副本也有采样与生效延迟。

拆开机制与保证范围

Linux 常见路径下 CPU limit 通过 cgroup 限制使用时间，CPU 受限可能表现为节流和尾延迟；memory limit 超过时可能被 OOM 处理。request 不等于永远独占该资源，limit 也不等于预留了足够物理容量。

Java 堆之外还有线程栈、堆外缓冲、原生模型和其他内存，GPU 也有单独显存预算。单个 Pod 增加 worker 和队列会放大内存与并发，下游数据库或模型服务可能先饱和。所有预算必须以实际计费和测量校准，不能只把 Xmx 填满 limit。

HPA 的 CPU 利用率等指标常以 request 为基准，并有取样、稳定策略和新 Pod 准备时延。等待 I/O 的服务可能 CPU 不高却队列严重积压；按队列指标扩容也须考虑热点键和下游上限。扩容是反馈控制，不是无限供给。

项目推演：CPU 图看起来未满机器总核数，Pod 却频繁节流；同时把线程数翻倍只增加竞争。应先核对容器配额、线程池排队与下游容量。

继续追问：“OOMKilled 就是 Java 泄漏？”还可能原生/缓冲或总预算不足。“加 Pod 必然降延迟？”启动时间、长连接和共享下游会限制效果。

如何验证：记录 cgroup 节流与内存事件、队列等待、堆/原生内存和下游占用；分组比较扩容前后，不用单张 CPU 图证明根因。

4. Startup、Liveness、Readiness 为什么不能共用一个“查所有依赖”接口？

从机制到边界，再用具体交错检验结论。

记忆关键词：启动资格 · 重启价值 · 接流量资格 · 故障放大

先这样回答

Startup 保护慢启动阶段，Liveness 判断是否需要重启容器，Readiness 判断是否接收相应流量。它们的失败动作不同，依赖检查要匹配这些动作的价值。

拆开机制与保证范围

启动模型和建立连接可能耗时，startup 成功前会影响其他探针的启用。把启动延迟误当存活失败会反复重启永远起不来；阈值和周期应基于真实启动分布，而不是复制固定模板。

liveness 失败达到阈值会触发相应重启行为，适合重启能改善的本地故障。若数据库不可用时所有应用 liveness 都失败，集体重启可能扩大连接洪峰，而不会修好数据库。readiness 可以控制服务资格，但全体摘流也需有明确用户与恢复语义。

readiness 变化影响匹配 Service 的端点资格，不强行撤销所有已经建立的长连接和业务执行。探针应低成本、有界并有错误分类；它与任务进展、模型质量和端到端业务成功是不同监控。

项目推演：新视觉服务加载权重需较长时间；startup 覆盖准备阶段，readiness 在真正能接收推理后通过，liveness 关注本地无法自恢复的失活，避免反复杀掉正常加载进程。

继续追问：“探针全绿就服务可用？”只证明定义的探测。“readiness 失败会重启吗？”其主要作用与 liveness 不同。

如何验证：模拟慢启动、本地卡死、共享下游故障和已有长连接，观察重启与端点变化；模型练习只核对不同失败动作。

5. Service、代理和 SSE 长连接为什么会影响负载与恢复？

从机制到边界，再用具体交错检验结论。

记忆关键词：端点选择 · 连接复用 · 缓冲 · 超时 · 跨实例游标

先这样回答

Service 提供面向后端端点的访问抽象，但长连接通常在建立后持续绑定某条路径。扩容、摘流与代理配置会改变新连接，不自动均匀搬迁已有连接。

拆开机制与保证范围

客户端、代理和 Service 实现可能各有连接复用与负载策略。大量 SSE 长连接集中在旧实例时，新 Pod 可用也未必立刻分担旧连接；按 CPU 总平均衡量容易漏掉单实例缓冲和连接数热点。

代理缓冲、压缩和闲置超时可能让 token 延后出现或频繁断线，具体配置取决于使用的代理/Ingress/Gateway。没有必要假定所有环境都可用某一 Nginx 响应头。业务心跳、读取 deadline 和任务进展监控应该分别定义。

重连可能到新实例，所以事件保留与权威结果查询不能只依赖旧实例内存。使用 run/seq 关联与共享或可路由的恢复存储，保证身份与权限；粘性会话可以帮助路由，却不能代替实例失效后的恢复协议。

项目推演：滚动发布切断一半连接，客户端重新订阅到新 Pod。如果游标只在旧进程，恢复会丢事件；如果重连时重建执行，则可能重复调用工具。

继续追问：“加副本能平均分流式会话？”既有连接未必重新分配。“关缓冲就端到端零延迟？”模型、网络和渲染仍有各自等待。

如何验证：模拟慢读、代理超时、换实例与断线重连，按实例记录连接、缓冲、事件缺口和内存；检查恢复任务身份不变。

6. 滚动发布如何保护 MQ、Temporal 和 Action 的在途工作？

从机制到边界，再用具体交错检验结论。

记忆关键词：摘流 · 停止准入 · 有界排空 · 持久边界 · 版本兼容

先这样回答

发布安全需要应用配合终止与版本协议。先停止新工作，再在可控期限内结束或保留可恢复边界；不能把所有未完成任务都标成失败或已确认。

拆开机制与保证范围

Pod 终止通常涉及端点变化、终止信号、应用清理与最后强制结束；具体信号、钩子和时间预算按镜像和集群配置核对。摘流与信号不是一个跨全部代理的原子事件，已有连接和旧请求仍可能继续进入清理路径。

MQ worker 在退出前只确认已安全处理的范围，未完成工作保留重投；Temporal worker 按 SDK shutdown 与历史兼容协议运行；Action 执行器保存身份和已知/未知结果。强杀可能留下外部成功但本地未知，恢复时查证而不是重建新身份。

新旧版本并存时，数据库 Schema、事件字段、配置、工具返回和工作流命令都要兼容。回滚应用镜像并不回滚已经写出的新数据或新历史 marker。迁移应有前后兼容阶段和受控切换证据，不能只看 deployment rollout 完成。

项目推演：新版增加复核步骤，旧历史仍被新 worker 接收；同时新消息字段被旧消费者读到。需要分别验证工作流版本桩和事件兼容，两个问题不是一次镜像回滚能包办。

继续追问：“preStop 睡几秒就安全？”延迟并不证明工作已排空。“退出统一 ack？”会跳过未完成业务结果。

如何验证：在确认/提交/回调各阶段滚动升级与强制结束，核对位点、历史和实际副作用；分别验收向前升级与已有新状态后的回滚。

7. AI Coding 怎样从“能生成代码”提升到“能证明修改正确”？

从机制到边界，再用具体交错检验结论。

记忆关键词：明确不变量 → 查真实调用 → 最小变更 → 反例 → 证据

先这样回答

AI 能加快产生候选实现，工程师仍需确认调用路径、依赖版本和可证明的业务行为。编译、单元测试、集成与故障验证提供不同强度的证据。

拆开机制与保证范围

先明确要保护什么，如旧回调不能覆盖终态、原请求重试不能二次下发、旧工作流历史可回放。阅读实际调用方、配置和现有约定，再让工具提出最小实现。没有源码证据时，不应把模型熟悉的 API 或类名描述成项目事实。

编译检查语法与部分类型，纯状态模型验证抽象规则，集成测试验证真实代理、数据库与 SDK，故障实验覆盖确认丢失和进程退出。测试如果只是复写实现判断而没有反例，可能和实现一起犯同一个错；每个关键保证至少要有能失败的输入。

可观测性把 request/message/event/workflow/run/config/model 这些身份按职责关联，记录关键状态转移与耗时。指标发现群体现象，trace 关联一次请求，日志留下具体事实；敏感载荷不必全部记录。交付时保留版本、验证范围和恢复方式，才能把“用了 AI”转成可解释的工程能力。

项目推演：AI 生成一个“超时后重试起飞”的补丁，测试只覆盖先失败后成功会通过。增加“设备成功但回包丢失”反例，才能暴露重复副作用。

继续追问：“所有测试通过就绝对正确？”只对覆盖的契约和环境增加证据。“日志很多就可排查？”身份、状态和时间边界要能关联且不泄露敏感内容。

如何验证：把每项结论对应到编译、模型、集成、回放或故障证据；明确缺少的环境验证，不把示例自检升级成生产安全声明。

8. 练习：从能讲到能反驳自己的假设

先说预期，再运行；如果结果相反，回到机制与边界。

预算与探针模型：内存总量和失败动作不能混淆

Python 3 标准库，数字是假设的 MiB 预算。探针函数只表达达到阈值后的作用分类，不模拟 Kubelet 时序、启动 gating 或 Service 传播。

保存为 practice.py，用 python practice.py 运行。

def memory_fits(limit, heap, native, stacks, buffers):
    values = (limit, heap, native, stacks, buffers)
    if any(v < 0 for v in values):
        raise ValueError("negative budget")
    return heap + native + stacks + buffers <= limit

def failure_action(kind, failures, threshold):
    if kind not in {"readiness", "liveness", "startup"} or threshold < 1:
        raise ValueError("invalid probe policy")
    if failures < threshold:
        return "below-threshold"
    return "remove-from-service" if kind == "readiness" else "restart-container"

assert not memory_fits(512, 300, 120, 60, 70)
assert memory_fits(512, 260, 100, 50, 50)
assert failure_action("readiness", 3, 3) == "remove-from-service"
assert failure_action("liveness", 3, 3) == "restart-container"
assert failure_action("startup", 3, 3) == "restart-container"
assert failure_action("liveness", 2, 3) == "below-threshold"
try:
    memory_fits(512, -1, 100, 20, 20)
    raise AssertionError("negative memory accepted")
except ValueError:
    pass
print("total memory budget and probe action distinctions passed")
