1. 总纲：三层堆叠

所有概念先摆对位置：谁是思想、谁是手段、谁是挂载点。

总纲一句话：AOP 是思想，动态代理是实现手段，BeanPostProcessor 是 Spring 把这个手段"挂"进 Bean 生命周期的钩子。方向别搞反——不是"AOP 实现了 BPP"，而是 Spring AOP 作为一个 BPP 跑在容器里；动态代理离开 Spring 也能用（Proxy.newProxyInstance 是 JDK 的 API）。

系列导航：① IoC 篇：容器、Bean 生命周期与循环依赖 · ② AOP 篇（本篇） · ③ Boot 篇：自动装配与启动流程 · ④ 能力全家桶篇：并发、调度、缓存与事件。本篇讲的 BeanPostProcessor 钩子，是 IoC 篇生命周期主线上的插件位；④ 篇的所有声明式能力（@Async、@Cacheable……）都挂在本篇讲的这条拦截器链上。

2. BeanPostProcessor：一切"魔法"的地基

容器内核极小，注解的语义全是插件提供的。

基础接口：只有两个回调，返回值可以替换 Bean

public interface BeanPostProcessor {
    default Object postProcessBeforeInitialization(Object bean, String beanName) { return bean; }
    default Object postProcessAfterInitialization(Object bean, String beanName) { return bean; }
    // 返回什么，容器里最终存的就是什么 —— "偷梁换柱"的合法入口
}

接口家族树：把 Bean 创建的每个阶段都留了钩子

BeanPostProcessor                                 // 初始化前 / 初始化后
  └─ InstantiationAwareBeanPostProcessor          // + 实例化前 / 实例化后 / 属性填充时
       ├─ MergedBeanDefinitionPostProcessor       // + 定义合并后（扫描注入元数据）
       └─ SmartInstantiationAwareBPP              // + 候选构造器 / 循环依赖提前引用
注解 / 功能处理者（插件）干活的钩子
@Autowired @Value @InjectAutowiredAnnotationBeanPostProcessor定义合并后扫描 + 属性填充时注入
@ResourceCommonAnnotationBeanPostProcessor同上（先按名字匹配）
@PostConstruct / @PreDestroyCommonAnnotationBeanPostProcessor初始化前 / 销毁回调
@TransactionalAOP（AbstractAutoProxyCreator）初始化后（包代理）
@AsyncAsyncAnnotationBeanPostProcessor初始化后（也是包代理）

核心认知：Spring 容器原生只认 XML / 编程式配置的属性，内核本身"不懂"注解。@Autowired、@Resource、@Transactional 的全部语义，都是标准扩展点上的插件加上去的——这就是 Spring"开放扩展、内核极小"的设计哲学。

3. @Autowired / @Resource：注入是怎么发生的

注入动作本身就发生在一个 BeanPostProcessor 的回调里，但坑位和 AOP 不同。

钩子一：找在哪注入

postProcessMergedBeanDefinition 在定义合并后扫描类里所有 @Autowired 字段和方法，封装成 InjectionMetadata 缓存，只找不注。

钩子二：真正注入

postProcessProperties 在属性填充阶段干活：resolveDependency 按类型找 Bean（处理 @Primary/@Qualifier），最后 field.set(bean, value)。

@Autowired vs @Resource

前者先按类型（支持 @Primary/@Qualifier），由 AutowiredAnnotationBPP 处理；后者先按名字、找不到再退回类型，由 CommonAnnotationBPP 处理。

时序决定结构：注入在 ③（populateBean），代理在 ⑤ 之后——所以 @Autowired 的依赖全打在原始对象身上，之后才包代理。循环依赖的提前暴露（三级缓存）恰好卡在 ② 与 ③ 之间：实例化后、注入前，通过 getEarlyBeanReference 提前把代理暴露给别人。

4. AOP 概念全景：从 Aspect 到 MethodInterceptor

术语各自回答一个问题，别混。

术语回答的问题例子
JoinPoint 连接点哪些位置可以拦方法的执行（Spring 只支持这一种）
Pointcut 切点具体拦哪些execution(* com.x.UserService.*(..))
Advice 通知拦到之后干什么@Before / @Around 修饰的方法逻辑
Advisor 通知器上面两者配成一对容器管理的最小增强单元
Aspect 切面一组横切逻辑的集合一个 @Aspect 注解的类
MethodInterceptor链上的执行形态proceed() 递归调用的拦截器

关键数量关系：一个 @Aspect 类 → N 个 Advisor

@Aspect
public class LogAspect {
    @Before("execution(* com.x.service.*.*(..))")   // → Advisor 1
    public void before() { ... }

    @Around("@annotation(LogRecord)")               // → Advisor 2
    public Object around(ProceedingJoinPoint pjp) { ... }

    @AfterThrowing("execution(* com.x..*.*(..))")   // → Advisor 3
    public void afterThrow() { ... }
}

每个通知方法各带各的切点表达式，被解析成一个独立的 Advisor（实现类 InstantiationModelAwarePointcutAdvisorImpl）。运行时它的 Advice 经 AdvisorAdapterRegistry 适配成 MethodInterceptor：@Around 天生就是这个结构；@Before 包成"先通知再 proceed()"；@AfterThrowing 包成"try-catch 包住 proceed()"。

点睛：声明式事务本身就是一个内置 Advisor——BeanFactoryTransactionAttributeSourceAdvisor，切点匹配 @Transactional，通知是 TransactionInterceptor。你写的 @Aspect 和 Spring 的事务支持，在容器眼里是同一种东西，所以能共存于同一条拦截器链。

5. 代理的诞生：创建期全链路

每个 Bean 初始化完成后，都要过一遍这场"面试"。

① 收集候选 Advisor

findCandidateAdvisors：普通 Advisor Bean + 扫描所有 @Aspect 类，把通知方法包装成 Advisor（懒解析、结果缓存，只做一次）。

② Bean 级匹配

canApply：先 ClassFilter.matches(类)，再 MethodMatcher 遍历所有方法——任意一个命中，整个 Bean 就要被代理。

③ 命中才造代理

未命中 → advisedBeans 记 false，原样返回，零代理成本；命中 → createProxy，容器里 Bean 名下挂的换成代理。

protected Object wrapIfNecessary(Object bean, String beanName, Object cacheKey) {
    Object[] interceptors = getAdvicesAndAdvisorsForBean(bean.getClass(), ...);
    if (interceptors == DO_NOT_PROXY) {
        advisedBeans.put(cacheKey, FALSE);            // 记住结论，不重复匹配
        return bean;                                  // 不需要代理，原样返回
    }
    return createProxy(bean.getClass(), interceptors, ...);  // 返回代理，替换原 Bean
}

// DefaultAopProxyFactory：在两种动态代理之间二选一
if (config.isProxyTargetClass() || hasNoUserSuppliedProxyInterfaces(config)) {
    return new ObjenesisCglibAopProxy(config);        // CGLIB
}
return new JdkDynamicAopProxy(config);                // JDK 动态代理
入口时机场景
postProcessAfterInitialization初始化完成后（主战场）99% 的代理在这里生成，包的是已完成注入和初始化的"成品"
getEarlyBeanReference实例化后、注入前循环依赖：提前把代理暴露到三级缓存；earlyProxyReferences 保证一个 Bean 只有一个代理
postProcessBeforeInstantiation实例化之前冷门：自定义 TargetSource 时短路 Bean 创建

偷梁换柱的准确含义：对象换了，名字没换。单例池里以这个 Bean 名注册的从此是代理，getBean 和 @Autowired 拿到的都是代理。

6. JDK 动态代理 vs CGLIB

区别远不止实现方式——类型关系直接决定你的代码会不会出事。

维度JDK 动态代理CGLIB
机制运行时实现接口（Proxy + InvocationHandler）ASM 生成子类重写方法（Enhancer + MethodInterceptor）
前提目标类必须实现接口类 / 方法不能是 final；private / static 拦不到
类型关系代理和目标是"兄弟"（同实现一个接口）代理是目标的"儿子"（子类）
可拦截范围只有接口里声明的方法类上所有可重写方法（含没写进接口的）
调用方式反射 method.invokeFastClass 索引定位（现代 JDK 下差距已不明显）
依赖JDK 自带第三方库（Spring 已内置重打包版本）

"兄弟"关系的代价

proxy instanceof UserService     // true（接口）
proxy instanceof UserServiceImpl // false！兄弟不是儿子
@Autowired UserServiceImpl s     // 按具体类型注入 → 报错

Spring Boot 2.x 起默认 proxy-target-class=true（强制 CGLIB），即使有接口也走 CGLIB——就是为了消灭这类按具体类注入失败的诡异问题。

CGLIB 特有的坑：final 方法 NPE

@Service
public class UserService {
    @Autowired
    private UserMapper userMapper;  // 注入在原始对象上

    public final void a() {         // final 无法被子类重写
        userMapper.xxx();           // 落在代理实例上执行
    }                               // 代理的字段 == null → NPE
}

CGLIB 代理用 Objenesis 创建、不走构造器，代理实例自己的字段全是默认值。

7. 代理与原始对象：堆里的两个对象

代理不是复制替换，是包一层——原始对象必须活着。

调用方 ──> 代理对象（容器单例池里注册的那个 Bean）
              │  JdkDynamicAopProxy#invoke / CglibAopProxy#intercept
              ├─ 拦截器链（TransactionInterceptor、@Around 切面 ...）
              └──> target = 原始对象   ★ 字段、@Autowired 依赖全在这
                        └─ 真正执行你的业务方法（this = 原始对象）
  • 状态只在原始对象上：字段、注入的 Mapper / Service 不重复存一份，代理只是"壳 + 拦截器链 + target 引用"；
  • 原始对象不是容器里的 Bean：它没被单独注册，只是代理肚子里被持有的 target，getBean 拿不到；
  • 想拿原始对象：((Advised) proxy).getTargetSource().getTarget() 或 AopProxyUtils.getSingletonTarget(bean)。

① 外部调有切面的方法

进代理 → 方法级匹配命中 → 开启事务 → target.method() → 提交 / 回滚。正常

② 外部调无切面的方法

同样进代理 → 匹配不上任何切面、链为空 → 直接放行调原始对象。路径经过代理，效果像直调。正常

③ 内部 this 调用

原始对象直接调原始对象，压根不经过代理——连入口都没有。将来加 @Transactional 也不生效。失效根源

关键认知：代理的粒度是 Bean，不是方法。只要一个方法命中切点，整个 Bean 被代理，所有外部调用都打到代理上——"用不用事务"决定这次调用挂不挂切面逻辑，"用不用代理"在 Bean 创建那一刻就定了，全类统一。

8. 运行期：一次方法调用的完整旅程

两级过滤的第二级在这里落地——每次调用现查链，按 Method 缓存。

List<Object> chain = advised.getInterceptorsAndDynamicInterceptionAdvice(method, targetClass);
if (chain.isEmpty()) {
    // 没有任何切面命中这个方法：连 MethodInvocation 都不创建，直接反射调原始对象
    return AopUtils.invokeJoinpointUsingReflection(target, method, args);
}
return new ReflectiveMethodInvocation(proxy, target, method, args, targetClass, chain).proceed();
// 两条路的终点都是同一行代码：method.invoke(target, args)

链是怎么现查出来的

  • 遍历这个代理上注册的所有 Advisor，逐个 MethodMatcher.matches(当前方法)；
  • 匹配的 Advice 经适配器转成 MethodInterceptor 放进链；
  • 结果按 Method 缓存（ConcurrentHashMap），一个方法只算一次；
  • 动态切点（表达式依赖参数值）每次调用还要带实参再 match 一次。

殊途同归

  • 链空 → 直接 invokeJoinpoint()；
  • 链非空 → 穿过所有拦截器后也是 invokeJoinpoint()；
  • 区别只是中间有没有拦截器挡路，对原始对象的调用方式完全一样；
  • "放行"不是换回原始对象——代理完成了一次没有环绕逻辑的委托。

两级过滤是整条链路的灵魂：创建时 Bean 级匹配决定"谁被代理"（一次），运行时方法级匹配决定"哪次调用走切面"（每次、有缓存）。

9. 现象地图：坑都是结构决定的

每个"诡异现象"都能在这张图上指到根因层。

现象根因落在哪层
this.b() 事务失效对象关系层：this 是原始对象，绕过代理，连入口都没有
CGLIB 下 final 方法 NPE代理结构层：final 无法重写，调用落在代理实例上，其字段是 null
JDK 代理按具体类注入失败选型层：代理和目标是"兄弟"不是"儿子"
循环依赖时有代理的 Bean 也能解BPP 层：getEarlyBeanReference 提前生成代理暴露到三级缓存
UnexpectedRollbackException拦截器链层：内层已标记 rollback-only——回滚的决定权在代理，不在业务代码
AspectJ 没有内部调用失效问题流派层：织入式直接改目标类，压根没有"内外两个对象"

断点一：没走代理

内部 this 调用、非 public 方法（静默忽略）、自己 new 的对象、接口注解 + CGLIB。

断点二：规则没命中

异常被 catch 吞掉、受检异常没配 rollbackFor（默认只回滚 RuntimeException 和 Error）。

断点三：上下文 / 环境断

多线程（事务绑 ThreadLocal）、多数据源没指定 transactionManager、MyISAM、DDL 隐式提交。

事务失效速记：所有场景收拢成三个断点——代理没走到、回滚规则没命中、异常没传到代理边界。回滚的决定权在代理层，不在业务代码里。

10. 面试口述简记卡片

每张 30~60 秒。背框架不背条目，留钩子引向准备充分的地方。

Q1 · BeanPostProcessor 和 AOP 的关系 ≈40s

BeanPostProcessor 是 Spring 容器的扩展点，在 Bean 初始化前后提供回调，返回值可以直接替换容器里的 Bean。Spring AOP 就建立在这个扩展点上：核心类 AbstractAutoProxyCreator 实现了 SmartInstantiationAwareBeanPostProcessor，在 postProcessAfterInitialization 里查找切面、匹配切点，匹配上就用 JDK 动态代理或 CGLIB 把原始 Bean 包成代理返回——容器里存的是代理，注入出去的也是代理。这也是事务内部调用失效的根源：this 调用走的是原始对象，没经过代理。循环依赖时则是通过 getEarlyBeanReference 提前暴露代理的。可以说 BeanPostProcessor 是 Spring 各种"魔法"的通用机制，AOP 是它最典型的应用。

Q2 · @Autowired 的原理 ≈35s

@Autowired 的注入就是在一个 BeanPostProcessor 回调里完成的，具体是 AutowiredAnnotationBeanPostProcessor。它用两个钩子分工：postProcessMergedBeanDefinition 在 BeanDefinition 合并后扫描出所有待注入的字段和方法并缓存；postProcessProperties 在属性填充阶段真正干活——按类型解析依赖，处理 Primary 和 Qualifier，最后反射 field.set 赋值。AOP 用的则是初始化后的钩子，两者是同一扩展机制下不同坑位的插件。这也说明 Spring 容器内核本身不懂注解，原生只认 XML 和编程式属性，@Autowired、@Resource、@PostConstruct 全是各个 BPP 插件提供的语义。@Resource 由 CommonAnnotationBeanPostProcessor 处理，先按名字匹配。

Q3 · 代理什么时候创建、怎么发现该代理谁 ≈40s

代理对象是在 Bean 初始化完成之后、postProcessAfterInitialization 这个回调里创建的，循环依赖时才会通过 getEarlyBeanReference 提前生成。判断"该不该建代理"靠切点匹配：先把容器里所有 Advisor 收集出来——包括普通 Advisor Bean，和扫描 @Aspect 类把每个通知方法包装成的 Advisor；然后对当前 Bean 做 canApply 检查，先用 ClassFilter 过滤类，再用 MethodMatcher 遍历所有方法，任何一个方法命中就算匹配；命中才 createProxy 生成 JDK 或 CGLIB 代理，一个都没命中就原样返回，不花代理成本。另外切点其实匹配了两次：创建时决定哪些 Bean 被代理，运行时每次方法调用还会再匹配一次，决定这次调用走不走通知。

Q4 · 生成了代理，原始对象还在吗 ≈40s

会有，而且必须有。代理不是复制，而是包一层：代理对象通过 TargetSource 持有原始对象的引用，真正执行业务方法、字段和 @Autowired 依赖都在原始对象上，代理本身只是壳和拦截器链。但容器层面，单例池里以 Bean 名注册的是代理，getBean 和注入拿到的都是代理，原始对象只是代理内部的目标，不能再从容器里获取。由此还有个经典坑：CGLIB 代理用 Objenesis 创建、不走构造器，代理实例的字段全是默认值，如果方法被 final 修饰，无法被代理类重写，调用会直接落在代理实例上，访问字段就是 null，直接 NPE。需要原始对象时可以用 ((Advised) proxy).getTargetSource().getTarget()。

Q5 · 有事务方法和非事务方法，各走什么 ≈30s

代理的粒度是整个 Bean 而不是方法。只要类里有一个方法命中切点，这个 Bean 就会被整体代理，容器里注册的是代理对象，所有外部调用都先打到代理上。有事务的方法，代理拦截后开启事务、委托原始对象执行方法体、最后提交或回滚；没注解的方法，调用同样进代理，但方法级匹配不上任何切面，拦截器链为空，直接放行去调原始对象——效果上和没代理一样，但路径上经过了代理。真正绕过代理的只有内部 this 调用，这也是事务失效的经典原因。"用不用事务"决定这次调用挂不挂切面，"用不用代理"在 Bean 创建那一刻就定了，全类统一。

Q6 · 没匹配到切面时怎么放行 ≈30s

代理的 invoke 方法里，每次调用会先按当前方法查拦截器链：遍历这个代理上注册的所有 Advisor，用 MethodMatcher 对这个方法做匹配，结果按 Method 缓存，所以每个方法只算一次。链是空的，就直接跳过整个拦截流程，用反射 method.invoke 调原始对象，CGLIB 用 methodProxy.invoke 走 FastClass，更快；链非空就创建 ReflectiveMethodInvocation 递归 proceed 走完拦截器，而链条的最后一环同样是对原始对象的反射调用。所以放行不是"换回原始对象"，而是代理完成了一次没有环绕逻辑的委托，调用方手里的始终是代理。

Q7 · JDK 动态代理 vs CGLIB ≈35s

JDK 动态代理基于接口，运行时让代理实现同样的接口，靠 InvocationHandler 拦截，代理和目标是"兄弟"关系，所以按具体类注入会失败，而且只能拦接口里声明的方法。CGLIB 用 ASM 生成目标类的子类，靠 MethodInterceptor 拦截，代理是目标的"儿子"，可以按具体类注入，但 final 方法没法重写所以拦不到，private 和 static 也不行。调用上 JDK 走反射，CGLIB 走 FastClass 索引，现代 JDK 下差距已经不大。Spring Boot 2 之后默认 proxy-target-class 等于 true，强制走 CGLIB，就是为了避免 JDK 代理类型不一致导致的按具体类注入失败。

Q8 · AOP、动态代理、AspectJ 什么关系 ≈45s

分三层看：AOP 是编程思想，动态代理是实现手段之一。AOP 有两大实现流派——代理式和织入式：Spring AOP 是代理式，运行时生成代理对象；AspectJ 是织入式，在编译期或类加载期直接改字节码，所以它能拦截构造器、字段这些 Spring AOP 拦不到的连接点，而且没有内部调用失效的问题。我们常用的 @Aspect 注解只是 Spring 借用的 AspectJ 语法，运行时还是代理。所以准确的说法是：Spring AOP 的底层是动态代理，AOP 本身不等于动态代理。

Q9 · Advisor 是什么 ≈35s

Advisor 是切点和通知的封装：Pointcut 回答"在哪些方法增强"，Advice 回答"增强逻辑是什么"，两者绑成一个 Advisor 才是容器管理的最小单元。一个 @Aspect 类会被解析成多个 Advisor——类里每个 @Before、@Around 方法各带各的切点表达式，各自成一个 Advisor。运行时 Advisor 的 Advice 会被适配器统一转成 MethodInterceptor 放进拦截器链：@Around 天生就是 MethodInterceptor 的结构，@Before、@AfterThrowing 需要包一层。有意思的是，Spring 的声明式事务本身就是一个内置的 Advisor——切点匹配 @Transactional，通知是 TransactionInterceptor，所以自定义切面和事务在容器眼里是同一种东西。

Q10 · 讲讲 Spring AOP 原理（终极版）≈60s

Spring AOP 的底层是动态代理，而它挂载在 BeanPostProcessor 这个容器扩展点上。核心类 AbstractAutoProxyCreator 在每个 Bean 初始化完成后的 postProcessAfterInitialization 里做两件事：先收集容器里所有 Advisor，再用切点对这个 Bean 做匹配——类过滤加方法遍历，任何一个方法命中，整个 Bean 就会被包成代理，容器里注册的从此是代理对象；一个都没命中就原样返回。代理内部通过 TargetSource 持有原始对象的引用，字段和依赖都在原始对象上，方法体也永远在原始对象上执行。调用时，代理先按当前方法查拦截器链——链空就直接反射调原始对象，链非空就穿过拦截器再调，事务就是在 TransactionInterceptor 这个拦截器里开启的。造代理的方式由 DefaultAopProxyFactory 在 JDK 动态代理和 CGLIB 之间二选一，Spring Boot 2 之后默认 CGLIB。所以事务内部调用失效这类问题，根源都在这：this 是原始对象，没经过代理。
