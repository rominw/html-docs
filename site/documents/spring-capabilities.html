1. 总纲：Spring 封装能力只有两种套路

不需要记十个能力，只需要记两个模式。

套路一：注解驱动（声明式）

一个注解 + 一个 AOP 拦截器 + 一个抽象层 + 可插拔实现。事务、@Async、@Cacheable、@Validated、@Retryable 全是这一套——它们都是 AOP 篇拦截器链上的插件，所以共享同一批坑：自调用失效、非 public 失效、final 拦不到、必须走代理。

套路二：模板方法（编程式）

XxxTemplate 消灭样板代码 + 统一异常/资源管理。JdbcTemplate、RestTemplate、KafkaTemplate、RabbitTemplate——把"打开资源 → 干活 → 处理异常 → 关闭资源"包掉，只留"干活"给你。

系列导航：① IoC 篇 · ② AOP 篇 · ③ Boot 篇 · ④ 能力全家桶篇（本篇）。前三篇讲骨架（对象怎么来、功能怎么增强、配置怎么自动来），本篇讲 Spring 在骨架之上装好的"出厂功能"。

2. @Async 与线程池：TaskExecutor

把方法调用变成"扔进线程池、立即返回"。

@EnableAsync
@Service
public class ReportService {
    @Async
    public CompletableFuture<Report> generate() {   // 立即返回，后台执行
        Report r = heavyWork();
        return CompletableFuture.completedFuture(r);
    }
}

原理链：@EnableAsync 注册 AsyncAnnotationBeanPostProcessor（又一个 BPP）→ 给 Bean 包代理 → 调用被拦截后提交到 TaskExecutor 线程池立刻返回。ThreadPoolTaskExecutor 本质是把 ThreadPoolExecutor 包成 Bean，方便配参数、纳管生命周期。

坑：异常被吞 高频

无返回值的 @Async 方法抛异常，只有 AsyncUncaughtExceptionHandler 打日志，调用方无感知。要么返回 CompletableFuture，要么显式处理。

坑：ThreadLocal 丢失

MDC traceId、SecurityContext 进新线程就没了。用 TaskDecorator 在任务提交时拷贝上下文（装饰 Runnable）。

坑：自调用失效

同类内 this.asyncMethod() 不走代理，异步失效变同步——和事务失效同一个根因（见 AOP 篇第 7 节三种调用路径）。

默认线程池注意：Spring 场景下默认用 SimpleAsyncTaskExecutor（不复用线程，每次新建，压测下会爆）。Spring Boot 有自动配置的 applicationTaskExecutor（8 核心 / 队列无限），生产环境应通过 spring.task.execution.* 或自定义 Bean 明确线程池参数。

3. @Scheduled 定时调度

三种触发模式语义不同，默认单线程是最大的坑。

模式语义踩坑点
cron日历语义（"每天 3 点"），可精确到秒单线程下到点也要排队；不识别年份；分布式重复执行
fixedDelay上次执行结束后等 N 秒再触发间隔 = 执行时长 + N，天然不并发，最安全
fixedRate理论上每 N 秒一次（固定频率起跑）单线程下上次没跑完就顺延，实际退化成 fixedDelay；任务必须幂等

原理

@EnableScheduling → ScheduledTaskRegistrar 把每个方法注册到 TaskScheduler（包装 ScheduledExecutorService）。

不支持分布式 高频

多实例部署每个节点都会跑。解决：ShedLock（数据库锁注解）、Quartz 集群模式、或干脆换 XXL-Job 等调度平台。

动态 cron

cron 存数据库、运行时可改：实现 SchedulingConfigurer，在 configureTasks 里从库里读。

4. @Cacheable 缓存抽象

Spring 只做抽象与拦截，存储实现可插拔。

@Cacheable(cacheNames = "user", key = "#id")     // 先查缓存：命中直接返回，方法体不执行
@CachePut(cacheNames = "user", key = "#id")     // 执行方法，并把返回值写进缓存
@CacheEvict(cacheNames = "user", key = "#id")   // 删除缓存（beforeInvocation 可选先删）
public User getUser(Long id) { return userMapper.selectById(id); }
CacheManager 实现类型适用短板
ConcurrentMapCacheManager（默认）本地内存demo / 单机无过期、无容量上限、重启即失
Caffeine本地内存（W-TinyLFU）高热点、读多写少多实例各自一份，不一致
Redis（spring-data）分布式多实例共享网络开销、序列化（默认 JDK 序列化，跨服务要换 JSON）

命中时方法体不执行

CacheInterceptor 查缓存命中直接返回——所以 @Cacheable 方法里的日志会"偶尔不打印"，不是 bug。

key 是 SpEL

#id、#user.name；不指定时按参数拼 SimpleKey。条件缓存：condition（是否缓存）、unless（结果不缓存）。

击穿防护

@Cacheable(sync=true)：同一 key 并发只放一个线程进方法，其余等待——单机版防击穿。

5. 事件机制：@EventListener 与事务绑定

默认同步是特性不是缺陷——配合事务相位才是完全体。

同步是默认

监听器和发布者同线程同事务执行。想异步：监听方法加 @Async（注意上下文拷贝问题回到第 2 节）。

解耦利器

下单后发积分、记日志、发通知——不用让主流程依赖一堆 Service，发布事件各听各的；不引 MQ 时的进程内首选。

事件即 POJO

Spring 4.2+ 事件不必继承 ApplicationEvent，任意类都能当事件发布；广播由 ApplicationEventMulticaster 完成。

6. 校验与重试

同为 AOP 套路，一个管入参、一个管失败后的再来一次。

@Validated vs @Valid

  • @Valid：JSR-380 标准注解，用在 Controller 参数上由 MVC 校验，失败抛 MethodArgumentNotValidException，@ControllerAdvice 统一接；
  • @Validated：Spring 扩展，标在类上开启方法级校验——由 MethodValidationPostProcessor（BPP）包代理实现，失败抛 ConstraintViolationException；
  • 还能分组校验（同一实体不同场景不同规则）与嵌套校验（对象字段上再标 @Valid）。

@Retryable 重试

@EnableRetry   // 需引入 spring-retry

@Retryable(retryFor = SocketTimeoutException.class,
           maxAttempts = 3,
           backoff = @Backoff(delay = 1000, multiplier = 2))
public CallResult call() { ... }

@Recover   // 3 次都失败后走这里兜底
public CallResult recover(SocketTimeoutException e) { ... }

只对抛出的异常类型重试；被重试的方法必须幂等；自调用同样失效。

7. 模板体系：数据访问与 HTTP 客户端

套路二：消灭样板代码 + 统一异常 + 屏蔽实现差异。

模板/抽象消灭了什么关键设计
JdbcTemplate获取连接 / 释放资源 / 异常处理的样板异常转译：各家数据库 error code 方言统一翻译成 DataAccessException 层级（如 DuplicateKeyException），换库不改异常处理代码
Spring Data（JPA/Redis/Mongo/ES）整套 DAO 层Repository 抽象：方法名生成查询（findByNameAndStatus），一套接口风格操作不同存储
RestTemplate → RestClientHTTP 连接、序列化、错误码处理RestTemplate 同步但已停止演进；Spring 6.1 的 RestClient 是它的流式接替者
WebClient同上（响应式）基于 Reactor，非阻塞；响应式技术栈才需要
HTTP Interface（@HttpExchange）整个调用代码声明式客户端：定义接口 + 注解，像自带版 Feign
KafkaTemplate / RabbitTemplate + @KafkaListener 等消息收发样板注意：@Transactional 只管本地事务，发消息不在事务边界内——要么事务消息，要么事务提交后再发（呼应第 5 节）

和套路一的组合：模板负责"怎么调"，注解负责"声明式增强"——比如 JdbcTemplate + @Transactional 是黄金搭档：模板提供异常转译，事务注解提供边界，各干各的。

8. 坑的总地图

套路一的坑是共享的，套路二的坑是个别的。

坑适用范围根因 / 解法
自调用失效事务 / @Async / @Cacheable / @Validated / @Retryable 全部this 不走代理（AOP 篇）；解法：拆 Bean、注入自身代理、AopContext
非 public / final 方法失效同上全部代理粒度限制；final 在 CGLIB 下甚至 NPE
无返回值 @Async 异常被吞@Async换 CompletableFuture 或配异常处理器
ThreadLocal / MDC 丢失@Async、异步事件TaskDecorator 拷贝上下文
任务串行互相阻塞@Scheduled默认单线程；配 spring.task.scheduling.pool.size
多实例重复执行@ScheduledShedLock / Quartz 集群 / XXL-Job
缓存与 DB 不一致 / 击穿@Cacheable更新时 CachePut 或失效；sync=true 防击穿；注意默认 ConcurrentMap 不能上生产
事务未提交就发消息事件 / MQ@TransactionalEventListener(AFTER_COMMIT)
重试放大副作用@Retryable只重试幂等操作；@Recover 兜底

面试点睛：被问任何一个具体能力的坑之前，先说"这些能力都是 AOP 代理实现的，所以先有共享的三类坑，再有各自的专属坑"——这一句就把你从背坑清单的候选人里区分出来了。

9. 面试口述简记卡片

每张 30~60 秒。D1 是总纲，先背熟它。

D1 · Spring 封装了哪些能力，怎么理解 ≈45s

Spring 在 IoC 和 AOP 之上封装了一批企业能力，套路就两种。一种是"注解加 AOP 拦截器加抽象层"：事务、@Async、@Cacheable、@Validated、@Retryable——底层全是动态代理拦截方法，共享同一批坑，最典型的就是自调用失效。另一种是"模板方法加抽象层"：JdbcTemplate、RestTemplate、KafkaTemplate，消灭样板代码并统一异常体系，比如 JdbcTemplate 把各数据库的异常方言翻译成统一的 DataAccessException 层级。把这些串起来的关键是：它们和事务一样，都是 BeanPostProcessor 挂进生命周期、拦截器链里跑的插件。

D2 · @Async 原理与坑 ≈45s

@EnableAsync 注册 AsyncAnnotationBeanPostProcessor，给 Bean 包代理；方法被调用后，拦截器把任务提交到 TaskExecutor 线程池立即返回。坑有四个：一是自调用失效，this 不走代理；二是无返回值时异常被 AsyncUncaughtExceptionHandler 吞掉，调用方无感知，建议返回 CompletableFuture；三是 ThreadLocal 上下文丢失，MDC、SecurityContext 进新线程就没了，要用 TaskDecorator 在提交时拷贝；四是默认线程池问题，纯 Spring 环境默认 SimpleAsyncTaskExecutor 不复用线程，每次新建，生产必须显式配置 ThreadPoolTaskExecutor 参数。

D3 · @Scheduled 的坑 ≈40s

最大的坑是默认单线程：所有 @Scheduled 任务在一个线程里串行，一个慢任务会饿死其他任务，fixedRate 也会退化成 fixedDelay，解法是配 spring.task.scheduling.pool.size 或给慢任务加 @Async。第二个坑是不支持分布式，多实例部署每个节点都会执行，要加 ShedLock 数据库锁、用 Quartz 集群模式或换 XXL-Job。另外任务里的异常会被吞掉只打日志，不影响下次调度，但最好自己 try-catch 保证状态干净。需要动态改 cron 就实现 SchedulingConfigurer 从数据库读。

D4 · fixedRate vs fixedDelay ≈30s

fixedDelay 是上次执行结束之后再等 N 秒，间隔等于执行时长加 N，天然不会并发，最安全；fixedRate 是固定频率，理论上每 N 秒起跑一次，不管上次跑没跑完——但在默认单线程的调度器里，上次没跑完就会顺延，实际效果退化成 fixedDelay，而且任务必须幂等。cron 是日历语义，适合"每天凌晨三点"这种，三种按场景选。

D5 · @Cacheable 原理 ≈35s

Spring Cache 是一个 AOP 拦截器：CacheInterceptor 在方法执行前按 key 查缓存，命中直接返回、方法体根本不执行；未命中才执行方法并把返回值写回缓存。三剑客分工：Cacheable 读缓存、CachePut 执行方法并更新缓存、CacheEvict 删除缓存。key 用 SpEL 指定，不指定就按参数拼 SimpleKey。抽象层是 CacheManager，默认 ConcurrentMap 只适合单机开发，生产换 Caffeine 或 Redis。它只做抽象和拦截，存储和过期策略都由具体实现负责。

D6 · 缓存一致性与击穿 ≈30s

一致性上一般用 Cache Aside：更新数据库后用 CachePut 更新或 CacheEvict 失效缓存，要点是先库后缓存；接受短暂不一致的读多写少场景用 Caffeine 本地缓存，要求强一致就 Redis 加短过期兜底。击穿用 @Cacheable 的 sync 属性，同一 key 并发只放一个线程进方法，其余等待。还有两个实践点：Redis 默认 JDK 序列化，跨服务共享要换 JSON 序列化器；缓存命中时方法体不执行，方法里的日志偶尔不打印不是 bug。

D7 · Spring 事件机制 ≈40s

通过 ApplicationEventPublisher 发布事件，@EventListener 监听，底层由 ApplicationEventMulticaster 分发。关键认知：默认是同步的，监听器和发布者在同一个线程同一个事务里执行——这既是解耦利器又是坑：如果监听器里发 MQ，此时事务还没提交，消费者来查库查不到；事务回滚了监听器的副作用也收不回来。解法是 @TransactionalEventListener 指定 AFTER_COMMIT 相位，提交后才执行。想异步处理就给监听方法加 @Async，但要注意上下文拷贝问题。事件本身不需要继承 ApplicationEvent，任意 POJO 都行。

D8 · @Validated vs @Valid ≈30s

@Valid 是 JSR-380 标准注解，主要用在 Controller 入参上，由 MVC 的参数解析器触发校验，失败抛 MethodArgumentNotValidException，用 @ControllerAdvice 统一处理。@Validated 是 Spring 的扩展，标在类上开启方法级校验，底层是 MethodValidationPostProcessor 给 Bean 包代理，失败抛 ConstraintViolationException。@Validated 还支持分组校验，@Valid 支持嵌套校验，两者经常配合：Controller 上 @Validated 指定分组，参数里 @Valid 级联。

D9 · JdbcTemplate 的价值 ≈30s

表面价值是消灭样板代码：获取连接、释放资源、异常处理都不用写了。更深的价值是异常转译：Java 原生 SQLException 只有 error code 各家数据库方言还不一样，Spring 把它们统一翻译成 DataAccessException 层级，比如唯一键冲突就是 DuplicateKeyException，业务代码 catch 的是语义化异常，换数据库不用改。再配合 @Transactional 提供事务边界，就是模板管"怎么调"、注解管"声明式增强"的组合。

D10 · RestTemplate / RestClient / WebClient 选型 ≈30s

RestTemplate 是老牌同步客户端，稳定但 Spring 已停止加新功能，存量项目继续用没问题。RestClient 是 Spring 6.1 推的接替者，同样是同步语义但用流式 API，更简洁。WebClient 基于响应式，非阻塞，只有技术栈本身是响应式（WebFlux）或需要高并发少量线程时才有意义。另外还有 HTTP Interface 声明式客户端，定义接口加 @HttpExchange 注解就生成实现，相当于自带版 Feign。新项目选型：普通同步用 RestClient，声明式用 HTTP Interface，响应式才上 WebClient。
