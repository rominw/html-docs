典型应用场景

多轮复核涉及循环编排、收敛条件和在途工作流的版本兼容。区分等待、失败与结果未知，分析持久历史如何支持恢复，以及它不能替代哪些业务协议。

本篇核心问题

能解释进程退出后为何恢复、哪些代码可重放、Activity 为什么仍需幂等，以及一次发版如何兼容旧历史。

阅读方式：先用记忆关键词复述机制，再推演例子的失败窗口，最后明确验证对象。场景用于解释技术取舍；练习能证明什么、不能证明什么，见版本与验证范围。

版本与验证范围：以 Temporal Java SDK 官方工作流与 Activity 文档为语境，具体 API 以实际依赖版本为准。历史模型练习不执行真实 SDK replay；生产变更必须用实际历史和目标 SDK 验证。

2. Temporal 怎样恢复工作流？重放为什么不会直接再起飞一次？

从机制到边界，再用具体交错检验结论。

记忆关键词：历史事件 → 确定性命令 → 结果重用 → 恢复状态

核心结论

Worker 可按持久历史重建工作流状态，并检查产生的命令与历史是否兼容。已经记录的 Activity 结果在重放中被使用，工作流代码重跑不等于重新执行所有外部动作。

拆开机制与保证范围

Workflow 决定调度 Activity、等待事件和定时器；对应事实进入 Event History。Worker 缓存可加快处理，缓存丢失后根据历史重建。不要把它描述为直接把任意进程堆、线程栈和 socket 保存到数据库。

确定性约束针对与历史相容的命令和状态演化。普通网络 I/O、实时系统时钟、随意随机数或外部配置读取会改变重放决定，应使用 SDK 允许的机制或转到 Activity。SideEffect 记录某些非确定性值，不应拿来包真实设备调用并宣称副作用永远只一次。

已完成并记录的 Activity 在重放中重用其结果；未能记录完成的外部调用可能被重试。恢复逻辑与外部效果恰好一次是两个保证。应对每个步骤指出“历史里是否已有证明”和“外部系统是否可按身份查证”。

场景推演：碰撞检测结果已记入历史，Worker 重启时无需再次调用服务才能恢复这一决定；下发已在设备生效却未记录完成，则必须查证原动作。

进一步思考：“代码执行一次还是多次？”Workflow 代码可多次重放，业务历史按协议推进。“持久变量都可随便改？”修改决策仍可能使旧历史不兼容。

如何验证：使用真实 SDK 的历史回放与 Worker 重启实验验证命令一致性；日志中标明 replay 语境，避免把重放日志当成重复外部执行。

3. Activity 的四类超时与重试怎样拆开等待、运行和结果未知？

从机制到边界，再用具体交错检验结论。

记忆关键词：排队 · 单次执行 · 总预算 · 心跳 · 外部身份

核心结论

排队超时、单次执行超时、整个 Activity 的总时限和心跳超时观察不同阶段。超时是调用方停止等待的条件，不自动停止已经运行的外部动作。

拆开机制与保证范围

Schedule-To-Start 约束单次任务被 worker 拾取前的等待；Start-To-Close 约束一次尝试；Schedule-To-Close 覆盖整个逻辑 Activity 的总时间与重试。Heartbeat 检测长任务的进展或失联，具体上限和策略按 SDK/服务版本核对。

重试可能因为 worker 消失、网络丢失或业务错误触发。参数错误和永久拒绝应识别为不可重试，暂时失败在总预算内退避。把所有异常包装成普通失败会丢掉错误分类，使不可重试问题变成无效循环。

心跳可以携带检查点，并帮助某些取消/恢复路径，但检查点与外部效果之间仍有窗口。请求取消也不是强行杀死所有代码；长循环和外部调用需合作检查取消并清理资源。过期旧 attempt 的回调应被代次和任务身份约束。

场景推演：图像批处理完成第 20 张后退出；心跳若只记到 18，重试会再处理部分图片。使用图片身份和幂等结果写入，使重叠不会重复形成业务记录。

进一步思考：“心跳没断就保证任务有进展？”可能只是空转心跳。“Activity 超时就安全重做起飞？”先查证外部结果。

如何验证：对排队、执行、心跳与总预算分别注入延迟；中断完成反馈并检查重试的业务身份和副作用次数，真实 SDK 参数需要集成测试。

4. Signal、Query 与 Update 为什么不能都叫“回调接口”？

从机制到边界，再用具体交错检验结论。

记忆关键词：异步输入 · 只读查询 · 接受/完成 · handler 交错

核心结论

Signal 注入异步消息，Query 查询工作流状态，Update 是可跟踪的状态变更请求。它们对历史、返回结果和处理完成的承诺不同。

拆开机制与保证范围

Signal 调用返回通常说明服务已接受，而不是工作流 handler 已处理完。Query 不用于修改状态，也不把查询本身当作持久业务事件。Update 可区分接受与完成，并支持验证拒绝等机制；应用要选与用户等待需求相符的协议。

handler 中等待 Activity 或条件时，工作流中的其他逻辑可能继续推进，不能因为单个 Workflow 的决策有确定性就忽略逻辑交错。可以把输入汇入主循环、定义处理资格和状态不变量，避免 handler 修改一半后等待导致其他逻辑看到半成状态。

消息应携带业务身份、执行代次和必要版本。服务接受消息不证明它的业务内容合法，更不证明设备执行成功；重复输入与跨 Continue-As-New 的去重范围也需明确。关联到 WorkflowId 和 RunId 的选择会改变迟到消息落到哪里。

场景推演：飞行完成 Signal 已返回成功，页面马上查询却仍显示处理中。应展示“已受理”，等工作流应用事件或查询权威结果后再展示“已完成”。

进一步思考：“Query 可用来确认后立刻执行？”查询与后续动作之间仍有竞态。“Update 接受即执行成功？”接受和最终结果不同。

如何验证：测试接受后 worker 暂停、handler 等待、重复/迟到消息与新 Run 切换；分别观察历史和调用方看到的接受/完成状态。

5. getVersion 为什么是历史兼容机制，而不只是普通 feature flag？

从机制到边界，再用具体交错检验结论。

记忆关键词：changeId · marker · 旧历史分支 · 命令顺序 · 回放

核心结论

普通开关读取当前配置，历史重放却必须保持曾经作出的决定。getVersion 将版本选择与历史绑定，使旧执行和新执行按兼容路径产生命令。

拆开机制与保证范围

比如在 review 与 waitCallback 之间新增 audit Activity，新代码若对所有重放都直接发 audit，会与只包含旧命令的历史冲突。版本桩让旧历史仍走旧分支，新执行记录新版本并选择新命令。changeId 标识具体变更，不是随意可重用的开关名称。

版本桩放置位置、保留分支及后续删除时机都影响兼容；不能等“发版过了几天”就删除旧分支，而要确认历史、在途执行和回放需求。Worker Versioning 是另一个部署/路由维度，需按版本策略理解，不能与 patching 混为一个功能。

兼容性还涉及 Activity 参数、结果结构和名称，旧 payload 必须能被新代码理解。只对一段 if 打桩不能保证所有字段变更安全。回滚新 worker 时，同样要考虑已记录新 marker 的历史是否能被旧实现处理。

场景推演：把复核算法由单轮变成收敛循环，旧任务应继续其既定路径；新任务采用新版循环。对升级前、升级中和升级后历史分别回放，才能确认发版边界。

进一步思考：“只给接口加版本够不够？”API 版本不自动绑定历史命令。“getVersion 能修复任意改动？”只能通过明确兼容分支保护相应变更。

如何验证：下方玩具模型只说明命令序列的版本选择；真实验收需用项目历史运行 WorkflowReplayer 或相应 SDK 测试，并覆盖新历史的回滚路径。

6. Continue-As-New、子工作流与父任务聚合如何控制状态规模？

从机制到边界，再用具体交错检验结论。

记忆关键词：WorkflowId/RunId · 新历史 · 携带状态 · 结束 handler

核心结论

Continue-As-New 在同一执行链中开始新 Run 和新历史，需要显式携带继续运行所需状态。子工作流拆分执行边界，父聚合还必须定义部分失败与唯一身份。

拆开机制与保证范围

长循环持续接收事件会扩大历史和重放成本；Continue-As-New 用新的 RunId 与历史继续，而非让旧历史无限增长。只传业务必需的游标、去重与收敛状态，不能假定旧内存变量自动迁入新 Run。

存在 Signal/Update handler 时，应从主流程在合适时机继续，并处理未完成 handler 与消息边界。去重集合若完全丢弃，旧回调可能在新 Run 再次被应用；无限带着全集又使 payload 不断膨胀，因此保留窗口与权威结果查询需共同设计。

父任务聚合子任务要分别定义子任务身份、成功条件、失败类别与取消策略。一个子任务完成不证明整个采集组就绪；父任务重试也不能无条件重新创建全部子任务。部分成功与结果未知需要保持可恢复证据。

场景推演：新 Run 带入已确认对象与下一轮游标，继续扫描；若只带轮次却丢掉已见集合，原本应收敛的复核又把旧对象当新增，产生重复任务。

进一步思考：“Continue-As-New 等于重新开始业务？”Run 变化不应改变业务身份。“父失败会撤销所有子效果？”取消与补偿都需按真实副作用定义。

如何验证：降低测试阈值触发新 Run，模拟切换前后消息到达与 handler 未结束；核对身份、游标、待处理消息和子任务不会丢失或重复创建。

7. 多轮复核如何从“固定轮数”变成有预算的收敛过程？

从机制到边界，再用具体交错检验结论。

记忆关键词：已见集合 · 新增集合 · 复现证据 · 终止条件 · 未知

核心结论

收敛循环应由业务状态变化驱动，并有轮次、时长与资源预算。无新增是选定观测范围内的终止条件，不等于已经证明真实世界永远没有遗漏。

拆开机制与保证范围

设 seen 为此前对象集合，observed 为本轮识别结果；新增是 observed−seen，复现是 observed∩seen。追加新增任务，按业务规则确认复现对象，再更新 seen。集合比较需建立可靠身份，车牌归一化、置信度、空间与时间匹配决定“同一个”的含义。

巡检结果会受遮挡、航线覆盖、识别噪声与延迟影响。未新增可能因为巡检失败或结果缺失，所以终止前要确认本轮观测有效。等待、确定失败与未知结果应分别处理，TTL 只能触发后续恢复策略，不能把未知观测当空集合。

持续新增会使循环不收敛，必须给总 deadline、轮次、工作量和人工接管路径。区域管理等级可以对应不同的确认条件与预算，实际阈值应来自业务规则与评估证据，而不是随意指定轮数。

场景推演：第一轮见 A/B，第二轮见 B/C：B 复现、C 新增；第三轮只见 C 且观测有效：C 复现，无新增可终止。如果第三轮结果未知，则应查证而不是按空集合结束。

进一步思考：“复现两次必然是真违停？”观测身份与业务时间条件仍需验证。“无新增就失败？”它可以是正常收敛，和任务失败不同。

如何验证：覆盖重复对象、持续新增、观测失败、未知结果和身份误匹配；核对终止理由与保留证据，再用真实 SDK 验证循环与历史兼容。

8. 动手验证与故障推演

先推导预期，再运行；如果结果相反，回到机制与边界。

历史模型练习：旧命令与新版本 marker 必须匹配

Python 3 标准库玩具模型，只比较命令列表来说明版本绑定。没有模拟 Temporal Event History 全部事件，也没有执行 Java SDK replay。

保存为 practice.py，用 python practice.py 运行。

DEFAULT_VERSION = -1

def commands(version):
    result = ["schedule:review"]
    if version >= 1:
        result.append("schedule:audit")
    result.append("wait:callback")
    return result

def replay(history_commands, marker):
    generated = commands(DEFAULT_VERSION if marker is None else marker)
    if generated != history_commands:
        raise ValueError("incompatible command sequence")
    return generated

old_history = ["schedule:review", "wait:callback"]
new_history = ["schedule:review", "schedule:audit", "wait:callback"]
assert replay(old_history, None) == old_history
assert replay(new_history, 1) == new_history
for history, wrong_marker in [(old_history, 1), (new_history, None)]:
    try:
        replay(history, wrong_marker)
        raise AssertionError("incompatible replay accepted")
    except ValueError:
        pass
print("old/new version binding and mismatch rejection passed")

遮住正文，回答四个问题

  • 历史中已有结果还是仅外部动作已经发生？
  • 重试和超时是否保留同一外部动作身份？
  • 版本桩是否用真实旧历史与新历史回放？
  • 本轮无新增是有效观测还是结果未知？
