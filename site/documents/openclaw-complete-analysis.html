2. 项目定位，以及它与 Pi 的真实关系

OpenClaw 的核心问题，是把智能体变成长期在线、可接入多渠道、可治理的个人或团队系统。

Pi 文档主要从编码智能体及其运行时组件向下拆解；OpenClaw 则从一个长期运行的 Gateway 向两端展开：一端连接聊天平台、控制界面和设备，另一端连接 Agent Harness、模型供应商、工具和持久化状态。模型负责生成候选动作，Gateway 与工具运行时负责接受请求、保留身份、限制执行并记录结果。

Gateway 是生命周期中心

它长期持有渠道连接、会话、事件、调度和控制接口。CLI、TUI 与 Control UI 通常连接它；客户端关闭，不自动等于已经接受的任务取消。

Harness 与 Provider 是两个维度

Provider 决定模型接口与认证；Harness 决定谁驱动智能体循环。更换模型不必更换 Harness；更换 Harness 也不意味着换掉 Gateway。

不能再直接套用“Pi 外面包一层网关”

维度本快照确认的关系阅读旧资料时的修正
内置 Agent 循环packages/agent-core + src/agents，OpenClaw 自己维护不能把核心循环归因于当前仍在运行的外部 pi-agent-core 包。
模型传输packages/llm-core + src/llm不能把多供应商接入全部画成外部 pi-ai 依赖。
终端 UI仍依赖 @earendil-works/pi-tui@0.86.1Pi TUI 的差分渲染思路仍相关，但不等于 Agent 执行也由 Pi 提供。
运行时名称内置 ID 为 openclaw；旧 pi 别名归一化到它配置接受旧名字属于兼容，并不证明外部 Pi 内核仍是实际执行者。
可插拔运行时例如 Codex 插件 Harness原生运行时拥有自己的回合完成与重试语义，宿主必须遵守适配契约。

架构演进的分析：OpenClaw 将控制平面、执行生命周期和存储契约收回同一维护边界，可以统一取消、重启恢复和权限检查；代价是需要自己维护更多模型兼容与运行时代码。保留 pi-tui 则说明终端组件的替换价值与运行时治理价值并不相同。

4. Gateway 协议与连接生命周期

控制连接先建立身份与能力，再接受会产生副作用的请求。

普通宿主安装默认绑定 127.0.0.1:18789，WebSocket 使用 JSON 文本帧；HTTP 也由 Gateway 提供相关界面和服务。容器镜像的暴露默认值有例外，不能把 loopback 当成所有部署形态的共同默认。协议类型以 TypeBox schema 为基础，并生成 JSON Schema 与客户端类型。

连接阶段：挑战 nonce → connect（身份、认证、角色、能力）→ hello-ok / 拒绝
请求：{ type: "req", id, method, params }
应答：{ type: "res", id, ok, payload 或 error }
事件：{ type: "event", event, payload, seq?, stateVersion? }
契约解决的问题不能推出的保证
首个请求必须是 connect先完成握手和认证，再执行 RPC已建立 TCP/WS 连接不代表获得操作权限。
device identity + challenge 签名绑定设备身份；避免把可复制 token 当成全部身份事实配对通过不代表所有工具都被允许。
operator / node 角色及 scope区分控制客户端和提供设备能力的节点声明 caps/commands 不等于执行端无需复核。
副作用 RPC 的 idempotency key相同请求短期重试可去重或重放结果不是对所有外部工具动作的无限期 exactly-once 承诺。
seq / 状态版本与重新查询客户端识别事件缺口并刷新状态Gateway 广播事件不是可无限回放的事件日志。

握手、Gateway 认证、设备配对和工具授权是分开的门。隧道改变传输路径，不替代这些门。Gateway 广播事件缺失后，客户端应重新读取权威状态；特定 RPC 的终态重放，不等同于整个事件总线都有历史回放。

核对依据：docs/concepts/architecture.md · docs/gateway/protocol.md

5. 路由、身份与 Session 键

先回答“谁的哪个会话”，才轮到回答“用哪个模型”。

resolveAgentRoute 接受 channel、accountId、peer、parentPeer、guild/team 和角色等事实，产出 agentId、sessionKey、mainSessionKey 与 matchedBy。绑定按照确定性的最具体匹配优先规则选择：精确 peer → 父 peer → peer 通配 → guild+roles → guild → team → account → channel → fallback。同级匹配按配置顺序决定。

标识生命周期 / 用途常见误读
agentId配置的 Agent 所有者，关联工作区、认证、会话与记忆不是某一次模型响应 ID。
sessionKey逻辑会话路由键，也是排队与可见性的重要输入不是聊天平台展示名；不同 Agent 即使键相同也不能串状态。
sessionId某一轮会话历史实例，重置后可以变化不能只靠逻辑键定位重置前后的全部历史。
runId一次已经接受的执行同一 session 可以有多个先后 run；同一 run 可有多个模型 attempt。
message / tool call ID把消息、动作与结果配对工具结果要对应真实调用，不能用自然语言猜配对。

默认连续性与多人隔离的取舍

默认 DM 汇入 Agent 的主会话，群组与房间按各自会话隔离。这很适合一个人从多个入口找同一助理；多人可访问时，默认 DM 合并可能造成上下文泄露。dmScope 决定按 main、peer、channel+peer 或 account+channel+peer 拆分；identityLinks 可以显式把跨渠道身份映射到同一 peer。Slack 某些 Agent/Assistant View DM 还有独立 thread 根会话例外。

{
  "session": { "dmScope": "per-channel-peer" }
}
// 仅演示这一配置字段，不是完整部署配置。

会话隔离解决上下文串话；它不自动隔离共享工作区文件、长期记忆、宿主进程或凭据。Agent 分目录也不是针对互不信任租户的 OS 安全边界。

6. 一条消息的端到端执行链

把“接收成功”“模型结束”“状态保存”“回复送达”拆成可分别判断的事实。

以 Gateway agent RPC 为切入点

入口先校验参数、解析会话并记录元数据，返回已接受的 runId。之后命令层选择模型、推理级别与技能快照，再调用 runEmbeddedAgent。本快照的 run.ts 只是导出入口，主要编排已拆到 run-orchestrator.ts，进一步调用会话准备、lane controller 和 run loop。不能看到文件名就把全部逻辑归到 run.ts。

渠道路线还会处理重投去重、连发 debounce、mention/access gate 与出站分块。当前入站去重缓存按 Agent 范围、渠道路由和消息 ID 建键，文档描述其期限为 20 分钟或 5000 项；这是内存防重，不是重启后所有副作用的持久去重证明。

阶段真实完成条件检查点
接受生成并返回 runId，完成必要入站记录不要把 accepted 当作任务完成。
执行Harness 报告对应回合的终态文本已经流出，也可能仍在调用工具。
状态提交当前 writer claim 允许写，事务成功保存失败不能假装历史已经记录。
投递目标渠道确认或产生明确失败/未知状态模型生成了答案，不证明外部平台收到了。
等待返回agent.wait 观察终态及相关 replay publicationwait timeout 只结束等待，不自动停止 run。

运行事件经 subscribeEmbeddedAgentSession 转成 tool、assistant、lifecycle 流；终态可以包含 terminalReply 与 terminalReceipt。sourceReplyDelivered: true 才是最终回复到外部源会话的特定证据。

7. Agent 内核：双层循环、工具批次与终止

循环的难点不是 while，而是如何把新输入、已经执行的动作和停止信号组织成一致历史。

内核入口 runAgentLoop 复制当前消息上下文、提交输入并发出 agent_start / turn_start 等事件。内层处理模型响应及其工具批次，工具结果成为下一次推理的输入；外层在当前推理链结束后读取 follow-up 与最终 steering，决定继续还是 agent_end。runAgentLoopContinue 对不存在或不允许继续的历史末态显式拒绝。

概念伪代码（非源码原样）：
提交已经接受的输入
while 本次运行可继续:
    响应 = 流式请求模型(当前上下文, 当前工具表面)
    批次 = 校验、授权并执行响应中的工具调用
    将响应与已结算工具结果按调用 ID 写回
    检查取消、host stop、endTurn、steering
    若模型仍需继续或收到 steering: 继续内层
    否则读取 follow-up；没有新输入则结束

源码中值得注意的边界

① Provider error/aborted 响应不启动剩余未执行工具。② 流式已经执行的 call ID 会被记录，终态处理只补剩余调用，避免同一响应的工具执行两遍。③ 工具批次可以有不同调度方式，不能假设所有工具天然并行安全。④ steering 可以跳过尚未启动的顺序尾部，但已经运行的工具先完成；并行批次也不会因为 steering 任意丢弃成员。⑤ 显式 endTurn: false 可能要求继续，即使这次响应只有文本；一次模型 response.completed 不是整个 Agent 的完成证据。

分析：循环维护的是一个受外部输入持续影响的执行历史，而不是“调用模型直到没有 function call”的最小脚本。取消后还要写出正确中断态、结算已启动动作并关闭 owner，因此“abort 触发了”与“所有资源已释放”也是不同事实。

核对依据：packages/agent-core/src/agent-loop.ts · packages/agent-core/src/agent-stream-response.ts · packages/agent-core/src/types.ts · docs/concepts/queue.md

8. 模型接入、Harness 选择与故障转移

模型名称、HTTP API、认证方式和 Agent 驱动器，需要分别解析。

层做什么边界
LLM 核心类型统一消息、toolCall、toolResult、usage 与流式事件统一形状不意味着各厂商参数、缓存与错误语义完全一致。
Provider 传输请求编码、流解析、认证与供应商差异不能在传输重连时盲目重放已经产生工具副作用的整轮。
Model runtime generation把 auth template、registry、catalog 原子发布为 Agent 范围快照避免本轮拿到新目录却配旧认证的半更新状态。
Harness registry选择内置或插件驱动器模型/provider 级 agentRuntime.id；model 配置优先。
run / attempt 编排重试、profile 轮换、fallback 与预算attempt 的失败不一定是 run 的终态；本地写冲突不是 provider 故障。

未显式指定或设置 default 时按 auto 选择；只有已注册 Harness 支持有效 Provider 路由时才选它，否则回内置 OpenClaw。仅靠 provider 名称前缀不会选 Harness。官方 OpenAI HTTPS Responses 路由在满足严格条件且没有用户请求覆盖时，可能隐式选择 Codex；自定义端点、Completions 适配器或用户编写的请求行为仍留在内置路径。

回退不应该偷偷改掉用户的会话模型

故障转移先对合格临时错误进行有界同模型恢复，再在当前 Provider 内轮换 auth profile，最后尝试模型 fallback 链。显式用户会话选择保持严格；允许 fallback 的路径即使本轮用了备用模型，也不会把它改成下一轮的所选模型。保存的是本轮实际执行和提示状态。

局部 transcript 写冲突由存储所有者处理：重新读取修订并有限重试。不能把写入失败包装为“模型有问题”，再调用另一个模型重做一次外部动作。原生 Codex 的网络重试、liveness 和精确 turn/completed 属于 Codex，而不是宿主根据静默时间推断。

9. 系统提示、工作区与上下文预算

把所有资料塞进 prompt 不是记忆系统；必须知道每一块内容的来源、权限与成本。

每轮准备工作区、bootstrap/context 文件、技能快照、工具 schema 和历史，再组装系统提示及覆盖项。工作区可以因为 sandbox 或 execution placement 改变；宿主源路径、执行端路径和模型看到的资源地址不一定相同。

输入层作用需要控制的变量
基础系统提示描述身份、工具、操作约束与宿主能力只能描述本轮真正启用的能力。
工作区 bootstrapAGENTS.md、SOUL.md、USER.md 等约定与背景文件注入有预算；磁盘完整文件不代表 prompt 完整注入。
技能目录 / 选中技能教模型什么时候使用既有工具指令文本不等于自动获得工具权限。
工具定义名字、参数 schema、执行契约启用表面太大增加 token、选择歧义和暴露面积。
历史与摘要保留近期过程与压缩后的旧事实保持 toolCall/toolResult 配对；防止旧 run 写回覆盖新历史。
检索结果 / 网页 / 附件按需提供外部证据带来源；数据内容不能升级成新的操作授权。

分析：上下文成本≈系统提示 + bootstrap + skill 元数据/正文 + tools + history + 当前输入 + 输出预留。只计算历史长度会高估剩余空间。长技能、几十个插件或巨大工具结果，会在用户对话很短时就触发预算压力。

调试优先使用 /context list、/context detail 看实际注入与截断，再检查模型上下文限制和 compaction 配置。不要通过不断扩大窗口掩盖错误工具表面或无限增长的 bootstrap。

核对依据：docs/concepts/system-prompt.md · docs/concepts/context.md · docs/concepts/agent-workspace.md · docs/concepts/memory.md

10. 工具表面、策略与副作用执行

工具不是模型返回一个名字就能直接调用的函数；宿主拥有最后的执行决定。

src/agents/agent-tools.ts 组装编码工具和 OpenClaw 工具，合并本轮能力、Agent/会话策略、消息渠道限制、模型/provider 策略与 sandbox 工作区边界。工具集合既是模型可见表面，也是运行时授权的输入；用户与委派来源的权限上限不能因为切换 Agent、收集队列或产生子任务而变宽。

工具族用途关键执行边界
read / write / edit 等读取文件、创建和改写内容根目录约束、路径身份、安全写入；规划结果与真正落盘分开。
exec / process运行命令、管理后台进程审批、执行位置、取消、子进程收尾；退出码与输出分开记录。
message渠道消息与动作接收者和会话范围；源身份是否仍有权发送。
session / subagent 工具读历史、发送输入、产生独立子执行会话可见性、委派权限上限和 parent/child 所有权。
browser / device / media浏览器、屏幕、相机和多媒体真实登录状态、网络目标、设备配对与命令许可。
memory / automation / plugin 工具检索、调度及扩展能力插件启用状态、身份与任务来源，不假设每个安装项本轮都可用。

一次工具动作至少经过四道判断

可见：是否进入这轮工具表面；合法：参数是否符合 schema；获准：策略、来源、审批和权限上限是否允许；可提交：真正副作用之前，owner 与取消状态是否仍然有效。异步规划之后要重新核对权限，因为等待期间用户可能停止任务、撤销设备或替换会话。

Sandbox 决定在哪儿执行，tool policy 决定能不能执行，elevated 决定某些 exec 是否升级到宿主。三者没有谁能够替代另外两个。特别是“工具在容器里”不等于消息发送、Gateway 控制或插件代码也全部在容器里。

核对依据：src/agents/agent-tools.ts · docs/gateway/sandbox-vs-tool-policy-vs-elevated.md · docs/tools/exec-approvals.md

11. 持久化：SQLite、会话树与迁移

区分运行事实、会话历史、用户文档和可重建索引，才知道怎样备份与恢复。

位置主要内容操作含义
~/.openclaw/state/openclaw.sqlite共享控制平面状态、registry、approval、plugin/runtime state不能当成一个可以随意删除的 cache。
~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite会话与 transcript、memory 索引、auth 与 Agent 范围状态删除它不是“仅清聊天”，会同时影响认证和其他状态。
~/.openclaw/openclaw.json用户配置与声明式输入备份时同时保留与数据库相配的配置。
workspace/ 与 Markdown用户可读产物、身份背景、持久记忆与日记这是命名的用户文档，不是另一套运行事务日志。
credentials/auth profile store 之外的 provider/channel 凭据与聊天记录有不同保密要求。
旧 sessions.json / transcript JSONL / auth-profiles.json迁移输入或历史兼容来源当前 runtime 不以它们为主存储；Doctor 负责相应导入。

SessionManager 是以明确 SQLite transcript identity 为基础的会话树管理外观。底层拆分 codec、读快照、write admission、branch rewrite 和 persistence；因此“数据库表里一串消息”不足以表达全部重置、分支与压缩语义。逻辑会话、历史实例、当前 leaf 与 active context 必须一起理解。

Schema 和线程边界

包内声明 state schema 20、agent schema 24；这些是独立 schema 版本，不是包版本。迁移前向执行；老程序拒绝较新的 schema。SQLite 访问主要由读取 worker 和 writer broker 承担，主线程安装发布后的事实；启动、迁移、一次性 Doctor 等有专门边界。WAL 与正在读取的快照也影响维护和磁盘回收，不能只看主数据库文件大小。

当前 transcript_events 可能存原始 JSON TEXT，也可能存压缩 BLOB。直接 SELECT event_json 会漏历史；应走 transcript accessor 或支持的导出。清理会话优先 /new、/reset 或 sessions cleanup；不要照搬旧文章删除整个 agent 目录。

12. 并发控制：Lane、Writer Claim 与资源所有权

串行会话保护决策顺序；事务围栏保护过期执行不能写回。

同一 session-key lane 按序执行，CLI、内置与 Codex 路径共享这条 lane，切换 Harness 也不能产生同会话竞争。不同会话可并行，再由 main、subagent 或 Swarm 等容量预算限制。队列规则处理“如何对待新消息”；执行 claim 处理“谁仍然拥有这一轮”。

机制维护的不变量为什么单靠它不够
Session lane同一逻辑会话不会同时启动互相冲突的回合输入可提前持久化；维护与异步收尾仍需存储层保护。
Main / 子任务并发预算控制同时在途的昂贵工作这是吞吐与资源控制，不等于数据写入权限。
activeWriterRunId写入当前属于哪个 run每次 append/rewrite 带 expectedWriterRunId 才能拒绝过期结果。
事务内核对检查声明与提交处于同一同步事务在 await 前查一次，await 后写入会出现 TOCTOU 竞态。
状态目录进程锁同一目录不被两个 Gateway / local agent 并发拥有它是宿主所有权，不是分布式数据库锁。
资源 owner / cleanup receipt取消、关闭与重启时知道谁应释放资源Promise 已 reject 不意味着 worker 或子进程已停止。

分析：这比“每个会话一把 mutex”多一步，但解决的是 mutex 无法覆盖的过期异步结果与重启边界。判断任务是否完成时同样要分开结果已返回、执行已结算、输入和原生资源已释放，避免取消后立即复用还被旧任务占有的资源。

核对依据：docs/concepts/agent-loop.md · docs/concepts/queue.md · docs/agent-runtime-architecture.md

13. 长期记忆与检索：文件、索引、来源

持久记忆是显式保存与可检索证据，不是模型永远记得全部聊天。

层内容读取方式 / 约束
USER.md偏好、沟通方式、关系和活跃项目背景独立的小预算；稳定偏好更适合指令化并有时效记录。
MEMORY.md长期事实、决策与精炼摘要bootstrap 可加载；超预算注入会截断，磁盘原文件保留。
memory/YYYY-MM-DD*.md每日上下文和细节记录今天/昨天在特定新会话准备中加载；其他细节按需检索。
DREAMS.md后台整合的可审查摘要不是另一份 raw transcript；用于人工审查长期提升。
SQLite 检索索引切块、关键字、向量和相关元数据文档中的可读来源与索引存储分开；索引不是模型自身记忆。

启用 embedding Provider 后，memory_search 使用语义向量与关键词混合检索；前者找相似表达，后者保留精确 ID、名字与代码符号。默认 memory-core 提供 memory_search、memory_get 和事件条件 intent；时间提醒继续由调度任务负责。其他记忆引擎可以通过插件接入。

检索命中不是执行授权

一条过去写下的“给某人发报告”可以是历史事实，也可能已经过期；检索命中不能自动授权现在发送。身份、受众、过期/替代关系和当前用户意图都要重新检查。会话 transcript 命中的 sessions/...jsonl 路径可能只是搜索引用，不能当成真实文件让 memory_get 读取；应走 sessions_search / sessions_history 并遵守独立可见性检查。

分析：把 Markdown 留作可审查的知识来源，把结构化状态与检索留给数据库，是可读性和工程一致性的折中。跨 DM 拆 Session 仍可能共享 Agent 长期记忆，因此多人部署还需检查记忆受众与工作区共享边界。

核对依据：docs/concepts/memory.md · docs/concepts/memory-search.md · docs/concepts/memory-provenance.md

14. 上下文压缩、Pruning 与记忆整合

三种“变短”改变的对象不同；不要把它们统称为自动记忆。

机制改变什么信息损失 / 风险
Compaction在 transcript 中追加压缩边界与摘要，重建模型上下文摘要会遗漏细节；旧历史保留供显式读取，但不再自动进入模型。
Context pruning缩减模型视图中的部分旧工具结果等内容节省即时 token，不等于产生永久知识摘要。
Memory flush / dreaming把值得长期保留的事实写入记忆文件并整合需要来源与质量约束；不能把所有模型输出提升为事实。

自动压缩既可在接近窗口时执行，也可在 Provider 返回 overflow 后恢复。切点必须保持 assistant toolCall 与 toolResult 的完整配对；已有完成结果的动作应继续沿结果推理，不能因压缩重放副作用。内置摘要估算包含中日韩字符；系统提示、工具 schema、输入和输出预留也参与预算。

超时恢复是一项明确的取舍

正常 safeguard 路径会检查最终摘要质量，无效则不提交。但活跃回合里的自动摘要若超时，当前实现可以采用确定性退路：保留近期完整尾部、当前请求及旧摘要，记录移除的旧消息数量，再继续回复。它保证会话可用，却放弃该次对被移除旧事实的标识保留保证；历史仍在磁盘，模型上下文不会自动恢复那些未被摘要的细节。手工 /compact、停止或其他错误不能直接套用此例外。

必要 checkpoint 与压缩在推理前完成；持久 Gateway 会话的可选 memory flush / compaction 等待回复投递与前台 owner 收尾后执行。新输入会取消并结算可选维护再读取上下文。可选维护失败记录日志，不把已完成的回复改成失败。

压缩摘要不是原始记录的无损替代品。关键订单号、文件路径、金额、待办与授权信息需要显式保存或重新检索；仅有“会话已压缩”状态不能证明这些细节仍在模型上下文。

核对依据：docs/concepts/compaction.md · docs/concepts/session-pruning.md · docs/concepts/memory.md

15. Plugins、Skills、Hooks 与 MCP

四者扩展的是不同契约；混在一起会把指令文本误当成隔离边界。

机制实际形态扩展层 / 信任成本
Skill带 frontmatter 的 SKILL.md 与支持资源教模型使用已有工具；文本指令本身不能赋权。
Native pluginmanifest + 可加载代码 + 注册 API提供渠道、Provider、工具、服务、媒体或记忆能力；代码是供应链信任对象。
Internal hookHOOK.md 等命令 / lifecycle 脚本宿主命令和 bootstrap 生命周期；不等于每个 slash command 都自动有事件。
Plugin hookapi.on(...) 类型化处理器before_prompt_build、before_tool_call、agent_end 等拦截与观察点。
HTTP webhook经鉴权的外部 HTTP 触发入口接受请求产生工作；不是订阅内部循环事件。
MCP外部工具服务协议与连接适配把远端能力接入工具面；仍需认证、来源和具体工具策略。

Plugin 的公共边界是文档化 openclaw/plugin-sdk/* 子入口；不能导入 src 私有实现。能力注册可区分 text inference、embedding、speech、channel、web search 等，避免所有扩展都挤成一堆通用 hook。导出存在不等于永远稳定，文档还区分了外部插件兼容基线和正在演进的 helper。

技能发现也有确定性优先级

当前文件技能从高到低为：工作区 skills → 项目 .agents/skills → 个人 .agents/skills → state-dir skills → workshop skills → bundled/custodian → extraDirs 与 plugin skills。同名取高优先级。还会根据配置、环境、二进制存在与 allowlist 做筛选；execution workspace 的附加资源具有专门优先级和同步规则，不能套用“随便扫描全机器”的模型。

分析：优先级提高可定制性，也意味着本地同名文件可以改变内置技能行为；需要明确记录来源。第三方 Skill 是提示供应链，第三方 Plugin 是代码供应链，MCP 是远程服务与数据供应链，各自审查重点不同。

核对依据：docs/plugins/architecture.md · docs/tools/skills.md · docs/tools/mcp.md · docs/concepts/agent-loop.md

16. MCP Server 接入步骤与最佳实践

先接一个受限的只读工具，验证真实调用，再逐步扩大能力。

本节于 2026-10-09 补充，仍以本页固定提交 e2dc6ad93f8a 为实现依据。命令与配置在同提交官方 MCP 文档中核对；下面的生产建议属于工程建议。示例路径和域名是占位值，未在真实 Gateway 上执行，也没有替读者安装或启动第三方 Server。

16.1 选择正确的接入方式

场景接入选择执行和认证边界
已有本地 Node / Python MCP 程序stdio：command + args + cwd由实际运行时启动子进程；文件路径、可执行文件与环境以运行它的机器为准。
共享或独立部署的远程服务显式 transport: streamable-http + url配置真实 MCP 端点；远程服务拥有业务数据与操作权限。
服务只提供旧 SSE 协议显式 transport: sse + url与 Server 的真实协议保持一致，不靠 URL 长相猜协议。
外部客户端需要读写 OpenClaw 渠道会话openclaw mcp serve这是相反方向：OpenClaw 提供服务，不是添加外部 Server。

原生接入使用 mcp.servers。旧教程里的 config/mcporter.json 属于另一份 mcporter registry，openclaw mcp list 不读取它。一般无需为了接入标准 MCP Server 再写一个 OpenClaw Plugin；只有需要专属渠道、宿主生命周期或非 MCP 能力时，才考虑插件。

16.2 最短可用流程：添加 → 探测 → 当前会话验证

界面入口：Control UI → Settings → MCP → Add server，选择名称与 transport，填写命令或 URL。会话内的 + → Connectors → Add MCP server 可以设置 This session / Everywhere；两者都保存全局定义，差别是会话启用策略。不要把 This session 误认为凭据或 Server 配置只存于该会话。

本地 stdio 示例，适用于 PowerShell；先把脚本路径换成已准备好的 MCP Server：

openclaw mcp add local-tools --command node --arg "D:\Tools\my-mcp\dist\server.js" --cwd "D:\Tools\my-mcp"
openclaw mcp doctor local-tools --probe

stdio Server 通过标准输入输出发送协议消息。作为 Server 作者，应把普通诊断写到 stderr，避免污染协议 stdout；作为部署者，使用明确的命令和参数，核对 Gateway 服务账户的 PATH、工作目录与数据权限。Windows 本地路径不适用于运行在 Linux 容器或远端的 Gateway。

远程 Streamable HTTP 示例，先只开放检索类工具：

openclaw mcp add docs --url "https://mcp.example.com/mcp" --transport streamable-http --include "search,read_*"
openclaw mcp doctor docs --probe
openclaw mcp status --verbose

status --verbose 主要检查保存配置；doctor --probe 还建立真实连接并发现 capabilities。add 通常会在保存前检查，OAuth 尚未登录或 --no-probe 时有例外。探测通过后，在实际 Agent 会话中触发一次低风险只读调用，并检查返回内容、工具名和身份；只有 probe 成功，不足以证明该 Agent 的工具策略允许调用。

16.3 可直接合并的配置

{
  "mcp": {
    "servers": {
      "docs": {
        "url": "https://mcp.example.com/mcp",
        "transport": "streamable-http",
        "enabled": true,
        "connectionTimeoutMs": 5000,
        "requestTimeoutMs": 20000,
        "toolFilter": {
          "include": ["search", "read_*"],
          "exclude": ["read_private_*"]
        }
      }
    }
  }
}

这是一段合并片段，不应替换已有的整份 openclaw.json。timeout 数值是示例，按 Server 的真实延迟调整；connectionTimeoutMs 管启动/连接，requestTimeoutMs 管请求。include/exclude 匹配原始 MCP 工具名与简单 * 通配；include 中的名字不是所有 Server 通用的标准名，应以 probe 输出为准。已有 Server 可用 openclaw mcp tools docs --include "search,read_*" 更新筛选。

远程 URL 模式省略 transport 时，当前默认使用 SSE，所以 Streamable HTTP 应显式声明。配置变更在开启 Gateway 热更新时退役受影响连接，后续回合重新发现；不能承诺正在执行的工具已瞬间切换。openclaw mcp reload 仅刷新当前 CLI 进程拥有的 runtime，不能替另一个 Gateway 进程重载。

16.4 身份认证：共享账户与每位请求者分开

Server 支持 MCP OAuth 时，在 docs 配置里加入 auth: "oauth"，需要时配置 oauth scope，再执行共享操作员登录：

openclaw mcp login docs
openclaw mcp doctor docs --probe

按输出 URL 完成授权；远端/无界面环境无法收到 loopback callback 时，使用登录流程打印的 --code 后备命令。认证保存与 Server 可达性仍是两个事实。OAuth 开启时，静态 Authorization header 不会同时作为另一份认证发送；不要盲目叠加两种凭据。API Token 型服务使用支持的敏感 header/env 与密钥机制，不把真实 token 放进 HTML、Git、命令参数或示例明文。

默认 OAuth 是共享操作员凭据；多人需要各自业务账户时，可以使用以下配置形态，而不是让所有用户共享一个管理员 token：

{
  "gateway": { "publicOrigin": "https://gateway.example.com" },
  "mcp": {
    "servers": {
      "docs": {
        "url": "https://mcp.example.com/mcp",
        "transport": "streamable-http",
        "auth": "oauth",
        "oauth": { "identity": "per-requester", "scope": "docs.read" }
      }
    }
  }
}

per-requester 的 scope 是服务自己的权限名，并非所有 Server 都接受 docs.read。用户由工具返回的登录链接授权，回调经 Gateway 的 publicOrigin；openclaw mcp login/logout 管共享账户，不管理各请求者账户。当前登录链接具有 bearer 属性，应只在符合官方互信假设的渠道使用，不能把它当成对敌对群成员的安全身份绑定方案。

16.5 从配置到工具执行的实现链

mcp.servers 配置与本轮来源
  → 按 Session / Requester 获取 runtime 与连接所有权
  → 认证、初始化、发现 tools / resources / prompts
  → toolFilter + Agent / Session 工具策略
  → 本轮模型可用工具
  → 模型调用 → 参数与权限检查 → MCP 请求
  → 结构化结果回到 Agent；记录错误与取消
  → 会话结束 / Stop / 配置更换时按 owner 释放连接

内置 OpenClaw 通过 Session MCP runtime 管理连接、lease 与 requester 分区；原生 Harness 则可按自己的契约接管目录与调用。coding、messaging profile 中可提供 MCP 工具，minimal 隐藏它们；tools.deny: ["bundle-mcp"] 可禁用这组工具。resource/prompt 能力也会生成读取辅助工具，并受相同过滤约束。读到远端 prompt 不等于收到新的用户授权。

16.6 最佳实践：按真实风险配置，不堆统一开关

建议具体做法为什么 / 边界
从只读最小能力开始只接一两个所需 Server；include 必需的 search/read 工具，排除敏感读取减少 token、错误工具选择与权限面；read_* 只是名字，仍要核对实际行为。
服务端也做业务授权API 账户只授目标数据集/项目权限；写操作核对当前调用身份OpenClaw 的工具筛选不能替服务端 ACL；同名工具不代表相同安全性。
高影响写操作分开将查询与发送、删除、付款等操作拆成清晰工具；使用实际 Harness 支持的审批策略Codex 的 --approval prompt 是其 Server 覆盖项，不是所有 Harness 的通用审批开关。
固定 stdio 启动来源使用已安装、已审查的 Server 版本与明确路径；不要每次临时拉 latest保证复现与供应链来源；stdio 进程不是天然继承工具 sandbox 的隔离环境。
保护认证材料HTTPS 保留证书验证；秘密用支持的机制；区分共享与 per-requester不要用 sslVerify: false 常态绕过证书，也不要把共享管理员权限投给多人。
有界 schema 与结果作为 Server 作者：限制参数长度、分页、返回条数与内容体积；错误包含可行动原因避免工具结果撑爆上下文；不能只让模型自行遵守无限制参数。
明确副作用与重试写入用业务幂等键或可查询状态；失败先核对动作是否已经生效连接失效可能发生在服务已提交之后；通信失败不能自动等同业务失败。
并行须有证据仅在 Server 真正支持且业务动作独立时设置 supportsParallelToolCalls这是调度提示，不能让本来互斥的写操作变安全。
验证实际会话与运行位置probe → 实际 Agent 只读调用 → 检查权限与返回；容器检查网络与路径本机 CLI 能连接，不保证另一个宿主上的原生 Harness 或 Gateway 可连接。
维护连接与观测监控连接失败、授权失败、超时与 Server 日志；大量闲置会话再评估 idle TTL复用连接减少启动成本；只记录必要元数据，避免把 token 与敏感结果写到日志。

上述 schema、固定版本、分页、业务幂等与部署验证是工程建议；OpenClaw 的现有机制包括工具策略、Server 筛选、timeout、runtime 所有权与有界恢复。不要把工程建议写成当前系统已经对任意第三方工具自动提供的保证。

17. 主动行为：Automations 与 Heartbeat

定时唤醒由持久调度事实驱动，模型负责被唤醒之后的判断。

Automations 保存任务与运行记录，在到期时启动 Agent 回合、命令或脚本，并将结果投递到聊天、webhook 或静默目标。openclaw automations 是当前 CLI 名称，openclaw cron 保留为别名。一次性时间、间隔与 cron 计划只是触发层；执行会话、payload、预算和投递策略是另外的维度。

方式用途本快照的重要语义
Heartbeat周期检查当前需要注意的事情已是 system-owned automation；每个启用 Agent 的调度状态由 Automations 管理。
独立 automation明确周期或时间的工作可以采用独立会话，避免把每次批处理混入主对话。
事件唤醒 / webhook收到外部事件或后台完成后继续外部数据不是新授权；事件来源与原执行 owner 要保留。
条件 intent满足事件条件时的持续意图区别于时间提醒；其创建和取消有显式语义。

Heartbeat 配置是 desired state，持久 monitor schedule 拥有实际 tick 与 cooldown；没有第二套 fallback 定时器。关闭 cron 后不再进行计划 heartbeat，但手动和事件唤醒仍可能可用。仅设 every=0m 关闭周期，并不自动禁止后台 exec 完成后唤醒；这需要另外控制 notifyOnExit。

定时任务也不能宣称任意副作用恰好一次

重启恢复根据已经接受的 occurrence、运行 claim 和投递事实判定是否继续、失败或未知。当前文档对某些计划消息写入设置投递围栏，但明确不把任意 command、script 或工具副作用升级为 exactly-once。遇到未知接收状态，应先核对接收端再重试，而不是直接让模型“再发一次”。

分析：一次 heartbeat 也会消耗上下文、模型调用和潜在工具成本。轻量上下文、独立执行与只在有价值时通知，比高频重复让模型读取整段主会话更容易控制成本与噪声。

核对依据：docs/automation/cron-jobs.md · docs/automation/cron-jobs/how-it-works.md · docs/automation/cron-jobs/schedules.md · docs/gateway/heartbeat.md

18. 设备节点、浏览器与远端执行

远端能力只是执行位置变化；控制所有权和权限来源不能丢。

Node 使用同一个 Gateway WS 服务，以 node 角色、设备身份和显式 caps/commands 接入。宿主可以派发相机、屏幕、位置等设备命令，平台应用提供的能力不同。Gateway 是控制平面，Node 是某类能力的执行端；Node 不是自动变成第二个独立会话控制中心。

执行形态能带来什么需要避免的误判
宿主工具直接读写文件、执行本地命令风险半径就是运行用户的实际权限。
Sandbox backend限制工具看到的文件与进程环境Gateway 留在宿主；挂载和网络决定真实隔离程度。
Paired Node设备端命令与执行配对和命令声明还要结合当前授权与能力支持。
Cloud / remote worker把工作放到远端环境远端 workspace 不是天然 OS sandbox；credentials 和传输另有契约。
Browser 自动化网页交互与已登录应用操作会继承会话、cookie 与页面权限；页面内容不能变成宿主授权。

分析：浏览器不仅是“拿网页文本”，还可能是进入真实账户的执行通道。网络 fetch、浏览器导航、节点执行和渠道消息应分别检查目标与来源。模型读到网页里的“请上传配置文件”，只能把它当网页数据，不能据此调用本地工具外传文件。

19. 安全模型与部署信任边界

系统安全依靠可执行策略与身份检查，不能只依赖模型遵守提示。

官方模型明确：一个 Gateway 对应一个可信边界，可以是个人或互相信任的团队；它不是让互相敌对租户共享宿主与凭据的隔离平台。普通宿主安装默认 loopback，大多数未知 DM 先走 pairing、群聊通常配 allowlist/mention gate。Sandbox 默认关闭；主会话工具通常在宿主执行。容器网络和部分 workspace 渠道有已文档化的默认例外。

边界应由什么执行提示词不能替代的检查
外部请求 → Gateway认证、设备配对、角色与 operator scope请求者是否是被认可的身份。
聊天 → Agentchannel access、mention gate、会话隔离是否接收和响应这位发送者。
模型 → 工具schema、tool policy、审批与 live authority这一次具体动作是否允许。
工具 → 文件 / 网络 / 节点路径约束、sandbox、目标检查、设备权限动作具体能触达什么。
扩展 → 宿主插件来源、安装策略、SDK 契约加载的代码是否可信。
状态 → 运维访问者OS 文件权限、备份权限与日志控制读取数据库可能读取历史与 auth 状态。

Prompt injection 的结构性原因，是模型同时看到用户指令与外部数据。隔离包装和来源标记帮助模型辨识，但不构成绝对阻断；真正涉及文件、发送、命令或凭据的动作，仍须靠宿主确定性检查。权限应来自当前用户/设备/角色事实，并在异步等待后、副作用前复核。

多人 DM 拆分只是第一步。对于不同信任域，官方建议分 Gateway 与凭据，最好分 OS 用户或宿主；不要因为存在多 Agent、容器或 tool denylist，就把一个安装宣称成对抗式多租户服务。

20. 超时、取消、重试与重启恢复

高可靠性来自每一种中断都保留准确事实，而不是所有错误都自动重试。

场景正确语义错误做法
agent.wait 超时等待者停止等；run 可仍然运行认为 wait timeout 就是任务已经停止。
模型长时间安静按 Provider / 原生 Harness 的 liveness 契约处理看到没有 token 就推断卡死并启动竞争 run。
run 执行预算到期终态为失败/timeout，停止继续恢复切到 fallback 重新获得一份无限预算。
用户取消阻止新动作，结算已启动工作；不能撤销已发生副作用把 cancel 当数据库或外部服务回滚。
审批等待内置运行时可暂停尚未用完的执行预算把所有等待都按同样方式暂停；ask_user 并不自动暂停总预算。
Gateway 重启以 claim、运行围栏、reply phase 和 delivery facts 恢复仅看 persisted running 状态就自动重做。
投递结果未知保留未知并先查目标系统把未知当失败，从头发送导致重复。
本地存储写冲突由 transcript 所有者处理修订与有限重试轮换 API key 或再调用一次模型。

当前 session 的持久 status 只存 done、failed、killed、timeout、interrupted 等 outcome；running/queued 是 registry 与队列所有者投影出的活跃状态。重启后“上次看起来还在跑”不足以授权继续，必须有合格恢复 claim。

原生 Codex 回合由它的精确终态管理。宿主在确切原生完成之后仍有本地 settlement 和 projection 的有界窗口；它们不因为看见进度而无限续期。内置模型路线则分总运行预算、模型流空闲 watchdog 与 Provider HTTP timeout，三者覆盖不同阶段。

幂等去重、模型重试、writer fence 和渠道投递回执分别覆盖不同边界。只有把副作用自己的业务幂等键与接收端证据也设计好，才有资格讨论业务上的“恰好一次”；OpenClaw 的通用工具层不能替第三方系统作这个保证。

21. 性能路径与工程约束

重点不是单次推理最快，而是高并发准备和慢外部调用时，Gateway 仍可响应。

模型运行时 generation 在启动或配置、插件、认证发布边界准备，多个查询面读取原子 catalog，避免每个回合或状态查询都重新扫描文件。计算任务使用 WorkerTaskPool，数据库访问有单独读/写所有者。异步 stage dispatch 也会让出事件循环，避免同时启动许多 Agent 时阻塞控制请求。

热点本快照的应对边界 / 需要测量什么
模型目录与认证发现Agent 范围 prepared generation发布必须完整；不能返回半新半旧快照。
编辑匹配、Unicode、diff 与压缩规划计算 worker；宿主仍拥有落盘和权限规划耗时、主线程延迟、输入占用、取消后的资源结算。
SQLite I/O读 worker 与 writer broker；连接生命周期内复用事实/statement慢查询、写队列与 WAL；不是所有历史路径都已完全无同步访问。
大量在途任务CPU / pending count / retained input admission文档默认计算池 128 pending、256 MiB 已报告输入；不等于总 worker heap 上限。
长会话有界历史读取、压缩、工具结果约束上下文预算与原始历史保留分开统计。
维护定时器GatewayScheduler 统一唤醒与关闭 admission域内 cleanup 顺序仍由各 owner 管，不全塞进一个调度器。

计算池在对应 isolate 内共享 max(1, availableParallelism()-1) 的 CPU admission；数据库与模型 generation workers 保持独立容量。取消不会因为结果已 reject 就提前释放仍在执行的原生资源；资源保留直到停止与输入准备结算满足契约。

测试和供应链

源码的 pnpm workspace 分离 packages、extensions、UI 与应用；包脚本定义 check、build、test 和架构守卫。运行时开发文档列出的完整 pre-push 门槛是 build、check、check:test-types、test；live tests 单独运行并需要真实 Provider 凭据。工作区配置还有依赖发布时间冷却、严格检查、禁止部分特殊子依赖来源及审查过的例外。

分析：这些机制说明项目已从简单聊天脚本进入有明确所有权的长期系统。代价是依赖边界、状态版本、生命周期和插件兼容面的复杂度；评价性能应量测首 token、排队时间、工具完成、投递时间和主线程响应，而不是只量模型 tokens/s。

23. 设计取舍，以及哪些思想值得复用

借鉴不必复制整个平台；按照业务真正拥有的生命周期选择机制。

设计选择收益成本 / 适用条件
一个 Gateway 统一控制连接、身份、会话与调度有明确中心共同故障域；不同信任域需要拆部署。
内核与 Provider 自己维护可以精确控制运行、恢复和状态契约需要持续承担模型兼容与测试维护。
插件化渠道 / Provider / Harness让新接入有清楚扩展边界SDK 演进、插件加载和生命周期需要治理。
每 Agent SQLite + 共享状态 DB本地优先、事务明确、分离 Agent 数据不是天然横向分布式架构；schema、备份与 worker 边界较复杂。
Markdown 记忆 + 检索索引知识可读可改，检索适配语义冲突、时效、来源和受众仍需管理。
会话串行 + 多会话并行保护对话顺序，同时允许吞吐长期运行占 lane；steering 与取消语义必须正确。
保守回执和恢复不把未知执行当成功，避免盲目重放部分未知状态必须让人核对外部系统。

最值得先借鉴

为 agent/session/run 建立不同身份；每个副作用保留来源与结果；区分 accepted、terminal、delivered；在事务内拒绝过期写入；重试前检查已完成动作。

什么时候才需要全部平台机制

多渠道、多用户、长期后台工作、插件与远端设备同时存在时，统一 Gateway、状态迁移和资源所有者会有价值。只有一个受控 CLI 工作流时，先用现有 Harness 和最小存储即可。

综合分析：OpenClaw 的价值不只在“能调用很多工具”，而在让一次生成过程进入长期运行系统后仍有明确身份、顺序、权限、结果与恢复路径。理解这一点，才能解释为什么代码里有大量 owner、generation、claim 和 receipt；它们服务的是具体竞态和中断边界，是否需要照搬取决于你的系统是否拥有相同边界。
